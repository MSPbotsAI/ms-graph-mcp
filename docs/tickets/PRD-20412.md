## Requirement understanding

One line: The reporter wants explicit evidence — either in the account-creation tool's definition or in its call result — that newly created Microsoft accounts are configured to require a password change at next sign-in (the Graph `passwordProfile.forceChangePasswordNextSignIn` parameter), because today that cannot be confirmed from what is visible to them.

The ticket has no `text_content` (description is empty) and no comments. All requirement content comes from two attached images (`clickup_get_task` → `attachments`, read via browser-less download + image read, since both ClickUp's `text_content` and `markdown_description` were empty for this ticket):

- Image 1 (`image.png`, 015543e2…): a Microsoft 365 admin center "Set up the basics" new-user screen, with "Require this user to change their password when they first sign in" checked and highlighted — the manual-UI behavior the reporter is using as the reference point.
- Image 2 (`image.png`, 0ed96a31…), Chinese, verbatim: "首次登录强制改密码：这项没有被我在当前可见的工具定义里明确确认到 / 也就是我现在缺少的是：`passwordProfile.forceChangePasswordNextSignIn` 这个参数被工具明确支持的证据 / 或者结果里会返回该设置已生效的证据" — i.e. the reporter could not confirm, from the tool definition visible to them, that `forceChangePasswordNextSignIn` is supported, and the tool's result gives no evidence that the setting took effect.

The reporter appears to be writing from the perspective of an onboarding-automation caller of the Microsoft Graph MCP connector (same "Onboarding Agent" context as the sibling ticket PRD-20413, which explicitly names "Connector: Microsoft Graph (ms-graph MCP)"), not a human admin — the ask is about what a *caller* of the tool can verify, not about the admin center UI itself.

## Current state (every claim carries path:line)

- `src/graph_mcp/tools/users.py:280-283` — `graph_create_user` already unconditionally sets `body["passwordProfile"] = {"password": password, "forceChangePasswordNextSignIn": True}` on every account it creates. There is no parameter to turn this off; it is a fixed security default already in place. **The behavior the reporter wants (force password change at first sign-in) is already happening** — the gap is that it is not observable.
- `src/graph_mcp/tools/users.py:263-269` — the tool's docstring: "Create a new Entra ID user account. `usage_location` is required because it must be set before any license can be assigned to the user. Address, phone, company and hire date can be set in the same call." It never mentions the forced password change at all, so a caller reading only the tool definition (what an LLM/agent sees, or what `mcp__*__list_tools` returns) has no way to know this happens.
- `src/graph_mcp/tools/users.py:311-313` — on success the tool returns `dump_json_capped(result)` where `result = await client.post("/users", body)` is Microsoft Graph's raw response, passed straight through with nothing added.
- Microsoft's own documented example responses for `POST /users` (learn.microsoft.com/en-us/graph/api/user-post-users, v1.0, checked 2026-10-13) show the response body contains only a small default property set (`id`, `displayName`, `givenName`, `surname`, `mail`, `mobilePhone`, `businessPhones`, `officeLocation`, `preferredLanguage`, `userPrincipalName`, and similar) — **`passwordProfile` is never present**, consistent with it being one of the Graph `user` resource's "`$select`-only" properties. So today, a successful `graph_create_user` call gives the caller zero confirmation that the password-change setting was even requested, let alone applied — this exactly matches what Image 2 describes.
- Contrast with the sibling tool in the same file, `graph_reset_password` (`src/graph_mcp/tools/users.py:320-372`): it also builds a `passwordProfile` with a force-change flag (`:353-358`) and sends it via `PATCH /users/{id}` (`:363`), which per Graph semantics returns `204 No Content` (confirmed in `src/graph_mcp/api_client.py:181-187`, `_parse_body` returns `None` on 204 / empty body) — and it does **not** try to pass that empty response through. Instead it builds its own explicit confirmation object (`:364-370`): `{"status": "success", "user_id": user_id, "message": "Password reset; user must change it at next sign-in."}`. This is already an established in-repo pattern for "don't rely on Graph's response to prove a `passwordProfile` setting took effect" — `graph_create_user` simply doesn't follow it yet.
- `README.md:71` — the tool table's one-line description of `graph_create_user` also does not mention forced password change.
- wiki (`ProductDocs/**`, synced 2026-10-13, product version v20261012.0718): **not covered**. `mbp.py wiki find` returned no hits for "onboarding agent", "create user", "ms-graph", or "force password", and the "password"/"entra" hits that did come back are all about the `agent.mspbots.ai` platform's own connector-configuration UI (OAuth dialog copy, connection forms), not about what an MCP connector tool does when it creates an Entra account. This is expected, not a gap in coverage: `ProductDocs` patrols `agent.mspbots.ai`'s own screens; this ticket is about an MCP tool's contract with its caller, which has no corresponding end-user screen to walk.
- External technical fact, not a product fact, verified via Microsoft's own docs and community reports (cited because it directly decides the technical design's option choice in §Tech design): a follow-up `GET /users/{id}?$select=passwordProfile` read-back is **not reliably usable as proof-of-effect** — multiple Microsoft Q&A / forum threads report `passwordProfile` coming back null/empty even when explicitly selected. See Tech design §11 for citations.

## Product design

### Goals / Non-goals

**Goals**:
- A caller of `graph_create_user` can confirm, by reading the tool's definition alone (no source access), that every account it creates is configured to require a password change at next sign-in, and that this is not configurable per call.
- A caller of `graph_create_user` can confirm, from the tool's own call result, that this setting was requested for the account just created — without needing a second tool call or any out-of-band check.

**Non-goals** (explicitly out of scope for this ticket):
- Making the forced password change optional/configurable. The current hardcoded "always on" behavior is a reasonable secure default and the ticket does not ask to relax it — see Open Questions if this needs revisiting later.
- Proving, via a Graph read-back call, that Entra actually persisted the setting server-side. See Tech design §Option analysis: this was considered and rejected — the relevant Graph property has documented, reproducible read-back unreliability, so a read-back would trade a false sense of rigor for added latency and spurious failures.
- Any change to `graph_reset_password`. It already has an equivalent, independently-built confirmation and is not affected by this ticket's gap.

### Acceptance criteria AC1..ACn

- **AC1**: Given a caller invokes `graph_create_user` with valid required parameters, When the call succeeds and Graph returns `201 Created`, Then the tool's returned JSON includes an explicit field confirming the account was created with "require password change at next sign-in" enabled (not merely the absence of an error).
- **AC2**: Given a caller or reviewer reads `graph_create_user`'s tool definition (its description, as surfaced by `list_tools()`/any MCP client) without reading source code, When they read what the tool does, Then the description states that every created account is configured to require a password change at the user's next sign-in, and that this is not configurable per call.
- **AC3**: Given account creation fails for any reason (e.g. Graph rejects a duplicate `userPrincipalName` or a policy violation), When `graph_create_user` returns its error envelope, Then the response does **not** contain the confirmation field from AC1 — an account that was never created cannot have had any setting "take effect" on it.
- **AC4** (backward compatibility): Given an existing caller already parses today's `graph_create_user` success response, When this change ships, Then every field present in today's response is still present with the same value — the confirmation field is additive only, nothing is renamed or removed.
- **AC5** (statelessness / no cross-call leakage): Given two consecutive `graph_create_user` calls are made with different access tokens, passwords and display names (simulating two different tenants or two different new hires), When both complete, Then each call's response — including the new confirmation field — reflects only that call's own input; nothing from the first call appears in the second call's result.
- **AC6** (ground truth, needs a live tenant): Given a real Entra ID tenant, When a newly created account signs in for the first time using the password returned by `graph_create_user`, Then Microsoft requires the user to set a new password before proceeding — i.e. the tool's claim in AC1 matches what Entra actually enforces, not just what we asked Entra to do. This is the strongest form of the evidence the reporter asked for, but it cannot be produced by this design leg (no live tenant access, read-only code leg) — see Test cases, marked `untested · local blind spot`, to be executed by the dev leg's self-test (`legs/dev.md` S5) if a sandbox tenant is available, same category of gap already recorded for `employeeId`/`givenName` data verification in `docs/modules/users.md § PRD-20321`.

### Open questions

- [不阻塞 / not blocking] Should `force_change_password` become an optional, explicit parameter the caller can turn off (e.g. for migrating pre-existing accounts that should keep their current password)? Current design assumes "always on, not configurable" stays unchanged, because the ticket asks to *confirm* the behavior, not to relax it. If a real need for an opt-out surfaces, it should be a separate ticket.
- [已假设 / assumed] The strongest possible evidence would be a Graph-side read-back proving the setting persisted, but that property is documented as unreliable to read back (Tech design §11). This design instead returns a deterministic echo of what was requested to Graph on a `201` success (Graph only returns `201` if the request body — including `passwordProfile` — was syntactically and semantically accepted; it does not silently drop a valid field). If the requirement owner considers "we asked Graph to do X" insufficient evidence and insists on "Graph confirms X happened," the Tech design's Option B needs to be revisited and accepted with its latency/reliability cost.
- [不阻塞 / not blocking] Exact line number in `README.md`'s tool table to update (currently `:71`) should be re-confirmed by the dev leg at implementation time, since the file may shift between design and dev.

## Tech design

### Conclusion

In `ms-graph-mcp`'s `graph_create_user` tool (`src/graph_mcp/tools/users.py:218-315`), make two additive changes: (1) update the docstring to state that every created account is configured to require a password change at next sign-in, and that this is not configurable; (2) on a successful `POST /users`, stop passing Graph's raw response straight through — instead merge in an explicit, deterministic confirmation field (e.g. `passwordChangeRequiredAtNextSignIn: true`) before returning. This mirrors the pattern `graph_reset_password` already uses in the same file (building its own confirmation object instead of trusting Graph's — mostly empty — response). No new tool, no new required parameter, no new permission.

### Where the current implementation lives

See Current state above — same `path:line` references apply:
- `src/graph_mcp/tools/users.py:218-315` — `graph_create_user` (signature, docstring, body assembly, the `POST` call and its return)
- `src/graph_mcp/tools/users.py:320-372` — `graph_reset_password`, the precedent for "build your own confirmation, don't trust Graph's response"
- `src/graph_mcp/api_client.py:118-187` — `GraphClient._request`/`_parse_body`, confirms `204`/empty bodies parse to `None`
- `README.md:71` — the tool-table description line to update

### Option analysis

| Option | Approach | Pros | Cost | Verdict |
|---|---|---|---|---|
| A. Deterministic echo in the tool's own response | After a `201`, merge `{"passwordChangeRequiredAtNextSignIn": True}` into the returned JSON; the value comes from what *we* sent, not from Graph's response | No extra network call; deterministic (doesn't depend on whether Graph happens to echo the field); matches the existing `graph_reset_password` pattern; small, low-risk diff | Only proves "we asked Graph for this," not "Graph's directory actually has it set" — though Graph returning `201` already means the request body (including `passwordProfile`) was accepted as valid, so this is a reasonable proxy, not a blind assumption | **Chosen** |
| B. Read-back confirmation via a follow-up `GET /users/{id}?$select=passwordProfile` | Ask Graph directly whether the setting is set, after creation | In principle closer to "ground truth" | (1) an extra Graph round-trip, added latency and a second failure point; (2) Microsoft Q&A/forum reports (cited below) show `passwordProfile` coming back null/empty even when explicitly `$select`-ed — unreliable in practice; (3) a null read-back would be indistinguishable from "didn't take effect" vs. "this property just doesn't read back," producing false negatives that would train callers to distrust a correct tool | **Rejected** — evidence of unreliability outweighs the theoretical rigor; recorded here instead of silently dropped |
| C. No change, document nothing, return nothing extra | — | Zero cost | Does not address the ticket at all | **Rejected** |

### Change list

- `src/graph_mcp/tools/users.py` [改] —
  - `graph_create_user` docstring (currently `:264-269`): add a sentence stating every created account requires a password change at next sign-in, and that it is not configurable.

The `isinstance` guard is defensive — Graph is documented to return `201` with a body for this endpoint, but the tool should not crash if that ever changes.
- `tests/test_tools.py` [改] — add test coverage for AC1/AC3/AC4/AC5 (see Test strategy below); existing tests (`test_create_user_sends_address_phone_company_and_hire_date`, `test_create_user_without_new_fields_keeps_prior_body_shape`) assert the **request** body shape and are unaffected by this change, which only touches the response.

Naming note (small, reversible choice per the design leg's "pick one and say why" rule): the new field is named `passwordChangeRequiredAtNextSignIn` rather than reusing Graph's own `passwordProfile.forceChangePasswordNextSignIn` verbatim, to avoid implying it is an echoed/re-read Graph value rather than our own deterministic confirmation. If the requirement owner prefers the Graph-native name for familiarity, this is a one-line rename with no other impact.

### Data & API contract

- Interface: `graph_create_user` MCP tool (not a REST endpoint — exposed over MCP HTTP-SSE per this server's transport). Request parameters: **unchanged**, no additions or removals.
- Success response (`201` from Graph), example after this change:
  ```json
  {
    "id": "87d349ed-44d7-43e1-9a83-5f2406dee5bd",
    "displayName": "Adele Vance",
    "userPrincipalName": "AdeleV@contoso.com",
    "mail": "AdeleV@contoso.com",
    "...": "...(Graph's other default-set fields, unchanged)",
    "passwordChangeRequiredAtNextSignIn": true
  }
  ```
- Error response: **unchanged**, `GraphError.to_envelope()`; per AC3 it must not contain the new field.
- Backward compatibility: purely additive field; no existing field is renamed or removed (AC4). Callers that only read specific known keys are unaffected; callers that do strict schema validation against an exact key set would need to allow the new key — this is the normal cost of any additive API change and is accepted here.

### Key flow / sequence

1. Caller → `graph_create_user` (required + optional profile params, unchanged)
2. Tool assembles `body` including the already-existing, unconditional `passwordProfile.forceChangePasswordNextSignIn = True` (unchanged)
3. Tool → Graph: `POST /users`
4. Graph → Tool: `201` + its default property set (no `passwordProfile`, per Current state)
5. **(new)** Tool merges `passwordChangeRequiredAtNextSignIn: true` into the result dict
6. Tool → Caller: JSON including the confirmation field
7. (Error path, unchanged) Graph returns a 4xx/5xx → `GraphError` → `e.to_envelope()` → no confirmation field present

### Non-functional

- **Idempotency/concurrency**: unchanged — `graph_create_user` creates a new resource and was never idempotent; this change doesn't alter that.
- **Performance**: zero added Graph calls (Option A, not B); the merge is an in-memory dict operation, negligible cost.
- **Security**: no new sensitive data is introduced or logged; the plaintext password was never included in the response before this change and still isn't — the new field is a boolean, not a copy of the password or the full `passwordProfile`.
- **Multi-tenant isolation**: not applicable in the usual sense — this connector is stateless and holds no credentials itself (`README.md:10`, "The server itself holds no credentials"); each call's tenant scope is determined entirely by the access token the caller passes per-request. AC5 is this ticket's concrete check that the change doesn't introduce any shared mutable state across calls.
- **Observability**: no new logging is required for this change; if the team later wants usage metrics on how often `graph_create_user` is called, that is a separate, broader concern not introduced here.

### Rollout & rollback

No feature flag — this is a deterministic, additive field, not a gradual-rollout feature. Follows this repo's normal flow: work branch → dev leg self-test → push the work branch, pending manual merge/release (per `references/docs-tree.md` / `references/handoff.md`, the design leg does not merge, release, or touch the base branch). Rollback is a plain revert of the commit(s), since the change is purely additive and self-contained to one function plus its docstring/README line.

### Test strategy

- Unit tests (all automatable with the existing `_CapturingClient`/`_FailingPostClient` mock pattern in `tests/test_tools.py` — no live Graph calls needed): cover AC1, AC3, AC4, AC5. See Test cases section and `.ac.json` for exact IDs.
- AC2 (tool description) is also automatable: FastMCP's tool registration exposes each tool's description text, so a test can assert the registered description string for `graph_create_user` mentions the forced password change.
- AC6 (does Entra actually enforce this on first sign-in) **cannot** be automated or verified without a live/sandbox Entra ID tenant — same category of local blind spot already recorded in `docs/modules/users.md § PRD-20321` for `employeeId` directory-schema behavior. Left for the dev leg's self-test (`legs/dev.md` S5) to attempt if a tenant is available; otherwise it stays `untested` with that reason stated, not marked `pass`.
- Regression surface: `graph_reset_password`, `graph_update_user`, and all other tools in this file are independent of `graph_create_user`'s return shape and are not expected to be affected.
