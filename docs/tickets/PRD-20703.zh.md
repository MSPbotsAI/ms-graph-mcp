# PRD-20703 · [Bug] Monthly Technology Report 邮件附件是占位 HTML,不是真实报告

工单: https://app.clickup.com/t/2280862/PRD-20703

## 需求理解

一句话：EMD 希望 Monthly Technology Report agent 发出的邮件里携带真实生成的报告文件,而不是一个占位 HTML 附件。

该 agent 能正确生成五页报告(产物核验:身份、周期、逐字核对、样式全部通过),但它通过 Microsoft Graph 的 `graph_send_mail` 发出的邮件附件是一个占位 HTML 文件,不是真实的约 57KB 报告。Microsoft Graph 返回 `sent`,所以整个运行看起来是成功的——从头到尾没有任何报错信号。EMD(Heath Beavers)于 2026-10-14 首次报告,2026-10-16 在测试另一张单 PRD-20659(审批规则修复)时内部复现。成功的样子是:每一封发出去的报告邮件附件都与该次运行实际产出的文件逐字节一致,任何做不到这一点的情况都应该表现为可见的失败,而不是静默的"已发送"。

## 产品设计

### 目标 / 非目标

- 目标:任何 SOP agent 通过 `graph_send_mail` 发出的报告邮件,其附件都与该 agent 实际产出的文件逐字节一致。
- 目标:如果因为任何原因无法附上正确的文件,发送必须可见地失败——不能存在"报告成功但内容被替换"的代码路径。
- 目标:提供附件字节的机制本身不能变成从任意或跨租户 URL 拉取/外带数据的通道(这个工具被多个租户的 SOP agent 共用)。
- 非目标:修改 Monthly Technology Report 这个 SOP 自己的 procedure/prompt——它不在本次设计能触达的任何代码仓库里(见「现状」);这个具体 agent 怎么调用工具,不在本单可触达的范围内。
- 非目标:重新验证报告生成这一步本身的正确性(五页构建、Executive Brief、Action Register)——工单和 PRD-20707 都说这部分已经通过全部检查;本单范围只是邮件附件这一步。
- 非目标:Graph 邮件工具的其它能力(读信、搜索、回复)——不受影响,未改动。

### 验收标准 AC1..ACn

- **AC1**:Given 调用方以 `content_url` 提供一个指向白名单 host 的附件,When 调用 `graph_send_mail`,Then 收件人收到的附件与该 URL 处的字节逐字节一致(sha256 相同)——不是占位符,不是截断,不是重新打字出来的。
- **AC2**:Given `content_url` 的下载因任何原因失败(host 不在白名单、响应非 200、网络错误,或文件超过 2.5MB 上限),When 调用 `graph_send_mail`,Then 完全不发送邮件——绝不会发出内容错误/占位的邮件,也绝不会部分发送。
- **AC3**(安全/多租户锚点):Given `content_url` 指向一个不在配置白名单里的 host(默认白名单:`agent.mspbots.ai`、`agentint.mspbots.ai`),When 调用 `graph_send_mail`,Then 在发起任何网络请求之前就拒绝(不尝试下载,也没有重定向绕过的漏洞)——这个工具不能被用来把任意外部数据或另一个租户的数据拉进发出的邮件里。
- **AC4**:Given 既有的 inline 附件路径(`content_text` / `content_base64`),When 调用方仍然使用它们,Then 行为与本次修复前完全一致(单文件 500KB / 合计 700KB 上限,超限拒绝且不部分发送)——新增的 `content_url` 路径不能让既有的 inline 路径出现回归。

### 数据与接口契约

本单不改动。供参考,现有(已上线)的契约:

- 工具:`graph_send_mail(to_recipients, subject, body, sender_id=None, body_content_type="Text", cc_recipients=None, bcc_recipients=None, save_to_sent_items=True, attachments=None)` —— `src/graph_mcp/tools/mail.py:498-529`。
- `attachments[i]` 恰好是以下三者之一:
  - `{"content_url": "<https 链接>", "filename": "<可选>"}` —— 服务器端下载字节;文件名默认取自 `Content-Disposition` 或 URL 路径(`mail.py:258`)。
  - `{"filename": "<必填>", "content_text": "<原始文本>"}` —— inline 文本,按 UTF-8 编码。
  - `{"filename": "<必填>", "content_base64": "<字节>"}` —— inline 二进制,容忍常见 base64 变体(`mail.py:123-134`)。
- Graph 调用:`POST /me/sendMail` 或 `POST /users/{sender_id}/sendMail`(`mail.py:564-567`),`message.attachments[]` 是一组 `#microsoft.graph.fileAttachment` 对象(`mail.py:301-310`)。
- 任意附件失败时的错误信封结构:`{"error": {"code": "...", "message": "...", "retryable": bool, "details": {...}}}`(`error_envelope`,贯穿 `_build_attachments` / `_fetch_attachment_url`)——附件校验或下载失败时,绝不会发起部分的 Graph 调用。

### 关键流程时序

1. 调用方(例如 Monthly Technology Report 这个 SOP)完成报告文件的生成,拿到它在平台上的 `https://agent.mspbots.ai/.../files/...` 链接。
2. 调用方调用 `graph_send_mail(..., attachments=[{"content_url": "<链接>"}])`。
3. `_build_attachments` → `_fetch_attachment_url`:校验 host 是否在白名单(`mail.py:170-178`)→ 若允许,发起 `follow_redirects=False` 的流式 `GET`,限 2.5MB(`mail.py:180-201`)→ 任何失败立即返回错误信封,后续什么都不做。
4. 下载成功后,字节被编码进 Graph 的 `fileAttachment` 字典,解析文件名/content-type,并记录 sha256(`mail.py:258-310`)。
5. 设置 `message["attachments"]`,发起 `POST .../sendMail`(`mail.py:552-567`)。
6. 第 3-4 步中任何一处失败都会在第 5 步之前短路——不存在"Graph 被调用,但内容被替换/错误"这条路径。

### 非功能

- **幂等/并发**:`graph_send_mail` 本身不幂等(每次调用都发一封新邮件);本单不改动,不在范围内。
- **性能**:流式下载,2.5MB 上限——对约 57KB 的报告文件毫无压力,无需改动。
- **安全**:host 白名单(`mail.py:170-178`、`config.py:17-21`)加上不跟随重定向的 GET(`mail.py:180`)是本次修复引入的唯一新增攻击面,且在设计上就是闭合的——`content_url` 不能指向白名单之外的任意外部 host 或另一个租户的平台实例。这也是 AC3 对应的多租户隔离点。
- **多租户隔离**:Graph token 的租户范围(未改动)仍然决定邮件以谁的身份发送/发给谁;白名单额外防止了附件下载这个机制本身被指向跨租户目标。
- **可观测性**:每个附件一条日志(文件名/字节数/sha256/来源,`mail.py:297-300`)是事后核对"到底发出去的是什么"的手段——对确认 AC1 在生产环境里是否成立特别有用,不用每次都回去读代码。

## 测试用例

(判定句写在这里;完整步骤在同目录的 .ac.json 里)

- **TC1**(AC1,手工,bug 复现 / 修复确认)—— Given American Ambulance of Visalia 的 Monthly Technology Report agent,When 开一个新对话让它生成并把 2026 年 9 月的报告发给 `mspbots_reports@emdnet.com`,Then 该地址收到的邮件附件与 `monthly-technology-report_american-ambulance-of-visalia_2026-09.html`(约 57KB)逐字节一致——不是占位符。**本次设计未执行**(本沙箱没有可用的线上 agent/邮箱会话);这是真正能回答本单未决问题的那一条用例。
- **TC2**(AC1,自动)—— `tests/test_tools.py::test_send_mail_content_url_attaches_exact_fetched_bytes` 确认服务器端机制:`content_url` 附件的字节原样进入 Graph payload(sha256 相同)。
- **TC3**(AC2,自动)—— `tests/test_tools.py::test_send_mail_content_url_fetch_failure_sends_nothing` 与 `tests/test_tools.py::test_send_mail_content_url_network_error_sends_nothing` 确认下载失败时整个发送被中止,而不是发出内容被替换的占位附件。
- **TC4**(AC2,自动)—— `tests/test_tools.py::test_send_mail_content_url_over_per_file_limit` 确认超限的 `content_url` 文件被拒绝(不会部分/截断发送),而不是被静默截断成一个更小的错误文件。
- **TC5**(AC3,自动,安全/多租户锚点)—— `tests/test_tools.py::test_send_mail_content_url_rejects_disallowed_urls_without_fetching` 确认不在白名单里的 host 在发起任何网络请求之前就被拒绝——这个机制不能被用来把跨租户或任意外部数据拉进发出的邮件。
- **TC6**(AC3,自动)—— `tests/test_tools.py::test_send_mail_content_url_disabled_when_allow_list_empty` 确认白名单配置为空时,该功能被完全禁用(而不是"全部放行")。
- **TC7**(AC4,自动)—— `tests/test_tools.py::test_send_mail_rejects_attachment_over_500kb` 与 `tests/test_tools.py::test_send_mail_rejects_attachments_over_700kb_total` 确认既有的 inline 附件上限不受本次修复影响。
- **TC8**(AC4,自动)—— `tests/test_tools.py::test_send_mail_attachments_do_not_leak_across_calls` 确认(既有的)inline 附件路径没有跨调用的状态泄漏。
