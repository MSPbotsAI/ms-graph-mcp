# PRD-20703 · [Bug] Monthly Technology Report emails a placeholder HTML attachment instead of the report

Ticket: https://app.clickup.com/t/2280862/PRD-20703

## Requirement understanding

One line: EMD wants the Monthly Technology Report agent's emailed report to carry the actual generated report file, not a placeholder HTML attachment.

The agent builds the five-page monthly report correctly (artifacts verified: identity, period, verbatim, styles all pass), but the email it sends through Microsoft Graph's `graph_send_mail` attaches a placeholder HTML file instead of the real ~57 KB report. Microsoft Graph returns `sent`, so the run looks successful to both the agent and the operator — there is no error signal anywhere in the path. EMD (Heath Beavers) first reported this 2026-10-14; it was reproduced internally 2026-10-16 while testing the unrelated approval-rule fix PRD-20659. Success looks like: every emailed report attachment is byte-identical to the report file the run actually produced, and any failure to do so surfaces as a visible error rather than a silent "sent".

## Product design

### Goals / Non-goals

- Goal: every report a SOP agent emails through `graph_send_mail` arrives with an attachment byte-identical to the file the agent actually produced.
- Goal: if the correct file cannot be attached for any reason, the send fails visibly — there must be no code path that reports success while substituting different content.
- Goal: the mechanism that supplies attachment bytes must not become a way to fetch or exfiltrate data from arbitrary or cross-tenant URLs (this tool is reachable by many different tenants' SOP agents).
- Non-goal: changing the Monthly Technology Report SOP's own procedure/prompt — it is not git-tracked in any repo this design pass could reach (see Current state); any change to how that specific agent calls the tool is outside this ticket's reachable scope.
- Non-goal: re-validating the correctness of the report-generation step itself (five-page build, Executive Brief, Action Register) — the ticket and PRD-20707 both state this already passes all checks; only the email-attach step is in scope.
- Non-goal: any other Graph mail capability (read, search, reply) — unaffected and unchanged.

### Acceptance criteria AC1..ACn

- **AC1**: Given a caller supplies an attachment as `content_url` pointing at an allow-listed host, When `graph_send_mail` is called, Then the attachment that reaches the recipient is byte-identical (same sha256) to the bytes at that URL — not a placeholder, not truncated, not retyped.
- **AC2**: Given the `content_url` fetch fails for any reason (disallowed host, non-200 response, network error, or the file is over the 2.5 MB cap), When `graph_send_mail` is called, Then no email is sent at all — never a mail with wrong/placeholder content and never a partial send.
- **AC3** (security / multi-tenant anchor): Given a `content_url` pointing at a host that is not on the configured allow-list (default `agent.mspbots.ai`, `agentint.mspbots.ai`), When `graph_send_mail` is called, Then the host is rejected before any network request is made (no fetch attempt, no redirect-following loophole) — the tool cannot be used to pull arbitrary external or another tenant's data into an outgoing email.
- **AC4**: Given the existing inline attachment paths (`content_text` / `content_base64`), When a caller still uses them, Then behavior is unchanged from before this fix (500 KB per file / 700 KB combined cap, rejected over that with no partial send) — the new `content_url` path must not regress the pre-existing inline path.

### Data & API contract

Unchanged by this ticket. For reference, the existing (already-shipped) contract:

- Tool: `graph_send_mail(to_recipients, subject, body, sender_id=None, body_content_type="Text", cc_recipients=None, bcc_recipients=None, save_to_sent_items=True, attachments=None)` — `src/graph_mcp/tools/mail.py:498-529`.
- `attachments[i]` is exactly one of:
  - `{"content_url": "<https link>", "filename": "<optional>"}` — server fetches the bytes; filename defaults from `Content-Disposition` or the URL path (`mail.py:258`).
  - `{"filename": "<required>", "content_text": "<raw text>"}` — inline text, UTF-8 encoded.
  - `{"filename": "<required>", "content_base64": "<bytes>"}` — inline binary, tolerant of common base64 variants (`mail.py:123-134`).
- Graph call: `POST /me/sendMail` or `POST /users/{sender_id}/sendMail` (`mail.py:564-567`) with a `message.attachments[]` array of `#microsoft.graph.fileAttachment` objects (`mail.py:301-310`).
- Error envelope shape on any attachment failure: `{"error": {"code": "...", "message": "...", "retryable": bool, "details": {...}}}` (`error_envelope`, used throughout `_build_attachments` / `_fetch_attachment_url`) — no partial Graph call is ever made when an attachment fails validation or fetch.

### Key flow / sequence

1. Calling agent (e.g. the Monthly Technology Report SOP) finishes building the report file and obtains its platform-hosted `https://agent.mspbots.ai/.../files/...` link.
2. Agent calls `graph_send_mail(..., attachments=[{"content_url": "<link>"}])`.
3. `_build_attachments` → `_fetch_attachment_url`: check host against allow-list (`mail.py:170-178`) → if allowed, `GET` with `follow_redirects=False`, streamed, capped at 2.5 MB (`mail.py:180-201`) → on any failure, return an error envelope immediately, nothing further happens.
4. On success, bytes are base64-encoded into a Graph `fileAttachment` dict, filename/content-type resolved, sha256 logged (`mail.py:258-310`).
5. `message["attachments"]` is set, `POST .../sendMail` is issued (`mail.py:552-567`).
6. Any failure anywhere in steps 3-4 short-circuits before step 5 — there is no path where Graph is called with substituted/wrong content.

### Non-functional

- **Idempotency / concurrency**: `graph_send_mail` is not idempotent (each call sends a new mail); unchanged by this ticket, out of scope.
- **Performance**: streamed download, 2.5 MB cap — negligible for a ~57 KB report; no change needed.
- **Security**: the host allow-list (`mail.py:170-178`, `config.py:17-21`) plus no-redirect GET (`mail.py:180`) is the only new attack surface this fix introduces, and it's closed by design — `content_url` cannot be pointed at an arbitrary external host or another tenant's platform instance outside the configured allow-list. This is also the multi-tenant isolation point for AC3.
- **Multi-tenant isolation**: Graph token scoping (unchanged) still determines which mailbox a mail is sent as/to; the allow-list additionally prevents the attachment-fetch mechanism itself from being pointed cross-tenant.
- **Observability**: per-attachment log line with filename/bytes/sha256/source (`mail.py:297-300`) is the mechanism to verify after the fact "what was actually attached" — directly useful for confirming AC1 in production without re-reading code each time.
