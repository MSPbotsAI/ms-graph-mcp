**Defect 1 — `graph_list_user_groups` pagination loses groups and never terminates** (acceptance item 1.1).

Code: `src/graph_mcp/tools/groups.py:92-121`. The tool pages over `GET /users/{user_id}/memberOf` (a polymorphic collection — groups, directoryRoles, administrative units, etc. can all appear in it), with `$top`/`$skiptoken` applied to that raw collection (`:94,97`). After the fetch, it filters the page's items in Python, keeping only objects that look like groups (`:102-105`: `if not (obj.get("@odata.type","").endswith("group") or "groupTypes" in obj): continue`). The filtered-out count never affects `$top`/`$skiptoken`, which are driven entirely by the raw (unfiltered) page. Acceptance's actual observation — page 1 returns `count=0` with a token, page 2 returns 1 group, every later page again returns `count=0` with a new token, and the walk never reaches `has_more=false` — matches this code path: a raw page whose items are all filtered out still carries a valid `@odata.nextLink`/`$skiptoken` (`groups.py:110`), so the client-visible walk can show runs of empty pages and, in the worst case the reporter hit, apparently never converge. `graph_list_group_members` (`groups.py:364-367`) does not have this problem because `/groups/{id}/members` has no sibling non-member-typed objects to filter out.

**Defect 2 — `graph_update_user`'s success response has no new values** (acceptance item 1.4, minor).

Code: `src/graph_mcp/tools/users.py:653-657`. On a successful PATCH, the tool returns `{"status": "success", "user_id": user_id, "updated": list(body.keys())}` — `list(body.keys())` is just the PATCH body's own key names (e.g. `["jobTitle"]`), never re-read from Graph. Acceptance confirms this is exactly what ships today and asks for the changed value itself (e.g. `{"jobTitle": "Interface Test"}`), not just the key name.

**Defect 3 — `graph_remove_manager`'s return value and idempotency** (acceptance item 1.5).

Code: `src/graph_mcp/tools/users.py:692-711`. The tool calls `DELETE /users/{user_id}/manager/$ref` and returns `{"status": "removed", "user_id": user_id}` on any non-error response; only a `GraphError` with `status_code == 404` is mapped to `{"status": "no_manager", ...}` (`:708-710`). Acceptance's two actual runs on `rewst_migtest01` show Graph does **not** 404 the second `DELETE` (against a user that already has no manager) — it returns success both times, so the `404`-is-the-only-no_manager-signal assumption this code relies on does not hold against the real API: the tool reports `removed` on a call that removed nothing, and never surfaces who the manager was before removal (no read-before-delete anywhere in this function).

**Defect 4 — `graph_get_user`'s missing default fields and broken `select`+`manager`** (acceptance item 1.6).

Code: `src/graph_mcp/tools/users.py:33-42` (`_USER_PROFILE_SELECT`, the default `$select`) and `:406-447` (`graph_get_user`). Two sub-defects, both confirmed by reading the code:
- `_USER_PROFILE_SELECT` (`:33-42`) does not include `onPremisesImmutableId`, `onPremisesSamAccountName`, `createdDateTime`, or `lastPasswordChangeDateTime` — acceptance's exact list of fields missing from the default response.
- When `select` is provided (`:436-438`), every requested name — including `"manager"` — is concatenated straight into `$select`. `manager` is a navigation property on the Graph `user` resource, not a flat property, so Graph silently drops it from a `$select` list instead of erroring; only the default (no-`select`) branch (`:439-441`) uses `$expand=manager(...)`, which is the only mechanism that actually returns it. The tool's own docstring (`:415-418`) promises `select=["manager"]` will return the manager — acceptance's test of exactly that call confirms the promise is false against real Graph. `tests/test_tools.py:1585-1592` (`test_get_user_custom_select_narrows_fields`) only exercises `select=["displayName","mail"]` — it never tried `"manager"` in `select`, so this gap was untested, not just unimplemented.

**Unaffected**: items 1.2 (`graph_list_groups`) and 1.3 (`graph_list_users`) passed acceptance unchanged — they page over `/groups` and `/users` directly, collections with no sibling non-matching type to filter, so Defect 1's root cause does not apply to them. No change proposed for either in this round.

**Out of scope, unchanged**: items 1.7/1.8 (`graph_transfer_onedrive`, `graph_start_cloud_sync`) remain excluded per the original ticket's own interview log (round 1 Non-goals) and acceptance's own note ("Items 1.7 / 1.8 are tracked in a separate ticket and not covered here").

## Product design

### Goals / Non-goals

**Goals** (this round, matching acceptance's 4 failing items exactly):
- G1: `graph_list_user_groups` pagination terminates correctly and returns every group exactly once, for any user regardless of how many non-group `memberOf` entries (directory roles, etc.) they also have.
- G2: `graph_update_user` returns the actual new value of every field it changed, not just the field's name.
- G3: `graph_remove_manager` reports whether a manager was actually removed, returns who the previous manager was when one existed, and never claims a removal that did not happen.
- G4: `graph_get_user`'s default response includes the four on-premises/audit fields acceptance asked for, and a `select` that names `"manager"` actually returns the manager.

**Non-goals** (explicitly out of scope for this round):
- Re-opening items 1.2/1.3 (`graph_list_groups`, `graph_list_users`) — they passed acceptance unchanged.
- Items 1.7/1.8 (`graph_transfer_onedrive`, `graph_start_cloud_sync`) — still pending a separate confirmation with Ginko, per round 1's Non-goals and acceptance's own note; not reopened here.
- Any further field additions to `graph_get_user`/`graph_update_user` beyond what acceptance's Expected/Acceptance sections literally ask for.

### Acceptance criteria AC1..AC7

(AC numbers below are local to this round 2 document; parenthetical notes map each to the original round-1 AC it supersedes, where applicable — the round-1 AC of that number in `docs/tickets/PRD-20393.md` is no longer the governing text for that behavior.)

- AC1 (supersedes original AC1): Given a user who belongs to ≥3 groups (and has at least one non-group `memberOf` entry, e.g. a directory role), When `graph_list_user_groups` is paginated with `max_results=1` to the end, Then it returns exactly the same set of groups as `max_results=200` in one call, with no empty pages, no duplicates, and the final page's `next_page_token` is `null`. (This is acceptance's own literal Acceptance line for item 1.1.)
- AC2 (new — not covered by any round-1 AC): Given `graph_update_user` changes one or more fields, When the call succeeds, Then the response's `updated` is an object mapping each changed field name to its new value as read back from Graph immediately after the PATCH (a field that was explicitly cleared reads back as `null`), not just a list of the field names that were sent.
- AC3 (supersedes original AC9): Given a user with an assigned manager, When `graph_remove_manager` is called, Then it returns `removed=true` and `previous_manager` populated with that manager's `id`/`display_name`/`user_principal_name`, and a subsequent `graph_get_user` shows no manager for that user.
- AC4 (supersedes original AC10): Given a user with no manager assigned, When `graph_remove_manager` is called, Then it returns `removed=false`, `previous_manager=null`, `reason="no_manager"`, with no error, calling it again is equally successful, and (per the new read-before-delete design in Tech design) no `DELETE` call is issued to Graph in this case at all.
- AC5 (supersedes/extends original AC11): Given a user with `onPremisesImmutableId`, `onPremisesSamAccountName`, `createdDateTime` and `lastPasswordChangeDateTime` populated, When `graph_get_user` is called with no `select` parameter, Then all four fields are present in the response alongside the fields the default response already returns today.
- AC6 (supersedes/extends original AC12): Given a `select` parameter that includes `"manager"` alongside other field names, When `graph_get_user` is called, Then the response contains exactly those other fields (plus `id`) and an expanded `manager` object (`id`, `displayName`, `userPrincipalName`).
- AC7 (tech-added, not literally asked by the acceptance report — see Tech design § Non-functional for why): Given a user's manager was present when `graph_remove_manager`'s read step ran but was removed by a concurrent caller before this call's own `DELETE` executes, When `graph_remove_manager` runs, Then it still returns `removed=true` with the `previous_manager` captured at read time, not an error — the race does not change the fact that a removal this call initiated is the one that (or already did) take effect.

Not blocking — `graph_get_user` already has this same characteristic for any expanded reference.

## Tech design

### Conclusion

All four fixes stay inside the two files round 1 already touched (`src/graph_mcp/tools/groups.py`, `src/graph_mcp/tools/users.py`) plus the test suite; no new file, no new dependency, no schema/DB. Defect 1 is fixed by moving the group-only filter from client-side Python to Graph's own OData type-cast URL (`/memberOf/microsoft.graph.group`), which removes the root cause instead of patching around it. Defect 2 is fixed by a follow-up `GET` after a successful `PATCH`. Defect 3 is fixed by a read-before-delete sequence that no longer depends on Graph's `DELETE` 404 behavior at all (which acceptance proved doesn't hold), with a new, intentionally breaking response shape (`removed`/`previous_manager`/`reason`, replacing `status`). Defect 4 is fixed by widening the default `$select` constant and special-casing `"manager"` in the `select` param to route it to `$expand` instead of `$select`.

### Data & API contract

**`graph_list_user_groups`** (modified) — no caller-visible request/response contract change. Internally, the Graph call path changes from `/users/{id}/memberOf` to `/users/{id}/memberOf/microsoft.graph.group`; the tool's own request/response JSON shape (`user_id`, `max_results`, `page_token` in; `count`, `groups`, `has_more`, `next_page_token` out) is unchanged — only its correctness is fixed.

**`graph_update_user`** (modified) — **breaking response change**: `updated` changes from an array of field names (`["jobTitle"]`) to an object mapping field name to new value (`{"jobTitle": "Interface Test"}`). Request shape is unchanged.

**`graph_remove_manager`** (modified) — **breaking response change**, full replacement:
- Old: `{"status": "removed"|"no_manager", "user_id": "..."}`
- New: `{"user_id": "...", "removed": true|false, "previous_manager": {"id": "...", "display_name": "...", "user_principal_name": "..."} | null, "reason": "no_manager" | null}`
- Graph calls: `GET /users/{id}/manager?$select=id,displayName,userPrincipalName` (new, always issued first) → `404` maps to `removed=false, reason="no_manager"` with no further call; `200` → `DELETE /users/{id}/manager/$ref` (a `404` on *this* call, from a concurrent removal, is now tolerated as success per AC7, not surfaced as an error).

**`graph_get_user`** (modified) — default response (no `select`) gains `onPremisesImmutableId`, `onPremisesSamAccountName`, `createdDateTime`, `lastPasswordChangeDateTime`. A `select` that includes `"manager"` now additionally returns an expanded `manager` object (`id`, `displayName`, `userPrincipalName`) — previously `"manager"` in `select` silently returned nothing for that key. Request shape (`select: list[string]`) is unchanged; only what `"manager"` inside it actually does is fixed.

**Backward compatibility**: `graph_list_user_groups` and `graph_get_user`'s changes are additive/corrective with no shape break. `graph_update_user`'s `updated` field and `graph_remove_manager`'s entire response are breaking changes to tools released days ago; see Non-functional for why this is accepted rather than made additive.

### Key flow / sequence

`graph_remove_manager` (new flow):

1. Caller → `graph_remove_manager(user_id="u1")`
2. Server → `GET /users/u1/manager?$select=id,displayName,userPrincipalName`
   - `404` → return `{"user_id": "u1", "removed": false, "previous_manager": null, "reason": "no_manager"}`. **No `DELETE` is issued.**
   - other error → return that error's envelope unchanged.
   - `200` → continue.
3. Server builds `previous_manager` from step 2's body.
4. Server → `DELETE /users/u1/manager/$ref`
   - `404` (race: already removed by someone else since step 2) → treated as success, not an error.
   - success → continue.
5. Server returns `{"user_id": "u1", "removed": true, "previous_manager": {...from step 3}, "reason": null}`.

`graph_update_user` (new tail, after the existing patch-safety/UPN-domain steps round 1 already designed):

1. Server builds `body` from every provided field exactly as round 1 designed (unchanged).
2. Server → `PATCH /users/{id}` with `body`.
3. If `body` is non-empty and the PATCH succeeded: Server → `GET /users/{id}?$select=<comma-joined body.keys()>`.
4. Server returns `{"status": "success", "user_id": "...", "updated": {k: result.get(k) for k in body}}` — `result` is step 3's response.

### Non-functional

- **Idempotency & concurrency**: `graph_remove_manager` is now idempotent by explicit design rather than by accident of Graph's error behavior (which acceptance proved doesn't hold) — the read-before-delete sequence, plus tolerating a `404` on the `DELETE` itself (AC7), means two concurrent `graph_remove_manager` calls against the same user converge to the same end state (no manager) with neither call erroring, and the "who was it" answer is preserved by whichever call's `GET` ran first. `graph_update_user`'s new re-read is a plain `GET` after the existing `PATCH` — no new concurrency hazard beyond what the PATCH itself already had (last-write-wins, unchanged from round 1); a concurrent writer between the `PATCH` and the follow-up `GET` would be reflected in the `GET`'s result, which is the more-correct outcome (the response describes what's actually stored at read time), not a regression.
- **Performance**: `graph_update_user` costs one extra Graph call (`GET`) per call that changes at least one field — not on every call (no-op update attempts are already rejected before reaching Graph by the existing "provide at least one attribute" check). `graph_remove_manager` costs one extra Graph call (`GET /manager`) on every call, replacing what was previously a single `DELETE` — both are the same class of cost round 1 already accepted for the UPN domain check (one extra read, not a loop). `graph_list_user_groups`'s fix has no new cost — it's the same number of Graph calls as today, just hitting a different (correctly-typed) path.
- **Security**: no new auth surface. `GET /users/{id}/manager` requires the same `User.Read.All`/`User.ReadWrite.All`-class permission the existing `DELETE .../manager/$ref` call already requires (manager is a standard Entra read, bundled under the same scope as the writes this connector already performs) — no new Graph app-registration permission is needed.
- **Multi-tenant isolation**: unchanged from round 1 — this server has no isolation logic of its own; every Graph call (including the new `GET /manager`) is scoped by the caller's own bearer token, which Microsoft itself scopes to exactly one tenant. Round 1's AC15 (manual, local blind spot) still stands and is not re-verified by this round; no new cross-tenant surface is introduced.
- **Observability**: no new logging beyond `GraphClient`'s existing retry/error path — same pattern as round 1 (errors are returned as envelopes to the caller, not logged server-side).

### Rollout & rollback

Same as round 1: no feature flag (this server has none), normal `ms-graph-mcp` release — merge → image rebuild → redeploy. Rollback is reverting the image; no data migration exists. **The two breaking response-shape changes need the same coordination round 1's pagination-contract change needed**: `graph_update_user`'s `updated` field and `graph_remove_manager`'s entire response shape change in a way a caller parsing the old shape would silently misread (e.g. code checking `result["status"] == "removed"` would raise a `KeyError` against the new shape, which is arguably safer than silently misreading `removed` as a string, but is still a break). The only known caller integrating against these tools is the reporter's own offboarding workflows (03/08), who filed the acceptance test that is driving this exact shape — so this round treats the break as expected and coordinated, not accidental, but it is called out here explicitly for groom to confirm no other caller exists, exactly as round 1's Open Questions flagged the pagination-contract change for the same reason.

The one genuinely new testing need is **simulating a mixed-type raw page** for Defect 1's regression test (a `memberOf`-shaped response containing a non-group item) — `_CapturingClient` already supports this by simply shaping `client._result["value"]` accordingly, the same mechanism `test_list_user_groups_returns_group_type_mail_enabled_and_sync_source` (`tests/test_tools.py:1339-1365`) already uses to control per-item shape; no new fixture class is needed.
