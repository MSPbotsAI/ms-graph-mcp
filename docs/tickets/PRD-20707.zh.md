## 需求理解

一句话:提单人希望 Monthly Technology Report agent 发出的邮件附件是真正生成的报告,而不是现在这种——Microsoft Graph 回报发送成功、但附件其实是占位符 HTML 文件。

EMD(Heath Beavers)于 2026-10-14 首次报告此问题;2026-10-16 在内部测试另一个无关的审批规则修复(PRD-20659)时又复现了一次。两次运行中,Monthly Technology Report agent 都正确生成了完整报告、Executive Brief 和 Action Register,所有内容校验(identity/period/verbatim/styles)全部通过,但通过 `graph_send_mail` 发往 `mspbots_reports@emdnet.com` 的邮件附带的是一个很小的占位符 HTML,而不是约 57 KB 的真实报告。发送本身在 Graph API 层面是成功的(无错误、无重试信号),所以当前流水线里没有任何环节能检测或标记这种不一致,唯一的信号是 agent 自己在聊天最终回复里的事后自述。邮件无法撤回。目前还在试点阶段,只有试点收件人收到过错误附件,但这会阻塞 EMD 原定 11 月初的正式客户交付。

## 现状(每条断言都带 path:line)

- `src/graph_mcp/tools/mail.py:377-449`(`graph_send_mail`)——本服务对外暴露、用于通过 Microsoft Graph(`/me/sendMail` 或 `/users/{id}/sendMail`)发信的 MCP 工具。其可选参数 `attachments`(`:402-407`)最多接受 5 项,每项需要 `filename` 加**恰好一个** `content_text`(原始文本,服务端编码)或 `content_base64`(二进制,已 base64)——没有第三种"按 id/URL 引用、由服务端自己取"的方式。调用方(生成这次工具调用的 LLM)必须把附件的每一个字节原样复述进自己生成的输出里。
- `:123-205`(`_build_attachments`)——校验并把 `attachments` 映射成 Graph 的 `fileAttachment` 字典。完整读过之后确认:这是一个**忠实的透传**。它按 `_MAX_ATTACHMENT_BYTES = 500_000` / `_MAX_TOTAL_ATTACHMENT_BYTES = 700_000`(`:98-99`)检查大小,归一化 base64 的各种变体(`:109-120`,PRD-20416 加的),按文件名后缀猜 `content_type`——但它**没有任何办法核实内容是否真的对应这个文件名**,因为它没有独立的事实来源能判断文件"应该"是什么。一个编码合法、大小合规的占位符,和真实的 57 KB 报告在这一层看起来一样干净。
- `:91-97`——一段先于本工单就存在的注释,正好写明了这个 bug 所依赖的机制:"内联附件是以 base64 工具参数的形式传入的,所以调用方 agent 必须先在自己的上下文里持有(并复述出)每一个字节。"对一份 57 KB 的 HTML 报告来说,这意味着生成 `graph_send_mail` 调用的模型要在自己生成的工具调用参数里原样复述约 57,000 字节的内容,而且往往是在报告实际生成好之后又过了好几轮对话。

## 产品设计

### 目标 / 非目标

**目标**(本单范围仅限 `ms-graph-mcp`):
- 一个已经(或将会)拥有可取附件 HTTPS URL 的调用方,能让**服务端**自己去取并附加那些精确字节,而不必在自己生成的工具调用输出里原样复述文件内容。
- 走这条路径的附件要受到和内联附件一样的大小限制(`_MAX_ATTACHMENT_BYTES` / `_MAX_TOTAL_ATTACHMENT_BYTES`),任何失败(URL 不可达、host 不在允许列表、内容超限)都要在发信**之前**以结构化错误报出来——绝不能静默替换成别的内容。
- 只有 host 在运维方显式配置的允许列表里的 HTTPS URL 才能被取;默认不配置任何 host(出厂默认)时,这项能力处于关闭状态,表现为清晰、有文档说明的 `invalid_argument`,而不是悄悄什么都不做。
- 任何带附件的 `graph_send_mail` 调用都要记录结构化元数据(文件名、字节数、sha256、来源),这样将来再发生类似不一致时可以从服务端日志里查到,而不是只能靠 agent 事后自己报告——本工单就是这么被发现的。

**非目标**(明确不在本单范围内):
- 在 Agent Platform 一侧真正暴露一个可取到生成报告/artifact 的 URL。那是另一个仓库(按架构推断最可能是 `mb-platform-agentos`,但本单 Code Project 能触达的代码级证据并不覆盖那个仓库的内部实现——见 Open Questions),本设计不会在没有证据的情况下去臆测那边的代码。本单只交付这套机制里"接收"的那一半,在那个 URL 出现、且配好允许列表之前都是闲置状态。
- 修复"调用方没有可持久化、可取的文件位置"这类通用的复述风险(例如内容只存在于模型自己的上下文里)。这类调用方维持今天不变的 `content_text`/`content_base64` 行为,以及它对大文件原本就存在的真实风险。
- 对 Monthly Technology Report agent 本身做任何提示词/SKILL 层面的改动(那部分内容不在本流水线能触达的任何仓库里——见现状)。
- URL 拉取的重试/退避策略,超出本仓库现有共享 HTTP 客户端已有的超时设置之外的部分。
- 改动 `_MAX_ATTACHMENTS`(5)或 700 KB 的合计上限。

### 验收标准 AC1..AC8

- **AC1**:Given 某附件项指定了 `content_url`,指向配置好的允许列表里的某个 HTTPS host,且该 URL 返回的内容在单文件大小限制以内,When 调用 `graph_send_mail`,Then 服务端自己取回那份内容并以这些精确字节作为附件发信——调用方不需要在自己的工具调用参数里内嵌这些字节。
- **AC2**:Given 某附件的 `content_url` host **不在**允许列表里,When 调用 `graph_send_mail`,Then 不发出任何 Graph 请求(邮件不会被发送),工具返回 `invalid_argument` 错误并指明被拒绝的 host。
- **AC3**:Given 允许列表为空(开箱默认状态),When 任意附件指定了 `content_url`,Then 返回 `invalid_argument`,说明该能力尚未配置——其余行为与今天完全一致。
- **AC4**:Given `content_url` 拉取失败(非 2xx 响应或网络超时),When 调用 `graph_send_mail`,Then 不发送邮件,工具返回结构化错误标明是取文件失败——绝不会用空内容或占位内容顶替一次失败的拉取。
- **AC5**:Given `content_url` 拉取成功,但取回的内容超过单文件或合计大小限制,When 调用 `graph_send_mail`,Then 不发送邮件,触发既有的大小超限错误,并如实引用实际取回的字节数。
- **AC6**:Given 某附件项同时指定了 `content_text` / `content_base64` / `content_url` 中的一个以上,When 调用 `graph_send_mail`,Then 按今天"必须恰好指定其中一个"的同一套校验逻辑拒绝,只是现在扩展到三者。
- **AC7(向后兼容)**:Given 附件只使用 `content_text` 或 `content_base64`,写法与改动前完全一样,When 调用 `graph_send_mail`,Then 行为与响应结构与改动前逐字节一致——PRD-19661/PRD-20416 留下的每一条既有测试都原样继续通过。
- **AC8(可观测性)**:Given 任意带有一个或多个附件的 `graph_send_mail` 调用,When 该调用结束(无论最终 Graph 发送是成功还是失败),Then 服务端为每个附件记录一条日志,包含文件名、解码后字节数、sha256、来源(`inline` 或 `url`)——这是全新能力,本仓库目前完全没有日志(见现状一节的确认)。

## 技术设计

### 结论

在 `graph_send_mail` 的 `attachments` schema 里新增第三种、与另两种互斥的附件内容来源 `content_url`。给定时,服务端自己拉取这个 URL(复用本仓库现有的共享 `httpx.AsyncClient`),对拉到的字节施加和今天一样的大小上限,且只有当该 URL 的 host 在一份新增的显式允许列表(`Settings.attachment_fetch_allowed_hosts`,默认空 = 功能关闭)里才会继续。这把模型从字节复述这条通路上移开——对任何已经有可取 URL 的调用方都适用——直接照搬本仓库自己在 PRD-20413 里已经验证过必要性的修法模式("把模型移出数据通路",在 PRD-20211 中纯提示词修法被 QA 实测证伪之后采纳)。同时新增结构化日志(本文件此前完全没有),不论来源,每次发信都记录附件元数据,让将来的不一致可以从服务端日志诊断。在 Agent Platform 一侧真正暴露一个可取到的 artifact URL 不在本单范围内——那是另一个仓库,本单 Code Project 没有证据覆盖到那边的实现(见 Open Questions)。

- `src/graph_mcp/_json.py:76-88`——`error_envelope(code, message, retryable, extra=None)`,已经支持结构化 `extra`(PRD-20413 为另一个工具加的),本设计的新错误码直接复用。

### 方案选型

| 方案 | 做法 | 优点 | 代价 | 结论 |
|---|---|---|---|---|

### 数据与接口契约

**MCP 工具契约**——`graph_send_mail` 附件项,扩展后:

```json
{"filename": "monthly-technology-report_american-ambulance-of-visalia_2026-09.html",
 "content_url": "https://artifacts.example-allowlisted-host/thread123/report.html"}
```

- `content_text` / `content_base64` / `content_url` 三者必须恰好指定一个(在今天双选校验的基础上扩展)。
- `content_url`:必须是 `https://`;其 host 必须出现在 `ATTACHMENT_FETCH_ALLOWED_HOSTS`(逗号分隔的环境变量;默认空值会拒绝任何 `content_url`)里。

错误响应(新增错误码,复用既有的 `error_envelope(code, message, retryable, extra)`):

| 错误码 | 触发条件 | `extra` |
|---|---|---|
| `invalid_argument` | `content_url` 的 scheme 不是 `https` | — |
| `invalid_argument` | `content_url` 的 host 不在允许列表(含默认空列表)| `{"host": "...", "allowed": [...]}` |
| `invalid_argument` | `content_text`/`content_base64`/`content_url` 同时给了一个以上 | — |
| `upstream_error`(可重试)| 拉取连接失败/超时/5xx | `{"url": "..."}` |
| `not_found`(不可重试)| 拉取返回 404 | `{"url": "..."}` |
| 既有大小超限错误(错误码不变)| 拉到的字节超过单文件或合计上限 | 沿用既有结构,引用的是实际拉到的字节数 |

**出站调用**:在既有的 `POST /me/sendMail` 或 `POST /users/{id}/sendMail` 之前,新增一次 `GET <content_url>`(对允许列表里的 host,走共享 `httpx` 连接池)。只要这次拉取失败,就完全不发出 Graph 调用——保持现有文档里"If any attachment is invalid nothing is sent"这条不变量。

**数据库**:无——本服务不持有状态(网关模式,只按请求带 token;本设计不改变这一点)。

**向后兼容**:纯增量。`content_text`/`content_base64` 的行为逐字节不变(AC7);`content_url` 是全新能力,配合出厂默认的空允许列表,等同于一个闲置功能(一律拒绝)——所以单独部署这个改动,对任何现有调用方都是零行为变化。

### 关键流程时序

```
agent → graph_send_mail(..., attachments=[{filename, content_url}])
  → _build_attachments():逐个附件
      ├─ 给的是 content_text / content_base64 → 既有路径,不变
      └─ 给的是 content_url
           ├─ scheme 不是 https                → invalid_argument
           ├─ host 不在允许列表                 → invalid_argument(回显 host 与允许列表)
           └─ GET content_url(共享 httpx 客户端,限大小的流式读取)
                ├─ 非 2xx / 超时                → upstream_error / not_found
                ├─ 字节数 > 单文件上限           → 既有大小超限错误
                └─ 成功                          → 字节的用法和 content_base64 完全一样
  → 对所有附件做大小校验(既有逻辑,现在不区分来源)
  → 每个附件 logger.info(...)(文件名、字节数、sha256、来源)
  → POST /me/sendMail(或 /users/{id}/sendMail),不变
```

### 非功能

- **幂等与并发**:拉取是一次无副作用的单纯 `GET`;`graph_send_mail` 维持原本正确的 `idempotentHint=False`(发信本来就不是幂等操作,不变)。不引入任何共享可变状态——允许列表是只读的 `Settings`,进程启动时加载一次,和现有 `graph_base_url` 是同一种模式。
- **性能**:只有用到 `content_url` 时才多一次出站往返;现有 `content_text`/`content_base64` 调用方零额外延迟。限大小的流式读取能防止一个很大或很慢的响应把某个 worker 无限期卡住,超时边界参照 `api_client.py` 现有的 `_TIMEOUT` 形状设置。
- **安全**:新增的出站拉取能力是本设计最主要的风险面,缓解手段是 (a) 只允许 HTTPS,(b) 一份默认为空的显式 host 允许列表(默认关闭、按需打开),(c) 和今天一样的字节上限。这**不能**完全消除允许列表被误配置成内部/私有地址时的 SSRF 风险——这一点在 `README.md`/`.env.example` 里明确写出来,让配置允许列表的人清楚这个约束。实现时应该再加一道便宜的额外防线:即便被误配置进允许列表,也自动拒绝私有/回环/链路本地的 IP 段(见风险一节,未单独列 AC)。不需要新增任何 Graph 权限范围。
- **多租户隔离**:不受影响。`content_url` 的拉取不带任何 Graph token、不带任何租户上下文——它是对允许列表里某个 host 发起的一次独立的、对本服务而言无需鉴权的 HTTPS GET。现有按请求隔离 Graph token 的机制(`contextvars`、`server.py`)不受触碰。
- **可观测性**:全新能力(AC8)——这个文件目前完全没有日志。每次带附件的 `graph_send_mail` 调用都新增一条 `logger.info`,不论附件来源,这样将来再出现内容不一致时可以从服务端日志诊断,而不是只能靠 agent 事后自述——这次工单本身就是这么被发现的。

### 风险与依赖

- **风险**:如果"限大小的流式读取"实现得不对(检查大小之前就整个缓冲完),会重新引入一个来自误配置或被攻陷的允许列表 host 的内存耗尽攻击面——在改动清单里已标注给开发棒注意。
- 不依赖 PRD-20211/PRD-20413 进一步完成什么——那两张单是同一仓库里的另一条代码路径(`sites.py`),这里引用它们只是作为修法模式的先例。
