## 现状（每条论断都带 path:line）

出处：comment `90170262303660`（Damon Zhou，2026-10-14 07:19 UTC，mspbots demo 租户验收测试）说明真实 Graph API 的实际行为 · 代码读自 `ms-graph-mcp@master (4731160)` 说明当前实现的实际行为 · wiki：本轮返工没有引入任何新的产品可见面（仍是同一批后端 MCP 工具，界面没有变化），所以第一轮的 wiki 引用原样沿用（`ProductDocs/15-Capabilities.md` § Connector detail view，_verified_ 2026-08-31，v4.1.518 —— Tools 列表是唯一的终端用户可见面，单个工具内部的正确性在那里不可见）。`wiki find "graph connector offboarding"` / `"ms-graph-mcp tools"` —— 均未命中，与第一轮记录的同一个覆盖缺口一致（wiki 不覆盖具体 MCP 工具调用语义）。

**缺陷 1 —— `graph_list_user_groups` 分页丢组且不终止**（验收 1.1 项）。

代码：`src/graph_mcp/tools/groups.py:92-121`。该工具分页读取 `GET /users/{user_id}/memberOf`（一个多态集合——组、目录角色、管理单元等都可能出现在里面），`$top`/`$skiptoken` 作用在这个未过滤的原始集合上（`:94,97`）。取到页面后再用 Python 过滤，只保留看起来像组的对象（`:102-105`：`if not (obj.get("@odata.type","").endswith("group") or "groupTypes" in obj): continue`）。被过滤掉的数量完全不影响 `$top`/`$skiptoken`——这两者完全由原始（未过滤）页驱动。验收的实际观察——第 1 页返回 `count=0` 且带 token，第 2 页返回 1 个组，之后每一页又都返回 `count=0` 并带新 token，走下去始终到不了 `has_more=false`——正好对应这段代码：一页如果全部被过滤掉，依然会带一个有效的 `@odata.nextLink`/`$skiptoken`（`groups.py:110`），所以客户端可见的游走过程会出现连续空页，在提单人遇到的最坏情况下表现为看似永不收敛。`graph_list_group_members`（`groups.py:364-367`）没有这个问题，因为 `/groups/{id}/members` 没有需要过滤掉的同级非成员类型对象。

**缺陷 2 —— `graph_update_user` 成功响应里没有新值**（验收 1.4 项，minor）。

代码：`src/graph_mcp/tools/users.py:653-657`。PATCH 成功后，该工具返回 `{"status": "success", "user_id": user_id, "updated": list(body.keys())}`——`list(body.keys())` 只是 PATCH 请求体自己的键名（例如 `["jobTitle"]`），从未回读 Graph。验收确认这正是今天线上的行为，并要求返回变更后的实际值本身（例如 `{"jobTitle": "Interface Test"}`），而不只是字段名。

**缺陷 3 —— `graph_remove_manager` 的返回值与幂等性**（验收 1.5 项）。

代码：`src/graph_mcp/tools/users.py:692-711`。该工具调用 `DELETE /users/{user_id}/manager/$ref`，任何非错误响应都返回 `{"status": "removed", "user_id": user_id}`；只有 `GraphError` 且 `status_code == 404` 才会映射成 `{"status": "no_manager", ...}`（`:708-710`）。验收在 `rewst_migtest01` 上的两次实测显示，针对一个已经没有 manager 的用户，Graph 的第二次 `DELETE` **并没有**返回 404——两次都返回成功，所以这段代码依赖的"唯一的 no_manager 信号就是 404"这个假设在真实 API 面前不成立：工具在没有移除任何东西的调用上报告了 `removed`，而且这个函数里完全没有"删除前先读一下"的步骤，所以也从不暴露移除前的 manager 是谁。

**缺陷 4 —— `graph_get_user` 缺省字段缺失、`select`+`manager` 组合失效**（验收 1.6 项）。

代码：`src/graph_mcp/tools/users.py:33-42`（`_USER_PROFILE_SELECT`，默认 `$select`）与 `:406-447`（`graph_get_user`）。两个子缺陷，均已读代码确认：
- `_USER_PROFILE_SELECT`（`:33-42`）不包含 `onPremisesImmutableId`、`onPremisesSamAccountName`、`createdDateTime`、`lastPasswordChangeDateTime`——正是验收列出的、默认响应里缺失的那几个字段。
- 当提供 `select` 时（`:436-438`），所有请求的字段名——包括 `"manager"`——都被直接拼进 `$select`。`manager` 在 Graph 的 `user` 资源上是导航属性，不是平铺属性，所以 Graph 会悄悄把它从 `$select` 里丢掉而不是报错；只有默认（不传 `select`）分支（`:439-441`）用了 `$expand=manager(...)`，那是唯一真正能拿到它的机制。该工具自己的 docstring（`:415-418`）承诺 `select=["manager"]` 能拿到 manager——验收恰好测了这个调用，确认这个承诺对真实 Graph 不成立。`tests/test_tools.py:1585-1592`（`test_get_user_custom_select_narrows_fields`）只测过 `select=["displayName","mail"]`，从未试过 `select` 里带 `"manager"`——这个缺口没被测过，不只是没被实现。

**不受影响**：1.2 项（`graph_list_groups`）与 1.3 项（`graph_list_users`）在验收中原样通过——它们直接分页 `/groups` 与 `/users`，这两个集合没有需要过滤掉的同级非匹配类型，所以缺陷 1 的根因不适用于它们。本轮对两者均不提出改动。

**范围外、维持不变**：1.7/1.8 项（`graph_transfer_onedrive`、`graph_start_cloud_sync`）按原工单自己的访谈记录（第一轮非目标）与验收自己的说明（"Items 1.7 / 1.8 are tracked in a separate ticket and not covered here"）继续排除在外。

## 产品设计

### 目标 / 非目标

**目标**（本轮，与验收的 4 个失败项一一对应）：
- G1：`graph_list_user_groups` 的分页能正确终止，且对任意用户都能恰好返回每个组一次，不论该用户还有多少个非组类型的 `memberOf` 条目（目录角色等）。
- G2：`graph_update_user` 返回它实际改动的每个字段的新值，而不只是字段名。
- G3：`graph_remove_manager` 准确报告是否真的移除了 manager、在存在 manager 时返回移除前是谁，且绝不在没有移除任何东西时报告"已移除"。
- G4：`graph_get_user` 的默认响应包含验收要求的四个 on-premises/审计字段，且 `select` 中包含 `"manager"` 时真的能拿到 manager。

**非目标**（本轮明确不做）：
- 重开 1.2/1.3 项（`graph_list_groups`、`graph_list_users`）——它们在验收中原样通过。
- 1.7/1.8 项（`graph_transfer_onedrive`、`graph_start_cloud_sync`）——仍待与 Ginko 的另案确认，按第一轮非目标与验收自身的说明，本轮不重开。
- 在验收 Expected/Acceptance 字面要求之外，继续给 `graph_get_user`/`graph_update_user` 加别的字段。

### 验收标准 AC1..AC7

（以下编号是本轮（第二轮）文档内部的局部编号；括号里标注了它取代的第一轮原 AC 编号——`docs/tickets/PRD-20393.md` 里对应编号的原 AC 对该行为不再是定论文本。）

- AC1（取代原 AC1）：Given 一个属于 ≥3 个组（且至少有一个非组类型 `memberOf` 条目，例如一个目录角色）的用户，When 以 `max_results=1` 对 `graph_list_user_groups` 分页直到结束，Then 返回的组集合与 `max_results=200` 一次调用完全相同，没有空页、没有重复，最后一页的 `next_page_token` 为 `null`。（这是验收自己对 1.1 项给出的字面 Acceptance 行。）
- AC2（新增——不对应任何第一轮 AC）：Given `graph_update_user` 改动了一个或多个字段，When 调用成功，Then 响应里的 `updated` 是一个对象，把每个被改动的字段名映射到 PATCH 之后立即回读 Graph 得到的新值（被显式清空的字段回读为 `null`），而不是一个字段名列表。
- AC3（取代原 AC9）：Given 一个已指定 manager 的用户，When 调用 `graph_remove_manager`，Then 返回 `removed=true` 且 `previous_manager` 填充了该 manager 的 `id`/`display_name`/`user_principal_name`，随后一次 `graph_get_user` 对该用户不再返回 manager。
- AC4（取代原 AC10）：Given 一个未指定 manager 的用户，When 调用 `graph_remove_manager`，Then 返回 `removed=false`、`previous_manager=null`、`reason="no_manager"`，不报错，再次调用同样成功，且（按技术设计中新的"先读后删"设计）这种情况下根本不会向 Graph 发出 `DELETE` 调用。
- AC5（取代/扩展原 AC11）：Given 一个 `onPremisesImmutableId`、`onPremisesSamAccountName`、`createdDateTime`、`lastPasswordChangeDateTime` 均有值的用户，When 不带 `select` 参数调用 `graph_get_user`，Then 这四个字段都出现在响应里，与今天默认响应已有的字段并列。
- AC6（取代/扩展原 AC12）：Given 一个 `select` 参数里既包含 `"manager"` 又包含其它字段名，When 调用 `graph_get_user`，Then 响应恰好包含那些其它字段（加 `id`）以及一个展开的 `manager` 对象（`id`、`displayName`、`userPrincipalName`）。
- AC7（技术设计自行补充，非验收报告字面要求——理由见技术设计「非功能」一节）：Given 在 `graph_remove_manager` 的读取步骤执行时某用户的 manager 还在，但在本次调用自己的 `DELETE` 执行之前被另一个并发调用移除了，When `graph_remove_manager` 运行，Then 仍然返回 `removed=true`，`previous_manager` 为读取时刻捕获到的值，而不是报错——这个竞态不改变"本次调用发起的移除已经（或本就）生效"这一事实。

### Open Questions

- [不阻塞] `previous_manager` 的 `display_name`/`user_principal_name` 来自判断 manager 是否存在的同一次读取；如果那个 manager 账号本身被禁用或配置不全，这两个字段可能为 `null`，即使 `id` 存在。不阻塞——`graph_get_user` 对任何展开引用都有同样的特性。
- [已假设] 验收对缺陷 2 的措辞（"re-read the user and return each changed field with its new value"）被按字面理解为*通过一次后续 `GET` 回读*，而不是*把请求里的输入值原样回显*——理由见技术设计「方案选型」，两者并不等价。若 groom 的本意是更便宜的回显方案，AC2 与技术设计第 4 节需要重做。
- [不阻塞] AC7（`graph_remove_manager` 的并发安全性）是本设计自行补充的，不是验收报告要求的——按本流水线自己的规矩，只有源自 AC 的判断才能不加说明地写进产品设计，所以这里显式标注。它直接来自技术设计自身对"新引入的先读后写序列"应尽的幂等/并发义务（`templates-design.md` §2.7），不是新的产品范围。

## 技术设计

### 结论

四处修复都留在第一轮已经动过的两个文件里（`src/graph_mcp/tools/groups.py`、`src/graph_mcp/tools/users.py`）加测试套件，没有新文件、没有新依赖、没有 schema/DB 变更。缺陷 1 的修法是把"只要组"的过滤从客户端 Python 挪到 Graph 自己的 OData 类型转换 URL（`/memberOf/microsoft.graph.group`），这是去根因而不是在症状上打补丁。缺陷 2 的修法是在 `PATCH` 成功后追加一次 `GET` 回读。缺陷 3 的修法是改成"先读后删"序列，完全不再依赖 Graph 的 `DELETE` 404 行为（验收已经证明这个假设不成立），并且有意引入一个破坏性的新返回结构（`removed`/`previous_manager`/`reason`，取代原来的 `status`）。缺陷 4 的修法是加宽默认 `$select` 常量，并对 `select` 参数里的 `"manager"` 做特判，把它导向 `$expand` 而不是 `$select`。

### 方案选型

| 缺陷 | 方案 | 做法 | 优点 | 代价 | 结论 |
|---|---|---|---|---|---|
| 1（分页） | A | 保留 `/users/{id}/memberOf`，只修客户端的计数逻辑（比如内部多请求几页，直到攒够一整页"组"再返回给调用方，把空页藏起来） | 改动小；不改 Graph 调用路径 | 没有解决真正的根因（页边界和类型边界依然互相独立）——在极端情况下（一个用户非组类型 `memberOf` 条目很多、真正的组很少）只是把卡住的位置挪得更深，而不是消除，而且会把第一轮刻意放弃的"内部走多页再返回"的形状又引回来 | 拒绝 |
| 1（分页） | B | 在 URL 里对导航属性做类型转换：`GET /users/{id}/memberOf/microsoft.graph.group`（标准的、有文档的 OData 具体类型转换写法） | Graph 自己就只返回组对象——`$top`/`$skiptoken` 和过滤后的集合天然是同一个集合；彻底去掉客户端过滤那块代码（净简化）；与验收自己字面的"Expected"一致 | 未发现——权限范围与今天的 `/memberOf` 调用相同，响应字段形状相同 | **采用** |
| 2（更新返回值） | A | 直接回显调用方传进来的值，不回读 | 零额外 Graph 调用 | 不能反映 Graph 自己做的任何规范化/拒绝/转换，更重要的是不符合验收的字面措辞（"re-read the user and return..."） | 拒绝 |
| 2（更新返回值） | B | PATCH 成功后，针对改动过的那些键发一次 `GET /users/{id}`（`$select` 限定为这些键），据此构造 `updated` | 符合验收的字面要求；反映的是 Graph 实际存下来的值，不是请求里写的值 | 每次至少改动一个字段的 `graph_update_user` 调用多一次 Graph 调用（与第一轮已经接受的 UPN 域名校验属于同一类代价） | **采用** |

| 3（remove_manager 结构） | B | 完全替换返回结构为 `removed`（布尔）/`previous_manager`/`reason`，基于一个完全不再依赖 Graph DELETE-404 行为的"先读后删"序列 | 与验收自己字面的"Expected"完全一致；唯一已知的调用方（离职流程 08，正是提交这份验收报告的人）要的就是这个结构；真正修复了根因，而不是在依然错误的信号上叠加字段 | 对一个几天前才发布的工具做破坏性改动——可接受，因为唯一已知调用方正是要求新结构的人，且第一轮自己做过的全仓检查没发现任何其它调用方 | **采用**——在「非功能」里显式标注为破坏性改动，不悄悄吸收 |
| 4（select+manager） | A | `select` 依然原样拼进 `$select`（今天线上的行为），只修 docstring，不再承诺 `select` 里的 `"manager"` 能生效 | 不改代码 | 没有修复验收实际提出的缺陷——即使按（修正后的）文档操作，调用方依然完全拿不到通过 `select` 获取 `manager` 的方式，只能走默认（不传 `select`）调用，但那样会被迫连带取回其它所有默认字段 | 拒绝 |
| 4（select+manager） | B | 构造请求时对 `"manager"` 做特判：从 `$select` 列表里摘掉它，若它出现过则额外加上 `$expand=manager($select=id,displayName,userPrincipalName)`（与默认分支已经在用的展开写法相同） | 与验收对 1.6 项字面的 Expected/Acceptance 一致；改动小且局部；复用已有的展开写法而不是另造一套 | 未发现 | **采用** |

### 数据与接口契约

**`graph_list_user_groups`**（改）—— 对调用方没有可见的请求/响应契约变化。内部 Graph 调用路径从 `/users/{id}/memberOf` 改为 `/users/{id}/memberOf/microsoft.graph.group`；工具自身的请求/响应 JSON 形状（入参 `user_id`、`max_results`、`page_token`；出参 `count`、`groups`、`has_more`、`next_page_token`）不变——只是修正了正确性。

**`graph_update_user`**（改）—— **破坏性响应变化**：`updated` 从字段名数组（`["jobTitle"]`）变成"字段名 → 新值"的对象（`{"jobTitle": "Interface Test"}`）。请求形状不变。

**`graph_remove_manager`**（改）—— **破坏性响应变化**，整体替换：
- 旧：`{"status": "removed"|"no_manager", "user_id": "..."}`
- 新：`{"user_id": "...", "removed": true|false, "previous_manager": {"id": "...", "display_name": "...", "user_principal_name": "..."} | null, "reason": "no_manager" | null}`
- Graph 调用：`GET /users/{id}/manager?$select=id,displayName,userPrincipalName`（新增，总是最先发出）→ `404` 映射为 `removed=false, reason="no_manager"`，不再发出后续调用；`200` → `DELETE /users/{id}/manager/$ref`（这一次调用上的 `404`，来自并发移除，按 AC7 容忍为成功，不再对外报错）。

**`graph_get_user`**（改）—— 默认响应（不传 `select`）新增 `onPremisesImmutableId`、`onPremisesSamAccountName`、`createdDateTime`、`lastPasswordChangeDateTime`。`select` 中包含 `"manager"` 时，响应额外包含一个展开的 `manager` 对象（`id`、`displayName`、`userPrincipalName`）——此前 `select` 里的 `"manager"` 对该键悄悄什么都不返回。请求形状（`select: list[string]`）不变，只是修正了 `"manager"` 在其中的实际行为。

**向后兼容**：`graph_list_user_groups` 与 `graph_get_user` 的改动是增量/纠正性质，没有结构性破坏。`graph_update_user` 的 `updated` 字段与 `graph_remove_manager` 的整个响应是对几天前刚发布的工具的破坏性改动；原因见「非功能」。

### 关键流程时序

`graph_remove_manager`（新流程）：

1. 调用方 → `graph_remove_manager(user_id="u1")`
2. 服务端 → `GET /users/u1/manager?$select=id,displayName,userPrincipalName`
   - `404` → 返回 `{"user_id": "u1", "removed": false, "previous_manager": null, "reason": "no_manager"}`。**不发出 `DELETE`。**
   - 其它错误 → 原样返回该错误的信封。
   - `200` → 继续。
3. 服务端用第 2 步的响应体构造 `previous_manager`。
4. 服务端 → `DELETE /users/u1/manager/$ref`
   - `404`（竞态：第 2 步之后被别的调用方抢先移除）→ 按成功处理，不报错。
   - 成功 → 继续。
5. 服务端返回 `{"user_id": "u1", "removed": true, "previous_manager": {...第 3 步}, "reason": null}`。

`graph_update_user`（在第一轮已设计的 patch-safety/UPN 域名校验步骤之后新增的尾部）：

1. 服务端按第一轮设计的逻辑（不变）构造 `body`。
2. 服务端 → `PATCH /users/{id}`，带 `body`。
3. 若 `body` 非空且 PATCH 成功：服务端 → `GET /users/{id}?$select=<body.keys() 逗号拼接>`。
4. 服务端返回 `{"status": "success", "user_id": "...", "updated": {k: result.get(k) for k in body}}`——`result` 为第 3 步的响应。

### 非功能

- **幂等与并发**：`graph_remove_manager` 现在的幂等性来自明确的设计，而不是依赖 Graph 错误行为的巧合（验收已经证明后者不成立）——先读后删的序列，加上容忍 `DELETE` 本身的 `404`（AC7），使两个针对同一用户的并发 `graph_remove_manager` 调用都能收敛到同一个终态（没有 manager），两者都不报错，"是谁"这个答案由先执行 `GET` 的那次调用保留下来。`graph_update_user` 新增的回读只是在已有 `PATCH` 之后多一次纯 `GET`——没有引入 PATCH 本身之外的新并发风险（仍是第一轮就有的后写者获胜，不变）；`PATCH` 和随后的 `GET` 之间如果有另一个并发写入者，会体现在 `GET` 的结果里，这是更准确的结果（响应描述的是读取那一刻实际存的值），不是退化。
- **性能**：`graph_update_user` 每次至少改动一个字段的调用多一次 Graph 调用（`GET`）——不是每次都多，因为"至少提供一个属性"的检查已经会在没有任何改动时提前拒绝，根本到不了 Graph。`graph_remove_manager` 每次调用多一次 Graph 调用（`GET /manager`），取代了原来单纯一次 `DELETE`——两者都与第一轮已经接受的 UPN 域名校验属于同一类代价（多一次读取，不是循环）。`graph_list_user_groups` 的修复没有新增成本——Graph 调用次数和今天一样，只是打到了一个类型正确的路径上。
- **安全**：没有新的鉴权面。`GET /users/{id}/manager` 所需的权限与现有 `DELETE .../manager/$ref` 调用所需的是同一类（`User.Read.All`/`User.ReadWrite.All` 级别——manager 是标准的 Entra 读操作，归在这个连接器已经在用的写权限同一个范围下）——不需要为 Graph 应用注册申请新权限。
- **多租户隔离**：与第一轮一致，没有变化——这个服务器本身没有隔离逻辑；每次 Graph 调用（包括新增的 `GET /manager`）都由调用方自己的 bearer token 限定范围，而该 token 本身被 Microsoft 限定在唯一一个租户内。第一轮的 AC15（人工、本地盲区）依然成立，本轮不重新验证；本轮没有引入新的跨租户面。
- **可观测性**：没有超出 `GraphClient` 既有重试/错误路径之外的新日志——与第一轮同一套模式（错误以信封形式返回给调用方，不在服务端记日志）。
