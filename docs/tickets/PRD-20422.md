## Requirement understanding

One line: Add two production-grade Graph interfaces for Microsoft 365/Entra offboarding workflows 08 and 03 — `graph_transfer_onedrive` (transfer a departing user's OneDrive content/ownership to a destination account or admin) and `graph_start_cloud_sync` (start the tenant's required cloud synchronization after lifecycle changes) — each returning an actionable success/failure/pending status with safe retry support, to replace the unreliable Rewst OneDrive-transfer workaround (defect D-10) and the currently undefined cloud-sync step.

The reporter (Damon Zhou) wants `ms-graph-mcp` to gain two new tools that internal offboarding automations "workflow 08" and "workflow 03" can call instead of relying on Rewst (whose OneDrive-transfer step is already broken by defect D-10) or separate manual Graph/Exchange/AD steps. `graph_transfer_onedrive` should move a departing user's OneDrive content to a destination user or admin; `graph_start_cloud_sync` should trigger whatever directory-sync mechanism this tenant uses after an offboarding change, so downstream systems see the update. Both must report back an actionable started/completed/failed/pending status — not just a bare boolean — and must be safe to call more than once without creating duplicate or conflicting state. This ticket is explicitly the deferred remainder of PRD-20393 (items 7–8 of that ticket's original eight); the reporter's own text says the exact production behavior, transfer mode, destination rules, and the actual sync mechanism "still need confirmation with Ginko and relevant platform owners" — i.e. the reporter already expects this design to carry open items pending that confirmation, not to resolve them unilaterally.

## Product design

### Goals / Non-goals

**Goals:**
- G1: Offboarding automations (workflow 08/03) can call a Graph MCP tool to copy a departing user's OneDrive root content into a destination user's OneDrive, without going through Rewst.
- G2: The same automations can call a Graph MCP tool to trigger this tenant's directory synchronization after an offboarding change, for the one sync mechanism reachable from Microsoft Graph (Azure AD Connect **cloud sync** — see Non-goals and Tech design §3 for why classic on-premises AD Connect cannot be reached from here).
- G3: Both tools return one of a small, fixed set of actionable statuses (e.g. `started`/`completed`/`in_progress`/`no_content`/`not_applicable`/an error code) instead of a bare success/failure boolean, so the calling workflow can decide to continue, retry, or escalate without a human reading logs.
- G4: Calling either tool more than once for the same source/destination (or the same user, for sync) never creates duplicate or conflicting operations — repeating a call after a timeout or a workflow retry is always safe, and *is* the intended way to poll for completion (see Tech design §1).

**Non-goals** (explicit, per the reporter's own text and this design's own findings):
- Triggering synchronization for a tenant whose hybrid identity sync is classic on-premises Azure AD Connect rather than cloud sync — no Microsoft Graph API can start that; it is a local action on the Connect server itself (`Start-ADSyncSyncCycle`). `graph_start_cloud_sync` reports this case with a clear, named error rather than silently doing nothing or claiming success (AC10).
- Full-fidelity OneDrive migration (permissions, sharing links, version history, deleted items). This is a content copy of the current top-level items, in the same spirit as this repo's existing SharePoint tools (bounded, best-effort), not a certified backup/migration tool.
- Granting the destination user "site collection administrator" rights on the source's OneDrive — the alternative, access-transfer-not-copy approach some SharePoint admins use. That mechanism lives in SharePoint Online's own admin REST surface, not Microsoft Graph, and needs a different token audience than this server's single Graph-only client supports (Tech design §3).
- Building offboarding workflows 08/03 themselves, or deciding when they call these tools — this ticket only adds the Graph tool surface they can call.
- Exact destination-folder naming convention, exact Entra permission scope strings for the synchronization-jobs endpoint, and which tenant's cloud-sync job(s) apply are explicit assumptions below (Open questions), pending the reporter's own stated "confirmation with Ginko."

### Acceptance criteria AC1..AC12

- AC1: Given the Microsoft Graph connector is connected in a tenant and a caller presses Refresh Tools, When the caller lists the connector's tools, Then two new rows appear — `graph_transfer_onedrive` and `graph_start_cloud_sync` — each with a one-line description and an **Available** badge, and the existing 39 tools are unaffected.
- AC2: Given a source user with items in the root of their OneDrive and an existing destination user, When `graph_transfer_onedrive` is called with that source and destination, Then the call returns `status: "started"`, a destination folder is created (or reused) in the destination's OneDrive, and each source root item is reported with `action: "copy_started"`.
- AC3: Given a prior transfer for a source/destination pair where every item already matches (same name and size present in the destination folder), When `graph_transfer_onedrive` is called again for the same pair, Then the call returns `status: "completed"` and no new copy is issued for any item (each item reports `action: "already_present"`).
- AC4: Given a transfer where some items are still mid-copy (present in the destination with a different size than the source) when the automation retries after a timeout, When `graph_transfer_onedrive` is called again, Then the call returns `status: "in_progress"`, those items are reported pending, and no duplicate copy is issued for them.
- AC5: Given a source user who has never been provisioned a OneDrive, When `graph_transfer_onedrive` is called with that source, Then the call returns a `drive_not_found` error identifying the source, and the destination's OneDrive is not modified.
- AC6: Given a source user whose OneDrive root has zero items, When `graph_transfer_onedrive` is called, Then the call returns `status: "no_content"`, no destination folder is created, and no copy operations are issued.
- AC7: Given a destination user id that does not exist or has no OneDrive provisioned, When `graph_transfer_onedrive` is called, Then the call returns a `drive_not_found` error identifying the destination, and the source is not modified.
- AC8: Given a user whose directory object has `onPremisesSyncEnabled = true` in a tenant where this MCP can discover exactly one Azure AD Connect cloud-sync job, When `graph_start_cloud_sync` is called for that user, Then the call returns `status: "started"` together with the resolved `job_id`/`service_principal_id`.
- AC9: Given a user whose directory object has `onPremisesSyncEnabled = false` (a cloud-only account, never synced from on-premises), When `graph_start_cloud_sync` is called for that user, Then the call returns `status: "not_applicable"` (not an error), explaining there is nothing to sync for this user.
- AC10: Given a tenant with no discoverable Azure AD Connect cloud-sync service principal/job (including, but not provable to specifically be, a tenant that uses classic on-premises AD Connect instead), When `graph_start_cloud_sync` is called for a user with `onPremisesSyncEnabled = true` in that tenant, Then the call returns a `no_sync_job_configured` error whose message explicitly states this MCP cannot reach classic on-premises AD Connect and names the on-prem alternative (`Start-ADSyncSyncCycle` on the Connect server), rather than reporting success or a generic failure.
- AC11: Given a tenant with more than one Azure AD Connect cloud-sync job registered, When `graph_start_cloud_sync` is called, Then the call returns a `sync_job_ambiguous` error listing the candidate job ids, rather than guessing one.
- AC12 (multitenancy anchor): Given two separate calls to `graph_start_cloud_sync` made with two different callers' Graph access tokens (two different tenants), When each call runs its service-principal/job discovery, Then each discovery is performed fresh against that call's own token — no service principal or job id resolved while serving one caller's token is cached, reused, or returned for a different caller's token.

## Tech design

### Conclusion

Add two new tools to `ms-graph-mcp` in a new `src/graph_mcp/tools/offboarding.py` module (neither tool has a natural home in `users.py`, `groups.py`, or `sites.py` — one is a cross-drive copy operation, the other a directory-sync trigger, and both are offboarding-specific the way `graph_remove_manager` was offboarding-specific without living in `groups.py`). `graph_transfer_onedrive` performs an idempotent, destination-folder-scoped copy of a departing user's OneDrive root items into the destination user's OneDrive using Graph's async `/drives/{id}/items/{id}/copy` endpoint; completion is re-derived each call by listing and diffing file name + size rather than by tracking a job id, since this server keeps no state between calls (`stateless_http=True`, `server.py:76`) — calling the tool again *is* the status check. `graph_start_cloud_sync` checks the target user's `onPremisesSyncEnabled` flag to short-circuit a clean no-op for cloud-only users, then discovers and starts the tenant's Azure AD Connect cloud-sync provisioning job via `/servicePrincipals/{id}/synchronization/jobs/{jobId}/start`. Neither tool needs a change to `api_client.py`'s existing request/response shape (see §3, Option analysis, "api_client change" row) — both work entirely from parsed JSON bodies, not response headers.

### Where the current implementation lives

- `src/graph_mcp/tools/sites.py` (whole file) — the only existing `/drives/*` usage, all scoped to `/sites/{id}/drive`; `_resolve_site`/`_resolve_drive`/`_resolve_file` (`:46-150`) are the direct structural template for this ticket's own resolve-then-act helpers, including the "fold ambiguous/missing cases into a structured `error_envelope`" pattern (`_resolve_site`'s `site_ambiguous` branch, `:94-103`, is the template for this ticket's `sync_job_ambiguous`).
- `src/graph_mcp/tools/groups.py:79-180` — the "walk every page internally up to a cap, then stop" pagination shape PRD-20393 deliberately *rejected* for list tools (replaced with single-page-per-call). That rejection does not transfer here: `graph_transfer_onedrive` is an orchestration tool acting on every item, not a list tool letting the caller resume a list, so walking all of a source drive's root pages internally (§5) is the right shape for this different use case.
- `src/graph_mcp/tools/groups.py:106-107`, `:327-328` and `src/graph_mcp/tools/users.py:38` — existing `onPremisesSyncEnabled` → `sync_source` derivation, reused as-is for AC9's not-applicable check.
- `src/graph_mcp/api_client.py:124-192` — `GraphClient._request`/`_parse_body`; confirms (see Current state §7) that response headers are never surfaced today, which is why §3's Option analysis explicitly avoids needing them.
- `src/graph_mcp/tools/licenses.py:124-140` (`graph_reprocess_license`) — the closest existing precedent for "a tool that triggers an async-ish Graph-side process and returns immediately without polling it to completion"; this ticket's two tools follow the same posture.
- `tests/test_tools.py:14-70` (`EXPECTED_TOOLS`), `:95-129` (tool-count cap, currently `<= 39`) — must be updated for the two new tools.
- `tests/test_tools.py:1603-1655` (`graph_remove_manager`'s two tests) — direct template for this ticket's "ambiguous/not-found folds into a structured status, not a crash" test shape, and for the fake-`GraphClient`-with-`.calls` test harness (`tests/test_tools.py:1-50`-ish `_register` helper) this ticket's new tests reuse unchanged.

### Option analysis

| Option | Approach | Pros | Cost | Decision |
|---|---|---|---|---|
| OneDrive transfer — content copy | Enumerate source drive root items, async-copy each into a destination folder via Graph's `/drives/{id}/items/{id}/copy` | Pure Microsoft Graph, same API family (`/drives/*`) this repo already calls for SharePoint; matches the ticket's own wording ("Graph-based composite interface"); server-side copy, no bytes pass through this MCP or the calling agent's context | Destination ends up with a *copy*, not the original — source item ids differ from destination item ids; large/odd item counts mean many sequential Graph calls (see §7 performance) | **Chosen** |
| OneDrive transfer — access/ownership grant | Make the destination user a site-collection administrator on the source's OneDrive site (the "transfer ownership" pattern SharePoint admins use via `Set-SPOUser`) | Destination gets the *original* content in place, no duplication | Not a Microsoft Graph operation — lives in SharePoint Online's own classic admin REST/PowerShell surface, which needs a token issued for a different audience (`https://<tenant>-admin.sharepoint.com`, not `https://graph.microsoft.com`) than this server's single `GraphClient` supports; would require a second HTTP client wired to a second audience, a materially larger architectural change than this ticket's two-tool scope | Rejected — out of reach of this repo's single-Graph-client architecture without a much bigger change; also contradicts the ticket's explicit "Graph-based" framing |
| OneDrive transfer — surface Graph's async monitor URL | Capture the `Location` header from the `202` copy response and return the monitor URL (or an opaque token for it) to the caller for polling | Lets the caller poll Graph's own authoritative per-copy job status instead of this tool's own name+size heuristic | Requires a new `api_client.py` capability (headers are currently discarded, Current state §7); monitor URLs are typically short-lived and (per Graph's own documented behavior) do not require re-sending a bearer token, so handing one to a caller is handing out a small bearer-less capability token that this repo has no existing precedent for guarding (closest analogue, `graph_get_file`'s `downloadUrl`, is already an accepted precedent for returning a pre-authenticated link, but that one is read-only; a copy-status monitor URL is operationally inert but still an extra credential-shaped value to track) | Rejected — the name+size diff approach (chosen row below) gives the same "is it done yet" answer by re-querying data this tool already has to fetch anyway, with no new `api_client.py` surface and no token-shaped value leaving the server |
| OneDrive transfer — completion tracking | (a) A second "check status" tool, tracking job ids somewhere; (b) make `graph_transfer_onedrive` itself idempotent: each call lists current state and only acts on what's missing, so calling it again *is* the status check | (b) needs no new tool (the ticket named exactly two), no state storage (this server has none — `stateless_http=True`), and directly satisfies G4 (safe retry) with the same mechanism that answers "is it done" | (b) means "check status" and "retry" are the same call, which is slightly less explicit than a dedicated read-only status tool | **(b) chosen** |
| Cloud sync — mechanism scope | (a) Support only Azure AD Connect cloud sync (Graph-reachable); (b) attempt to also support classic on-premises AD Connect | (a) is the only mechanism Microsoft Graph can actually trigger | (b) has no Graph API surface at all — "supporting" it would mean this MCP silently doing nothing while claiming to have started a sync, which directly violates G3 | **(a) chosen**; (b) is the consequential Open Question above, not an implementation choice |
| Cloud sync — job targeting | (a) Caller passes an explicit `service_principal_id`/`job_id`; (b) auto-discover by filtering service principals for the known cloud-sync agent application and listing its jobs | (b) matches this ticket's parameter shape (reporter only mentions `user_id`-level inputs, not tenant plumbing); keeps the calling workflow's contract simple | (b) adds two extra Graph calls per invocation and a new `sync_job_ambiguous` failure mode if a tenant has more than one job; the exact application-id/display-name filter to use needs verification against Graph's own reference before implementation (Open Questions) | **(b) chosen**, with the verification step called out explicitly as a pre-implementation risk |
| api_client change | (a) Add header-surfacing to `GraphClient._request`; (b) make no change | Both tools' chosen designs (content-copy diffing, direct `/start` POST) only need parsed JSON bodies | (a) would only be needed if the rejected monitor-URL option (above) were chosen | **(b) chosen — no `api_client.py` change required** |

### Data & API contract

Both are MCP tool-call contracts (JSON-RPC `tools/call`); the server's own HTTP contract (`POST /mcp`, `X-Ms-Graph-Token` header, `GET /health`) is unchanged.

**`graph_transfer_onedrive`** (new)
- Request: `{"source_user_id": "...", "destination_user_id": "...", "destination_folder_name"?: string}`
- Response (success): `{"source_user_id", "destination_user_id", "destination_folder": {"id", "name"}, "status": "started"|"in_progress"|"completed"|"no_content", "items": [{"name", "size", "action": "copy_started"|"already_present"}]}`
- Errors: `drive_not_found` (source or destination, `retryable: false`, `extra: {"role": "source"|"destination"}`), plus whatever `GraphError.to_envelope()` already classifies (`invalid_argument`/`unauthorized`/`upstream_error`/`rate_limited`, `api_client.py:30-37`).

**`graph_start_cloud_sync`** (new)
- Request: `{"user_id": "...", "sync_job_id"?: string}`
- Response (success): `{"user_id", "status": "started"|"not_applicable", "service_principal_id"?, "job_id"?, "reason"?}` (`reason` present only for `not_applicable`)
- Errors: `not_found` (user id doesn't resolve), `no_sync_job_configured` (`retryable: false`, message names the on-prem `Start-ADSyncSyncCycle` alternative), `sync_job_ambiguous` (`retryable: false`, `extra: {"candidates": [...]}`), plus the shared `GraphError` classes above.

Both tools are additive — no existing tool's request or response shape changes. No DB (this server has none). No events/messages. Backward compatibility: trivially satisfied, these are brand-new tool names.

### Key flow / sequence

**`graph_transfer_onedrive`:**
1. Resolve source drive (`_resolve_drive`, role=`source`) → `drive_not_found` short-circuits (AC5).
2. Resolve destination drive (role=`destination`) → `drive_not_found` short-circuits (AC7).
3. List source drive root children, walking every `@odata.nextLink` page internally (unlike the PRD-20393 list tools — see §2 for why that shape fits here). Empty → `status: "no_content"`, return (AC6).
4. Resolve-or-create the destination folder (`_resolve_or_create_destination_folder`).
5. List the destination folder's current children ($select=`name,size`).
6. For each source item: if a same-named destination child exists with matching `size` → `already_present`; if same-named but different `size` → `in_progress` (still copying, do not re-issue); if absent → `POST /drives/{source}/items/{id}/copy` with `parentReference: {driveId: dest, id: destFolderId}` → `copy_started`.
7. Roll up overall `status`: all `already_present` → `completed`; any `in_progress` or freshly `copy_started` mixed with some `already_present` → `in_progress`; all freshly `copy_started` → `started`.

**`graph_start_cloud_sync`:**
1. `GET /users/{user_id}?$select=onPremisesSyncEnabled` → 404 → `not_found`.
2. `onPremisesSyncEnabled` falsy → `status: "not_applicable"`, return (AC9).
3. Discover the tenant's cloud-sync service principal (`GET /servicePrincipals?$filter=...` on the known cloud-sync agent application — exact filter TBD, Open Questions) → zero or the job list (`GET /servicePrincipals/{id}/synchronization/jobs`) empty → `no_sync_job_configured` (AC10); more than one → `sync_job_ambiguous` (AC11).
4. `POST /servicePrincipals/{spId}/synchronization/jobs/{jobId}/start` → `status: "started"` (AC8).

### Non-functional

- **Idempotency & concurrency**: `graph_transfer_onedrive`'s own idempotency is structural (§6 step 6 — re-derived from live Graph state every call, no local bookkeeping to go stale). `graph_start_cloud_sync` issues at most one `/start` call per invocation; whether Microsoft Graph's own job engine de-duplicates concurrent `/start` calls across *separate* invocations is Microsoft's documented server-side behavior, not controlled by this code (flagged, not asserted — §11). Neither tool caches anything across requests — consistent with this server holding no state (`stateless_http=True`) and no credentials (Current state).
- **Performance**: `graph_transfer_onedrive`'s own call latency is dominated by HTTP round-trips, not bytes (Graph performs the copy server-side) — but that is itself a risk: a source OneDrive with hundreds of root items means hundreds of sequential Graph calls in one invocation, which can approach this server's own 30s read timeout (`api_client.py:11`, `_TIMEOUT`). Not mitigated in this design (flagged in Risks, §11) — a future iteration could cap items-per-call and report the remainder as still-pending for the next retry, reusing the same idempotent mechanism.
- **Security**: both tools forward the caller's own bearer token to Graph exactly like every existing tool — Graph itself enforces whether that token's tenant/scope may read the named source/destination user's drive or service principals; no new authorization logic is added in this server. `graph_transfer_onedrive` is the first tool to actually exercise the already-granted-but-dormant `Files.*` scope (Current state §4) — worth a deliberate security sign-off before enabling, even though no new consent click is required.
- **Multi-tenant isolation**: both tools resolve everything (drive ids, service principal id, job id) fresh per call from the caller's own token — nothing is cached at module or process scope, so no value resolved for one tenant's token can leak into another tenant's call (AC12). This matches the existing pattern of per-request `GraphClient` construction (`server.py:21-25`, `get_client_from_context`).
- **Observability**: this repo has no logging today (`grep -rn "logging\|logger" src/graph_mcp` returns nothing) — not a regression introduced by this ticket, just the existing baseline. The structured `error_envelope` codes (`drive_not_found`, `no_sync_job_configured`, `sync_job_ambiguous`, `not_applicable`) are the only diagnostic surface, same as every other tool in this repo.

### Rollout & rollback

No feature-flag mechanism exists in this repo — a tool exists once its code ships and is live the next time a connected tenant's caller presses **Refresh Tools**. `graph_transfer_onedrive` needs no new tenant consent (permission already granted, Current state §4) and is effectively live for every already-connected tenant as soon as this change merges and deploys — there is no per-tenant gating available, which is itself worth flagging to whoever signs off on enabling it (Non-functional, Security). `graph_start_cloud_sync` needs a *new* Entra permission (`Synchronization.ReadWrite.All`); following the exact precedent this repo already documents for Mail/Calendar (`README.md:173-174`), already-connected tenants will get `unauthorized` from this tool until (a) the platform's `msgraph.py` OAuth union is updated and (b) each tenant re-authorizes. Rollback is a plain revert of this ticket's commit(s) — no data is written anywhere by either tool's own code (Graph's own copy/sync side effects are not reversible by this server, same as every existing write tool here).

### Test strategy

Unit tests follow this repo's existing convention exactly: a fake `GraphClient` stand-in registered via `client_factory`, asserting on `.calls`/`.methods`/returned JSON, no real network (`tests/test_tools.py:1-50`-ish harness; `_DeleteRaisingClient`, `:1619-1631`, is the direct template for a fake client that raises a specific `GraphError` on demand — this ticket's tests need a similar fake that can return different canned responses per path for the multi-step discovery flow). AC1 (tool list/count) extends the existing `test_tools_list_snapshot`. AC2–AC7 and AC8–AC12 are each one or two focused tests per the ac.json test cases below — all `auto`, all unit-level, all achievable without a real tenant.

**What cannot be unit-tested and must wait for a real, consented tenant** (same category of gap this README already discloses for Mail/Calendar/Intune, `README.md:169-174`): whether the assumed cloud-sync service-principal/job discovery filter actually matches a real tenant's registered agent, and whether Graph's own `/start` endpoint behaves as assumed under a concurrent retry. One manual end-to-end test case (TC13) is reserved for this and marked `untested` until an INT tenant with cloud sync configured is available.

Regression surface: none of the eight existing tool modules are touched except `server.py`'s registration list and the shared `tests/test_tools.py` snapshot/count — no existing tool's behavior changes.

### Risks & dependencies

- **Consequential risk**: this entire design assumes the tenant(s) behind workflow 08/03 use Azure AD Connect cloud sync, not classic on-premises AD Connect. If wrong, `graph_start_cloud_sync` as scoped cannot be built at all — see the consequential Open Question above. Mitigation: get Ginko's confirmation before starting Subtask B; Subtask A (OneDrive transfer) does not depend on this and can proceed regardless.
- **Permission-string risk**: the exact Entra scope(s) and the cloud-sync agent application's filter string for service-principal discovery are not yet confirmed against Microsoft's own reference (Open Questions). Mitigation: verify both at the start of Subtask B, before writing the discovery code, the same discipline PRD-20393 used for its sentinel-default parameter shape.
- **Rollout dependency**: `graph_start_cloud_sync` depends on the platform's `MCP-Management-Service` (`auth/oauth/vendors/msgraph.py`, referenced but not owned by this repo) adding `Synchronization.ReadWrite.All` to the granted scope union, and on every already-connected tenant re-authorizing before the tool stops returning `unauthorized` — out of this repo's control, same dependency shape already documented for Mail/Calendar.
- **Performance risk**: large source OneDrives (many root items) could push `graph_transfer_onedrive` close to this server's 30s read timeout in one invocation (Non-functional). Not blocking for the MVP (the ticket's own "Minimal Viable Slice" language accepts a first production implementation); flagged for a follow-up if real offboarding mailboxes turn out to have very large root item counts.
- **No dependency on any other repo or open ticket** beyond the platform-side permission grant above.
