## 产品设计

### 目标 / 非目标

**目标**（对应 comment 的两项必修 + 一项可选改进）：
- G1：`graph_remove_manager` 在 `user_id` 无法解析到任何用户时返回 `not_found` 错误；仅当用户存在但确实没有经理时才继续返回 `removed=false, reason="no_manager"`。
- G2：`graph_update_user` 的回读在 `userPrincipalName` 改名后依然成功（用新 UPN 回读）；且一次成功 `PATCH` 之后发生的回读失败要报成「写入成功 + readback_error 字段」，绝不能是普通错误信封。
- G3（可选，按 comment 原文的「二选一」）：提示调用方回读值在 Graph 复制延迟下偶尔可能是旧值。

**非目标**：
- 不重开第二轮的 4 项修复——按这条 comment，它们都已重新通过，或者正确地被租户权限阻塞（不是代码缺陷）。
- 不在本轮重新验证第二轮仍未验证的写权限路径（1.4 的「改成新值后回读」、1.5 的 `removed=true` + `previous_manager`、UPN 改名端到端对 Graph 的效果）——comment 本身建议在有写权限的租户（演示租户，SOP 225）上重跑，本轮同样拿不到这样的租户。
- 不超出这条 comment 三项内容字面要求的任何额外字段。

### 验收标准 AC1..AC3

- AC1（新增，问题 1）：给定一个无法解析到任何 Entra ID 用户的 `user_id`，当调用 `graph_remove_manager` 时，应返回 `not_found` 错误信封，绝不是 `{"removed": false, "reason": "no_manager"}`。给定一个能解析、但确实没有经理的 `user_id`，当调用 `graph_remove_manager` 时，应仍然返回 `{"removed": false, "previous_manager": null, "reason": "no_manager"}`，与第二轮完全一致（回归防护——本轮新增的检查不能削弱真实用户的 no_manager 路径）。
- AC2（新增，问题 2）：给定 `graph_update_user` 修改了 `user_principal_name` 且调用成功，当工具回读用户以构建 `updated` 时，应使用新 UPN 回读，而不是原始的 `user_id` 参数，这样回读就不会因为旧 UPN 已失效而 404。给定一次 `graph_update_user` 调用的 `PATCH` 成功但后续回读失败，当工具返回时，应返回 `{"status": "success", "updated": <发送的值>, "readback_error": {...}}`，绝不能是错误信封——写入已经发生，不能被报成失败。
- AC3（技术附加，按 comment 原文「二选一」而非独立要求「说明或重试」）：给定 `graph_update_user` 的工具描述，当 agent 在调用前读取它时，应说明返回的 `updated` 值来自写入后立即发起的回读，在 Graph 复制延迟下偶尔可能是旧值。

## 技术设计

### 结论

两项必修都保持在第二轮已经改过的 `src/graph_mcp/tools/users.py` 里的同两个函数（`graph_remove_manager`、`graph_update_user`）之内，外加测试文件；不新增文件、不引入新依赖、不涉及 schema/DB。问题 1 的修法是只在「没经理或 404」这一条分支上加一次纯存在性检查（`GET /users/{id}?$select=id`）。问题 2 的修法是：(a) 当 PATCH body 含新 UPN 时，把回读目标算成新 UPN；(b) 把 `PATCH` 和回读拆成两个独立的 `try`/`except`，这样回读失败就不会被报成写入失败。问题 3 的修法是给工具的 docstring 加一小段说明——不是重试——理由见方案选型。

### 改动清单

- `src/graph_mcp/tools/users.py` [改]：
  - `graph_remove_manager`（`:733-769`）：`GET /users/{id}/manager` 返回 404 时，在返回 `no_manager` 之前加一步 `try: await client.get(f"/users/{user_id}", params={"$select": "id"})`；若这一步本身抛出 `GraphError`，返回该错误自己的信封（其 `status_code` 分类——`404` 自然映射成 `not_found`），而不是 `no_manager`。有经理那条路径不变。

### 数据与接口契约

**`graph_remove_manager`**（已改）—— **新增性质，非破坏性**：响应形状不变（`{"user_id", "removed", "previous_manager", "reason"}`）；唯一变化是一个从未解析成功的 `user_id` 现在返回 `not_found` 错误信封，而不是 `no_manager` 成功。任何正确处理第二轮已有错误信封的调用方不受影响；一个依赖第二轮那个 bug（把 `no_manager` 当成「id 有效」的证据）的调用方，现在会看到真实的错误——这正是本次修复的意图。

**`graph_update_user`**（已改）—— **新增性质，非破坏性**：`status`/`user_id`/`updated` 保持第二轮的形状（`updated` 仍是 `{field: value}`）；新增的 `readback_error` 键只会在 `status: "success"` 且回读恰好失败时才会出现，它不存在时（常见情况）对现有调用方没有任何改变。

### 关键流程时序

`graph_remove_manager`（本轮新增，替换第二轮步骤 2a）：

1. 调用方 → `graph_remove_manager(user_id="u1")`
2. 服务端 → `GET /users/u1/manager?$select=id,displayName,userPrincipalName`
   - `404` → 服务端 → `GET /users/u1?$select=id`（**本轮新增**）
     - `404` → 返回该错误自己的信封（`not_found`）。**不再有后续调用。**
     - 成功 → 返回 `{"user_id": "u1", "removed": false, "previous_manager": null, "reason": "no_manager"}`，与第二轮完全一致。
   - 其他错误 → 原样返回该错误的信封。
   - `200` → 继续走第二轮原有流程（读经理、`DELETE`、容忍 `DELETE` 本身的并发移除 404）。

`graph_update_user`（本轮改动末尾部分，替换第二轮单个合并 `try`）：

1. 服务端照第二轮设计构建 `body`（不变）。
2. 服务端 → `PATCH /users/{id}`，带 `body`。失败则返回该错误的信封——**与第二轮一致，不变**。
3. 服务端计算 `readback_id = body.get("userPrincipalName", user_id)`（**本轮新增**——发送了新 UPN 时用新 UPN，否则用原始 `user_id`）。
4. 服务端 → `GET /users/{readback_id}?$select=<body.keys() 逗号拼接>`。
   - 成功 → 返回 `{"status": "success", "user_id": user_id, "updated": {k: result.get(k) for k in body}}`，与第二轮形状一致。
   - 失败（**本轮新增**）→ 返回 `{"status": "success", "user_id": user_id, "updated": dict(body), "readback_error": {"status_code": ..., "message": ...}}`，而不是把错误继续往外传。

### 非功能

- **幂等性与并发**：`graph_remove_manager` 新增的存在性检查是纯 `GET`，不改变状态——对同一个不存在的 `user_id` 调用两次都一样是 `not_found`，对同一个有效但没经理的用户调用两次都一样是 `no_manager`（已通过更新后的 `test_remove_manager_returns_no_manager_without_calling_delete` 确认，该测试现在调用了两次）。`graph_update_user` 按新 UPN 回读只是一次无副作用的 `GET`；如果在本次调用的 `PATCH` 和 `GET` 之间又发生了一次并发改名，`GET` 会反映读取那一刻实际存的值（或失败，本轮通过 `readback_error` 而不是错误信封呈现出来）——不是第二轮已有并发风险之外的新风险。
- **性能**：问题 1 的修复恰好只增加一次 Graph 调用，且只发生在 `GET /manager` 本来就已经 404 的分支（最便宜的分支——这条路径原本就不会走到 `DELETE`）。有经理这条路径（真实下线场景里更常见）不受影响。问题 2 的修复零额外 Graph 调用——还是第二轮那套两次调用的形状，只是在发了 UPN 时第二次调用的目标不同。
- **安全性**：两项修复都不引入新的鉴权面。`GET /users/{id}?$select=id` 所需权限与现有的 `GET /users/{id}/manager` 调用一样，都是 `User.Read.All` 这一档。
- **多租户隔离**：与第一轮/第二轮一致——本服务没有自己的隔离逻辑，每次 Graph 调用都由调用方自己的 bearer token 限定租户。
- **可观测性**：`readback_error` 的 `status_code`/`message` 给调用方提供的信息，和一个被继续往外传的错误信封本来能提供的信息完全一样，只是挂在一个成功响应上而不是取代它——没有丢失任何信息，只是纠正了「误判成失败」这一点。

### 上线与回滚

与第一轮/第二轮一致：没有功能开关（本服务没有这个机制），走 `ms-graph-mcp` 正常发布流程——合并 → 重建镜像 → 重新部署。回滚就是回退镜像；不涉及数据迁移。两项修复都没有改变任何已有响应字段的类型或把字段删掉——相对第二轮的形状都是新增性质（一个新的错误分类、一个新的可选键），不像第二轮那两处破坏性变更那样需要协调调用方。

### 测试策略

本轮五条新增/修改的测试（见改动清单）都可以针对本仓已有的假客户端模式做单元测试——除了扩展 `_ManagerRemovalClient`（按路径区分两处 GET 调用点）和新增一个小的新假客户端（`_UpdateUserReadbackClient`，一个「GET 队列 + PATCH 永远成功」的组合，现有假客户端都不支持）之外，不需要新的测试基础设施。AC3（docstring 说明）用一条直接断言注册后工具 `description` 的测试验证，而不是留作一条未经核实的说法。
