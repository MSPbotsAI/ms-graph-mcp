## 需求理解

一句话：平台团队希望把阻塞或拖慢 W2 用户入职的 MCP 连接器工具/参数缺口——涵盖 IT Glue、ConnectWise Manage、Microsoft Graph 三个连接器——补齐，依据是 2026-10-09 的 4 次 SOP 223 真实运行，交付一份带厂商 API 映射、优先级理由、可供分诊（triage）的缺口清单。

提单人（Vow.Meng@mspbots.ai，经 Teams 提交，2026-10-09）针对 `mspbots` 租户跑了 4 次 SOP 223（一个 W2 入职自动化流程），并读回了实际暴露给它的 MCP 工具清单。针对三个厂商连接器（IT Glue、ConnectWise Manage、Microsoft Graph），逐条列出缺失的工具/参数、对应的厂商 API、阻塞的"入职契约"条目，以及优先级（P0–P3）。按工单自己写的 Success Criteria，"成功"是"一份清晰、带优先级、带厂商 API 映射的连接器缺口工单，可供分诊"——也就是说提单人明确要的是一份经过验证的待办清单，而不只是代码。本次设计棒把每一条声称的缺口都对照真实工具源码核实了一遍，并在交给 groom 之前先把清单订正（见 §现状、§验收标准 4.5）。

## 现状（每条陈述都带 path:line）

**架构**：`mcp-service-gateway`（https://github.com/MSPbotsAI/mcp-service-gateway@release, 5719ab2）是 MCP 网关/凭据层。它自己不实现厂商工具逻辑——它在 `vendor/registry.yaml` 里登记每个厂商的 MCP 容器，并通过 HTTP header 按租户注入凭据。某个厂商实际可调用的工具，落在该厂商条目 `repo_url` 指向的那个仓库里（`vendor/registry.yaml:1-17` 记录了 `self_built` / `internal_app` / `open_source` / `third_party` 这套分类）。

| 厂商 | `registry.yaml` 条目 | 工具代码落在 | MSPbots 自有？ | 在 Code Project 字段里？ |
|---|---|---|---|---|
| IT Glue | `vendor/registry.yaml:91-111` | `wyre-technology/itglue-mcp`（已核实 @ feec047） | 否 | 否 |
| ConnectWise Manage | `vendor/registry.yaml:44-59` | `wyre-technology/connectwise-manage-mcp`（已核实 @ 86ba595） | 否 | 否 |
| Microsoft Graph | `vendor/registry.yaml:448-457` | `MSPbotsAI/ms-graph-mcp`（本仓库，@ f61cb05） | 是 | 是（`ms-graph-mcp` 选项） |

用 `git ls-remote` 核实过：`https://github.com/MSPbotsAI/itglue-mcp.git` 与 `https://github.com/MSPbotsAI/connectwise-manage-mcp.git` 都不存在——这两个连接器今天都没有 MSPbots 自己的 fork。`mcp-service-gateway/scripts/vendor_deploy.py:503-508` 证实部署路径就是一次普通的 `git clone <repo_url>`（`update` 时是 `git pull --ff-only`），**没有锁定任何 tag/sha**——所以正在跑的容器到底是哪个版本，取决于上一次有人在主机上跑 `vendor_deploy.py update` 是什么时候，这件事本设计棒（只读代码、不碰线上环境）看不到。

这种处境有一个明确的先例：`ninjaone` 原本也是同类的第三方 `wyre-technology/ninjaone-mcp` 条目；2026-08-21 MSPbots 把它 fork 成了 `MSPbotsAI/ninjaone-mcp`，标 `source: self_built`（`vendor/registry.yaml:127-163`），原因是开源版本的工具面覆盖不了平台需要的能力（23 个工具 vs. 开源版本更小的集合）——这正是本单对 IT Glue 和 ConnectWise 描述的同一类缺口。

**逐厂商工具清单（读实际已注册的工具列表核实，不采信工单原文的说法）：**

### IT Glue（`wyre-technology/itglue-mcp@feec047`，`src/mcp-server.ts:1134-2030` 共注册 30 个工具）
确认：`search_passwords`（`:1442`）与 `get_password`（`:1484`）存在。整个文件里没有 `create_password` 或 `update_password`。工单的说法准确。

### ConnectWise Manage（`wyre-technology/connectwise-manage-mcp@86ba595`，共 79 个 `cw_*` 工具）
- `cw_create_contact`（`src/tools/contacts.ts:99-132`）：只有 `firstName, lastName, companyId, email, phone, title`。工单说法准确。
- `cw_update_contact`（`src/tools/contacts.ts:133-148`）：**已经存在。** 这是一个 JSON Patch 工具（`PATCH /company/contacts/{id}`），支持 `path` 取值 `firstName, lastName, title, inactiveFlag, site, communicationItems, customFields`。设置 `inactiveFlag` 正是"禁用联系人"（工单里 W3 离职第 9 步的用例），`communicationItems` 已经能让调用方一次调用替换掉全部电话/邮箱条目（数组整体替换语义，不是增量追加）。**工单 P0 声称"没有更新工具"是不准确的**——见 Open Questions Q1。
- 整个仓库里没有 `cw_list_sites` 工具（`src/tools/companies.ts` 只在创建公司时顺带内联创建一个 site，`:52-56`）。工单说法准确。
- 没有专门的 `cw_add_contact_communication` / `cw_update_contact_communication` 工具——但这个能力已经可以通过 `cw_update_contact` 的 `communicationItems` patch 路径达成。缺口是真的，但比工单描述的小：这是"整体替换 vs. 增量操作"的易用性缺口，不是能力缺口。
- `cw_search_contacts`（`src/tools/contact-search.ts:174-213`，`buildContactSearchQuery`）：`childConditions` 参数几乎原样透传给 ConnectWise 的 API（只做了引号归一化）。ConnectWise Manage 的 `/company/contacts` 原生支持 `communicationItems/value="x@y.com"` 这类子集合过滤条件——和 `types/name=...` 用的是同一个机制。**按邮箱去重搜索今天就能用**，走 `childConditions` 即可；缺的只是工具描述/示例里没写出来，所以不了解 ConnectWise 子集合语法的调用方发现不了这个用法。不是代码缺口——是文档/可发现性缺口。
- 没有暴露 `cw_list_contact_types` 工具；`src/tools/contact-type-update.ts` 只有一个内部解析函数（`pickContactType`、`findTypeAssociations`），供 `cw_update_contact_types` 内部使用，不是一个独立的列表工具。工单说法准确。

### Microsoft Graph（`MSPbotsAI/ms-graph-mcp@f61cb05`，本仓库）
- `graph_create_user`（`src/graph_mcp/tools/users.py:145-205`）：参数是 `display_name, user_principal_name, mail_nickname, password, usage_location, account_enabled, given_name, surname, job_title, department`。没有 `streetAddress, city, state, postalCode, officeLocation, businessPhones, mobilePhone, companyName, employeeHireDate`。工单说法准确。
- `graph_update_user`（`:307-360`）：已经覆盖 `account_enabled, usage_location, mobile_phone, business_phones, job_title, department, office_location`。仍然缺 `streetAddress, city, state, postalCode, companyName, employeeHireDate`。**部分已解决**——缺口比工单暗示的要窄。
- 没有 `graph_list_domains`，没有 `graph_get_group`（只有 `graph_list_groups`/`graph_list_owned_groups`/`graph_list_user_groups`——都不接受 group id），没有 `graph_reprocess_license`。工单说法准确。
- `tests/test_tools.py:14-54` 有一个工具清单快照测试（`EXPECTED_TOOLS`），列出每个已注册工具及其必填参数——这是以后工具签名一旦漂移唯一需要改动的地方，也是测试策略（见技术设计 §9）依赖的机制。

### IT Glue 连接器接入（"installed_disconnected"）
工单的 P2 条目（"连接器本身接入 — 租户里 installed_disconnected，需 EMD 的 API key 和 itglue_org_id"）是一项租户凭据/运维任务，不是代码缺口：`mspbots-agent-mcp/src/mspbots_agent_mcp/tools/connectors.py:22,41`（`MSPbotsAI/mspbots-agent-mcp@release`, e45ded6）显示 `installed_disconnected` 是一个正常的、已支持的连接器状态，意思是该租户还没完成凭据配置。IT Glue 的凭据表单本身在产品里已经是上线状态（`wiki: ProductDocs/_connector-fields.md § IT Glue`——API Key / Region / Base URL，与 `mcp-service-gateway/vendor/registry.yaml:96-111` 完全对应）。缺的是有人去拿到该租户的 IT Glue API key 和 `itglue_org_id` 并填好这个表单——是运维任务，不是工程任务。

**wiki 覆盖情况**（`mbp.py wiki sync`，HEAD 717cc62，产品版本 v20260929.0931）：对"W2 onboarding"、"SOP 223"、"onboarding contract"均**未覆盖**——这些是内部 SOP/自动化概念，还没进产品事实库（`wiki: 未覆盖 W2 onboarding / SOP 223 / onboarding contract`）。`ProductDocs/_connector-fields.md` 与 `ProductDocs/_gaps.md` 覆盖的是连接器*连接/凭据*界面（字段名、关于哪些字段存在的疑问），没有涉及某个连接器*工具能力*这一层——这证实本单问的正是 wiki 巡检目前还没走到的那一层。

## 产品设计

### 目标 / 非目标

**目标：**
- 补齐 Microsoft Graph 的工具/参数缺口（AC9–AC13）——这些在 MSPbots 自有的仓库里今天就能动手。
- 交付一份经代码核实、订正过的 IT Glue / ConnectWise Manage / Microsoft Graph 连接器缺口清单，让 groom 能基于准确信息分诊，而不是提单草稿（草稿里有一条 P0 判断不准确、一条 P2 其实已经解决）。
- 把"IT Glue 和 ConnectWise 的缺口实际卡在一个架构决策上（自建 fork / 向上游贡献 / 缩小范围）"这件事，明确摆成一个可以被回答的问题。

**非目标（本单范围内不做）：**
- 在 `itglue-mcp` 或 `connectwise-manage-mcp` 里实现任何东西——这两个仓库今天都不是 MSPbots 自有的，Open Questions Q2 没有答案之前没有分支可开、没有东西可推。
- 为 IT Glue 或 ConnectWise 新建一个自建 fork 仓库（`ninjaone` 先例）——这是一个平台归属决策（新容器、新的凭据迁移、相对上游的持续维护成本），不是本设计棒能单方面拍板的。
- 改动连接器的连接/凭据配置界面——那是另一个产品界面（`wiki: ProductDocs/_connector-fields.md`），不受本单影响。
- IT Glue 租户激活（API key + `itglue_org_id`）——是运维/账号任务，列为 AC14 仅做可见性追踪。

### 验收标准 AC1..AC14

按厂商分组。"现在可动手"＝ Code Project `ms-graph-mcp` 已覆盖；其余需要先解决 Open Question Q2。

**IT Glue**（卡在 Q2——不存在 MSPbots 自有仓库）
- AC1（P0）：Given 某租户已连接 IT Glue，When 入职流程调用 IT Glue 连接器的密码创建工具，传入 organization_id/name/username/password/notes/password_category_id，Then 在该租户的 IT Glue organization 下创建出一条新密码记录，工具返回该记录的 id。
- AC2（P0）：Given 同一个 IT Glue organization 下某用户名已有密码记录，When 入职流程对该用户名调用密码更新工具，Then 原记录被就地更新（不产生重复），工具返回更新后记录的 id。

**ConnectWise Manage**（卡在 Q2，除 AC3/AC7 不需要代码改动外）
- AC3（P0 → 已满足，仅需核实）：Given 一个已存在的 ConnectWise 联系人，When 调用 `cw_update_contact`，传入 `operations: [{"op":"replace","path":"inactiveFlag","value":true}]`，Then 该联系人在 ConnectWise Manage 中被禁用，之后调用 `cw_get_contact` 显示 `inactiveFlag: true`。
- AC4（P1）：Given 入职流程中要创建一个新联系人，When 调用 `cw_create_contact` 并传入 `types`、`site`、`addressLine1`/`addressLine2`、`city`、`state`、`zip`、`department`、`managerContact`，Then 该联系人在 ConnectWise Manage 中创建成功且上述字段均已设置。
- AC5（P1）：Given 某联系人需要同时记录手机号、座机号与分机号，When 调用所选工具（增强版 `cw_update_contact` 或新的专用通讯方式工具）一次，Then 之后该联系人身上三项通讯方式均存在，且调用方无需先读回再重发已有的条目。
- AC6（P1）：Given 一个公司 id，When 调用 `cw_list_sites`，Then 返回该公司的 site 列表（id + name），与 `GET /company/companies/{id}/sites` 的返回一致。
- AC7（P2 → 已满足，仅需核实）：Given 某联系人已知邮箱地址，When 调用 `cw_search_contacts`，传入 `childConditions: 'communicationItems/value="<email>"'`，Then 只返回邮箱匹配的那个联系人，不返回其它。
- AC8（P3）：Given 需要联系人类型下拉选项，When 调用 `cw_list_contact_types`，Then 返回 `GET /company/contacts/types` 的完整联系人类型列表。

**Microsoft Graph**（现在可动手，Code Project = `ms-graph-mcp`）
- AC9（P1）：Given 一条含街道地址、城市、州、邮编、办公地点、业务电话、手机号、公司名、入职日期的新员工记录，When 调用 `graph_create_user` 并传入这些作为附加参数，Then 创建出的 Entra ID 用户上述属性均已设置。
- AC10（P2）：Given 一个已存在的 Entra ID 用户，When 调用 `graph_update_user` 并传入 `street_address`、`city`、`state`、`postal_code`、`company_name` 或 `employee_hire_date`，Then 每个传入的属性被更新，未传入的属性保持不变（与该工具现有参数"只改传入的字段"的约定一致）。
- AC11（P2）：Given 某租户有多个已验证域名，When 调用 `graph_list_domains`，Then 返回该租户的域名列表，与 `GET /domains` 的返回一致。
- AC12（P3）：Given 一个 group id，When 调用 `graph_get_group`，Then 返回该组的详情，与 `GET /groups/{id}` 的返回一致。
- AC13（P3）：Given 某用户的许可证分配处于失败/待处理状态，When 调用 `graph_reprocess_license`，Then 触发 Graph 的 `POST /users/{id}/reprocessLicenseAssignment`，工具依据返回结果汇报成功/失败。

**运维（非工程）**
- AC14（P2，仅做可见性追踪，不由任何开发棒实现）：Given 某租户的 IT Glue 连接器显示 `installed_disconnected`，When 有人拿到该租户的 IT Glue API key 与 `itglue_org_id` 并填写现有凭据表单，Then 该连接器状态变为 `connected`。不需要代码改动；这需要一个账号/运维动作，不是本流水线开发棒要接的工单。

## 技术设计

### 结论

今天只有 Microsoft Graph 的缺口可以落地：`ms-graph-mcp` 是 MSPbots 自有仓库，并且已经有一个 pytest 工具清单快照测试在守着。做法是给 `graph_create_user`/`graph_update_user` 加缺失的可选参数，再新增三个只读/动作类工具（`graph_list_domains`、`graph_get_group`、`graph_reprocess_license`），沿用 `src/graph_mcp/tools/users.py` 里既有的 `@mcp.tool(...)` + Pydantic `Annotated` 写法。IT Glue 和 ConnectWise 的工作在 Open Question Q2（仓库归属）解决之前无法开始——没有一个 MSPbots 自有的仓库可以开分支。

### 现有实现定位

- `src/graph_mcp/tools/users.py:145-205` —— `graph_create_user`
- `src/graph_mcp/tools/users.py:307-360` —— `graph_update_user`
- `src/graph_mcp/server.py` —— 工具注册入口（`create_mcp_server`），其中 `:94-97` 的入职流程 docstring 已经提到 `graph_create_user`/`graph_update_user`，新参数落地后应同步更新
- `tests/test_tools.py:14-54` —— `EXPECTED_TOOLS` 快照，需要为 2 个新工具加条目；`graph_create_user`/`graph_update_user` 的必填参数集合保持不变（新参数全部是可选的）
- groups/domains/license 相关工具目前都不存在；形状最接近的参照：`graph_check_license_stock`（已有，只读，无参数）可参照写 `graph_list_domains`；`graph_get_user`（按 id GET）可参照写 `graph_get_group`。

### 方案选型

| 方案 | 做法 | 优点 | 代价 | 结论 |
|---|---|---|---|---|
| 给现有 `graph_create_user`/`graph_update_user` 加可选参数 | 加 `Annotated[str \| None, ...] = None` 参数，按条件加进 `body` dict——和现有 `given_name`/`surname` 等参数完全同一种写法 | 不新增工具、API 面不膨胀、与现有风格一致 | 无明显代价 | **采用** |
| 新建 `graph_create_user_v2` 而不是扩展现有工具 | 避免改动其它流程可能已经在调的工具 | 规避签名风险 | 两个工具做几乎同一件事，会让入职流程的作者搞不清用哪个；而且新参数都是可选/追加的，签名风险本就不存在 | 不采用 |
| `graph_list_domains`/`graph_get_group`/`graph_reprocess_license` 做成新工具 | 每个一个 `@mcp.tool` 函数，薄封装 `client.get`/`client.post` | 符合现有"一个端点一个工具"的约定 | 无明显代价 | **采用**——这几个端点没有现成工具可扩展，没有别的可行方案 |

### 数据与接口契约

- `graph_create_user` 新增可选参数 → Graph `POST /users` body 新增字段：`streetAddress: str`、`city: str`、`state: str`、`postalCode: str`、`officeLocation: str`、`businessPhones: list[str]`、`mobilePhone: str`、`companyName: str`、`employeeHireDate: str`（ISO 8601，例如 `"2026-10-20T00:00:00Z"`——Graph 这个字段要求完整的 date-time）。
- `graph_update_user` 新增可选参数 → Graph `PATCH /users/{id}` body 新增字段：`streetAddress`、`city`、`state`、`postalCode`、`companyName`、`employeeHireDate`（类型同上）。未传入的参数不发送（保留现有"只改传入字段"的约定）。
- `graph_list_domains` → Graph `GET /domains`，无请求体；响应通过现有 `dump_json_capped` helper 透传，与其它列表类工具一致。
- `graph_get_group(group_id: str)` → Graph `GET /groups/{group_id}`；Graph 返回 404 时走现有 `GraphError.to_envelope()` 路径，与 `graph_get_user` 的错误处理一致。
- `graph_reprocess_license(user_id: str)` → Graph `POST /users/{user_id}/reprocessLicenseAssignment`，空 body；成功是 HTTP 204（无内容）——工具应像 `graph_assign_manager` 那样返回一个 `{"status": "success", "user_id": ...}` 信封，不要尝试解析响应体。
- 向后兼容：`graph_create_user`/`graph_update_user` 的所有改动都是新增且可选的——现有调用方（包括 SOP 223 自身）不受影响。

### 关键流程时序

入职流程（SOP 223）→ `graph_create_user(..., street_address=..., company_name=...)` → Graph `POST /users` → 一次调用创建出带完整档案的用户，取代现在"先创建、地址/公司名字段再另外手动补"的方式。本单不涉及、也不改动入职流程编排本身（那部分逻辑在本仓库之外）。

### 非功能

- **幂等与并发**：`graph_create_user` 本来就不是幂等的（Graph 每次调用都新建一个用户）——本次改动不影响这一点。`graph_reprocess_license` 按设计幂等（如果没什么需要重新处理，Graph 侧是空操作）。`graph_update_user`/`graph_get_group`/`graph_list_domains` 天然幂等（局部 PATCH / GET）。
- **性能**：五个工具都是单次 Graph API 调用，不涉及分页问题（单租户的域名/组列表量级很小；本次改动不引入"遍历所有租户"这类路径）。
- **安全**：不引入新的鉴权面——五个工具全部复用 `client_factory()` 现有的 OAuth 注入 token（`X-Ms-Graph-Token`，由 manager 隐藏注入，见 `mcp-service-gateway/vendor/registry.yaml:453-457`），与本文件里其它所有工具一致。不需要新的凭据字段；是否需要超出当前 Graph 应用注册范围的新 scope，应在合并前核实而非假设（已在"风险"一节标注，不构成设计阶段的阻塞）。
- **多租户隔离**：不受影响——调用租户自己的 `X-Ms-Graph-Token` 由网关按请求注入（`mcp-service-gateway` 的凭据层，不在本仓库），五个新增/改动工具都不接受租户参数，也无法被指向另一个租户的数据。不引入任何跨租户面。
- **可观测性**：沿用现有模式——错误走 `GraphError.to_envelope()`（已经会记录/结构化 Graph 的错误响应）；除了 `client.post`/`client.get`/`client.patch` 已有的行为外不需要新增日志。

### 上线与回滚

- 单仓库、单部署单元（`ms-graph-mcp` 容器，经由 `mcp-service-gateway` 的 `vendor_deploy.py update ms-graph`）。不需要 feature flag——所有改动都是新增的可选参数和全新工具；对现有调用方没有任何删除或行为变化。
- 回滚：revert 对应提交并重新部署；因为没有删除任何既有能力，不涉及数据迁移回退。
- `ms-graph` 与 `ms-graph-app` 两个注册条目（`vendor/registry.yaml:448-474`）指向同一个 `repo_url`/镜像，所以两种鉴权方式（委派 与 app-only）会在同一次部署中一起拿到改动——不需要为第二个条目单独上线。

### 风险与依赖

- **依赖**：`graph_create_user`/`graph_update_user` 的新字段假设支撑本连接器的 Graph 应用注册已经有覆盖这些属性的 `user.readwrite.all`（或等效）写权限——现有工具已经在写 `jobTitle`/`department` 等字段，所以大概率已经有这个权限，但应在合并前核实，不应假设。
