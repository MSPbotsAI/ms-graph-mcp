## Requirement understanding

One line: The platform team wants the MCP connector tool/parameter gaps that are blocking or degrading W2 user onboarding — across IT Glue, ConnectWise Manage, and Microsoft Graph — closed, based on 4 real SOP 223 runs on 2026-10-09, with a prioritized, vendor-API-mapped gap list ready for triage.

The reporter (Vow.Meng@mspbots.ai, filed via Teams, 2026-10-09) ran SOP 223 (a W2 onboarding automation) four times against the `mspbots` tenant and read back the actual MCP tool list exposed to it. For each of three vendor connectors (IT Glue, ConnectWise Manage, Microsoft Graph) they listed specific missing tools/parameters, the vendor API that would back each one, which "onboarding contract" item it blocks, and a priority (P0–P3). Success, per the ticket's own Success Criteria, is "a clear, prioritized connector-gap ticket with vendor API mapping, blockers, and priority rationale, ready for triage" — i.e. the reporter is explicitly asking for a validated backlog, not just code. This design leg validated every claimed gap against the live tool source and corrects the list before handing it to groom (§2, §4.5).

## Current state (every claim carries path:line)

**Architecture**: `mcp-service-gateway` (https://github.com/MSPbotsAI/mcp-service-gateway@release, 5719ab2) is the MCP gateway/credential layer. It does not implement vendor tool logic itself — it registers each vendor's MCP container in `vendor/registry.yaml` and injects per-tenant credentials via HTTP headers. The actual callable tools for a vendor live in whatever `repo_url` that vendor's entry points to (`vendor/registry.yaml:1-17` documents the `self_built` / `internal_app` / `open_source` / `third_party` taxonomy).

Confirmed by `git ls-remote`: `https://github.com/MSPbotsAI/itglue-mcp.git` and `https://github.com/MSPbotsAI/connectwise-manage-mcp.git` do not exist — there is no MSPbots-owned fork of either connector today. `mcp-service-gateway/scripts/vendor_deploy.py:503-508` confirms the deploy path is a plain `git clone <repo_url>` (or `git pull --ff-only` on `update`) with no pinned tag/sha — so what a running container has depends on when it was last `vendor_deploy.py update`d on the host, which this (read-only, code-only) design leg cannot observe.

There is a documented precedent for exactly this situation: `ninjaone` was originally the same kind of third-party `wyre-technology/ninjaone-mcp` entry; on 2026-08-21 MSPbots forked it into `MSPbotsAI/ninjaone-mcp` with `source: self_built` (`vendor/registry.yaml:127-163`) because the upstream open-source server's tool surface didn't cover what the platform needed (23 tools vs. the open-source server's smaller set) — the same category of gap this ticket describes for IT Glue and ConnectWise.

ConnectWise Manage's `/company/contacts` natively supports child-collection filters like `communicationItems/value="x@y.com"` — the same mechanism already used for `types/name=...`. **Email-based de-dup search already works today** via `childConditions`; it is only missing from the tool's description/examples, so a caller who doesn't already know ConnectWise's child-collection syntax won't discover it. Not a code gap — a documentation/discoverability gap.
- No `cw_list_contact_types` tool exposed; `src/tools/contact-type-update.ts` only has an internal resolver (`pickContactType`, `findTypeAssociations`) used by `cw_update_contact_types`, not a standalone listing tool. Ticket's claim is accurate.

## Product design

### Goals / Non-goals

**Goals:**
- Close the Microsoft Graph tool/parameter gaps (AC9–AC13) — these are actionable today in a repo MSPbots owns.
- Deliver a corrected, code-verified connector-gap inventory for IT Glue, ConnectWise Manage, and Microsoft Graph, so groom can triage with accurate information instead of the submitted draft (which has one incorrect P0 claim and one P2 claim that's already solved).
- Surface the architecture decision that IT Glue and ConnectWise gaps are actually gated on (self-build fork vs. upstream contribution vs. descope) as an explicit, answerable question.

**Non-goals (this ticket):**
- Implementing anything inside `itglue-mcp` or `connectwise-manage-mcp` — neither is an MSPbots-owned repo today; there is nothing to branch or push to until Open Question Q2 is answered.
- Standing up a new self-built fork repo for IT Glue or ConnectWise (the `ninjaone` precedent) — that is a platform-ownership decision (new container, new credential migration, ongoing maintenance burden vs. staying on upstream), not something this design leg decides unilaterally.
- Changing the connector connection/credential-setup UI — that's a different product surface (`wiki: ProductDocs/_connector-fields.md`), unaffected by this ticket.
- The IT Glue tenant activation (API key + `itglue_org_id`) — an ops/account task, tracked as AC14 for visibility only.

### Acceptance criteria AC1..AC14

Grouped by vendor. "Actionable now" = Code Project `ms-graph-mcp` covers it; the rest need Open Question Q2 resolved first.

**IT Glue** (blocked on Q2 — no MSPbots-owned repo exists)
- AC1 (P0): Given a tenant with IT Glue connected, when the onboarding flow calls the IT Glue connector's password-create tool with organization_id/name/username/password/notes/password_category_id, then a new password record is created in that tenant's IT Glue organization and the tool returns the created record's id.
- AC2 (P0): Given a password record already exists for a given username in the same IT Glue organization, when the onboarding flow calls the password-update tool for that username, then the existing record is updated in place (not duplicated) and the tool returns the updated record's id.

**ConnectWise Manage** (blocked on Q2, except AC3/AC7 which need no code change)
- AC3 (P0 → already satisfied, verify only): Given an existing ConnectWise contact, when `cw_update_contact` is called with `operations: [{"op":"replace","path":"inactiveFlag","value":true}]`, then the contact is disabled in ConnectWise Manage and a subsequent `cw_get_contact` shows `inactiveFlag: true`.
- AC4 (P1): Given a new contact being created during onboarding, when `cw_create_contact` is called with `types`, `site`, `addressLine1`/`addressLine2`, `city`, `state`, `zip`, `department`, and `managerContact`, then the contact is created in ConnectWise Manage with all of those fields set.
- AC5 (P1): Given a contact that needs a mobile number, a work number, and an extension recorded simultaneously, when the chosen tool (either an enhanced `cw_update_contact` or a new dedicated communications tool) is called once, then all three communication items exist on the contact afterward without the caller having to first read back and resend the existing ones.
- AC6 (P1): Given a company id, when `cw_list_sites` is called, then it returns the company's site list (id + name) as returned by `GET /company/companies/{id}/sites`.
- AC7 (P2 → already satisfied, verify only): Given a contact with a known email address, when `cw_search_contacts` is called with `childConditions: 'communicationItems/value="<email>"'`, then it returns the matching contact(s) and no others.
- AC8 (P3): Given a request for the contact-type picklist, when `cw_list_contact_types` is called, then it returns the full list of contact types from `GET /company/contacts/types`.

**Microsoft Graph** (actionable now, Code Project = `ms-graph-mcp`)
- AC9 (P1): Given a new-hire record with a street address, city, state, postal code, office location, business phone(s), mobile phone, company name, and hire date, when `graph_create_user` is called with those as additional parameters, then the created Entra ID user has all of those attributes set.
- AC10 (P2): Given an existing Entra ID user, when `graph_update_user` is called with `street_address`, `city`, `state`, `postal_code`, `company_name`, or `employee_hire_date`, then each provided attribute is updated and attributes not provided are left unchanged (same "only provided fields change" contract the tool already has for its existing parameters).
- AC11 (P2): Given a tenant with multiple verified domains, when `graph_list_domains` is called, then it returns the tenant's domain list as returned by `GET /domains`.
- AC12 (P3): Given a group id, when `graph_get_group` is called, then it returns that group's details as returned by `GET /groups/{id}`.
- AC13 (P3): Given a user whose license assignment is in a failed/pending state, when `graph_reprocess_license` is called, then Graph's `POST /users/{id}/reprocessLicenseAssignment` is invoked and the tool reports success/failure based on the response.

**Operational (not engineering)**
- AC14 (P2, tracked for visibility, not implemented by any dev leg): Given a tenant whose IT Glue connector shows `installed_disconnected`, when someone obtains that tenant's IT Glue API key and `itglue_org_id` and submits the existing credential form, then the connector status becomes `connected`. No code change is required; this needs an account/ops action, not a ticket in this pipeline's dev leg.

## Tech design

### Conclusion

Only the Microsoft Graph gaps are implementable today: `ms-graph-mcp` is MSPbots-owned and already pytest-covered with a tool-inventory snapshot test. Add the missing optional parameters to `graph_create_user`/`graph_update_user` and three new read-only/action tools (`graph_list_domains`, `graph_get_group`, `graph_reprocess_license`), following the existing `@mcp.tool(...)` + Pydantic-`Annotated` pattern in `src/graph_mcp/tools/users.py`. IT Glue and ConnectWise work cannot start until Open Question Q2 (repo ownership) is resolved — there is no MSPbots-owned repo to branch in.

### Where the current implementation lives

- `src/graph_mcp/tools/users.py:145-205` — `graph_create_user`
- `src/graph_mcp/tools/users.py:307-360` — `graph_update_user`
- `src/graph_mcp/server.py` — tool registration entrypoint (`create_mcp_server`), onboarding flow docstring at `:94-97` that already references `graph_create_user`/`graph_update_user` and should be updated once new params land
- `tests/test_tools.py:14-54` — `EXPECTED_TOOLS` snapshot, must gain entries for the 2 new tools and updated required-arg sets stay unchanged (new params are all optional)
- Groups/domains/license tools do not exist yet; nearest sibling for shape reference: `graph_check_license_stock` (existing, read-only, no args) for `graph_list_domains`'s shape, and `graph_get_user` (`id`-keyed GET) for `graph_get_group`'s shape.

### Option analysis

| Option | Approach | Pros | Cost | Verdict |
|---|---|---|---|---|
| Extend existing `graph_create_user`/`graph_update_user` with optional params | Add `Annotated[str \| None, ...] = None` params, conditionally add to `body` dict — exact pattern already used for `given_name`/`surname`/etc. | Zero new tools, zero API-surface churn, matches existing style | None significant | **Chosen** |
| New tool `graph_create_user_v2` instead of extending | Avoids touching a tool other flows may already call | Avoids any signature risk | Two tools doing almost the same thing confuses onboarding-flow authors, no actual signature risk since all new params are optional/additive | Rejected |
| `graph_list_domains`/`graph_get_group`/`graph_reprocess_license` as new tools | One `@mcp.tool` function each, thin wrapper over `client.get`/`client.post` | Matches existing one-tool-per-endpoint convention | None significant | **Chosen** — no viable alternative; these endpoints have no existing tool to extend |

### Change list

- `src/graph_mcp/tools/users.py` [改] — add 9 optional params to `graph_create_user` (`street_address, city, state, postal_code, office_location, business_phones, mobile_phone, company_name, employee_hire_date`), mapped to Graph's `streetAddress, city, state, postalCode, officeLocation, businessPhones, mobilePhone, companyName, employeeHireDate`; add 6 optional params to `graph_update_user` (`street_address, city, state, postal_code, company_name, employee_hire_date`) following the existing `if x is not None: body[...] = x` pattern at `:338-348`.
- `src/graph_mcp/tools/users.py` or a new `src/graph_mcp/tools/groups.py` [改/新增] — add `graph_get_group(group_id)` → `GET /groups/{group_id}`, read-only.
- `src/graph_mcp/tools/domains.py` [新增] — add `graph_list_domains()` → `GET /domains`, read-only, no args (same shape as `graph_check_license_stock`).
- `src/graph_mcp/tools/users.py` [改] — add `graph_reprocess_license(user_id)` → `POST /users/{user_id}/reprocessLicenseAssignment`, mutating, idempotent (reprocessing an already-correct assignment is a no-op on Graph's side).
- `tests/test_tools.py` [改] — update `EXPECTED_TOOLS` (`:14-54`) to add `graph_list_domains: set()`, `graph_get_group: {"group_id"}`, `graph_reprocess_license: {"user_id"}`; required-arg sets for `graph_create_user`/`graph_update_user` stay unchanged since all new fields are optional.
- `src/graph_mcp/server.py` [改] — update the onboarding-flow docstring (`:94-97`) to mention the new address/phone/hire-date params are available on create/update, for discoverability.
- `src/graph_mcp/tools/__init__.py` (or wherever tools are collected for registration — confirm exact file when implementing) [改] — register the new tool module(s) if a new file is added for domains/groups.

### Data & API contract

- `graph_create_user` new optional params → Graph `POST /users` body additions: `streetAddress: str`, `city: str`, `state: str`, `postalCode: str`, `officeLocation: str`, `businessPhones: list[str]`, `mobilePhone: str`, `companyName: str`, `employeeHireDate: str` (ISO 8601, e.g. `"2026-10-20T00:00:00Z"` — Graph requires full date-time for this field).
- `graph_update_user` new optional params → Graph `PATCH /users/{id}` body additions: `streetAddress`, `city`, `state`, `postalCode`, `companyName`, `employeeHireDate` (same types as above). Omitted params are not sent (existing "only provided fields change" contract preserved).
- `graph_list_domains` → Graph `GET /domains`, no request body; response passed through via the existing `dump_json_capped` helper (same as other list tools).
- `graph_get_group(group_id: str)` → Graph `GET /groups/{group_id}`; 404 from Graph maps through the existing `GraphError.to_envelope()` path, same as `graph_get_user`'s error handling.
- `graph_reprocess_license(user_id: str)` → Graph `POST /users/{user_id}/reprocessLicenseAssignment`, empty body; success is HTTP 204 (no content) — tool should return a `{"status": "success", "user_id": ...}` envelope like `graph_assign_manager` does, not try to parse a body.
- Backward compatibility: all `graph_create_user`/`graph_update_user` changes are additive and optional — existing callers (including SOP 223 itself) are unaffected.

### Key flow / sequence

Onboarding flow (SOP 223) → `graph_create_user(..., street_address=..., company_name=...)` → Graph `POST /users` → user created with full profile in one call, instead of today's create-then-separate-manual-step for address/company fields. No change to the surrounding onboarding orchestration (that lives outside this repo and outside this ticket's scope).

### Non-functional

- **Idempotency/concurrency**: `graph_create_user` is already not idempotent (Graph assigns a new user each call) — unchanged by this work. `graph_reprocess_license` is idempotent by design (Graph no-ops if nothing needs reprocessing). `graph_update_user`/`graph_get_group`/`graph_list_domains` are naturally idempotent (PATCH-partial / GET).
- **Performance**: all five tools are single Graph API calls, no pagination concerns (domains/groups lists for a single tenant are small; this doesn't add a list-all-tenants path).
- **Security**: no new auth surface — all five tools reuse `client_factory()`'s existing OAuth-injected token (`X-Ms-Graph-Token`, hidden/manager-injected per `mcp-service-gateway/vendor/registry.yaml:453-457`), same as every other tool in this file. No new credential fields, no new scopes expected beyond what's already granted for user/group/domain read-write (should be confirmed against the current Graph app registration's scopes before merging — flagged as a risk in §Risks, not a blocker for design).
- **Multi-tenant isolation**: unaffected — the gateway injects the calling tenant's own `X-Ms-Graph-Token` per request (`mcp-service-gateway` credential layer, not this repo); none of the five new/changed tools take a tenant parameter or could be pointed at another tenant's data. No cross-tenant surface is introduced.
- **Observability**: follow the existing pattern — errors go through `GraphError.to_envelope()` (already logs/structures Graph's error response); no new logging needed beyond what `client.post`/`client.get`/`client.patch` already does.

### Rollout & rollback

- Single repo, single deploy unit (`ms-graph-mcp` container via `mcp-service-gateway`'s `vendor_deploy.py update ms-graph`). No feature flag needed — all changes are additive optional parameters and net-new tools; nothing is removed or behaviorally changed for existing callers.
- Rollback: revert the commit and redeploy; since nothing existing is removed, there's no data migration to undo.
- Both `ms-graph` and `ms-graph-app` registry entries (`vendor/registry.yaml:448-474`) point at the same `repo_url`/image, so both auth variants (delegated and app-only) pick up the change on the same deploy — no separate rollout needed for the second entry.

### Test strategy

- **Unit (auto)**: extend `tests/test_tools.py`'s `EXPECTED_TOOLS` snapshot (catches signature drift for free, same mechanism already protecting the other 31 tools); add request-body-shape tests for the two extended tools and three new tools, mocking `client.post`/`get`/`patch` the same way `test_user_lookup_escapes_apostrophe` and neighboring tests already do.
- **Manual**: one live-tenant smoke test per new/changed tool, against a non-production Entra tenant if one exists for this repo's test suite (confirm with whoever owns Graph app credentials — not established in this design).
- **Regression surface**: `graph_create_user`/`graph_update_user`'s existing callers (SOP 223 and any other onboarding/offboarding SOP) — since changes are additive-optional, risk is low, but the onboarding-flow docstring update (`server.py:94-97`) should be reviewed by whoever maintains SOP 223 so the new params actually get used.

### Effort & breakdown

- Microsoft Graph gaps (AC9–AC13): 1–2 engineer-days (5 small, well-isolated tool changes in one file, one test-file update, no new infra).
- IT Glue gaps (AC1–AC2): cannot be estimated until Q2 is resolved — effort differs by an order of magnitude between "add 2 tools to an existing self-built repo" and "stand up a brand-new forked repo, container, and deploy pipeline."
- ConnectWise gaps (AC4–AC6, AC8): same caveat as IT Glue; additionally AC3 and AC7 need zero engineering (verification only).
- Recommended subtask split for groom: (1) this ticket limited to AC9–AC14 (Microsoft Graph + the operational IT Glue item), ready for `5c` once groomed; (2) a new ticket for the Q2 decision itself, blocking; (3) follow-on ticket(s) for IT Glue/ConnectWise implementation once (2) resolves, each with its own `Code Project` once the repo exists.

### Risks & dependencies

- **Dependency**: new `graph_create_user`/`graph_update_user` fields assume the Graph app registration backing this connector already has write permission for `user.readwrite.all` (or equivalent) covering these attributes — the existing tool already writes `jobTitle`/`department` etc., so this is very likely already granted, but should be confirmed, not assumed, before merging.
- **Risk**: `employeeHireDate` requires a full ISO 8601 datetime, not a bare date — a caller passing `"2026-10-20"` will get a Graph 400. The tool should document the exact expected format in its `Field(description=...)`, mirroring how `password`'s description already warns about complexity policy.
- **Dependency (blocking, not for this ticket)**: Q2 (repo ownership for IT Glue/ConnectWise) — see Open Questions.
- **Dependency**: `vendor_deploy.py`'s lack of a pinned ref for third-party vendors (not this repo, but relevant context raised by this ticket) means "is the gap actually still present in production" can silently drift from "is it present in the vendor's current default branch" — worth flagging to whoever owns `mcp-service-gateway`, independent of this ticket.
