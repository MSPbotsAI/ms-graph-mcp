# PRD-20412 · Microsoft account creation lacks a tool to force a password change upon first login

仓库: https://github.com/MSPbotsAI/ms-graph-mcp@master (968369d)

## 需求理解

一句话：提单人想要的是——无论从账号创建工具的定义里，还是从它调用结果里——能明确拿到证据，证明新建的 Microsoft 账号已经被设置为"下次登录时必须修改密码"（即 Graph 的 `passwordProfile.forceChangePasswordNextSignIn` 参数），因为目前从他能看到的信息里无法确认这一点。

该工单 `text_content` 为空（描述为空），也没有任何 comment。全部需求内容来自两张附件图片（通过 `clickup_get_task` 的 `attachments` 下载后用图片阅读工具读取——本单的 `text_content` 与 `markdown_description` 均为空）：

- 图1（`image.png`，015543e2…）：Microsoft 365 管理中心"Set up the basics"新建用户界面截图，"Require this user to change their password when they first sign in"复选框被勾选并被红框高亮——这是提单人用来对照的参考行为。
- 图2（`image.png`，0ed96a31…），中文，原文：「首次登录强制改密码：这项没有被我在当前可见的工具定义里明确确认到 / 也就是我现在缺少的是：`passwordProfile.forceChangePasswordNextSignIn` 这个参数被工具明确支持的证据 / 或者结果里会返回该设置已生效的证据」——即提单人无法从他能看到的工具定义里确认 `forceChangePasswordNextSignIn` 被支持，也无法从工具的返回结果里得到该设置已生效的证据。

提单人看起来是以"调用 Microsoft Graph MCP 连接器的 onboarding 自动化流程"的身份在写这条工单（与姊妹单 PRD-20413 同一个"Onboarding Agent"语境，该单明确写了"Connector: Microsoft Graph (ms-graph MCP)"），而不是人类管理员的视角——问的是"调用方能验证什么"，不是管理中心界面本身。

## 现状（每条断言带 path:line）

- `src/graph_mcp/tools/users.py:280-283` —— `graph_create_user` 在创建每一个账号时都已经无条件地设置 `body["passwordProfile"] = {"password": password, "forceChangePasswordNextSignIn": True}`。没有任何参数可以关闭这个行为，它已经是一个固定的安全默认值。**提单人想要的行为（首次登录强制改密码）其实已经在发生**——缺的不是行为本身，是行为的可观测性。
- `src/graph_mcp/tools/users.py:263-269` —— 该工具的 docstring："Create a new Entra ID user account. `usage_location` is required because it must be set before any license can be assigned to the user. Address, phone, company and hire date can be set in the same call." 完全没有提到强制改密码这件事，所以调用方只读工具定义（也就是 LLM/agent 或 `list_tools()` 能看到的内容）是无从得知这一行为的。
- `src/graph_mcp/tools/users.py:311-313` —— 成功时工具返回 `dump_json_capped(result)`，而 `result = await client.post("/users", body)` 就是 Microsoft Graph 的原始响应，原样透传，没有附加任何内容。
- Microsoft 官方文档对 `POST /users` 的示例响应（learn.microsoft.com/en-us/graph/api/user-post-users，v1.0，2026-10-13 查阅）显示，响应体只包含一个很小的默认属性集合（`id`、`displayName`、`givenName`、`surname`、`mail`、`mobilePhone`、`businessPhones`、`officeLocation`、`preferredLanguage`、`userPrincipalName` 等）——**`passwordProfile` 从未出现**，这与它是 Graph `user` 资源里"仅 `$select` 才返回"的属性之一是吻合的。所以今天，一次成功的 `graph_create_user` 调用给调用方的确认是零——连"请求过这个设置"都确认不了，更不要说"是否生效"，这正好对应图2描述的缺口。
- 对照同一文件里的姊妹工具 `graph_reset_password`（`src/graph_mcp/tools/users.py:320-372`）：它同样构造了带强制改密码标志的 `passwordProfile`（`:353-358`），通过 `PATCH /users/{id}` 发出（`:363`），而按 Graph 的语义 PATCH 会返回 `204 No Content`（已在 `src/graph_mcp/api_client.py:181-187` 的 `_parse_body` 确认：204/空响应体会解析成 `None`）——而它**没有**尝试把这个空响应透传出去，而是自己构造了一个明确的确认对象（`:364-370`）：`{"status": "success", "user_id": user_id, "message": "Password reset; user must change it at next sign-in."}`。这已经是本仓库里现成的惯例——"不要依赖 Graph 的响应来证明 `passwordProfile` 设置生效了"——只是 `graph_create_user` 还没照着做。
- `README.md:71` —— 工具清单表里 `graph_create_user` 那一行的描述同样没有提到强制改密码。
- wiki（`ProductDocs/**`，2026-10-13 已同步，产品版本 v20261012.0718）：**未覆盖**。`mbp.py wiki find` 对"onboarding agent"、"create user"、"ms-graph"、"force password" 均无命中；"password"/"entra" 命中到的内容全部是 `agent.mspbots.ai` 平台自身的连接器配置界面（OAuth 弹窗文案、连接表单），不是某个 MCP 连接器工具创建 Entra 账号时的行为。这是预期之中的空白，不是巡检的疏漏：`ProductDocs` 巡检的是 `agent.mspbots.ai` 自己的界面，而本单是 MCP 工具与调用方之间的契约问题，没有对应的终端用户界面可走查。
- 外部技术事实（不是 MSPBots 产品事实，所以不来自 wiki，是通用的 Microsoft Graph 平台行为，已核实，直接决定了技术设计的方案选型，见下方 Tech design §11 引用）：追加一次 `GET /users/{id}?$select=passwordProfile` 读回**并不能可靠地作为"已生效"的证据**——多个 Microsoft Q&A / 论坛帖子报告，即使显式 `$select` 了该属性，读回仍然是 null/空值。引用见技术设计第 11 节。

## 产品设计

### 目标 / 非目标

**目标**：
- `graph_create_user` 的调用方只读工具定义（不需要访问源码）就能确认：这个工具创建的每一个账号都被配置为下次登录必须改密码，而且这个行为不可按次调用配置。
- `graph_create_user` 的调用方能从工具自身的调用结果里确认：刚创建的这个账号确实被请求设置了这项——不需要第二次工具调用，也不需要任何带外检查。

**非目标**（本单明确不做）：
- 把强制改密码变成可选/可配置的。当前"始终开启、不可关闭"是一个合理的安全默认值，工单也没有要求放宽它——如果以后确实需要，见 Open Questions。
- 用 Graph 的读回调用去证明 Entra 服务端真的持久化了这个设置。见技术设计「方案选型」：这个方案被认真评估过并否决——相关 Graph 属性的读回不可靠性是有文档和社区报告支撑的，追求这种"更严谨"的确认，换来的只是额外延迟和偶发的假失败。
- 对 `graph_reset_password` 的任何改动。它已经有一套独立构造的确认机制，不受本单这个缺口影响。

### 验收标准 AC1..ACn

- **AC1**：Given 调用方用合法的必填参数调用 `graph_create_user`，When 调用成功且 Graph 返回 `201 Created`，Then 工具返回的 JSON 里包含一个明确字段，确认该账号已被设置为"下次登录必须改密码"（而不只是"没有报错"这种沉默式的成功）。
- **AC2**：Given 调用方或评审者只读 `graph_create_user` 的工具定义（它的 description，即 `list_tools()`/任意 MCP 客户端能看到的内容），不读源码，When 他们查看这个工具做什么，Then 该 description 明确写明：每个创建出来的账号都会被配置为下次登录必须改密码，且这个行为不可按次调用配置。
- **AC3**：Given 账号创建因任何原因失败（例如 Graph 因 `userPrincipalName` 冲突或策略校验拒绝），When `graph_create_user` 返回它的错误信封，Then 响应里**不**包含 AC1 中那个确认字段——一个从未被创建出来的账号，不可能有任何设置"生效"。
- **AC4**（向后兼容）：Given 现有调用方已经在解析今天 `graph_create_user` 的成功响应，When 本次改动上线后，Then 今天响应里的每一个字段都原样保留、值不变——新增的确认字段是纯增量，不改名、不删除任何既有字段。
- **AC5**（无状态/不跨调用泄露）：Given 连续两次调用 `graph_create_user`，分别使用不同的访问令牌、不同的密码、不同的显示名（模拟两个不同租户或两个不同新员工），When 两次调用都完成，Then 每次调用的响应（包括新增的确认字段）只反映该次调用自己的输入，第一次调用的任何内容都不会出现在第二次调用的结果里。
- **AC6**（最终事实依据，需要真实租户）：Given 一个真实的 Entra ID 租户，When 一个新建账号第一次使用 `graph_create_user` 返回的密码登录，Then Microsoft 会要求该用户在继续之前先设置一个新密码——也就是说 AC1 里工具自己的说法，与 Entra 实际强制执行的行为是一致的，不只是"我们对 Entra 提了这个请求"。这是提单人要的证据里最强的一种，但本次设计棒（只读代码，没有真实租户访问权限）做不出来——见测试用例，标记为 `未执行 · 本地盲区`，留给开发棒的自测环节（`legs/dev.md` S5）在有沙箱租户可用时执行；这与 `docs/modules/users.md § PRD-20321` 里已经记录过的"`employeeId` 目录数据侧需要真实租户验证"属于同一类缺口。

### Open Questions

- [不阻塞] `force_change_password` 要不要变成一个可选的、调用方可以显式关闭的参数（比如迁移历史账号时希望保留原密码）？当前设计假设"始终开启、不可配置"维持不变，因为工单要的是**确认**这个行为，不是放宽它。如果以后真的出现需要关闭的场景，应该走一张独立的工单。
- [已假设] 理论上最强的证据是 Graph 侧的读回确认，但该属性的读回已被证实不可靠（见技术设计第11节）。本设计选择的是：在 `201` 成功时返回一个"我们对 Graph 请求了什么"的确定性回显（Graph 只有在请求体——包括 `passwordProfile`——语法和语义都被接受时才会返回 `201`，不会悄悄丢弃一个合法字段）。如果需求方认为"我们请求过 X"不够、必须要"Graph 确认 X 已发生"，技术设计的方案 B 需要被重新评估并接受其延迟与不可靠性代价。
- [不阻塞] `README.md` 工具表里具体是第几行（目前是 `:71`）需要开发棒在实现时重新核对，因为文件内容在设计到开发之间可能已经变化。

## 技术设计

### 结论

在 `ms-graph-mcp` 的 `graph_create_user` 工具（`src/graph_mcp/tools/users.py:218-315`）上做两处纯增量改动：(1) 更新 docstring，写明每个创建出来的账号都被配置为下次登录必须改密码，且不可配置；(2) 在 `POST /users` 成功后，不再把 Graph 的原始响应直接透传，而是在返回之前合并进一个明确的、确定性的确认字段（例如 `passwordChangeRequiredAtNextSignIn: true`）。这与同文件里 `graph_reset_password` 已经在用的模式一致（自己构造确认对象，而不是信任 Graph 那个基本是空的响应）。不新增工具，不新增必填参数，不新增权限。

### 现有实现定位

与「现状」一节引用的 `path:line` 相同：
- `src/graph_mcp/tools/users.py:218-315` —— `graph_create_user`（签名、docstring、请求体拼装、`POST` 调用及其返回）
- `src/graph_mcp/tools/users.py:320-372` —— `graph_reset_password`，"自己构造确认对象、不信任 Graph 响应"这条惯例的先例
- `src/graph_mcp/api_client.py:118-187` —— `GraphClient._request`/`_parse_body`，证实 `204`/空响应体会被解析成 `None`
- `README.md:71` —— 需要更新的工具表描述行

### 方案选型

| 方案 | 做法 | 优点 | 代价 | 结论 |
|---|---|---|---|---|
| A. 在工具自身响应里做确定性回显 | `201` 成功后，把 `{"passwordChangeRequiredAtNextSignIn": True}` 合并进返回的 JSON；这个值来自**我们自己发出的请求**，不是 Graph 的响应 | 零额外网络调用；确定性（不依赖 Graph 是否碰巧回显这个字段）；与现有的 `graph_reset_password` 模式一致；改动小、风险低 | 只能证明"我们对 Graph 发起了这个请求"，不能直接证明"Entra 目录里真的落了这个设置"——不过 Graph 只有在请求体（含 `passwordProfile`）被接受为合法时才会返回 `201`，所以这是一个合理的代理证据，不是凭空假设 | **采用** |
| B. 创建成功后追加一次 `GET /users/{id}?$select=passwordProfile` 读回确认 | 直接问 Graph 这个设置是否已生效 | 理论上更接近"最终事实" | (1) 多一次 Graph 往返，增加延迟和一个新的失败点；(2) 已查证多个 Microsoft Q&A/论坛帖子报告，即便显式 `$select` 了该属性，读回仍然是 null/空值，不可靠；(3) 读回为空时，根本分不清"确实没生效"还是"这个属性本来就读不出来"，会制造假阴性，反而让调用方开始怀疑一个本来正确的工具 | **不采用**——不可靠性的证据压过了理论上的严谨性，这里记录下来而不是悄悄略过 |
| C. 什么都不做 | —— | 零成本 | 完全不解决本单的问题 | **不采用** |

### 改动清单

- `src/graph_mcp/tools/users.py` [改] ——
  - `graph_create_user` 的 docstring（目前在 `:264-269`）：补一句，写明每个创建出来的账号都要求下次登录改密码，且不可配置。
  - `graph_create_user` 的返回逻辑（目前在 `:311-313`，`return dump_json_capped(result)`）：改成在返回前合并确认字段，例如 `merged = dict(result) if isinstance(result, dict) else {"result": result}; merged["passwordChangeRequiredAtNextSignIn"] = True; return dump_json_capped(merged)`。这个 `isinstance` 判断是防御性的——Graph 文档说这个接口会返回带 body 的 `201`，但工具不应该在这个前提万一变化时直接崩溃。
- `tests/test_tools.py` [改] —— 为 AC1/AC3/AC4/AC5 新增测试覆盖（见下方测试策略）；现有测试（`test_create_user_sends_address_phone_company_and_hire_date`、`test_create_user_without_new_fields_keeps_prior_body_shape`）断言的是**请求体**形状，只影响响应的本次改动不会动到它们。
- `README.md` [改] —— 更新 `graph_create_user` 那一行（目前 `:71`），补上强制改密码的说明，措辞与最终 docstring 保持一致。
- `docs/modules/users.md`（累积层）[本棒不碰] —— 按 `references/docs-tree.md` 的规矩，这里只在开发棒交付后追加，设计棒不碰。

命名说明（小的、可逆的选择，按设计棒"自己选一个合理的并说明理由"的规矩）：新字段取名 `passwordChangeRequiredAtNextSignIn`，而不是直接照搬 Graph 自己的 `passwordProfile.forceChangePasswordNextSignIn`，是为了避免让人误以为这是从 Graph 回显/重新读取出来的值，而不是我们自己的确定性确认。如果需求方更想要与 Graph 同名以便于理解，这是一处不影响其它任何地方的改名。

### 数据与接口契约

- 接口：`graph_create_user` MCP 工具（不是 REST 端点——这个服务器通过 MCP HTTP-SSE 传输暴露工具）。请求参数：**不变**，不增不减。
- 成功响应（Graph 返回 `201`），本次改动后的示例：
  ```json
  {
    "id": "87d349ed-44d7-43e1-9a83-5f2406dee5bd",
    "displayName": "Adele Vance",
    "userPrincipalName": "AdeleV@contoso.com",
    "mail": "AdeleV@contoso.com",
    "...": "...(Graph 其余默认字段，不变)",
    "passwordChangeRequiredAtNextSignIn": true
  }
  ```
- 失败响应：**不变**，仍是 `GraphError.to_envelope()`；按 AC3，它不应包含新字段。
- 向后兼容：纯增量字段；不改名、不删除任何既有字段（AC4）。只读取特定已知字段的调用方不受影响；对精确字段集合做严格 schema 校验的调用方需要放开容纳这个新 key——这是任何增量式 API 改动的正常代价，本单接受这个代价。

### 关键流程时序

1. 调用方 → `graph_create_user`（必填+可选参数，不变）
2. 工具拼装 `body`，其中已经存在、不变的无条件 `passwordProfile.forceChangePasswordNextSignIn = True`
3. 工具 → Graph：`POST /users`
4. Graph → 工具：`201` + 它的默认属性集合（不含 `passwordProfile`，见「现状」）
5. **（新增）** 工具把 `passwordChangeRequiredAtNextSignIn: true` 合并进返回结果
6. 工具 → 调用方：包含确认字段的 JSON
7. （失败路径，不变）Graph 返回 4xx/5xx → `GraphError` → `e.to_envelope()` → 不含确认字段

### 非功能

- **幂等与并发**：不变——`graph_create_user` 本来就是创建新资源、从来不是幂等操作，本次改动不改变这一点。
- **性能**：零额外 Graph 调用（选的是方案 A 而不是 B）；合并操作是纯内存字典操作，开销可忽略。
- **安全**：不引入也不记录任何新的敏感数据；明文密码本来就不在响应里，本次改动之后依然不在——新字段是一个布尔值，不是密码或完整 `passwordProfile` 的拷贝。
- **多租户隔离**：严格意义上不适用——这个连接器本身无状态、不持有任何凭据（`README.md:10`："The server itself holds no credentials"），每次调用的租户范围完全由调用方当次传入的访问令牌决定。AC5 就是本单针对"这次改动有没有引入跨调用共享的可变状态"给出的具体检查。
- **可观测性**：本次改动不需要新增日志；如果团队以后想统计 `graph_create_user` 的调用情况，那是一个更大、本单不涉及的独立话题。

### 上线与回滚

不需要 feature flag——这是一个确定性的、纯增量字段，不是一个需要灰度的功能。走本仓库的常规流程：工作分支 → 开发棒自测 → 推送工作分支，等待人工合入/发布（按 `references/docs-tree.md`/`references/handoff.md`，设计棒不合入、不发布、不碰基线分支）。回滚就是直接 revert 相关 commit，因为改动是纯增量且集中在一个函数里，回滚风险很低。

### 测试策略

- 单元测试（全部可以用 `tests/test_tools.py` 现成的 `_CapturingClient`/`_FailingPostClient` mock 模式完成，不需要真实 Graph 调用）：覆盖 AC1、AC3、AC4、AC5。具体用例 id 见「测试用例」一节与 `.ac.json`。
- AC2（工具描述）同样可自动化：FastMCP 的工具注册会暴露每个工具的 description 文本，可以直接断言 `graph_create_user` 注册后的 description 字符串包含强制改密码的说明。
- AC6（Entra 是否真的在首次登录时强制执行）**无法**在没有真实/沙箱 Entra 租户的情况下自动化或验证——与 `docs/modules/users.md § PRD-20321` 里已经记录过的"`employeeId` 目录 schema 行为"属于同一类本地盲区。留给开发棒的自测环节（`legs/dev.md` S5）在有租户可用时尝试执行；没有租户时保持 `未执行` 并说明原因，不能标 `pass`。
- 回归面：`graph_reset_password`、`graph_update_user` 以及本文件里的其它工具都不依赖 `graph_create_user` 的返回结构，预期不受影响。

### 工作量与拆分

## 测试用例

（完整的前置条件/步骤留在同目录的 `PRD-20412.ac.json` 里；本节只写每条用例的判定句。）

- **TC1 · AC1 · 自动**：Given 用最小必填参数调用 `graph_create_user` 且 Graph 返回 `201`，When 工具返回结果，Then JSON 里包含 `passwordChangeRequiredAtNextSignIn: true`。
- **TC2 · AC2 · 自动**：Given 读取 MCP 服务端注册的工具定义，When 查看 `graph_create_user` 的 description，Then 其中明确写明创建出来的账号会被配置为下次登录必须改密码，且这个行为不可按次调用配置。
- **TC3 · AC3 · 自动**：Given Graph 对 `POST /users` 返回了一个错误（例如 `userPrincipalName` 冲突），When `graph_create_user` 返回它的错误信封，Then 响应里不包含 `passwordChangeRequiredAtNextSignIn`。
- **TC4 · AC4 · 自动**：Given 只用必填参数调用 `graph_create_user`（不带任何可选资料字段），When 把响应与今天的响应形状对比，Then 今天已有的每个字段都原样保留，外加新增的确认字段。
