# PRD-20707 · [Bug] Monthly report email sends placeholder HTML

Ticket: https://app.clickup.com/t/2280862/PRD-20707
Repo: https://github.com/MSPbotsAI/ms-graph-mcp@master (40d0c86)

## Requirement understanding

One line: the reporter wants the Monthly Technology Report agent's email to carry the actual generated report as its attachment instead of the placeholder HTML file it currently sends while Microsoft Graph still reports the send as successful.

EMD (Heath Beavers) first reported this on 2026-10-14; it was reproduced internally on 2026-10-16 while testing an unrelated approval-rule fix (PRD-20659). In both runs, the Monthly Technology Report agent built the full report, Executive Brief and Action Register correctly and all content checks passed, but the email sent to `mspbots_reports@emdnet.com` via `graph_send_mail` carried a small placeholder HTML attachment instead of the ~57 KB report. The send itself succeeds at the Graph API level (no error, no retry signal), so nothing in the current pipeline detects or flags the mismatch except the agent's own after-the-fact self-report in its final chat reply. The email cannot be unsent. This is pre-production: only the pilot recipient has received a wrong attachment so far, but it blocks EMD's move to live client delivery planned for early November.

## Current state (every claim carries path:line)

- `src/graph_mcp/tools/mail.py:377-449` (`graph_send_mail`) — the MCP tool this server exposes for sending mail via Microsoft Graph (`/me/sendMail` or `/users/{id}/sendMail`). Its optional `attachments` argument (`:402-407`) accepts up to 5 items, each needing a `filename` plus **exactly one** of `content_text` (raw text, server-encoded) or `content_base64` (binary, already base64) — there is no third way to reference a file by id/URL and have the server fetch it itself. The caller (the LLM generating the tool call) must reproduce every byte of the attachment inline, in its own output.
- `:123-205` (`_build_attachments`) — validates and maps `attachments` into Graph `fileAttachment` dicts. Read in full: this is a **faithful passthrough**. It checks size against `_MAX_ATTACHMENT_BYTES = 500_000` / `_MAX_TOTAL_ATTACHMENT_BYTES = 700_000` (`:98-99`), normalizes base64 variants (`:109-120`, added by PRD-20416), guesses `content_type` from the filename extension — but it has **no way to check whether the content is actually correct** for the stated filename, because it has no independent source of truth for what the file is supposed to contain. A validly-encoded, under-the-cap placeholder passes exactly as cleanly as the real 57 KB report would.
- `:91-97` — a pre-existing comment (not written for this ticket) that states the exact mechanism this bug depends on: *"Inline attachments arrive as a base64 tool argument, so the calling agent has to hold (and emit) every byte in its own context first."* For a 57 KB HTML report, that means the model generating the `graph_send_mail` call has to reproduce roughly 57,000 bytes of exact content inside its own generated tool-call arguments, often several conversation turns after the report was actually built.

## Product design

### Goals / Non-goals

**Goals** (this ticket, scoped to `ms-graph-mcp` only):
- A caller of `graph_send_mail` that has (or will have) a fetchable HTTPS URL for its attachment can have the **server** fetch and attach those exact bytes, instead of having to reproduce the file's content inline in its own generated tool-call output.
- Attachments sourced this way are subject to the same size limits as inline ones (`_MAX_ATTACHMENT_BYTES` / `_MAX_TOTAL_ATTACHMENT_BYTES`), and any failure (unreachable URL, disallowed host, oversized content) is reported as a structured error **before** any mail is sent — never silently substituted.
- Only HTTPS URLs whose host is on an explicit, operator-configured allow-list may be fetched; with no hosts configured (the shipped default), this capability is inert and behaves as a clear, documented `invalid_argument` rather than silently doing nothing.
- Every `graph_send_mail` call that includes attachments logs structured metadata (filename, byte length, sha256, source) so a future mismatch is diagnosable from server logs, not only from an agent's own after-the-fact self-report (which is how this ticket was found).

**Non-goals** (explicitly out of this ticket):
- Exposing an actual fetchable URL for a generated report/artifact on the Agent Platform side. That is a different repository (most likely `mb-platform-agentos`, based on architecture, but not confirmed by code-level evidence reachable from this ticket's Code Project — see Open Questions) and is not something this design can specify without guessing at code this pipeline has no evidence for. This ticket ships the *receiving* half of the mechanism, inert until that URL exists and an allow-list is configured.
- Fixing the general verbatim-reproduction risk for callers that have no persisted, fetchable location for their file (e.g., content that only ever exists in the model's own context). Those callers keep today's unchanged `content_text`/`content_base64` behavior and its existing, real risk for large files.
- Any prompt/SKILL-level change to the Monthly Technology Report agent itself (that content is not in any repo this pipeline can reach — see Current state).
- Retry/backoff policy for the URL fetch beyond what this repo's existing shared HTTP client timeout already provides.
- Changing `_MAX_ATTACHMENTS` (5) or the combined 700 KB cap.

### Acceptance criteria AC1..AC8

- **AC1**: Given an attachment item specifies `content_url` pointing to an HTTPS host on the configured allow-list, and the URL serves content within the per-file size limit, When `graph_send_mail` is called, Then the server fetches that content itself and sends the mail with exactly those fetched bytes as the attachment — the caller never had to embed the bytes in its own tool-call arguments.
- **AC2**: Given an attachment's `content_url` host is **not** on the allow-list, When `graph_send_mail` is called, Then no Graph request is made (mail is not sent) and the tool returns an `invalid_argument` error naming the rejected host.
- **AC3**: Given the allow-list is empty (the out-of-the-box default), When any attachment specifies `content_url`, Then it is rejected with `invalid_argument` stating the feature is not configured — behavior is otherwise unchanged from today.
- **AC4**: Given a `content_url` fetch fails (non-2xx response or network timeout), When `graph_send_mail` is called, Then no mail is sent and the tool returns a structured error identifying the failed fetch — it never substitutes empty or placeholder content for a failed fetch.
- **AC5**: Given a `content_url` fetch succeeds but the fetched content exceeds the per-file or combined size limit, When `graph_send_mail` is called, Then no mail is sent and the existing size-limit error fires, citing the actual fetched byte count.
- **AC6**: Given an attachment specifies more than one of `content_text` / `content_base64` / `content_url`, When `graph_send_mail` is called, Then it is rejected the same way today's "needs exactly one of" check works, extended to all three.
- **AC7 (backward compatibility)**: Given attachments using only `content_text` or `content_base64` exactly as before, When `graph_send_mail` is called, Then behavior and response shape are byte-for-byte identical to pre-change — every existing PRD-19661/PRD-20416 test continues to pass unmodified.
- **AC8 (observability)**: Given any `graph_send_mail` call that includes one or more attachments, When the call completes (whether the eventual Graph send succeeds or fails), Then the server logs, for each attachment, its filename, decoded byte length, sha256, and source (`inline` or `url`) — this is new; the repo has no logging today (confirmed in Current state).

## Tech design

### Conclusion

Add a third, mutually-exclusive attachment content source, `content_url`, to `graph_send_mail`'s `attachments` schema. When given, the server fetches the URL itself (reusing this repo's existing shared `httpx.AsyncClient`), enforces the same byte caps against the fetched bytes, and only proceeds if the URL's host is on a new, explicit allow-list (`Settings.attachment_fetch_allowed_hosts`, empty by default = feature off). This removes the LLM from the byte-reproduction path for any caller with a fetchable URL, directly mirroring the fix pattern this same repo already established and proved necessary in PRD-20413 ("remove the model from the data path" after a prompt-only fix for verbatim copying was empirically falsified by QA in PRD-20211). Also add structured logging (net-new to this file) of attachment metadata on every send, regardless of source, so a future mismatch is diagnosable from server logs. Exposing an actual fetchable artifact URL on the Agent Platform side is out of scope — different repo, not evidenced as reachable from this ticket's Code Project (see Open Questions).

### Data & API contract

**MCP tool contract** — `graph_send_mail` attachment item, extended:

```json
{"filename": "monthly-technology-report_american-ambulance-of-visalia_2026-09.html",
 "content_url": "https://artifacts.example-allowlisted-host/thread123/report.html"}
```

- Exactly one of `content_text` / `content_base64` / `content_url` is required (extends today's two-way check).
- `content_url`: must be `https://`; its host must be in `ATTACHMENT_FETCH_ALLOWED_HOSTS` (comma-separated env var; empty default rejects every `content_url`).

Error responses (new codes, via existing `error_envelope(code, message, retryable, extra)`):

| Code | When | `extra` |
|---|---|---|
| `invalid_argument` | `content_url` scheme isn't `https` | — |
| `invalid_argument` | `content_url` host not on the allow-list (includes the empty-allow-list default) | `{"host": "...", "allowed": [...]}` |
| `invalid_argument` | more than one of `content_text`/`content_base64`/`content_url` given | — |
| `upstream_error` (retryable) | fetch connection/timeout/5xx | `{"url": "..."}` |
| `not_found` (not retryable) | fetch returned 404 | `{"url": "..."}` |
| existing size-limit error (unchanged code) | fetched bytes exceed per-file or combined cap | existing shape, now citing the fetched byte count |

**Outbound calls**: one new `GET <content_url>` (to the allow-listed host, via the shared `httpx` pool) before the existing `POST /me/sendMail` or `POST /users/{id}/sendMail`. If the fetch fails for any reason, no Graph call is made at all — preserving the existing docstring's "If any attachment is invalid nothing is sent" invariant.

**DB**: none — this service holds no state (gateway mode, per-request token only; unchanged by this design).

**Backward compatibility**: fully additive. `content_text`/`content_base64` behavior is byte-for-byte unchanged (AC7); `content_url` is new and, with the shipped empty allow-list, is a no-op feature (always rejects) — so deploying this change alone causes zero behavior change for any existing caller.

### Key flow / sequence

```
agent → graph_send_mail(..., attachments=[{filename, content_url}])
  → _build_attachments(): for each attachment
      ├─ content_text / content_base64 given → existing path, unchanged
      └─ content_url given
           ├─ scheme != https                 → invalid_argument
           ├─ host not in allow-list           → invalid_argument (host + allowed list echoed)
           └─ GET content_url (shared httpx client, size-capped streamed read)
                ├─ non-2xx / timeout           → upstream_error / not_found
                ├─ bytes > per-file cap         → existing size-limit error
                └─ success                      → bytes used exactly as content_base64 would be
  → size checks across all attachments (existing, now source-agnostic)
  → logger.info(...) per attachment (filename, bytes, sha256, source)
  → POST /me/sendMail (or /users/{id}/sendMail), unchanged
```

### Non-functional

- **Idempotency / concurrency**: the fetch is a single side-effect-free `GET`; `graph_send_mail` remains correctly `idempotentHint=False` (sending mail is never idempotent, unchanged). No shared mutable state introduced — the allow-list is read-only `Settings`, loaded once at process start, same pattern as the existing `graph_base_url`.
- **Performance**: one additional outbound round trip only when `content_url` is used; existing `content_text`/`content_base64` callers see zero added latency. The streamed, size-capped read prevents a large or slow response from blocking a worker indefinitely, bounded by a timeout mirroring `api_client.py`'s existing `_TIMEOUT` shape.
- **Security**: the new outbound-fetch capability is this design's main risk surface, mitigated by (a) HTTPS-only, (b) an explicit host allow-list defaulting to empty (opt-in, not opt-out), (c) the same byte caps as today. This does **not** eliminate SSRF risk if the allow-list is ever misconfigured to include an internal/private address — that risk is called out explicitly in `README.md`/`.env.example` so whoever configures the allow-list understands the constraint. Implementation should additionally reject private/loopback/link-local IP ranges even if accidentally allow-listed, as a cheap second guard (flagged in Risks, not separately ACed). No new Graph permission scope is required.
- **Multi-tenant isolation**: unaffected. The `content_url` fetch carries no Graph token and no tenant context — it is a separate, unauthenticated-to-this-server HTTPS GET to an allow-listed host. The existing per-request Graph token isolation (`contextvars`, `server.py`) is untouched.
- **Observability**: net-new (AC8) — this file has zero logging today. Adds one `logger.info` per attachment on every `graph_send_mail` call that includes attachments, regardless of source, so a future content mismatch is diagnosable from server logs rather than solely from an agent's self-report (which is literally how this ticket was found).

### Rollout & rollback

- No feature-flag infrastructure exists in this repo (confirmed in PRD-20413's own Rollout note: `grep -rn "feature_flag" src/` — no hits). Ships enabled by default but inert: with `ATTACHMENT_FETCH_ALLOWED_HOSTS` unset/empty, every `content_url` is rejected, so deploying this causes zero behavior change for any existing caller.
- Release order: single repo (`ms-graph-mcp`); no cross-repo dependency for shipping this half. The companion piece (an Agent-Platform-side fetchable artifact URL) is a separate, optional follow-up this ticket does not block on — AC8's logging is independently useful even if `content_url` is never configured.

### Test strategy

This is a bug ticket, but its root symptom (an LLM reproducing wrong bytes inside a tool call) occurs inside an agent run, not inside this repo's deterministic code — there is no failing unit test to write for "the bug itself" here. TC1 below instead characterizes the structural gap that motivates this design (today's contract has no way to verify attachment content against anything); TC2 onward are red→green for the new `content_url` mechanism.

Unit tests (`tests/test_tools.py`, extending the existing `_send`/`_mail_mcp`-style fixtures with a mocked HTTP fetch):

- TC1 (characterization): today, `graph_send_mail` accepts and sends any validly-encoded `content_base64`/`content_text` attachment with zero correctness check against the stated filename — already true, demonstrates why `content_url` (server-controlled bytes) is the chosen mechanism rather than a content-correctness check (which is impossible without a source of truth).
- AC1 → TC2: `content_url` to an allow-listed host, mocked fetch returns known bytes under the cap → attachment sent with exactly those bytes.
- AC2 → TC3: `content_url` host not on the allow-list → `invalid_argument`, no Graph call made.
- AC3 → TC4: empty/default allow-list + `content_url` given → `invalid_argument` (feature inert by default).
- AC4 → TC5, TC6: mocked fetch returns 500 and, separately, 404 → `upstream_error` / `not_found` respectively, no Graph call made in either case.
- AC5 → TC7: mocked fetch returns bytes over `_MAX_ATTACHMENT_BYTES` → existing size-limit error fires, citing the fetched byte count, no Graph call made.
- AC6 → TC8: attachment with both `content_text` and `content_url` → `invalid_argument` ("needs exactly one of").
- AC7 → TC9: explicit regression gate — existing `test_send_mail_attaches_one_file_correctly` / `test_send_mail_attaches_multiple_files_up_to_limit` / etc. (PRD-19661/PRD-20416) must continue to pass unmodified.
- AC8 → TC10: successful send with attachments → assert (via `caplog`) one `logger.info` per attachment carrying filename/byte-length/sha256/source.

Integration / manual (cannot be unit-tested, needs a real allow-listed host + a live Graph test mailbox — executed in the dev+test leg):

### Effort & breakdown

**1–2 person-days.** Lower bound: mostly additive code in one file plus config/README updates; the pattern (allow-list + fetch + existing size caps) is small and self-contained. Upper bound's uncertainty: extracting/exposing the shared `httpx` client from `api_client.py` cleanly, and writing the streamed, size-capped-read fetch correctly (avoiding full-buffering of an oversized response before checking its size) takes more care than the rest. No further sub-task split is needed within this repo — one file's one feature addition does not decompose into independently-shippable pieces. (The companion Agent-Platform-side URL-exposure work, if groom wants it pursued, is a separate ticket in a different repo and is not included in this estimate.)

### Risks & dependencies

- **Dependency**: a real allow-listed host serving real agent-produced artifacts over HTTPS must exist before `content_url` is useful to any actual caller — not confirmed to exist yet (Open Questions). Shipping this ticket alone does not, by itself, fix PRD-20707's user-visible symptom; it ships the mechanism a companion change (different repo) would need to close the loop, plus the logging improvement (AC8) which is useful regardless.
- **Risk**: allow-list misconfiguration (pointing it at an internal/private address) would reintroduce SSRF exposure — mitigated by explicit documentation and an empty default; implementation should add an automatic private/loopback/link-local IP rejection as a cheap additional guard on top of the host allow-list (see Non-functional § Security).
- **Risk**: implementing the size-capped streamed read incorrectly (fully buffering before checking size) would reintroduce a memory-exhaustion vector from a misconfigured or compromised allow-listed host — flagged for the dev leg's attention in the Change list.
- No dependency on PRD-20211/PRD-20413 completing anything further — those are a different code path (`sites.py`) in the same repo, cited here only as precedent for the fix pattern.
