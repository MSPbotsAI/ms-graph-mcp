## 需求理解

一句话：提单人希望 Graph send email 支持发送带附件的邮件，因为当前该能力只能发送纯文本/HTML 正文、无法携带附件，导致依赖附件的邮件工作流被阻塞。

David Hu 通过 Teams 提出该需求：现有 `graph_send_mail` 只能发不带附件的邮件，David / Toby 需要用它发送带文件附件的邮件，当前没有替代方案（"No workaround"）。提单人标注为紧急，最小可行范围（Minimal Viable Slice）是"先支持常见文件附件"，成功标准是"能成功发送一个或多个附件"。完成后需要在 Teams 通知 David 与 Toby。

## 现状（每条断言带 path:line）

- `src/graph_mcp/tools/mail.py:67-128` —— `graph_send_mail` 工具的完整实现：签名只有 `to_recipients`/`subject`/`body`/`sender_id`/`body_content_type`/`cc_recipients`/`bcc_recipients`/`save_to_sent_items`，`:106-114` 组装的 `message` dict 里没有 `attachments` 字段，`:122` 走 `/me/sendMail` 或 `/users/{id}/sendMail`，一次性 `POST`（`:125`）。这与工单描述"Graph send email cannot include attachments"逐字吻合。

## 产品设计

### 目标 / 非目标

**目标**：`graph_send_mail` 支持在发送邮件时附带一个或多个文件附件（工单的"minimal viable slice"：先支持常见文件附件），附件与邮件一起送达，收件人可以看到并下载。

**非目标**（本次不做）：
- 超过本工具内联上限（单文件解码后 500 KB、合计 700 KB）的文件——更大的文件需要改为服务端取文件（引用 SharePoint/OneDrive driveItem）或 Graph 的 resumable upload session 流程，那要求把"一次性 sendMail"改造成"建草稿 + 分块上传 + 发送草稿"的三段式调用，是明显更大的改动，本次不做（见 Open Questions 与技术设计 §3 方案 C）。
- 从 SharePoint/OneDrive 等外部存储按链接引用附件（"帮我把那个文件当附件发出去"这种引用式用法）——工单要的是"发送时带上文件内容"，不是"文件引用解析"。
- 内嵌图片（`isInline`）、S/MIME 签名附件、转发另一封邮件作为附件（`itemAttachment`）——工单原话只提"attachments"，没有这些更复杂的子类型。

### 方案（用户可见行为）

#### 主流程
调用方（agent）在调用 `graph_send_mail` 时，除了收件人/主题/正文等既有参数外，额外提供一份或多份附件（文件名 + 文件内容 + 可选的文件类型）。工具照常发出邮件，此次邮件多带上这些附件。收件人在自己的邮箱里能看到并下载这些附件，文件名、类型、内容与调用方提供的一致。

#### 界面与交互变化
不适用：这是 MCP 工具层的能力（供 agent 调用），没有直接面向终端用户的 UI 界面改动。收件人在自己的邮件客户端里看到的是标准的邮件附件展示，不是本次改动引入的新界面。

#### 边界与异常
- 不提供附件：邮件照常发送，行为与改造前完全一致（向后兼容）。
- 附件内容无法识别/损坏：邮件不发送，调用方收到明确指出是哪个文件出了问题的错误，而不是发出一封"看起来正常但附件打不开"的邮件。
- 附件过大（单个或合计超过本设计设定的上限）或附件数量过多：邮件不发送，调用方收到明确的超限说明（超的是大小还是数量），并被建议改用更小的文件或分多封邮件发送。
- 附件缺必要信息（比如没给文件名）：邮件不发送，错误信息指出缺了什么。
- 以上任何一种校验失败，都不允许"先发邮件、附件丢了"这种部分成功——要么完整发出，要么完全不发。

#### 权限与多租户
不引入新的权限维度：仍然是调用方自带的 Graph 访问令牌（`Mail.Send`）决定能以谁的身份发到哪个邮箱，附件内容不改变这个授权模型。每次调用相互独立，一次调用提供的附件内容不会出现在另一次调用（哪怕是同一进程内紧接着的下一次调用）的结果里——这条本身不是"新增的隔离机制"，而是这个工具从设计上就是无状态的（每次请求的 token 与参数完全由该次请求决定，不做跨请求缓存），本次改动不引入任何跨请求共享的可变状态,所以不会破坏这一点。

### 影响面

- 受影响方：所有调用 `ms-graph-mcp` 的 `graph_send_mail` 的 agent/工作流。
- 现有行为不变：不传新参数的调用方，请求/响应形状与改造前逐字节一致。
- 无需迁移：不涉及存量数据（该服务本身不落库）。
- 无需公告：纯增量能力，旧用法不受影响，新用法需要调用方自己知道新参数怎么传（README 会同步更新工具说明）。

### 验收标准 AC1..ACn

- **AC1**：Given 调用方对 `graph_send_mail` 传入 `to_recipients`/`subject`/`body` 及 1 个附件（文件名、可选类型、base64 内容，解码后 ≤500 KB），When 调用该工具，Then 邮件被发送到收件人邮箱，且邮件带有 1 个与传入文件名/类型一致、内容字节相同的附件。
- **AC2**：Given `attachments` 传了 2–5 个文件，且每个都 ≤500 KB、合计 ≤700 KB，When 调用，Then 全部附件都出现在邮件里，文件名/类型/内容分别与传入一致。
- **AC3**：Given 不传 `attachments`（省略参数，或传 `null`/空列表），When 调用，Then 行为与改造前完全一致——邮件正常发出且不带任何附件。
- **AC4**：Given 某个附件的 `content_base64` 不是合法 base64，When 调用，Then 工具返回 `invalid_argument` 错误，明确指出是哪个文件名解不出来，且不发送邮件。
- **AC5**：Given 单个附件解码后超过 500 KB，或全部附件合计解码后超过 700 KB，或附件数量超过 5 个，When 调用，Then 工具返回 `invalid_argument` 错误，说明具体超限的是哪一项（单个大小 / 合计大小 / 数量），且不发送邮件。
- **AC6**：Given `attachments` 里某一项缺少 `filename` 或 `content_base64` 这两个必填字段之一，When 调用，Then 返回 `invalid_argument` 错误，指出缺失的具体字段名，且不发送邮件。
- **AC7（多租户/隔离）**：Given 连续两次调用分别使用不同的访问令牌/不同收件邮箱、各自带不同的附件内容，When 依次调用，Then 第二次调用的请求里不包含第一次调用的附件内容，两次调用互不影响——即这个工具是无状态的，不存在跨调用的附件内容残留或串扰。

### Open Questions

- [已决策 2026-09-30] 上限定为 **单文件 500 KB / 合计 700 KB / 最多 5 个**（见下方「决策记录」）。如果以后常见更大文件，走服务端取文件（driveItem 引用）或 upload session，作为独立的后续迭代，不是本单的返工触发条件。
- [已确认 2026-09-30，David Hu / Toby Huang] 附件内容由调用方（agent）以 base64 直接作为本次工具调用的参数传入；Toby 确认实际文件为几十 KB、不超过 500 KB。原假设说明：，而不是"先把文件传到别处、这里只传一个引用链接"——因为工单原话是"支持发送带附件的邮件"，且这与仓库里 `sites.py` 现有的"内容作为单次工具调用参数传入"的既有模式一致。若这个假设不成立（比如实际期望的是"引用一个 SharePoint 文件发出去"），技术设计第 5 节的接口契约需要重做成"先引用后解析"的两段式。
- [不阻塞] `content_type` 缺省时按 `application/octet-stream` 处理，不做基于文件名后缀的自动类型推断——需要更友好的类型识别可以后续按需加。

## 技术设计

### 结论

在 `ms-graph-mcp` 的 `graph_send_mail` 工具（`src/graph_mcp/tools/mail.py:67`）上新增一个可选参数 `attachments`，每项包含 `filename`/`content_base64`/可选 `content_type`；发送时转换成 Microsoft Graph 的 `fileAttachment` 数组，塞进现有一次性 `POST {base}/sendMail` 请求体的 `message.attachments` 字段。不引入新工具、不改变现有必填参数、不新增依赖、不改变鉴权（仍是 `Mail.Send`）。上限为单文件 500 KB、合计 700 KB、最多 5 个（决策依据见「决策记录」）；更大文件的场景本次不做，列为后续迭代。

### 数据与接口契约

**MCP 工具契约**（`graph_send_mail`，其余既有参数不变）：

请求新增字段示例：
```json
{
  "attachments": [
    {"filename": "quote.pdf", "content_type": "application/pdf", "content_base64": "JVBERi0xLj..."},
    {"filename": "notes.txt", "content_base64": "SGVsbG8h"}
  ]
}
```
- `filename`：必填，字符串。
- `content_base64`：必填，标准 base64（含 padding），解码后代表文件原始字节。
- `content_type`：可选，缺省 `"application/octet-stream"`。
- 省略 / 传 `null` / 传 `[]` → 行为与改造前一致（无附件）。

成功返回：不变，仍是 `{"status": "sent"}`（`dump_json_capped` 包一层）。

失败返回（新增校验分支，均为 `error_envelope("invalid_argument", <message>, False)`，即不重试）：
- 缺 `filename` 或 `content_base64` → `"attachments[<i>] missing required field 'filename'/'content_base64'"`
- `content_base64` 解不出来 → `"attachments[<i>] ('<filename>') is not valid base64: <原始异常信息>"`
- 单个超限 → `"attachment '<filename>' is <N> bytes decoded, exceeds the 500,000-byte (500 KB) per-file limit for inline attachments — compress the file or share a link instead"`
- 合计超限 → `"attachments total <N> bytes decoded, exceeds the 700,000-byte (700 KB) combined limit; send in multiple emails or fewer/smaller attachments"`
- 超过数量上限 → `"5 attachments max per call, got <N>"`

**Microsoft Graph 层调用**（对下游只多这一个字段，其余不变）：`POST /me/sendMail`（或 `/users/{id}/sendMail`），`message.attachments` 数组元素形如 `{"@odata.type": "#microsoft.graph.fileAttachment", "name": "quote.pdf", "contentType": "application/pdf", "contentBytes": "JVBERi0xLj..."}`（Microsoft Graph `user: sendMail` API 文档 Example 3，v1.0，2026-09-30 查阅）。

**DB**：无——这个服务不落库（网关模式，无状态转发）。

**向后兼容**：现有调用方不传 `attachments` 时请求/响应形状与改造前逐字节相同；`tests/test_tools.py:39` 的 `required` 断言不变即是这条的机器验证。

### 关键流程时序

```
调用方(agent) → graph_send_mail(..., attachments=[...])
  → _build_attachments(): 逐项校验必填字段 → base64 解码 → 校验单项/合计/数量上限
      └─ 任一项不过 → 立即返回 error_envelope(invalid_argument)，不发起任何 Graph 请求
  → 全部通过 → message["attachments"] = built
  → GraphClient.post("/me/sendMail" 或 "/users/{id}/sendMail", payload)
      ├─ Graph 侧 4xx（本地校验没覆盖到的情况）→ GraphError → error_envelope(按现有 _classify 规则)
      └─ 成功 → 202 Accepted → dump_json_capped({"status": "sent"})
```
（沿用现有 `mail.py` 的 try/except GraphError 结构，附件校验是新增的"发起 HTTP 请求之前"的前置门。）

### 非功能

- **幂等/并发**：`graph_send_mail` 本身不是幂等的（发邮件不可撤回，`:93-97` 既有 docstring 已说明），本次改动不改变这一点；新增校验逻辑是纯函数、无共享可变状态，不引入并发问题。
- **性能**：base64 解码是纯 CPU/内存操作，700 KB 上限下单次解码开销可忽略；不引入额外网络往返（仍是一次 `POST`）。本次没有性能相关验收标准（工单未提出并发/负载要求），故不产出性能用例。
- **安全**：不新增鉴权面——仍由调用方持有的 `Mail.Send` token 决定能发到哪个邮箱；附件内容完全由调用方提供，本工具不做内容扫描（与现有 `graph_write_file_text` 等写类工具的既有边界一致，未额外加严也未放松）。校验错误信息会回显调用方提供的 `filename`，这与仓库里其它工具（如 `graph_list_messages` 的 `received_after` 校验错误）回显调用方输入的既有模式一致，不是本次新引入的风险。
- **多租户隔离**：`GraphClient` 按请求持有 token（`api_client.py:69-77`），不跨请求缓存任何东西；`attachments` 参数和其它参数一样是单次调用的局部变量，天然不跨租户/跨请求泄漏——对应 AC7。
- **可观测**：不新增日志（`mail.py` 现状没有任何显式日志调用，这是既有约定，本次不引入新约定）；失败原因通过 `error_envelope` 的 `message` 字段回给调用方，足够定位是哪个文件、哪条规则触发。

### 上线与回滚

- 无 feature flag、无灰度机制（仓库目前没有该类基础设施，`grep -rn "feature_flag" src/` 无命中）——新增参数可选且默认 `None`，天然向后兼容，等同于"开箱即灰度安全"。
- 发布顺序：单仓库改动（`ms-graph-mcp` 只有一个），无跨仓库依赖，走既有的 `docker compose up --build` / CI 流程直接发布。
- 回滚：`git revert` 该改动的 commit 即可——参数是新增可选项，回滚后已经在用 `attachments` 的调用会收到 MCP schema 层面的"未知参数"报错，属于正常的功能不可用而非数据损坏，无需数据回滚。

### 风险与依赖

- **依赖**：需要一个已完成 OAuth 同意、且 token 带 `Mail.Send` 的租户/邮箱来做集成验证；`ms-graph-mcp` 是网关模式，不持有凭据，验证账号由调用方（开发+测试棒或平台侧的 `mcp-service-gateway`/`mspbots-mcp-manager`）提供，本次设计范围内不涉及凭据配置本身。
- **风险**：Graph 官方文档对"直接内联进 `sendMail` 一次性调用"的附件，是否存在一个不同于"先建草稿再逐个 POST 到 `attachments` 导航属性"场景的独立总大小上限，本次未能从公开文档查到比"单文件 3 MB"更精确的数字（`outlook-large-attachments` 文档描述的是对着已有 message/event 逐个 POST 附件的场景，不完全等同于 sendMail 一次性调用里内联多个 fileAttachment）。（已不构成风险：最终上限合计 700 KB，编码后约 0.93 MB，远低于 Graph 约 4 MB 的请求上限。）原设计保守地把"单文件 3 MB + 合计 3 MB + 最多 5 个"都当成本工具自己的强约束，即使 Graph 实际允许更大也不放开——失败模式是"过于保守拒绝"而不是"放过量 request 到 Graph 后才在那边报错"，代价可接受。
- **风险**：`README.md:164` 记录的现状——真实租户上 `Mail.Read` 相关授权尚未走完重新 consent；发邮件用的是 `Mail.Send`，理论上已经在用（`graph_send_mail` 早已上线），但如果验证账号恰好也卡在同一个"租户需要重新 authorize 才能拿到最新 scope"的问题上，会拖慢集成验证这一步——不阻塞设计，记在这里供开发+测试棒排查参考。

### 决策记录（2026-09-30）

- **附件方式**：内联 base64。David Hu 提出「agent 编 base64 放进 tool 参数会占模型 token，单文件只能限 500 KB」，Toby Huang 确认实际文件为几十 KB、不超过 500 KB，接受该方式。
- **单文件上限 500 KB**：与 `src/graph_mcp/tools/sites.py:32-42` 的 `_MAX_WRITE_BYTES = 500_000` 保持一致（内容需先进入 agent 自己的上下文）。
- **合计上限 700 KB**（Leo 确认）：网关前 nginx 目前为默认 `client_max_body_size 1m`（1,048,576 字节）。700,000 字节编码后约 933,334 字符，给正文、收件人和 MCP JSON-RPC 包装留出约 110 KB，不依赖 nginx 调整即可上线。**注意**：正文很长（约 >100 KB 的 HTML）并且附件接近 700 KB 时，仍可能被 nginx 退回 413；nginx 调到 8m 后可把 `_MAX_TOTAL_ATTACHMENT_BYTES` 放大（例如 2 MB），只改这一个常量。
- **token 成本**：50 KB 文件编码后约 6.7 万字符，模型需输出上万 token。偶发小附件可接受；高频场景建议由工作流代码节点传附件，而不是让模型生成 base64。
- **部署**：INT/PRD 的 `vendor/ms-graph`（委派）与 `vendor/ms-graph-app`（app-only）都来自本仓库，两份都要 update，集成验证覆盖 `/me/sendMail` 与 `/users/{id}/sendMail`。
