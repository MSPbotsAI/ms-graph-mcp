## 需求理解

一句话：为 Microsoft 365/Entra offboarding workflow 08 与 03 增加两个生产级 Graph 接口——`graph_transfer_onedrive`（把离职用户的 OneDrive 内容/归属转移给目的账号或管理员）与 `graph_start_cloud_sync`（在生命周期变更后触发该租户所需的云同步），两者都要返回可据以决策的 success/failure/pending 状态并支持安全重试，用来替代现在不可靠的 Rewst OneDrive 转移变通方案（缺陷 D-10）以及目前尚未定义的 cloud-sync 步骤。

提单人（Damon Zhou）希望 `ms-graph-mcp` 新增两个工具，供内部 offboarding 自动化流程「workflow 08」与「workflow 03」调用，取代现在依赖的 Rewst（其 OneDrive 转移步骤已被缺陷 D-10 拖垮）或各自独立的手工 Graph/Exchange/AD 操作。`graph_transfer_onedrive` 应把离职用户的 OneDrive 内容转移给目的用户或管理员；`graph_start_cloud_sync` 应触发该租户实际使用的目录同步机制，使下游系统能看到 offboarding 变更。两者都必须回报可据以决策的 started/completed/failed/pending 状态——而不是一个裸布尔值——并且必须支持重复调用而不产生重复或冲突的状态。本单明确就是 PRD-20393 被推迟的那部分（该单原始八项中的第 7、8 项）；提单人原话写明确切的生产行为、转移方式、目的地规则以及实际的同步机制「仍需要与 Ginko 及相关平台负责人确认」——也就是说，提单人自己就预期这份设计会带着待确认的开放项，而不是要求本设计单方面替它们拍板。

## 现状（每条论断都带 path:line）

这是与 PRD-20393 相同的后端 MCP 服务，自身没有网页 UI；它唯一对终端用户可见的界面是 agent.mspbots.ai Capabilities 页面里 Microsoft Graph 连接器详情页的 **Tools** 列表，列表内容由这个服务按 **Refresh Tools** 时实际暴露的工具决定（wiki: `ProductDocs/15-Capabilities.md` § Connector detail view，_verified_ 2026-08-31，v4.1.518——「Tools——一个计数徽标……每个工具一行：等宽字体的工具名……一行描述，以及一个 **Available** 徽标」；同一小节还记录了该租户已连接 Microsoft Graph，且其第四个头部按钮是 **Reconnect** 而非 **Reconfigure**，这是 OAuth 类连接器的标准表现）。wiki 没有覆盖 offboarding「workflow 08」「workflow 03」具体做了什么——那是 `ProductDocs/**` 之外的 SOP/自动化定义，PRD-20393 已经记录过同一处缺口。

两项被请求能力的代码级现状，目前**完全不存在**：

1. **`graph_transfer_onedrive` 在本仓库任何地方都不存在。** `grep -rn "graph_transfer_onedrive" src/` 零命中。这个名字唯一出现的位置是本仓库自己的 `docs/tickets/PRD-20393.md:12,43` 及其 `.zh.md` 对应处，PRD-20393 在那里明确把它列为「第 7 项……搁置待 Ginko 确认」。
2. **`graph_start_cloud_sync` 同样不存在**，grep 结果相同，同样的 PRD-20393.md 引用处（`:12,44`）。
3. **完全没有任何 OneDrive（个人盘）相关代码。** 这个服务今天调用的 `/drives/*` 端点只有 `/sites/{id}/drive` 一种，全部用于 SharePoint 文档库（`src/graph_mcp/tools/sites.py` 全文件——`graph_search_sites`、`graph_list_drive_items`、`graph_get_file`、`graph_read_file_text`、`graph_read_site_file_text`、`graph_write_file_text`、`graph_create_file_text`、`graph_delete_file`）。README 明确写出了这条边界并点明是有意为之：「本文件里所有 SharePoint 工具全部只调用 Graph 的 `/sites/*` 和 `/drives/*` 端点，从不触碰 `/me/drive` 或 `/users/{id}/drive`」（`README.md:107`）。触达用户个人 OneDrive（`/users/{id}/drive`）对本仓库而言是全新领域，不是现有 drive 代码的延伸。
4. **已申请的 Entra 权限并集里已经包含 `Files.Read.All`/`Files.ReadWrite.All`**（`README.md:116`），但 README 记录这是防御性申请的，不是因为哪个工具需要它：「`Files.*` 同时覆盖每个用户的 OneDrive，而这里没有任何工具会去碰它」（`README.md:123`）。所以上线 `graph_transfer_onedrive` 不需要对已连接租户走新的授权步骤——但它是本仓库第一个真正使用这个此前一直闲置、波及面覆盖所有已连接租户的权限授予的工具。
5. **不存在任何名目下的同步触发能力。** 没有任何代码碰 `/servicePrincipals/*/synchronization/*`，已申请的 Entra 权限并集（`README.md:111-118`）里也没有 `Synchronization.Read.All`/`Synchronization.ReadWrite.All`——这是一个真正全新的权限申请，和 README 已经记录过的 Mail/Calendar 上线形态一样（`README.md:173-174`：权限已申请但租户必须重新授权才会生效）。
6. **`onPremisesSyncEnabled` 已经被读取并展示，但只是一个被动标签。** 组：`src/graph_mcp/tools/groups.py:106-107`（`graph_list_user_groups`）与 `:327-328`（`graph_get_group`）据此推导出 `sync_source: "on-premises"|"cloud"`。用户：PRD-20393 已把它加进 `graph_get_user` 的默认 `$select`（`src/graph_mcp/tools/users.py:38`，`_USER_PROFILE_SELECT`）。目前没有任何代码据这个标志去触发什么——今天它是只读的。
7. **`api_client.py` 唯一的请求路径只返回已解析的响应体，从不返回响应头。** `GraphClient._request`（`src/graph_mcp/api_client.py:124-172`）最终执行 `self._raise_for_status(resp); return resp.content if raw else self._parse_body(resp)`——没有任何地方捕获 `resp.headers`。Graph 的 drive-item copy 端点（`POST /drives/{id}/items/{id}/copy`）会回 `202 Accepted` 并带一个指向 monitor URL 的 `Location` 头；现有客户端读不到它（见技术设计 §4，说明为什么本设计干脆不需要它）。

## 产品设计

### 目标 / 非目标

**目标：**
- G1：offboarding 自动化流程（workflow 08/03）能调用一个 Graph MCP 工具，把离职用户 OneDrive 根目录内容复制进目的用户的 OneDrive，不再经过 Rewst。
- G2：同样的自动化流程能调用一个 Graph MCP 工具，在 offboarding 变更后触发该租户的目录同步——限于 Microsoft Graph 能触达的那一种同步机制（Azure AD Connect **cloud sync**；经典本地 AD Connect 为什么触达不了见「非目标」与技术设计 §3）。
- G3：两个工具都返回一组固定的、可据以决策的状态（例如 `started`/`completed`/`in_progress`/`no_content`/`not_applicable` 或某个错误码），而不是一个裸的成功/失败布尔值，使调用方的工作流能在不需要人读日志的情况下决定继续、重试还是升级。
- G4：对同一个 source/destination 组合（或同一个用户，对于 sync）重复调用任一工具，都不会产生重复或冲突的操作——超时或工作流重试后的重复调用始终安全，而且**重复调用本身就是查进度的方式**（见技术设计 §1）。

**非目标**（明确列出，依据提单人原话与本设计自己的发现）：
- 为使用经典本地 Azure AD Connect（而非 cloud sync）的租户触发同步——没有任何 Microsoft Graph API 能做到这件事，那是 Connect 服务器本机上的动作（`Start-ADSyncSyncCycle`）。`graph_start_cloud_sync` 对这种情况回报一个明确命名的错误，而不是悄悄什么都不做或谎报成功（AC10）。
- 全量保真的 OneDrive 迁移（权限、分享链接、版本历史、已删除项）。这是对当前根目录项的一次内容复制，精神上与本仓库现有 SharePoint 工具一致（有边界、尽力而为），不是认证级备份/迁移工具。
- 让目的用户成为源用户 OneDrive 的「站点集合管理员」——部分 SharePoint 管理员使用的、转移访问权而非复制内容的替代做法。那个机制属于 SharePoint Online 自己的管理端 REST 接口，不是 Microsoft Graph，需要与本服务当前单一 Graph 客户端不同的令牌受众（技术设计 §3）。
- 构建 offboarding workflow 08/03 本身，或决定它们何时调用这两个工具——本单只新增它们可以调用的 Graph 工具面。
- 目的文件夹的确切命名规则、synchronization-jobs 端点所需的确切 Entra 权限字符串、以及该租户的 cloud-sync job 究竟是哪一个/哪几个，均作为下方「Open Questions」中的明确假设处理，待提单人原话所说的「与 Ginko 确认」。

### 验收标准 AC1..AC12

- AC1：Given 某租户已连接 Microsoft Graph 连接器且某调用方点击了 Refresh Tools，When 该调用方列出该连接器的工具，Then 出现两行新工具——`graph_transfer_onedrive` 与 `graph_start_cloud_sync`——各带一行描述和一个 **Available** 徽标，且现有 39 个工具不受影响。
- AC2：Given 一个 OneDrive 根目录有内容的源用户和一个已存在的目的用户，When 用该源与目的调用 `graph_transfer_onedrive`，Then 调用返回 `status: "started"`，目的用户 OneDrive 下建立（或复用）一个目的文件夹，且每个源根目录项都报告 `action: "copy_started"`。
- AC3：Given 此前已为某 source/destination 组合完成过一次转移（目的文件夹里每个项的名称与大小都与源一致），When 对同一组合再次调用 `graph_transfer_onedrive`，Then 调用返回 `status: "completed"`，且不对任何项发起新的复制（每项报告 `action: "already_present"`）。
- AC4：Given 某次转移里有些项还在复制中（目的文件夹里存在但大小与源不同），且自动化在超时后重试，When 再次调用 `graph_transfer_onedrive`，Then 调用返回 `status: "in_progress"`，这些项被报告为 pending，且不对它们发起重复复制。
- AC5：Given 一个从未被配发过 OneDrive 的源用户，When 用该源调用 `graph_transfer_onedrive`，Then 调用返回一个指明是源的 `drive_not_found` 错误，且目的用户的 OneDrive 不受任何改动。
- AC6：Given 一个 OneDrive 根目录零内容的源用户，When 调用 `graph_transfer_onedrive`，Then 调用返回 `status: "no_content"`，不创建目的文件夹，也不发起任何复制操作。
- AC7：Given 一个不存在或没有配发 OneDrive 的目的用户 id，When 调用 `graph_transfer_onedrive`，Then 调用返回一个指明是目的的 `drive_not_found` 错误，且源不受任何改动。
- AC8：Given 一个目录对象上 `onPremisesSyncEnabled = true` 的用户，且该租户下本 MCP 能发现恰好一个 Azure AD Connect cloud-sync job，When 为该用户调用 `graph_start_cloud_sync`，Then 调用返回 `status: "started"`，并附带解析出的 `job_id`/`service_principal_id`。
- AC9：Given 一个目录对象上 `onPremisesSyncEnabled = false` 的用户（纯云端账号，从未从本地同步过），When 为该用户调用 `graph_start_cloud_sync`，Then 调用返回 `status: "not_applicable"`（不是错误），并说明该用户没有需要同步的内容。
- AC10：Given 某租户下本 MCP 找不到任何可发现的 Azure AD Connect cloud-sync service principal/job（包括但不能确证就是因为该租户改用了经典本地 AD Connect），When 为该租户下 `onPremisesSyncEnabled = true` 的用户调用 `graph_start_cloud_sync`，Then 调用返回 `no_sync_job_configured` 错误，其消息明确说明本 MCP 无法触达经典本地 AD Connect，并点名本地替代方案（在 Connect 服务器上执行 `Start-ADSyncSyncCycle`），而不是报告成功或一个笼统的失败。
- AC11：Given 某租户注册了不止一个 Azure AD Connect cloud-sync job，When 调用 `graph_start_cloud_sync`，Then 调用返回 `sync_job_ambiguous` 错误并列出候选 job，而不是猜一个。
- AC12（多租户锚点）：Given 用两个不同调用方的 Graph access token（两个不同租户）分别调用 `graph_start_cloud_sync`，When 每次调用各自运行 service-principal/job 的发现逻辑，Then 每次发现都针对该次调用自己的 token 重新执行——服务某个调用方 token 时解析出的 service principal 或 job id，不会被缓存、复用，或返回给另一个调用方的 token。

### Open Questions

- [已假设] 「destination account or administrator」（工单原话）理解为：调用方始终提供一个已存在的目的用户 id；不存在与用户 id 区分开的另一种「管理员」身份——管理员也只是另一个目的用户。如果提单人实际想要的是「可选地放进一个不对应真实目的用户的暂存邮箱」，AC2–AC7 与技术设计 §4/§5 需要重做。
- [已假设] 目的地布局：复制的内容落进目的用户 OneDrive 根目录下新建的一个顶层文件夹，命名为 `offboarded-{source_user_principal_name}-{yyyy-mm-dd}`（已做冲突检查，见技术设计 §5）。命名规则如有不同，只影响技术设计 §4/§5；AC2–AC4 的形状不受影响。
- [不阻塞] 「OneDrive content」是否只指物理落在根目录的文件/文件夹，还是也要特殊处理可能出现在个人 OneDrive 里的 Teams/SharePoint 快捷方式，本设计假设后者不在本次范围内（快捷方式不是内容本身，复制它会造成误导）。如果判断有误，技术设计 §4 需要加一条按项类型过滤的规则。
- **[已假设 — 影响重大]** `graph_start_cloud_sync` 只支持使用 Azure AD Connect **cloud sync**（轻量级、基于 agent 的机制，其 job 可通过 Graph 的 `/servicePrincipals/{id}/synchronization/jobs` API 触达）的租户。若租户改用经典本地 AD Connect，本工具完全无法服务——Microsoft Graph 没有任何 API 能触达它。**如果 workflow 08/03 背后的租户实际使用经典 AD Connect，这个工具按当前范围就是不可行的，G2 需要一套完全不同的实现形态**（例如本 MCP 对外暴露一个 webhook，供本地脚本调用——这是完全不同的架构，超出本单范围）。这正是提单人原话已经说明需要 Ginko 确认的那件事；本设计按 cloud-sync 这一假设继续，是因为它是纯 Graph MCP 唯一能触达的机制，而不是因为它已被确认。若此假设有误，AC8/AC10/AC11 与技术设计 §1/§3 需要整体重做，而非打补丁。
- [已假设] 本 MCP 通过查询 `/servicePrincipals` 定位已知的 Azure AD Connect cloud-sync agent 应用，再列出该 service principal 的 `/synchronization/jobs` 来自动发现该租户的 cloud-sync job；若发现不止一个 job 则报 `sync_job_ambiguous`。如果某租户需要调用方显式传入 job id，只影响技术设计 §4/§5。
- [不阻塞] synchronization-jobs 端点所需的确切 Entra 权限字符串（推测为 `Synchronization.Read.All` + `Synchronization.ReadWrite.All`，应用权限）在这次只读阅读中未对照 Microsoft 官方权限参考核实——技术设计 §7 把它列为实现前必须核实的一步，与 PRD-20393 对其 sentinel-default 参数形状所要求的核实属于同一类风险。
- [不阻塞] Microsoft Graph 自己的 synchronization-job `/start` 端点本身是否幂等（已有一次运行在进行中时是否干净地空操作或排队），与本 MCP 自身的单次调用行为（每次调用最多发起一次 `/start`）是两回事——前者是 Microsoft 自己的服务端行为，不由本设计控制，列为风险（§11），不作为既成事实断言。
- [不阻塞] wiki 未覆盖「workflow 08」「workflow 03」具体做了什么（PRD-20393 已记录过同一处缺口）；本设计完全依赖工单自己对两处能力缺口的描述。

## 技术设计

### 结论

在 `ms-graph-mcp` 新增一个 `src/graph_mcp/tools/offboarding.py` 模块承载两个新工具（两者在 `users.py`、`groups.py`、`sites.py` 里都没有自然归属——一个是跨 drive 的复制操作，另一个是目录同步触发，而且两者都和 `graph_remove_manager` 一样是 offboarding 专属，但不属于 `groups.py`）。`graph_transfer_onedrive` 使用 Graph 的异步 `/drives/{id}/items/{id}/copy` 端点，对离职用户 OneDrive 根目录内容做一次幂等的、限定到目的文件夹的复制；由于本服务两次调用之间不保留任何状态（`stateless_http=True`，`server.py:76`），完成与否每次都靠重新列出并按文件名+大小做 diff 来推导，而不是跟踪某个 job id——再次调用这个工具**本身就是查进度**。`graph_start_cloud_sync` 先检查目标用户的 `onPremisesSyncEnabled` 标志，为纯云端用户干净地空操作返回，再通过 `/servicePrincipals/{id}/synchronization/jobs/{jobId}/start` 发现并启动该租户的 Azure AD Connect cloud-sync provisioning job。两个工具都不需要改动 `api_client.py` 现有的请求/响应形状（见 §3「方案选型」里「api_client 改动」一行）——两者都只需要已解析的 JSON 响应体，不需要响应头。

### 现有实现定位

- `src/graph_mcp/tools/sites.py`（全文件）——现有唯一的 `/drives/*` 用法，全部限定在 `/sites/{id}/drive`；`_resolve_site`/`_resolve_drive`/`_resolve_file`（`:46-150`）是本单自己「先解析再动作」辅助函数的直接结构模板，包括「把歧义/缺失情形折进结构化 `error_envelope`」这个模式（`_resolve_site` 的 `site_ambiguous` 分支，`:94-103`，就是本单 `sync_job_ambiguous` 的模板）。
- `src/graph_mcp/tools/groups.py:79-180`——PRD-20393 为列表类工具刻意**否决**的「内部遍历所有页直到上限再停」分页形状（已换成单页单调用）。这条否决不适用于本单：`graph_transfer_onedrive` 是一个要作用到每一项内容的编排型工具，不是让调用方断点续查列表的列表工具，所以在 §5 内部遍历源 drive 根目录所有分页是适合这个不同使用场景的形状。
- `src/graph_mcp/tools/groups.py:106-107`、`:327-328` 以及 `src/graph_mcp/tools/users.py:38`——现有的 `onPremisesSyncEnabled` → `sync_source` 推导逻辑，原样复用于 AC9 的「不适用」判定。
- `src/graph_mcp/api_client.py:124-192`——`GraphClient._request`/`_parse_body`；印证（见现状 §7）响应头今天从不被暴露，这也是 §3「方案选型」明确避免需要它的原因。
- `src/graph_mcp/tools/licenses.py:124-140`（`graph_reprocess_license`）——「触发一个 Graph 侧类异步过程、不等它跑完就返回」这一做法最接近的现有先例；本单两个工具采用同样的姿态。
- `tests/test_tools.py:14-70`（`EXPECTED_TOOLS`）、`:95-129`（工具数量上限，目前 `<= 39`）——需要为两个新工具更新。
- `tests/test_tools.py:1603-1655`（`graph_remove_manager` 的两个测试）——「歧义/未找到折成一个结构化状态而不是崩溃」这一测试形状的直接模板，以及本单新测试原样复用的「带 `.calls` 的假 `GraphClient` 测试框架」（`tests/test_tools.py` 里 `_register` 辅助函数所在的开头部分）。

### 方案选型

| 方案 | 做法 | 优点 | 代价 | 结论 |
|---|---|---|---|---|
| OneDrive 转移——内容复制 | 枚举源 drive 根目录项，通过 Graph 的 `/drives/{id}/items/{id}/copy` 把每一项异步复制进目的文件夹 | 纯 Microsoft Graph，与本仓库已在用于 SharePoint 的 API 族（`/drives/*`）一致；符合工单原话（「Graph-based composite interface」）；服务端复制，字节不经过本 MCP 或调用方的上下文 | 目的地得到的是一份*副本*而非原件——源与目的的 item id 不同；项数多或很大时意味着一次调用里要发很多次串行 Graph 请求（见 §7 性能） | **采用** |

### 数据与接口契约

两者都是 MCP 工具调用契约（JSON-RPC `tools/call`）；本服务自身的 HTTP 契约（`POST /mcp`、`X-Ms-Graph-Token` 头、`GET /health`）不变。

**`graph_transfer_onedrive`**（新增）
- 请求：`{"source_user_id": "...", "destination_user_id": "...", "destination_folder_name"?: string}`
- 响应（成功）：`{"source_user_id", "destination_user_id", "destination_folder": {"id", "name"}, "status": "started"|"in_progress"|"completed"|"no_content", "items": [{"name", "size", "action": "copy_started"|"already_present"}]}`
- 错误：`drive_not_found`（源或目的，`retryable: false`，`extra: {"role": "source"|"destination"}`），以及 `GraphError.to_envelope()` 已有的那套分类（`invalid_argument`/`unauthorized`/`upstream_error`/`rate_limited`，`api_client.py:30-37`）。

**`graph_start_cloud_sync`**（新增）
- 请求：`{"user_id": "...", "sync_job_id"?: string}`
- 响应（成功）：`{"user_id", "status": "started"|"not_applicable", "service_principal_id"?, "job_id"?, "reason"?}`（`reason` 仅在 `not_applicable` 时出现）
- 错误：`not_found`（用户 id 解析不到）、`no_sync_job_configured`（`retryable: false`，消息点名本地 `Start-ADSyncSyncCycle` 替代方案）、`sync_job_ambiguous`（`retryable: false`，`extra: {"candidates": [...]}`），以及上面共享的 `GraphError` 分类。

两个工具都是纯新增——不改变任何现有工具的请求或响应形状。无 DB（本服务没有 DB）。无事件/消息。向后兼容：天然满足，因为这些都是全新的工具名。

### 关键流程时序

**`graph_transfer_onedrive`：**
1. 解析源 drive（`_resolve_drive`，role=`source`）→ `drive_not_found` 短路返回（AC5）。
2. 解析目的 drive（role=`destination`）→ `drive_not_found` 短路返回（AC7）。
3. 列出源 drive 根目录项，内部遍历每一页 `@odata.nextLink`（与 PRD-20393 的列表类工具不同——原因见 §2）。为空 → `status: "no_content"`，返回（AC6）。
4. 解析或创建目的文件夹（`_resolve_or_create_destination_folder`）。
5. 列出目的文件夹当前的子项（`$select=name,size`）。
6. 对每个源项：若目的文件夹里存在同名且 `size` 一致的子项 → `already_present`；若同名但 `size` 不同 → `in_progress`（仍在复制中，不重新发起）；若不存在 → `POST /drives/{source}/items/{id}/copy`，body 带 `parentReference: {driveId: dest, id: destFolderId}` → `copy_started`。
7. 汇总整体 `status`：全部 `already_present` → `completed`；存在 `in_progress` 或新发起的 `copy_started` 与部分 `already_present` 混合 → `in_progress`；全部是新发起的 `copy_started` → `started`。

**`graph_start_cloud_sync`：**
1. `GET /users/{user_id}?$select=onPremisesSyncEnabled` → 404 → `not_found`。
2. `onPremisesSyncEnabled` 为假 → `status: "not_applicable"`，返回（AC9）。
3. 发现该租户的 cloud-sync service principal（`GET /servicePrincipals?$filter=...`，针对已知的 cloud-sync agent 应用——确切 filter 待定，见 Open Questions）→ 若为零或其 job 列表（`GET /servicePrincipals/{id}/synchronization/jobs`）为空 → `no_sync_job_configured`（AC10）；若不止一个 → `sync_job_ambiguous`（AC11）。
4. `POST /servicePrincipals/{spId}/synchronization/jobs/{jobId}/start` → `status: "started"`（AC8）。

### 非功能

- **幂等与并发**：`graph_transfer_onedrive` 自身的幂等性是结构性的（§6 第 6 步——每次调用都从 Graph 实时状态重新推导，没有本地簿记会过期）。`graph_start_cloud_sync` 每次调用最多发起一次 `/start`；Microsoft Graph 自己的 job 引擎是否会对*不同*调用之间的并发 `/start` 去重，是 Microsoft 自己记录的服务端行为，不受本代码控制（§11 标注为风险，不作为既成事实断言）。两个工具都不跨请求缓存任何东西——与本服务不保留状态（`stateless_http=True`）、不持有凭据的既有现状一致（见「现状」）。
- **性能**：`graph_transfer_onedrive` 自身的调用时延主要来自 HTTP 往返次数而非字节量（复制由 Graph 服务端完成）——但这本身就是一个风险：源 OneDrive 根目录项数以百计时，一次调用就要串行发出几百次 Graph 请求，可能逼近本服务自己的 30 秒读超时（`api_client.py:11`，`_TIMEOUT`）。本设计未缓解这一点（列入风险 §11）——后续迭代可以考虑每次调用限制处理的项数、把剩余部分报告为仍待处理交给下次重试，复用同一套幂等机制。
- **安全**：两个工具都和现有每个工具一样，把调用方自己的 bearer token 转发给 Graph——该 token 的租户/scope 是否有权读取指定的源/目的用户的 drive 或 service principal，由 Graph 自己把关，本服务不新增任何授权逻辑。`graph_transfer_onedrive` 是第一个真正使用此前一直闲置的 `Files.*` 权限的工具（见现状 §4）——即便不需要新的授权点击，上线前也值得有一次专门的安全签字确认。
- **多租户隔离**：两个工具的一切解析结果（drive id、service principal id、job id）都在每次调用时现查现用，不在模块或进程级别缓存任何东西，所以不会有某个租户 token 解析出的值泄漏进另一个租户的调用（AC12）。这与现有的「每个请求现建一个 `GraphClient`」模式一致（`server.py:21-25`，`get_client_from_context`）。
- **可观测性**：本仓库今天没有任何日志（`grep -rn "logging\|logger" src/graph_mcp` 零命中）——这不是本单引入的倒退，只是既有的基线。结构化 `error_envelope` 错误码（`drive_not_found`、`no_sync_job_configured`、`sync_job_ambiguous`、`not_applicable`）是唯一的诊断面，与本仓库其它所有工具一致。

### 上线与回滚

本仓库没有任何 feature flag 机制——代码一上线、下次已连接租户的调用方点击 **Refresh Tools**，工具就在了。`graph_transfer_onedrive` 不需要新的租户授权（权限已授予，见现状 §4），一旦本改动合入并部署，对每个已连接租户实际上立刻生效——没有按租户灰度的手段，这一点本身值得提醒审批上线的人（见「非功能」安全一条）。`graph_start_cloud_sync` 需要一个*新*的 Entra 权限（`Synchronization.ReadWrite.All`）；完全照搬本仓库已经记录过的 Mail/Calendar 先例（`README.md:173-174`），已连接租户在（a）平台侧 `msgraph.py` 的 OAuth 并集更新、且（b）每个租户重新授权之前，调用这个工具都会收到 `unauthorized`。回滚就是直接 revert 本单的提交——两个工具自身的代码都不往任何地方写数据（Graph 自己的复制/同步副作用不可被本服务撤销，这与本仓库现有每个写操作工具一致）。

### 风险与依赖

- **影响重大的风险**：整份设计假设 workflow 08/03 背后的租户使用 Azure AD Connect cloud sync，而非经典本地 AD Connect。如果判断有误，`graph_start_cloud_sync` 按当前范围根本做不出来——见上面「影响重大」的 Open Question。缓解：在启动子任务 B 之前先拿到 Ginko 的确认；子任务 A（OneDrive 转移）不依赖这个判断，可以照常推进。
- **权限字符串风险**：service-principal 发现所需的确切 Entra 权限与 cloud-sync agent 应用的过滤字符串，在这次阅读里未对照 Microsoft 官方参考核实（见 Open Questions）。缓解：在子任务 B 开始写发现逻辑之前先核实两者，与 PRD-20393 对其 sentinel-default 参数形状采用的同一套纪律。
- **上线依赖**：`graph_start_cloud_sync` 依赖平台侧 `MCP-Management-Service`（`auth/oauth/vendors/msgraph.py`，本仓库引用但不拥有）把 `Synchronization.ReadWrite.All` 加进已授予权限并集，并依赖每个已连接租户重新授权，否则这个工具会一直返回 `unauthorized`——这不在本仓库控制范围内，与 Mail/Calendar 已记录过的依赖形状相同。
- **性能风险**：源 OneDrive 根目录项数较多时，`graph_transfer_onedrive` 单次调用可能逼近本服务 30 秒读超时（见「非功能」）。对本单的 MVP 不构成阻塞（工单自己的「Minimal Viable Slice」措辞本来就接受一次首版生产实现）；如果真实 offboarding 邮箱的根目录项数很大，列为后续迭代的跟进项。
- 除上面的平台侧权限授予之外，**不依赖任何其它仓库或未完成的工单**。

━━━━━━━━━━
TL;DR：两个被请求的工具（`graph_transfer_onedrive`、`graph_start_cloud_sync`）都可以只用 Microsoft Graph 端点在 `ms-graph-mcp` 里实现，不需要改动共享的 `api_client.py`。OneDrive 转移是一个直接的、权限已就绪的 drive 复制操作，没有架构性阻碍。Cloud sync 有一处影响重大、提单人自己也承认的未知数——真实租户到底用的是 cloud sync（可实现）还是经典本地 AD Connect（Graph 完全触达不了）——本设计把它列为交给 Ginko 的 Open Question，而不是去猜；其余部分都建立在写明、标注清楚的假设之上继续推进。
