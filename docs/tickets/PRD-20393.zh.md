# PRD-20393 · [Feature] Graph offboarding API changes

工单: https://app.clickup.com/t/86e3pjf8w
仓库: https://github.com/MSPbotsAI/ms-graph-mcp@master (ea3c39a)
工作分支: dev01.mbagent/PRD-20393
状态: 进行中

## 需求理解

一句话：为 Graph MCP 工具增加分页能力、组路由元数据、具备补丁语义（patch-safe，省略=不变、显式 null=清空）的用户属性更新（含修改 UPN 前的租户域校验）、移除 manager 的能力，以及更丰富的用户资料读取，使 offboarding workflow 08 与 03 不再需要依赖 Rewst 来弥补这些能力缺口（另外两项——OneDrive 转移与 cloud-sync——按提单人原话明确搁置，待 Ginko 确认后再议）。

提单人需要对现有 5 个 `graph_mcp` 工具做修改、新增 1 个工具，使内部两条 offboarding 自动化流程（workflow「08」与「03」）能够判断某个组应该走 Graph、Exchange 还是 AD 路由，能在不误清空字段的前提下安全地修补用户资料，并能在 offboarding 动作前后完整读取用户的目录属性。提单人自己的访谈记录（见下方引用）已把本单的 MVP 范围限定在原始八项里的第 1–6 项；第 7、8 项（`graph_transfer_onedrive`、`graph_start_cloud_sync`）按提单人原话明确搁置，等待与「Ginko」单独确认，**不在本次设计范围内**。

## 现状（每条陈述均带 path:line 出处）

这是一个没有自己 Web UI 的后端 MCP 服务器；它的「用户」是发起调用的工作流/agent，唯一对终端用户可见的表现是 agent.mspbots.ai Capabilities 页面里该连接器的 **Tools** 列表（当某个调用方已连接到它之后）（wiki: `ProductDocs/15-Capabilities.md` § Connector detail view，_verified_ 2026-08-31，v4.1.518 ——「Tools —— 一个数量徽标，……每个工具一行：等宽字体的工具名、一行描述，以及一个 Available 徽标」；`ProductDocs/_connector-fields.md:134`，_verified_ 2026-08-31 —— 「Microsoft Graph」在本租户已经处于已连接状态，唯一的重新授权入口是 **Reconnect** 而非 **Reconfigure**，且没有 Webhook 按钮）。修改或新增这里的工具，只会改变点击 **Refresh Tools** 之后那份 Tools 列表的内容，不会影响产品其它任何部分。wiki 未覆盖：offboarding「workflow 08」与「workflow 03」自身的具体定义——它们是 `ProductDocs/**` 之外的 SOP/自动化流程定义，不属于 wiki 巡检会走到的 Web UI。

六项需求各自对应的现有代码状态，均已实现但缺少本次要求的改动：

1. **`graph_list_user_groups` 分页** —— 当前靠在内部不断追逐 `@odata.nextLink` 来累积结果，直到达到 `max_results`（默认 50，硬上限 200）或目录耗尽为止，调用方拿不到任何可以在上限之外继续翻页的手段（`src/graph_mcp/tools/groups.py:79-126`）。`$select` 已经包含 `groupTypes` 与 `mailEnabled`（`groups.py:102`），但没有 `onPremisesSyncEnabled`，组路由元数据并不完整。
2. **`graph_list_groups` 分页** —— 同样是「内部累积到上限即停」的形状，调用方侧的限制相同（`groups.py:128-180`）。
3. **`graph_list_users` 分页** —— 形状相同（`src/graph_mcp/tools/users.py:150-218`）。
4. **`graph_update_user` 的补丁安全语义** —— 目前每个可选字段都遵循 `if x is not None: body[key] = x`（`users.py:456-480`），这已经给出了「省略 → 不变」的语义，但它根本没有 `employee_id`、`user_principal_name`、`display_name`、`given_name`、`surname` 这几个参数，而且这份代码库里目前没有任何机制能区分「省略」与「显式设为 null」——两者在 Python 里的默认值都是 `None`，所以今天无法通过这个工具要求 Graph 清空一个字段。
5. **`graph_remove_manager`** —— 不存在。唯一跟 manager 相关的工具是 `graph_assign_manager`，它要求必填 `manager_id`，且永远只会 `PUT` 一个新 manager（`users.py:497-520`）；没有删除路径。
6. **更丰富的 `graph_get_user`** —— 当前 `$select` 返回 `id,displayName,userPrincipalName,mail,accountEnabled,usageLocation,jobTitle,department,mobilePhone,businessPhones,officeLocation,streetAddress,city,state,postalCode,companyName,employeeHireDate,provisionedPlans,assignedLicenses,licenseAssignmentStates`，外加 `$expand=manager($select=id,displayName,userPrincipalName)`（`users.py:392-406`）。它不返回 `proxyAddresses`、`identities`、`employeeId`，也不返回任何 `onPremises*` 字段，且字段集是写死的——没有 `select` 参数可以缩小或扩大它。

有一个直接相关的既有先例，已经完全实现了第 1–3 项要求的那种分页形状：`graph_list_group_members`，在本单提出前一天的提交中加入（commit `ea3c39a`，"feat(groups): paged group members, proxyAddresses lookup, group sync source (PRD-20223)"）。它接受一个可选的 `page_token`，原样作为 Graph 的 `$skiptoken` 查询参数传下去，并通过一个小助手函数从下一页的 `@odata.nextLink` 里提取出 `next_page_token`（`groups.py:28-35` 的 `_skiptoken`，`groups.py:334-380`）。`graph_get_group` 已经用同样的方式，从 `onPremisesSyncEnabled` 推导出 `"on-premises"`/`"cloud"` 的 `sync_source`，正是第 1 项要求 `graph_list_user_groups` 做的事（`groups.py:326-329`）。`graph_list_domains` 已经暴露了租户已验证域名列表，正是第 4 项 UPN 域校验需要的东西（`src/graph_mcp/tools/domains.py:13-39`）。

这个仓库自己的测试套件强制了两件与范围和风险都相关的事：一个快照测试断言了精确的工具名集合与每个工具的必填参数集合（`tests/test_tools.py:14-50` 的 `EXPECTED_TOOLS`，`tests/test_tools.py:84-120` 的 `test_tools_list_snapshot`），同一个测试目前把工具总数硬编码上限在 37（`tests/test_tools.py:120` 的 `assert len(names) <= 37`）——这个仓库今天恰好就是 37 个工具，所以新增 `graph_remove_manager` 必须把这个字面上限往上调，并照着之前每一次递增都用的同一种写法加一行理由注释（见 `test_tools.py:96-119`）。

## 产品设计

### 目标 / 非目标

**目标**（MVP = 提单人自己定的「先出 1.1–1.6」切片）：
- G1：`graph_list_user_groups`、`graph_list_groups`、`graph_list_users` 支持通过分页令牌在一页之外继续翻页，使一个大于一页的目录可以被完整且恰好一次地遍历。
- G2：`graph_list_user_groups` 额外报告每个组的类型、是否启用邮件，以及是否从本地 AD 同步，使调用方无需二次查询即可把一个组路由到 Graph、Exchange 或 AD。
- G3：`graph_update_user` 可以设置 `employee_id`、`user_principal_name`、`display_name`、`given_name`、`surname`，语义为「省略则不变，显式 null 则清空」，并在 `user_principal_name` 的目标域不是已验证租户域时拒绝该次修改。
- G4：调用方可以移除一个用户的 manager 而无需知道或设置替代人选，在该用户本就没有 manager 时执行该操作不应报错。
- G5：`graph_get_user` 能一次性返回足够支撑 offboarding 决策的目录资料（`proxyAddresses`、`identities`、`employeeId`、本地同步属性、manager），且调用方可以把响应缩小到只要的字段。

**非目标**（按提单人自己的访谈记录明确排除在本单之外）：
- `graph_transfer_onedrive`（第 7 项）—— 搁置，待与 Ginko 确认 OneDrive 转移在生产发布中是否仍然需要。
- `graph_start_cloud_sync`（第 8 项）—— 搁置，待与 Ginko 确认实际使用的是哪种同步机制。
- 对 `graph_assign_manager`、`graph_create_user`，或原始八项之外任何工具的改动。
- 构建 offboarding workflow 08/03 本身——本单只改变它们调用的 Graph 工具接口。

### 验收标准 AC1..AC15

- AC1：Given 某用户所属的组数超过一个 Graph 分页能容纳的数量，When 反复调用 `graph_list_user_groups`、首次之后每次都带上上一次响应的 `next_page_token`，Then 该用户所属的每个组在这些调用中恰好出现一次，最后一次调用报告 `has_more=false` 且 `next_page_token=null`。
- AC2：Given 某用户所属的任意一个组，When 调用 `graph_list_user_groups`，Then 响应里每个组条目都包含 `groupTypes`、`mailEnabled`，以及取值为 `"on-premises"` 或 `"cloud"` 的 `sync_source`。
- AC3：Given 某租户的组数超过一个 Graph 分页能容纳的数量，When 按 AC1 同样的方式反复调用 `graph_list_groups` 并串联 `next_page_token`，Then 每个组恰好出现一次，最后一次调用报告 `has_more=false`。
- AC4：Given 某租户的用户数超过一个 Graph 分页能容纳的数量，When 以同样方式反复调用 `graph_list_users`，Then 每个用户恰好出现一次，最后一次调用报告 `has_more=false`。
- AC5：Given 一次 `graph_update_user` 调用里 `employee_id`、`user_principal_name`、`display_name`、`given_name`、`surname` 全部省略，When 该调用执行，Then 这五个属性在目标用户上都不发生变化。
- AC6：Given 这五个属性中恰好一个被显式传入 `null`，When `graph_update_user` 执行，Then 目标用户上该属性被清空，且其它属性不受影响。
- AC7：Given `user_principal_name` 被设置为一个域名不属于该租户已验证域名的地址，When `graph_update_user` 执行，Then 该调用被拒绝并返回 invalid-argument 错误，且用户的 `userPrincipalName` 保持不变。
- AC8：Given `user_principal_name` 被设置为一个属于已验证租户域名的地址，When `graph_update_user` 执行，Then 更新成功，随后的 `graph_get_user` 能看到新的 `userPrincipalName`。
- AC9：Given 某用户已指派 manager，When 调用 `graph_remove_manager`，Then manager 关系被移除，随后的 `graph_get_user` 对该用户不再返回 manager。
- AC10：Given 某用户没有被指派 manager，When 调用 `graph_remove_manager`，Then 调用成功并报告 `no_manager` 状态而非错误，再次调用同样成功。
- AC11：Given 某用户的 `proxyAddresses`、`identities`、`employeeId` 及本地同步属性均有值，When 不带 `select` 参数调用 `graph_get_user`，Then 响应中除了今天已返回的字段外，还包含上述所有字段。
- AC12：Given 一个指定字段子集的 `select` 参数，When 调用 `graph_get_user`，Then 响应恰好包含这些字段（外加 `id`），不包含今天默认字段集里的其它字段。
- AC13：Given 向 `graph_list_user_groups` / `graph_list_groups` / `graph_list_users` 任意一个传入一个无效或已过期的分页令牌，When 调用该工具，Then 它返回既有的结构化错误信封，而不是未处理的异常。
- AC14：Given 调用 `graph_update_user` 时不带任何属性（新旧字段都不带），When 该调用执行，Then 依然按既有的 "Provide at least one attribute to update" 错误被拒绝（回归项——G3 改动的正是这段共享的 body 构造代码）。
- AC15：Given 调用方的访问令牌作用域为租户 A，When 本单涉及的任意一个（修改过的或新增的）工具被传入属于租户 B 的 `user_id`/`group_id`，Then Microsoft Graph 自身会对这次跨租户引用返回 not-found/unauthorized ——本服务器自身不做任何租户校验；隔离完全依赖调用方自带 bearer token 自身的租户作用域。这一条无法用仓库内的 fake Graph client 验证，需要一次真实的双租户核验（见「测试用例」）。

## 技术设计

### 结论

把三个既有的列表工具（`graph_list_user_groups`、`graph_list_groups`、`graph_list_users`）扩展到 `graph_list_group_members` 已经在用的同一套分页契约（`page_token` 入参、`next_page_token` 出参，复用既有的 `_skiptoken` 助手）；给 `graph_update_user` 新增五个带补丁安全语义的可选参数，用一个哨兵默认值区分「省略」与「显式 null」，并在改动前对照 `graph_list_domains` 自身的逻辑做一次预检；新增一个工具 `graph_remove_manager`，照搬 `graph_remove_group_member` 的「对已不存在的状态幂等」模式；给 `graph_get_user` 的 `$select` 加宽并提供一个可选的 `select` 覆盖参数。六项改动全部落在 `ms-graph-mcp` 一个仓库内，涉及两个既有文件（`tools/groups.py`、`tools/users.py`）及其共享助手（`tools/_common.py`）与测试套件，不需要新依赖、不涉及数据库，也不涉及其它仓库。

### 数据与接口契约

六项改动全部是 MCP 工具调用契约（JSON-RPC `tools/call`），不是这个服务器自己的 REST 面——服务器自身的 HTTP 契约（`POST /mcp`、`X-Ms-Graph-Token` 请求头、`GET /health`）不变。

**`graph_list_user_groups`**（修改）
- 请求：`{"user_id": "...", "max_results"?: int, "page_token"?: string}`
- 响应（变化）：`{"user_id", "count", "groups": [{..., "groupTypes", "mailEnabled", "sync_source": "on-premises"|"cloud", ...}], "has_more": bool, "next_page_token": string|null}` —— `has_more`/分页语义现在与 `graph_list_group_members`（每次调用一个 Graph 分页）一致，而不是今天的「内部累积到 max_results」。

**`graph_list_groups`**（修改）—— 同样的 `page_token` 入参 / `next_page_token` 出参；组对象字段不变。

**`graph_list_users`**（修改）—— 同样的 `page_token` 入参 / `next_page_token` 出参；用户对象字段不变。

**`graph_update_user`**（修改）
- 请求新增：`{"employee_id"?: string|null, "user_principal_name"?: string|null, "display_name"?: string|null, "given_name"?: string|null, "surname"?: string|null}` —— 省略 = 不变，`null` = 清空，字符串 = 设置。
- 新错误：当 UPN 的域名未通过校验时，`{"error": {"code": "invalid_argument", "message": "userPrincipalName domain '<domain>' is not a verified domain for this tenant.", "retryable": false}}` —— 与这份代码库里其它任何 `invalid_argument` 用的是同一个信封格式（`src/graph_mcp/_json.py` 的 `error_envelope`，到处都在用）。
- Graph PATCH body：`employeeId`、`userPrincipalName`、`displayName`、`givenName`、`surname` —— 都是标准的 Entra 用户属性，在 Graph 一侧均可为空。

**`graph_remove_manager`**（新增）
- 请求：`{"user_id": "..."}`
- 响应：`{"status": "removed", "user_id": "..."}` 或 `{"status": "no_manager", "user_id": "..."}`
- Graph 调用：`DELETE /users/{id}/manager/$ref` → `204`（已移除）或 `404`（本就不存在，映射为 `no_manager` 而非报错）。

**`graph_get_user`**（修改）
- 请求新增：`{"select"?: list[string]}` —— 提供时替代默认 `$select` 列表（服务器始终包含 `id`）。
- 响应新增（`select` 省略时的默认情形）：`proxyAddresses`、`identities`、`employeeId`、`onPremisesSyncEnabled`、`onPremisesLastSyncDateTime`、`onPremisesDistinguishedName`。

**向后兼容**：每个新参数都是可选且增量式的；没有任何既有必填参数或响应字段被移除。唯一可能被现有调用方察觉的行为变化是三个列表工具的分页契约切换（见「方案选型」与 Open Questions）——从未超出旧内部累积逻辑有效页大小的调用方不会察觉差异；超出过的调用方现在需要跟进 `next_page_token`，而不是一次拿到全部结果。

### 关键流程时序

补丁安全的 UPN 修改（`graph_update_user` 带 `user_principal_name`）：

1. 调用方 → `graph_update_user(user_id, user_principal_name="alice@newdomain.com", ...)`
2. 服务器 → `_verified_domains(client)` → Graph `GET /domains?$select=...&isVerified`（与 `graph_list_domains` 发起的是同一个调用）
3. 服务器核对 `newdomain.com` 是否在已验证集合里。
   - 未验证 → 返回 `invalid_argument` 信封；**不向 Graph 发送 PATCH**。
   - 已验证 → 继续。
4. 服务器把每个非 `_UNSET` 字段构造进 PATCH body（显式的 `null` 也作为 JSON 里的 `null` 带入）→ Graph `PATCH /users/{id}`
5. Graph → `200`/`204` → 服务器返回 `{"status": "success", "user_id", "updated": [...]}`（既有响应格式，不变）。

分页（以 `graph_list_users` 为代表；`graph_list_groups`/`graph_list_user_groups` 形状相同）：

1. 调用方 → `graph_list_users(max_results=50)`（不带 `page_token`）
2. 服务器 → Graph `GET /users?$top=50&$select=...`（不带 `$skiptoken`）
3. 服务器从响应的 `@odata.nextLink` 提取 `next_page_token`（`_skiptoken`），返回 `{"users": [...], "has_more": true, "next_page_token": "..."}`
4. 调用方 → `graph_list_users(max_results=50, page_token="...")`
5. 服务器 → Graph `GET /users?$top=50&$select=...&$skiptoken=...` → 重复直到 `has_more=false`。

### 非功能

- **幂等与并发**：`graph_remove_manager` 天然幂等（404→`no_manager`，与 `graph_remove_group_member` 既有的 404 处理一致）——连续调用两次，或与另一次移除并发调用，都会收敛到同一个终态且两条路径都不报错。`graph_update_user` 的 PATCH 本身对并发写入并不幂等（后写覆盖前写，与今天一致），本单不改变这一点。
- **性能**：没有引入新的 N+1 模式——分页改动反而减少了每次调用的服务器端工作量（一个 Graph 分页，而不是最多翻 `_HARD_CAP_MAX_RESULTS=200` 条对应的若干页）；UPN 域校验只给真正设置了 `user_principal_name` 的 `graph_update_user` 调用多加一次 Graph 调用（`/domains`），不影响其它调用。
- **安全**：没有新增鉴权面——每个工具仍然在调用方自己的逐请求 bearer token 下运行（`server.py` 的 `GatewayTokenMiddleware`/contextvar），`graph_remove_manager` 所需权限不超过 `graph_assign_manager` 已经要求的那一类（Graph 应用注册里 `User.ReadWrite.All` 级别的权限）。UPN 域校验是对误输入或恶意跨域改名的一道安全带，不是一道安全边界——拒绝未验证域名只是让这个错误在我们这里被更清楚地拒绝，而不是等 Graph 自己返回一个含糊的错误。
- **多租户隔离**：这个服务器本来就没有自己的隔离逻辑，本单也不新增——每次 Graph 调用都由调用方自己的 bearer token 限定作用域，而这个 token 的租户作用域是由 Microsoft 限定的，不是由这份代码决定的（见 AC15；这是整个服务器既有的架构属性，不是本单改变或能够改变的）。
- **可观测性**：不新增超出 `GraphClient` 既有重试/错误路径（`api_client.py:140-170`）之外的日志——被拒绝的 UPN 域名修改和 `no_manager` 结果都会在工具自身的响应里返回给调用方，这是这份代码库既有的模式（错误是响应里的信封，不是服务器端日志），与文件里其它任何工具一致，不是本单新引入的缺口。

### 上线与回滚

没有 feature flag——这个服务器本来就没有，本单的每一项改动要么是增量式的（新增可选参数、新增一个工具），要么是「小结果集下输入输出不变」的分页形状切换。上线走 `ms-graph-mcp` 的常规发布：合并 → 镜像重新构建 → 重新部署该 gateway-mode 服务器。回滚即还原镜像；不存在数据迁移，因为这个服务器不持有任何持久状态。回滚唯一可能在运行中造成影响的是分页契约的切换——如果某个调用方在回滚前已经开始依赖新的 `next_page_token` 形状，回滚后它需要退回旧的 max_results 语义，这是调用方侧的代码路径问题，不是数据安全问题。

### 测试策略

本单的一切都可以针对仓库既有的 `_CapturingClient` fake（`tests/test_tools.py:150-204`）做单元测试——它只记录请求的 method/path/params/body，不真正调用 Graph，这份文件里每一个既有工具都是这么测的（例如 `test_list_group_members_returns_only_the_skiptoken`，`tests/test_tools.py:1219-1238`），所以 AC1–AC14 不需要任何新的测试基础设施。AC15（真正的跨租户隔离）无法针对 fake client 执行——它需要两个真实的 Entra 租户，在下方用例里标为手工用例，执行一次、留痕，之后作为一条常设的架构事实而不是每次发布都要跑的回归检查。

回归面：`graph_update_user` 既有的「不带任何属性即拒绝」行为（AC14）与 `graph_list_group_members` 已经上线的分页测试必须原样继续通过——本单是在扩展同一套代码路径（`_skiptoken`、`if x is not None` 的 body 构造模式），而不是替换它们。

### 风险与依赖

- **风险**：哨兵默认值方案（「方案选型」）区分「省略」与「显式 null」的做法，尚未针对已安装的 `mcp[cli]>=1.9.0` SDK 的实际参数绑定行为做过验证。缓解措施：子任务 2 的第一步应先写一个一次性的探针测试，确认该 SDK 确实把「参数缺失」和「参数=null」还原成两个不同的 Python 值，再在这个假设之上构建 `graph_update_user` 的其余逻辑。如果验证不通过，退回「方案选型」里的 `clear_X` 布尔形状。
- **风险**：把三个列表工具的分页契约切换（「方案选型」，分页形状 B）可能会让某个假设「一次调用拿到 max_results 以内全部结果」的外部调用方感到意外。缓解措施：已在 Open Questions 与工单「结论」一行里显式点出，供 groom 在本单上线前确认没有已知调用方依赖旧形状。
- **依赖**：不依赖其它工单或仓库。第 7、8 项（本单的非目标）在「同属一个父需求」的意义上算是一种软依赖，但它们既不阻塞本单，也不被本单阻塞。
