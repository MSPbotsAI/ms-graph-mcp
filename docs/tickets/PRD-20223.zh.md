## 需求理解

一句话：升级 Microsoft Graph MCP 技能，使其能够分页列出一个组的成员、按 ID 查询组详情（含是否启用邮件、同步来源）、列出租户域名、以及通过 proxyAddresses 检查用户是否存在——补齐阻碍 Ginko 从 Rewst 迁移到 MSPbots 达成功能对等（提单人目标为 11 月 7 日）的四处缺口。

负责 Ginko 迁移的开发者需要仅用这个 Graph MCP 的工具,复现 Rewst 现有自动化已经在做的四类目录查询。当前工具集覆盖的是相邻但不同的问题(按显示名搜索组、列出用户自己所属的组、按精确 UPN/邮箱核实用户是否存在),而且完全没有域名列表工具。提单人明确确认这四项必须一起交付,不接受部分切片——见工单「Minimal Viable Slice」与「Priority」两节(提单人设为 High:"blocks parity ... for the Nov 7 migration goal")。

## 现状(每条陈述都带 path:line)

- `graph_list_groups`(`src/graph_mcp/tools/groups.py:118-169`)按显示名搜索/列出组;不接受组 ID,也不返回某个组的成员列表。
- `graph_list_user_groups`(`groups.py:69-115`)与 `graph_list_owned_groups`(`groups.py:171-250`)都是从**用户**这一侧走组成员关系(用户所属的组/用户拥有的组);没有工具从**组**这一侧走(这个组里有谁)。
- 没有工具能按 ID 取某个组的完整详情。最接近的是 `graph_list_groups`/`graph_list_user_groups` 内部的 `$select`(`id,displayName,groupTypes,securityEnabled,mailEnabled`),已经证明 `mailEnabled` 是可读的——只是没有一个按 ID 查询的工具把它暴露出来,而 `onPremisesSyncEnabled` / `onPremisesLastSyncDateTime`(工单要的"同步来源")在本文件里哪里都没被 select 过。
- `src/graph_mcp/tools/` 下完全没有 `domains.py`——该目录的完整模块列表是 `calendar.py, devices.py, groups.py, licenses.py, mail.py, sites.py, users.py`(目录列表实测确认)。租户域名列表在本仓库里没有任何现成入口。
- `graph_check_user_exists`(`src/graph_mcp/tools/users.py:32-72`)只接受 `user_principal_name` 或 `mail` 两者之一,走精确 `$filter` 匹配;没有 `proxy_address` 参数,整个仓库也没有 `proxyAddresses/any(...)` 这类过滤(`grep -rn "proxyAddress" src/` → 零命中)。
- 权限证据(只读参考,另一个仓库,本单不要求在那里改代码):`https://github.com/MSPbotsAI/mcp-service-gateway@release (5719ab2)`,`mspbots-mcp-manager/mcp_manager/auth/oauth/vendors/msgraph.py:120-129`——平台对这个连接器固定申请的 OAuth 同意里,已经包含 `Group.Read.All`、`GroupMember.Read.All`、`GroupMember.ReadWrite.All` 和 `Directory.Read.All`。同一个文件 69-72 行的注释写明 `Directory.Read.All` 是"operator-added ... No tool requires it — it is here to match the app registration."(运维额外加的,当前没有工具用到,只是为了跟 app 注册的授权集合对齐)。Microsoft Graph 的 `GET /domains` 刚好能被 `Directory.Read.All` 满足。**后果:域名列表功能不需要任何新的平台侧授权,也不需要租户重新授权**——这和 `Mail.Read` / `Calendars.ReadWrite` 那两批上线(本仓库 README § Known Gaps,PRD-19103 / PRD-18631)不同,那两批确实需要在那个文件里扩大 scope,且每个已连接的租户都要重新授权工具才能用。
- 产品 UI 证据:wiki `ProductDocs/15-Capabilities.md § Connector detail view`(`_verified_ 2026-08-31, v4.1.518`)——连接器的工具清单是"Tools provided at run time by the MCP gateway once this connector is connected"(连接器一连上,工具清单就由 MCP 网关在运行时提供),详情页上带一个 **Refresh Tools** 控件。所以这四个工具一旦实现并部署,会直接出现在 Capabilities > Connectors > Microsoft Graph 里,不需要任何额外的平台 UI 改动。
- wiki 缺口:没有任何 `ProductDocs` 页面覆盖这个 MCP server 自己的工具目录(它是面向 agent 的工具接口,不是终端用户可见页面,走查式产品文档本来就不适用这类对象);"Ginko" 和 "proxyAddresses" 在 wiki 里零命中——这两个都是预期之内的缺失(Ginko 是外部客户名,proxyAddresses 是 Graph API 层面的细节),不说明任何问题。

## 产品设计

### 目标 / 非目标

目标:
- G1:agent 能分页列出某个 Entra ID 组的成员,遵循仓库现有的分页约定(默认 50 / 硬顶 200 / `has_more`)。
- G2:agent 能按组的 object ID 查询该组详情,包含是否启用邮件、以及是否本地同步("同步来源")。
- G3:agent 能列出租户已注册的域名。
- G4:agent 能通过 proxy address(而不只是主 UPN/邮箱)检查用户是否存在——匹配 Rewst 现有自动化的行为。
- G5(提单人要求):四项一起随同一个发布交付,不接受部分切片。

非目标:
- NG1:对组、域名或 proxyAddresses 的任何写/变更操作——工单「Desired Behavior」一节只要求查询,四项能力均为只读。
- NG2:平台侧(`mcp-service-gateway`)的任何改动——根据上面「现状」的证据不需要,且那个仓库不是本单的 Code Project。
- NG3:Rewst 那一侧的任何改动——本单范围只限 MSPbots 自己的 Graph 技能。

### 验收标准 AC1..AC5

- AC1:Given 一个成员数超过请求页大小的组,When agent 调用组成员工具并传 `max_results=N`,Then 最多返回 N 个成员且 `has_more=true`;When `max_results` 大于等于该组成员总数,Then `has_more=false` 且每个成员恰好返回一次。
- AC2:Given 一个合法的组 object ID,When agent 调用组详情工具,Then 返回内容包含该组的显示名、是否启用邮件、以及本地同步状态(本地 AD 同步 vs 纯云端,同步时还带最后同步时间);When 该 ID 查不到对应的组,Then 工具返回 not-found 错误,而不是一个空的成功结果。
- AC3:Given 不带任何过滤条件,When agent 调用域名列表工具,Then 返回该租户注册的全部域名,并附带每个域名的已验证/默认/认证类型标记;When 租户域名列表为空,Then 返回空列表而不是错误。
- AC4:Given 一个 proxy address 字符串(例如不是用户主邮箱或 UPN 的次要 SMTP 别名),When agent 用这个值调用存在性检查工具,Then 若有任意用户的 `proxyAddresses` 集合包含该值,返回 `exists=true` 及该用户的基础档案,否则返回 `exists=false`。
- AC5:Given 上述四个工具已实现并部署,When 租户管理员打开 Capabilities > Connectors > Microsoft Graph > Tools 并点击 **Refresh Tools**,Then 四个新工具出现在清单里,不需要任何其它平台改动(wiki:`ProductDocs/15-Capabilities.md § Connector detail view`)。

### 4.1 主流程

agent 先通过现有工具(例如 `graph_list_groups`、`graph_check_user_exists`)解析出一个组或用户,再用该 ID 调用四个新/扩展工具之一来回答具体问题(这个组里有谁 / 这个组的详情是什么 / 租户有哪些域名 / 这个别名是不是属于某个人)——与本仓库 README「Typical Workflows」里已经写明的"先解析、再操作"模式(如 `graph_list_user_groups` → `graph_assign_groups`)一致。

### 4.2 界面与交互变化

通常意义上的 UI 不适用——本仓库没有终端用户画面。唯一的用户可见界面是 Capabilities > Connectors > Microsoft Graph 的工具列表(见 AC5),它会自动更新;不新增、也不改动任何对话框、字段或控件。

### 4.3 边界与异常

- 空组(零成员)→ 返回空列表,`has_more=false`,不是错误。
- 不存在的组 ID(列成员和按 ID 查详情都适用)→ 返回 `not_found` 错误(复用现有 `GraphError`/404 → `not_found` 映射),绝不能是空的成功结果——调用方必须能区分"没有成员"和"根本没这个组"。
- 域名数为 0 或 1 的租户 → 列表照常正确返回;Graph 的 `/domains` 端点不需要特殊处理。
- proxy address 值里带单引号等 OData 敏感字符(例如 `O'Brien's alias`)→ 必须按本仓库现有每一个 `$filter` 字面量的处理方式转义(`odata_quote`),否则查询会 400。
- proxy address 查无此人 → 返回 `exists=false`,不是错误(与今天 `graph_check_user_exists` 对不存在的 UPN/邮箱的行为一致)。

### 4.4 权限与多租户

本仓库的租户隔离模型不受影响:四个工具和现有全部 32 个工具一样,都是通过 `X-Ms-Graph-Token` 请求头按次接收调用方自己的 Graph 访问令牌,靠 `contextvars.ContextVar` 按请求隔离(`src/graph_mcp/server.py` 的 `GatewayTokenMiddleware`),每一次经 `GraphClient` 发出的 Graph 调用只带那一个令牌(`src/graph_mcp/api_client.py:69-77`)。没有按租户缓存或共享的 client,所以一个租户的令牌不可能通过这几个新工具泄露另一个租户的组/用户/域名数据。也不需要申请新 scope(见「现状」)——`Directory.Read.All` 已经是当前同意集合里权限最广的一项,且目前尚未被任何工具使用。

## 5. 范围切分

MVP = 四个工具全部,这是提单人明确的不可谈判项("ship all four together");本单不应产出更小的切片。未来某次迭代(不在本单)如果出现写支持的需求(例如改一个域名的联邦设置),可以再加——目前没有这样的需求被提出。

### 数据与接口契约

**`graph_list_group_members`**
- 请求:`group_id: str`(必填),`max_results: int = 50`(硬顶 200,与其它列表工具一致)。
- Graph 调用:`GET /groups/{group_id}/members?$select=id,displayName,userPrincipalName,mail&$top=<page_size>`,跟随 `@odata.nextLink` 直到达到 `max_results` 或没有更多页。
- 返回:`{"group_id": "...", "count": 3, "members": [{"id": "...", "displayName": "...", "userPrincipalName": "...", "mail": "...", "member_type": "user"}], "has_more": false}`。
- 错误:`group_id` 不存在 → Graph 404 → `{"error": {"code": "not_found", "message": "...", "retryable": false}}`(现有映射,不变)。

**`graph_get_group`**
- 请求:`group_id: str`(必填)。
- Graph 调用:`GET /groups/{group_id}?$select=id,displayName,description,mail,mailEnabled,mailNickname,securityEnabled,groupTypes,visibility,onPremisesSyncEnabled,onPremisesLastSyncDateTime,onPremisesSamAccountName`。
- 返回:`{"id": "...", "displayName": "...", "mailEnabled": true, "mail": "...", "securityEnabled": false, "groupTypes": ["Unified"], "sync_source": "cloud-only", "onPremisesSyncEnabled": null, "onPremisesLastSyncDateTime": null}`。
- 错误:`group_id` 不存在 → `not_found`(同样映射)。

**`graph_list_domains`**
- 请求:无参数。
- Graph 调用:`GET /domains?$select=id,isDefault,isVerified,isAdminManaged,authenticationType`。
- 返回:`{"count": 2, "domains": [{"id": "contoso.com", "isDefault": true, "isVerified": true, "isAdminManaged": true, "authenticationType": "Managed"}, ...]}`。
- 错误:除了现有通用 `GraphError` 映射外没有特别的(例如令牌所在租户万一缺了已授予的 scope 导致 `403`——按「现状」不应该发生,但现有 `unauthorized` 映射已经防御性地覆盖了这种情况)。

**`graph_check_user_exists`(扩展后)**
- 请求:`user_principal_name`、`mail`、`proxy_address` 三者恰好传一个。
- Graph 调用(新增分支):`GET /users?$filter=proxyAddresses/any(x:x eq '<odata_quote(proxy_address)>')&$count=true&$select=id,displayName,userPrincipalName,mail,accountEnabled`,请求头 `ConsistencyLevel: eventual`。
- 返回:形状不变——`{"exists": true, "user": {...}}` 或 `{"exists": false, "user": null}`。
- 错误:`user_principal_name`/`mail`/`proxy_address` 传了 0 个或 2 个以上 → `{"error": {"code": "invalid_argument", "message": "Provide exactly one of user_principal_name, mail, or proxy_address.", "retryable": false}}`。
- 向后兼容:只传 `user_principal_name` 或 `mail` 的现有调用方不受影响——新分支只在传了 `proxy_address` 时才激活。

没有数据库、没有迁移脚本、没有事件/消息改动——本仓库没有持久化层(是一个无状态的 Graph 网关)。

### 关键流程时序

1. agent 解析出一个组 ID(例如通过 `graph_list_groups`)或已经从上一步拿到。
2. agent 调用 `graph_list_group_members(group_id, max_results=50)`。
3. `GraphClient.get("/groups/{id}/members", params={...})` → Graph API。
4. 如果存在 `@odata.nextLink` 且未达 `max_results`,工具跟随它继续取(与 `graph_list_groups` 同样的循环形状)。
5. 工具把 `{members, has_more}` 返回给 agent。

(按 ID 查组、列域名、proxy-address 检查都是同一形状的单次请求变体——第 3-5 步收敛成一次调用,没有循环。)

### 非功能

- **幂等与并发**:四项都是只读 GET,没有状态变更;任意并发调用都安全;不需要协调。
- **性能**:`/groups/{id}/members` 对大组可能很长——在 `max_results`(硬顶 200)处截断并停止,与 `graph_list_groups`/`graph_list_user_groups` 一致;刻意**不采用** `graph_list_owned_groups` 那种 N+1 全量扫描形状(那个工具没有替代方案;这个有,因为对一个**已知**组 ID 做原生成员列举,不存在逼出那个 N+1 设计的"按 owner 过滤不了"的问题)。
- **安全**:不需要申请任何新权限(复用已授予的 scope,见「现状」)。proxy-address 过滤必须像今天 `mail`/`display_name` 过滤一样复用 `odata_quote`(`_common.py:8-16`)——跳过这一步会让单引号或构造过的值破坏或操纵 `$filter` 子句。相关的 OWASP API Top-10 条目:API3:2023(对象属性级别授权缺失/过度数据暴露)——匹配成功时只返回 `graph_check_user_exists` 今天已经返回的那几个最小档案字段(`id, displayName, userPrincipalName, mail, accountEnabled`),不返回完整的 `proxyAddresses` 集合,这样这个查询就不能被用来枚举一个用户的其它别名。
- **多租户隔离**:不受影响——见产品设计 §4.4;每次调用都由调用方自己的按请求令牌限定范围,和现有全部 32 个工具一致。
- **可观测性**:原样复用现有 `GraphError` → `error_envelope` 映射;本仓库本来就没有超出 `httpx`/`GraphClient` 之外的工具级日志,所以相对仓库现状不引入新的缺口。

### 上线与回滚

- 本仓库没有 feature flag 机制(`config.py`/`server.py` 确认干净,没有任何 flag 基础设施)——按正常版本号升级发布即可;四项改动都是增量的(三个新工具 + 一个新的可选参数),不改变任何现有 agent 可见行为。
- 这几个工具生效前**不需要**任何平台侧(`mcp-service-gateway`)改动(见「现状」)——与 `Mail.Read`/`Calendars.ReadWrite` 的先例不同,这里没有"已连接租户必须重新授权"这一步。
- 建议顺序:实现 → 扩展 `EXPECTED_TOOLS`/抬高硬顶断言 → 合并 → 部署 → 租户管理员在 Microsoft Graph 连接器上点 **Refresh Tools**(wiki:`ProductDocs/15-Capabilities.md`),四个新工具立即可用。
- 回滚:回退 commit / 重新部署上一个镜像。工具从 MCP 能力列表里消失是安全的——agent 只是看不到它们了,不会破坏任何现有功能,因为对现有工具(`graph_check_user_exists`)的唯一改动是一个向后兼容的可选参数。

### 测试策略

- **单测/快照**(不碰网络):扩展 `tests/test_tools.py` 的 `EXPECTED_TOOLS` 和硬顶断言——现成模式,不需要新基础设施。
- **Mock client 测试**:复用 `test_tools.py` 里现有的 `_CapturingClient` 模式,断言每个新/改工具构造出正确的 Graph 请求——路径、`$select`/`$filter` 内容,尤其是 proxy-address 调用必须带上 `ConsistencyLevel: eventual` 和 `$count=true`——全程不碰真实租户。
- **发布前必须做真实租户的人工验证**(与本仓库 README「Known Gaps」里对每一批工具的既有告诫一致):需要 (a) 一个成员数超过一页的真实组,(b) 一个真实 AD 同步组和一个真实纯云端组来核对 `sync_source` 的派生逻辑,(c) 该租户真实的域名列表来核对 `graph_list_domains` 的输出,(d) 一个带真实次要 proxy address 的真实用户来确认这个租户/这个 Graph 版本确实按文档接受这个高级查询语法——微软的高级查询行为在这个仓库里已经出现过不符合文档的租户特定边界情况(见 README「Known Gaps」里 `graph_list_owned_groups` 的 delta 端点分页 bug 那段故事),所以这是本设计标记的最高风险验证项。
- **回归**:四项改动中,除了 `graph_check_user_exists` 那个增量可选参数外,没有改动任何现有工具的请求形状——重跑现有全部测试套件确认。

### 工作量与拆分

- 1.5–2.5 人日:`domains.py`(最小,约 0.25 天)+ 组成员与按 ID 查组(约 0.75 天,同一文件,形状与现有代码类似)+ proxy-address 扩展(约 0.5 天,高级查询请求头需要格外小心)+ 测试更新(约 0.5 天)+ README 表格/Known-Gaps 更新(约 0.25 天)。

### 风险与依赖

- **R1(已核实,低)**:不存在平台侧 scope/同意依赖——见「现状」对 `mcp-service-gateway` 的 `msgraph.py` 的引用。特意点明这一条,避免评审默认套用 `Mail.Read`/`Calendars.ReadWrite` 那种"需要重新授权"的模式——这里不适用。
- **R2(中)**:Graph 对多值、非索引属性(如 `proxyAddresses`)做过滤要求的高级查询(`ConsistencyLevel: eventual`)是文档记录的 Graph API 行为,但本仓库此前从未用过(`grep -rn "ConsistencyLevel" src/` → 零命中)——这是本代码库第一次用这个模式。主要技术风险;缓解办法是合并进 release 分支前先做真实租户验证,如果合并时还没验证完,按仓库惯例在 README「Known Gaps」补一条。
- **R3(低)**:`/groups/{id}/members` 可能返回嵌套组和服务主体,不只是用户——`member_type` 不能假定每一行都是用户。
- **依赖**:不依赖其它在途工单。`mcp-service-gateway` 仅作为只读证据引用;本单不要求在那里做任何代码改动。
