## Requirement understanding

One line: Add pagination, group-routing metadata, patch-safe user-attribute updates (with tenant-domain validation on UPN changes), manager removal, and richer user-profile retrieval to the Graph MCP tools, so offboarding workflows 08 and 03 no longer need Rewst for these gaps (two further items — OneDrive transfer and cloud-sync — are explicitly deferred pending Ginko confirmation).

The reporter needs five existing `graph_mcp` tools modified and one new tool added so that two internal offboarding automations (workflows "08" and "03") can decide whether a group should be routed through Graph, Exchange or AD, can safely patch a user's profile without accidentally clearing fields that were not meant to change, and can fully read a user's directory attributes before and after offboarding actions. The reporter's own interview log (quoted below) scopes this ticket's MVP to items 1–6 of the eight originally listed; items 7–8 (`graph_transfer_onedrive`, `graph_start_cloud_sync`) are explicitly held pending a separate confirmation with "Ginko" and are **out of scope** for this design.

## Current state (every claim carries path:line)

This is a backend MCP server with no web UI of its own; its "user" is the calling workflow/agent, and its only end-user-visible surface is the per-connector **Tools** list shown in the agent.mspbots.ai Capabilities page once a caller is connected to it (wiki: `ProductDocs/15-Capabilities.md` § Connector detail view, _verified_ 2026-08-31, v4.1.518 — "Tools — a count badge, ... one row per tool: the tool name in monospace ..., its one-line description, and an Available badge"; `ProductDocs/_connector-fields.md:134`, _verified_ 2026-08-31 — "Microsoft Graph" is already connected in this tenant, and the only re-auth entry point is **Reconnect**, not **Reconfigure**, with no Webhook button). Changing or adding a tool here changes what that Tools list shows after a **Refresh Tools**; it does not change any other part of the product UI. wiki not covered: the internal definitions of offboarding "workflow 08" and "workflow 03" themselves — those are SOP/automation definitions outside `ProductDocs/**`, not web UI the wiki patrol walks.

Code-level state of the six requested capabilities, each already implemented without the requested change:

1. **Pagination, `graph_list_user_groups`** — currently returns up to `max_results` (default 50, hard cap 200) by internally walking every `@odata.nextLink` page until that cap is hit or the directory is exhausted, then stops; the caller gets no way to resume beyond the cap (`src/graph_mcp/tools/groups.py:79-126`). The $select already includes `groupTypes` and `mailEnabled` (`groups.py:102`) but not `onPremisesSyncEnabled`, so group-routing metadata is incomplete.
2. **Pagination, `graph_list_groups`** — identical internal-walk-then-stop shape, same caller-side limitation (`groups.py:128-180`).
3. **Pagination, `graph_list_users`** — identical shape (`src/graph_mcp/tools/users.py:150-218`).
4. **Patch-safe `graph_update_user`** — today every optional field follows `if x is not None: body[key] = x` (`users.py:456-480`), which already gives "omitted → unchanged" for the fields it has, but it has no `employee_id`, `user_principal_name`, `display_name`, `given_name` or `surname` parameters at all, and nothing in the codebase currently distinguishes "omitted" from "explicitly set to null" — `None` is the Python default for both, so there is no way today to ask Graph to *clear* a field via this tool.
5. **`graph_remove_manager`** — does not exist. The only manager-related tool is `graph_assign_manager`, which requires `manager_id` and only ever `PUT`s a new manager (`users.py:497-520`); there is no delete path.
6. **Richer `graph_get_user`** — the current `$select` returns `id,displayName,userPrincipalName,mail,accountEnabled,usageLocation,jobTitle,department,mobilePhone,businessPhones,officeLocation,streetAddress,city,state,postalCode,companyName,employeeHireDate,provisionedPlans,assignedLicenses,licenseAssignmentStates` plus an `$expand=manager($select=id,displayName,userPrincipalName)` (`users.py:392-406`). It does not return `proxyAddresses`, `identities`, `employeeId`, or any `onPremises*` field, and the field set is fixed — there is no `select` parameter to narrow or widen it.

One directly relevant existing precedent already ships the exact pagination shape items 1–3 ask for: `graph_list_group_members`, added one day before this ticket was filed (commit `ea3c39a`, "feat(groups): paged group members, proxyAddresses lookup, group sync source (PRD-20223)"). It takes an optional `page_token`, passes it through as Graph's `$skiptoken` query parameter, and returns `next_page_token` extracted from the next page's `@odata.nextLink` via a small helper (`groups.py:28-35` `_skiptoken`, `groups.py:334-380`). `graph_get_group` already derives a `sync_source` of `"on-premises"`/`"cloud"` from `onPremisesSyncEnabled` the same way item 1 asks `graph_list_user_groups` to (`groups.py:326-329`). `graph_list_domains` already exposes the tenant's verified domains needed for item 4's UPN-domain check (`src/graph_mcp/tools/domains.py:13-39`).

The repo's own test suite enforces two things that matter for scope and risk: a snapshot test asserts the exact tool-name set and each tool's required-parameter set (`tests/test_tools.py:14-50` `EXPECTED_TOOLS`, `tests/test_tools.py:84-120` `test_tools_list_snapshot`), and that same test currently hard-caps the tool count at 37 (`tests/test_tools.py:120` `assert len(names) <= 37`) — the repo already has exactly 37 tools today, so adding `graph_remove_manager` requires bumping that literal cap, with a one-line justification comment matching the pattern already used for every earlier increment (see `test_tools.py:96-119`).

## Product design

### Goals / Non-goals

**Goals** (MVP = reporter's own "ship 1.1–1.6 first" slice):
- G1: `graph_list_user_groups`, `graph_list_groups`, `graph_list_users` support resuming a listing beyond one page via a pagination token, so a directory larger than one page can be walked completely and exactly once.
- G2: `graph_list_user_groups` additionally reports each group's type, mail-enabled flag, and whether it syncs from on-premises AD, so a caller can route a group to Graph, Exchange, or AD without a second lookup.
- G3: `graph_update_user` can set `employee_id`, `user_principal_name`, `display_name`, `given_name`, `surname`, with "omitted leaves it unchanged, explicit null clears it" semantics, and rejects a `user_principal_name` change whose domain is not a verified tenant domain.
- G4: a caller can remove a user's manager without needing to know or set a replacement, and doing so when no manager is set is not an error.
- G5: `graph_get_user` returns enough of a user's directory profile (`proxyAddresses`, `identities`, `employeeId`, on-premises sync attributes, manager) to support offboarding decisions in one call, and a caller can narrow the response to just the fields it needs.

**Non-goals** (explicitly out of scope for this ticket, per the reporter's own interview log):
- `graph_transfer_onedrive` (item 7) — held pending confirmation with Ginko on whether OneDrive transfer is still required for production release.
- `graph_start_cloud_sync` (item 8) — held pending confirmation with Ginko on which sync mechanism is actually used.
- Any change to `graph_assign_manager`, `graph_create_user`, or any tool not named in the eight original items.
- Building the offboarding workflows 08/03 themselves — this ticket only changes the Graph tool surface they call.

### Acceptance criteria AC1..AC15

- AC1: Given a user who is a member of more groups than fit on one Graph page, When `graph_list_user_groups` is called repeatedly, each call after the first passing the previous response's `next_page_token`, Then every group the user belongs to is returned exactly once across the calls, and the final call reports `has_more=false` and `next_page_token=null`.
- AC2: Given any group a user belongs to, When `graph_list_user_groups` is called, Then each group entry in the response includes `groupTypes`, `mailEnabled`, and a `sync_source` of `"on-premises"` or `"cloud"`.
- AC3: Given a tenant with more groups than fit on one Graph page, When `graph_list_groups` is called repeatedly with `next_page_token` chained the same way as AC1, Then every group is returned exactly once and the final call reports `has_more=false`.
- AC4: Given a tenant with more users than fit on one Graph page, When `graph_list_users` is called repeatedly the same way, Then every user is returned exactly once and the final call reports `has_more=false`.
- AC5: Given `employee_id`, `user_principal_name`, `display_name`, `given_name`, `surname` are all omitted from a `graph_update_user` call, When the call runs, Then none of those five attributes changes on the target user.
- AC6: Given exactly one of those five attributes is passed as an explicit `null`, When `graph_update_user` runs, Then that one attribute is cleared on the target user and no other attribute changes.
- AC7: Given `user_principal_name` is set to an address whose domain is not one of the tenant's verified domains, When `graph_update_user` runs, Then the call is rejected with an invalid-argument error and the user's `userPrincipalName` is unchanged.
- AC8: Given `user_principal_name` is set to an address on a verified tenant domain, When `graph_update_user` runs, Then the update succeeds and a subsequent `graph_get_user` shows the new `userPrincipalName`.
- AC9: Given a user with an assigned manager, When `graph_remove_manager` is called, Then the manager relationship is removed and a subsequent `graph_get_user` no longer returns a manager for that user.
- AC10: Given a user with no manager assigned, When `graph_remove_manager` is called, Then the call succeeds and reports a `no_manager` status rather than an error, and calling it again is equally successful.
- AC11: Given a user with `proxyAddresses`, `identities`, `employeeId`, and on-premises sync attributes populated, When `graph_get_user` is called with no `select` parameter, Then all of those fields are present in the response alongside the fields already returned today.
- AC12: Given a `select` parameter naming a subset of fields, When `graph_get_user` is called, Then the response contains exactly those fields (plus `id`) and omits the rest of today's default set.
- AC13: Given an invalid or expired pagination token is passed to any of `graph_list_user_groups` / `graph_list_groups` / `graph_list_users`, When the tool is called, Then it returns the existing structured error envelope rather than an unhandled exception.
- AC14: Given `graph_update_user` is called with none of its attributes set (including none of the five new ones), When the call runs, Then it is still rejected with the existing "Provide at least one attribute to update" error (regression — the shared body-building code is being touched by G3).
- AC15: Given a caller's access token is scoped to tenant A, When any modified or new tool in this ticket is called with a `user_id`/`group_id` belonging to tenant B, Then Microsoft Graph itself returns not-found/unauthorized for the cross-tenant reference — this server performs no tenant check of its own; isolation is entirely delegated to the per-request bearer token's own tenant scope. This cannot be verified against the in-repo fake Graph client and needs a real two-tenant check (see Test cases).

## Tech design

### Conclusion

Extend three existing list tools (`graph_list_user_groups`, `graph_list_groups`, `graph_list_users`) to the same single-page-per-call pagination contract `graph_list_group_members` already ships (`page_token` in, `next_page_token` out, via the existing `_skiptoken` helper); add five new optional, patch-safe parameters to `graph_update_user` using a sentinel-default to distinguish "omitted" from "explicit null", plus a pre-flight domain check against `graph_list_domains`'s own logic; add one new tool `graph_remove_manager` mirroring `graph_remove_group_member`'s idempotent-on-absent pattern; and widen `graph_get_user`'s `$select` with an optional `select` override. All six changes live in `ms-graph-mcp` only, touch two existing files (`tools/groups.py`, `tools/users.py`) plus their shared helper (`tools/_common.py`) and the test suite, and need no new dependency, no DB, and no other repo.

### Data & API contract

All six changes are MCP tool-call contracts (JSON-RPC `tools/call`), not a REST surface of this server's own; the server's own HTTP contract (`POST /mcp`, `X-Ms-Graph-Token` header, `GET /health`) is unchanged.

**`graph_list_user_groups`** (modified)
- Request: `{"user_id": "...", "max_results"?: int, "page_token"?: string}`
- Response (changed): `{"user_id", "count", "groups": [{..., "groupTypes", "mailEnabled", "sync_source": "on-premises"|"cloud", ...}], "has_more": bool, "next_page_token": string|null}` — `has_more`/pagination semantics now match `graph_list_group_members` (one Graph page per call) instead of today's "walked internally up to max_results".

**`graph_list_groups`** (modified) — same `page_token` in / `next_page_token` out shape; group object fields unchanged.

**`graph_list_users`** (modified) — same `page_token` in / `next_page_token` out shape; user object fields unchanged.

**`graph_update_user`** (modified)
- Request adds: `{"employee_id"?: string|null, "user_principal_name"?: string|null, "display_name"?: string|null, "given_name"?: string|null, "surname"?: string|null}` — omitted = unchanged, `null` = clear, string = set.
- New error: `{"error": {"code": "invalid_argument", "message": "userPrincipalName domain '<domain>' is not a verified domain for this tenant.", "retryable": false}}` when the UPN's domain fails the check — same envelope shape as every other `invalid_argument` in this codebase (`src/graph_mcp/_json.py` `error_envelope`, already used throughout).
- Graph PATCH body: `employeeId`, `userPrincipalName`, `displayName`, `givenName`, `surname` — standard Entra user properties, all nullable on the Graph side.

**`graph_remove_manager`** (new)
- Request: `{"user_id": "..."}`
- Response: `{"status": "removed", "user_id": "..."}` or `{"status": "no_manager", "user_id": "..."}`
- Graph call: `DELETE /users/{id}/manager/$ref` → `204` (removed) or `404` (already absent, mapped to `no_manager` rather than surfaced as an error).

**`graph_get_user`** (modified)
- Request adds: `{"select"?: list[string]}` — when present, replaces the default `$select` list (server always includes `id`).
- Response adds (default, when `select` omitted): `proxyAddresses`, `identities`, `employeeId`, `onPremisesSyncEnabled`, `onPremisesLastSyncDateTime`, `onPremisesDistinguishedName`.

**Backward compatibility**: every new parameter is optional and additive; no existing required parameter or response field is removed. The one behavior change that existing callers could notice is the pagination contract switch on the three list tools (see Option analysis and Open questions) — callers that never exceeded the old internal walk's effective page size will see no difference; callers that did will now need to follow `next_page_token` instead of getting everything in one call.

### Key flow / sequence

Patch-safe UPN change (`graph_update_user` with `user_principal_name` set):

1. Caller → `graph_update_user(user_id, user_principal_name="alice@newdomain.com", ...)`
2. Server → `_verified_domains(client)` → Graph `GET /domains?$select=...&isVerified` (same call `graph_list_domains` makes)
3. Server checks `newdomain.com` against the verified set.
   - Not verified → return `invalid_argument` envelope; **no PATCH is sent to Graph**.
   - Verified → continue.
4. Server builds the PATCH body from every non-`_UNSET` field (explicit `null`s included as `null` in the JSON body) → Graph `PATCH /users/{id}`
5. Graph → `200`/`204` → server returns `{"status": "success", "user_id", "updated": [...]}` (existing response shape, unchanged).

Pagination (`graph_list_users` as the representative case; `graph_list_groups`/`graph_list_user_groups` are the same shape):

1. Caller → `graph_list_users(max_results=50)` (no `page_token`)
2. Server → Graph `GET /users?$top=50&$select=...` (no `$skiptoken`)
3. Server extracts `next_page_token` from the response's `@odata.nextLink` (`_skiptoken`), returns `{"users": [...], "has_more": true, "next_page_token": "..."}`
4. Caller → `graph_list_users(max_results=50, page_token="...")`
5. Server → Graph `GET /users?$top=50&$select=...&$skiptoken=...` → repeat until `has_more=false`.

### Non-functional

- **Idempotency & concurrency**: `graph_remove_manager` is idempotent by construction (404→`no_manager`, same as `graph_remove_group_member`'s existing 404 handling) — calling it twice, or concurrently with another removal, converges to the same end state with no error on either path. `graph_update_user`'s PATCH is not itself idempotent against concurrent writers (last-write-wins, same as today), unchanged by this ticket.
- **Performance**: no new N+1 pattern is introduced — pagination changes reduce server-side work per call (one Graph page instead of walking up to `_HARD_CAP_MAX_RESULTS=200` worth of pages); the UPN domain check adds exactly one extra Graph call (`/domains`) only on the `graph_update_user` calls that actually set `user_principal_name`, not on every call.
- **Security**: no new auth surface — every tool continues to run under the caller's own per-request bearer token (`server.py`'s `GatewayTokenMiddleware`/contextvar), and `graph_remove_manager` requires nothing beyond what `graph_assign_manager` already requires (the Graph app registration's existing `User.ReadWrite.All`-class permission). The UPN domain check is a safety rail against a typo'd or malicious cross-domain rename, not a security boundary — rejecting an unverified domain prevents Graph itself from rejecting it with a less clear error, nothing more.
- **Multi-tenant isolation**: this server has no isolation logic of its own and none is added — every Graph call is scoped by the caller's own bearer token, which is itself scoped to exactly one Entra tenant by Microsoft, not by this codebase (see AC15; this is a pre-existing architectural property of the whole server, not something this ticket changes or could change).
- **Observability**: no new logging is added beyond what `GraphClient`'s existing retry/error path already does (`api_client.py:140-170`) — a rejected UPN-domain change and a `no_manager` result are both returned to the caller in the tool's own response, which is the existing pattern for this codebase (errors are envelopes in the response, not server-side logs); this is consistent with every other tool in this file, not a gap newly introduced here.

### Rollout & rollback

No feature flag — this server has none, and every change here is additive (new optional params, one new tool) or a same-input-same-output-for-small-results pagination shape change. Deploy is a normal `ms-graph-mcp` release: merge → image rebuild → redeploy the gateway-mode server. Rollback is reverting the image; no data migration exists since this server holds no persistent state. The one thing a rollback would undo that could matter mid-flight is the pagination contract switch — if a caller started relying on the new `next_page_token` shape before a rollback, it would need to fall back to the old max_results semantics, which is a caller-side code path, not a data-safety issue.

### Test strategy

Everything in this ticket is unit-testable against the repo's existing `_CapturingClient` fake (`tests/test_tools.py:150-204`), which records the request method/path/params/body instead of calling real Graph — this is how every existing tool in this file is tested (e.g. `test_list_group_members_returns_only_the_skiptoken`, `tests/test_tools.py:1219-1238`), so no new test infrastructure is needed for AC1–AC14. AC15 (true cross-tenant isolation) cannot be exercised against the fake client — it requires two real Entra tenants and is marked manual in the test cases below, to be executed once, documented, and treated as a standing architectural fact rather than a per-release regression check.

Regression surface: `graph_update_user`'s existing "no attributes → reject" behavior (AC14) and `graph_list_group_members`'s already-shipped pagination tests must keep passing unmodified — this ticket extends the same code paths (`_skiptoken`, the `if x is not None` body-building pattern) rather than replacing them.

### Effort & breakdown

Rough order of magnitude: **2–3 engineer-days**, the range driven mainly by how much time the sentinel-default verification (Option analysis, "Omitted-vs-null distinction") takes — if the `mcp[cli]` SDK handles it cleanly this is close to 2 days, if it needs a workaround (e.g. the `clear_X` boolean fallback) it is closer to 3.

Suggested sub-tasks, each independently verifiable against its own ACs:
1. Shared helpers + pagination for the three list tools (AC1–AC4, AC13) — `_common.py`, `groups.py`, `users.py` list functions.
2. `graph_update_user` patch-safe fields + UPN domain check (AC5–AC8, AC14) — `users.py`, `_common.py`.
3. `graph_remove_manager` (AC9, AC10) — `users.py`, test-suite cap bump.
4. `graph_get_user` field widening + `select` param (AC11, AC12) — `users.py`.
5. AC15 manual cross-tenant verification — no code, a one-time documented check against a real two-tenant setup.

### Risks & dependencies

- **Risk**: the sentinel-default approach for "omitted vs. explicit null" (Option analysis) is unverified against the installed `mcp[cli]>=1.9.0` SDK's actual argument-binding behavior. Mitigation: the first implementation step for sub-task 2 should write a throwaway probe test confirming the SDK round-trips "argument absent" and "argument = null" to two distinct Python values before building the rest of `graph_update_user`'s logic on top of that assumption. If it does not, fall back to the `clear_X` boolean shape from Option analysis.
- **Risk**: switching the three list tools' pagination contract (Option analysis, Pagination shape B) could surprise an external caller that currently assumes one call returns everything up to `max_results`. Mitigation: called out explicitly in Open questions and in the ticket's Conclusion line so groom can confirm no known caller depends on the old shape before this ships.
- **Dependency**: none on another ticket or repo. Items 7–8 (this ticket's non-goals) are a soft dependency in the sense that they are listed in the same parent request, but they do not block or get blocked by the work in this ticket.
