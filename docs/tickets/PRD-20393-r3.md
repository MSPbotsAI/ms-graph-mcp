**Issue 1 — `graph_remove_manager` reports `no_manager` for a user_id that does not exist** (comment's "Fix needed 1", confirmed on INT).

Code: `src/graph_mcp/tools/users.py:734-744` (at `e994c6f`). On a `404` from `GET /users/{id}/manager`, the tool unconditionally returns `{"removed": false, "reason": "no_manager"}` — the fix round 2 shipped for Defect 3 correctly stopped trusting `DELETE`'s 404 behavior, but it still trusts `GET /users/{id}/manager`'s 404 to mean exactly one thing. Minnie Zhou's repro: `graph_remove_manager(user_id="nonexistent.qa20393@mspbots.ai")` on the production tenant returns `{"removed": false, "previous_manager": null, "reason": "no_manager"}` — Graph returns 404 on `GET /users/{id}/manager` both when the user has no manager and when `user_id` doesn't resolve to any user at all, and round 2's code can't tell those two cases apart. Impact (per the comment): workflow 08 with a mistyped user_id would silently "succeed" and record that the user had no manager, instead of surfacing that the id was wrong.

**Issue 2 — `graph_update_user`'s read-back 404s after a `userPrincipalName` rename, reporting a write that actually succeeded as an error** (comment's "Fix needed 2", high risk, found in code review).

Code: `src/graph_mcp/tools/users.py:663-676` (at `e994c6f`, round 2's own Defect 2 fix). The follow-up `GET /users/{user_id}` after a successful `PATCH` always uses the original `user_id` parameter. When the PATCH body contains `userPrincipalName` (a UPN rename — workflow 08's own use case during offboarding) and `user_id` was passed as the *old* UPN string rather than a GUID, the old UPN stops resolving the instant the rename takes effect, so the read-back 404s even though the PATCH already wrote the new value. Round 2's code treats any `GraphError` from the whole `try` block identically — a read-back failure is indistinguishable from a PATCH failure, so this path returns an error envelope for a write that succeeded. Not exercisable on INT in this round (the test connector has no user-write permission against the production tenant — comment's 1.4 result is BLOCKED, not failing), so this is a code-review finding, not an INT repro.

**Issue 3 — `graph_update_user`'s read-back can show a stale value under Graph replication lag** (comment's "Minor (optional)").

No code defect — Graph's own eventual-consistency window means a `GET` issued immediately after a `PATCH` can occasionally still return the pre-write value for the field just changed. Round 2's design didn't mention this risk at all.

**Unaffected**: round 2's other three results (1.1 `graph_list_user_groups` pagination, 1.6 `graph_get_user` default fields + `select`/`manager`, and `graph_remove_manager`'s has-a-manager path) all PASSED on INT per this comment. No change proposed for any of them in this round.

## Product design

### Goals / Non-goals

**Goals** (matching the comment's two required fixes plus its one optional improvement):
- G1: `graph_remove_manager` returns a `not_found` error when `user_id` does not resolve to any user, and continues to return `removed=false, reason="no_manager"` only when the user exists but genuinely has no manager.
- G2: `graph_update_user`'s read-back succeeds after a `userPrincipalName` rename (reads back using the new UPN), and a read-back failure that happens *after* a successful `PATCH` is reported as a successful write with a `readback_error` field, never as a plain error envelope.
- G3 (optional, per the comment's own "either/or"): callers are warned that the read-back value can rarely be stale due to Graph replication lag.

**Non-goals**:
- Re-opening any of round 2's four fixes — all re-passed or are correctly BLOCKED by tenant permissions, not by a code defect, per this comment.
- Re-running round 2's still-unverified write-permission paths (1.4 set-to-new-value read-back under write permission, 1.5 `removed=true` + `previous_manager`, UPN rename end-to-end against Graph) — the comment itself asks for this to happen on a tenant with write permission (the demo tenant, SOP 225), not in this round's own verification, which has no such tenant available either.
- Any further field additions beyond what this comment's three items literally ask for.

### Acceptance criteria AC1..AC3

- AC1 (new, Issue 1): Given a `user_id` that does not resolve to any Entra ID user, When `graph_remove_manager` is called, Then it returns a `not_found` error envelope, never `{"removed": false, "reason": "no_manager"}`. Given a `user_id` that does resolve but has no manager assigned, When `graph_remove_manager` is called, Then it still returns `{"removed": false, "previous_manager": null, "reason": "no_manager"}` exactly as round 2 shipped (regression guard — this round must not weaken the existing no_manager path for a real user).
- AC2 (new, Issue 2): Given `graph_update_user` changes `user_principal_name` and the call succeeds, When the tool reads the user back to build `updated`, Then it reads back using the *new* UPN, not the original `user_id` parameter, so the read-back does not 404 against a UPN that no longer resolves. Given a `graph_update_user` call whose `PATCH` succeeds but whose follow-up read-back fails for any reason, When the tool returns, Then it returns `{"status": "success", "updated": <the values that were sent>, "readback_error": {...}}`, never an error envelope — the write already happened and must not be reported as having failed.
- AC3 (tech-added per the comment's explicit either/or, not independently requested beyond "note this or retry"): Given `graph_update_user`'s tool description, When an agent reads it before calling the tool, Then it states that the returned `updated` values come from an immediate post-write read-back and can rarely be stale due to Graph replication lag.

### Open questions

- [不阻塞] AC1's existence check (`GET /users/{id}?$select=id`) is a second Graph call on the already-slow "no manager or doesn't exist" path. It was not needed before this round because round 2's code never distinguished the two 404 causes. Cost analysis in Tech design § Non-functional.
- [已假设] The comment names two options for Issue 2a: "read back using the new UPN" or "resolve user_id to the object id before the PATCH and use the id for both calls." This design takes the first (simpler, no extra pre-PATCH call) — see Tech design § Option analysis for why the two are equivalent in outcome here.
- [已假设] The comment names two options for Issue 3: "note this in the tool description" or "retry the read once after a short delay." This design takes the first — see Tech design § Option analysis for why a retry was rejected for this round.

## Tech design

### Conclusion

Both required fixes stay inside the two functions round 2 already touched in `src/graph_mcp/tools/users.py` (`graph_remove_manager`, `graph_update_user`) plus the test suite; no new file, no new dependency, no schema/DB. Issue 1 is fixed by adding a plain existence check (`GET /users/{id}?$select=id`) only on the already-404 "no manager or doesn't exist" branch. Issue 2 is fixed by (a) computing the read-back target as the new UPN when one was sent, and (b) splitting the `PATCH` and the read-back into separate `try`/`except` blocks so a read-back failure cannot be reported as a write failure. Issue 3 is fixed by a short addition to the tool's docstring — not a retry — see Option analysis for why.

### Option analysis

| Issue | Option | Approach | Pros | Cost | Decision |
|---|---|---|---|---|---|
| 1 (nonexistent user) | A | Treat a 404 from `GET /users/{id}/manager` as ambiguous and return a generic "cannot determine" error without an extra call | No extra Graph call | Does not match the comment's literal proposed fix, and leaves the common no_manager-for-a-real-user case (the overwhelmingly more frequent call shape) worse off than today — it would now also error instead of succeeding | Rejected |
| 1 (nonexistent user) | B | On a 404 from `GET /users/{id}/manager`, issue `GET /users/{id}?$select=id`; 404 there → `not_found` error; success → `no_manager` as before | Matches the comment's literal proposed fix exactly; only adds a Graph call on the branch that was already about to return (the common has-a-manager path is untouched, zero extra cost there) | One extra Graph call, but only on the no-manager-or-404 branch, which was already the cheapest path (no DELETE) | **Chosen** |
| 2a (UPN read-back) | A | Resolve `user_id` to the object's GUID with a lookup *before* the PATCH, then use that GUID for both the PATCH and the read-back | Works regardless of what changes; a GUID never stops resolving | One extra Graph call on *every* `graph_update_user` call, not just UPN-rename calls — most calls don't touch `userPrincipalName` at all, so this would tax the common case to fix an edge case | Rejected |
| 2a (UPN read-back) | B | If the PATCH body contains `userPrincipalName`, read back using that new value instead of `user_id`; otherwise read back using `user_id` exactly as round 2 did | Matches the comment's literal first option; zero extra Graph calls — same two-call shape (`PATCH` then `GET`) round 2 already had, just picks a different target for the second call only when needed | None identified — the new UPN is already in hand (it's the value the caller sent and Graph just set it to) | **Chosen** |
| 2b (read-back failure handling) | A | Keep a single `try` around both the PATCH and the read-back, as round 2 shipped it | No code change | This is the actual defect — a read-back-only failure is indistinguishable from a PATCH failure, so it's reported as the whole call failing when the write already succeeded | Rejected |
| 2b (read-back failure handling) | B | Split into two `try` blocks: the PATCH's own failure still returns its error envelope unchanged (no behavior change for a genuine write failure); a read-back failure after a successful PATCH returns `{"status": "success", "updated": <sent values>, "readback_error": {...}}` | Matches the comment's literal second option; a write that succeeded is never reported as failed, while a write that actually failed still gets its real error | None identified | **Chosen** |
| 3 (replication lag) | A | Add a short retry: after the read-back, if a value differs from what was sent, sleep briefly and read back once more | Could actually mask a true-stale read on a sleepy test run or a genuinely slow tenant | Several fields this tool accepts are normalized by Graph on write (e.g. `employeeHireDate`'s date-time formatting), so a naive sent-vs-read-back comparison would flag those as "stale" on every call and retry needlessly; scoping the comparison correctly per-field is more complexity than this optional, "either/or" item justifies on its own | Rejected for this round |
| 3 (replication lag) | B | Document the behavior in the tool's description | Zero behavioral change, zero risk of a spurious retry or added latency; matches the comment's literal first option | None identified, other than the tool description already being close to this repo's 500-char soft budget (`tests/test_tools.py::test_tools_list_snapshot`) — required trimming existing wording to fit, done without changing any of its prior meaning | **Chosen** |

### Data & API contract

**`graph_remove_manager`** (modified) — **additive, not breaking**: the response shape is unchanged (`{"user_id", "removed", "previous_manager", "reason"}`); the only change is that a `user_id` that never resolved to a user now returns a `not_found` error envelope instead of a `no_manager` success. Any caller correctly handling round 2's documented error envelope already handles this; a caller that was relying on round 2's bug (treating `no_manager` as proof the id was valid) would now see the actual error, which is the intended fix.

**`graph_update_user`** (modified) — **additive, not breaking**: `status`/`user_id`/`updated` keep their round-2 shapes (`updated` stays `{field: value}`); the new `readback_error` key is only ever present alongside `status: "success"` when the read-back specifically failed, and its absence (the common case) changes nothing for an existing caller.

### Key flow / sequence

`graph_remove_manager` (round 3's addition, replacing round 2's step 2a):

1. Caller → `graph_remove_manager(user_id="u1")`
2. Server → `GET /users/u1/manager?$select=id,displayName,userPrincipalName`
   - `404` → Server → `GET /users/u1?$select=id` (**new this round**)
     - `404` → return that error's own envelope (`not_found`). **No further call.**
     - success → return `{"user_id": "u1", "removed": false, "previous_manager": null, "reason": "no_manager"}`, exactly as round 2.
   - other error → return that error's envelope unchanged.
   - `200` → continue exactly as round 2 (read manager, `DELETE`, tolerate a concurrent-removal 404 on the `DELETE` itself).

`graph_update_user` (round 3's change to the tail, replacing round 2's single combined `try`):

1. Server builds `body` exactly as round 2 designed (unchanged).
2. Server → `PATCH /users/{id}` with `body`. On failure, return that error's envelope — **unchanged from round 2**.
3. Server computes `readback_id = body.get("userPrincipalName", user_id)` (**new this round** — uses the new UPN when one was sent, else the original `user_id`).
4. Server → `GET /users/{readback_id}?$select=<comma-joined body.keys()>`.
   - success → return `{"status": "success", "user_id": user_id, "updated": {k: result.get(k) for k in body}}`, exactly as round 2's shape.
   - failure (**new this round**) → return `{"status": "success", "user_id": user_id, "updated": dict(body), "readback_error": {"status_code": ..., "message": ...}}` instead of propagating the error.

### Non-functional

- **Idempotency & concurrency**: `graph_remove_manager`'s new existence check is a plain `GET`, no state change — calling it twice on the same nonexistent `user_id` is equally `not_found` both times, and twice on the same managerless-but-real user is equally `no_manager` both times (confirmed by the updated `test_remove_manager_returns_no_manager_without_calling_delete`, which now calls it twice). `graph_update_user`'s read-back-by-new-UPN is a plain `GET` with no side effect; if a second concurrent rename happened between this call's `PATCH` and its `GET`, the `GET` would reflect whatever is actually stored at read time (or fail, now surfaced via `readback_error` rather than an error envelope) — not a new concurrency hazard beyond what round 2 already had.
- **Performance**: Issue 1's fix adds exactly one Graph call, and only on the branch where `GET /manager` already 404'd (the cheapest branch — no `DELETE` was ever going to run there). The has-a-manager path (the more common real-world case for an actual offboarding) is untouched. Issue 2's fix adds zero Graph calls — same two-call shape as round 2, just a different target for the second call when a UPN was sent.
- **Security**: no new auth surface for either fix. `GET /users/{id}?$select=id` requires the same `User.Read.All`-class permission the existing `GET /users/{id}/manager` call already requires.
- **Multi-tenant isolation**: unchanged from round 1/round 2 — no isolation logic of its own, every Graph call scoped by the caller's own bearer token.
- **Observability**: `readback_error`'s `status_code`/`message` give the caller the same information a propagated error envelope would have carried, just attached to a success response instead of replacing it — no information is lost, only mis-classified as failure is corrected.

### Rollout & rollback

Same as round 1/round 2: no feature flag (this server has none), normal `ms-graph-mcp` release — merge → image rebuild → redeploy. Rollback is reverting the image; no data migration exists. Neither fix changes an existing response field's type or removes a field — both are additive relative to round 2's shapes (a new error classification for an edge case, and a new optional key), so no caller coordination is needed the way round 2's two breaking changes required.

> === Fix needed 1 (defect, confirmed on INT): graph_remove_manager reports no_manager for a user that does not exist ===
> Repro: graph_remove_manager user_id="nonexistent.qa20393@mspbots.ai"
> Actual: {"user_id": "nonexistent.qa20393@mspbots.ai", "removed": false, "previous_manager": null, "reason": "no_manager"}
> Expected: an error envelope (code not_found), not a no_manager success.
> Root cause: src/graph_mcp/tools/users.py graph_remove_manager treats any 404 from GET /users/{id}/manager as no_manager. Graph returns 404 both when the user has no manager and when the user does not exist.
> Proposed fix: on a 404 from GET /users/{id}/manager, call GET /users/{id}?$select=id. If that also 404s, return the not_found error envelope; only if the user exists return removed=false, reason="no_manager". Add a unit test for the nonexistent-user case.
>
> === Fix needed 2 (high risk, found in code review, could not be exercised on INT): graph_update_user read-back fails after a UPN change ===
> Scenario: graph_update_user user_id="<old UPN>" user_principal_name="<new UPN>".
> Problem: after the PATCH succeeds, the r2 read-back calls GET /users/{user_id} with the OLD UPN. Once the rename is applied the old UPN no longer resolves, so the read-back 404s and the tool returns an error although the user was already renamed. Workflow 08 renames UPNs during offboarding, so this path is hit in practice.
> Proposed fix: (a) if the body contains userPrincipalName, read back using the new UPN (or resolve user_id to the object id before the PATCH and use the id for both calls); (b) if the PATCH succeeds but the read-back fails, return status "success" with the sent values and a readback_error field instead of an error envelope. Add unit tests for both cases.
