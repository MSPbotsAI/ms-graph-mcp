# PRD-20413 · [QA][Onboarding Agent][Connector] Microsoft Graph: add a tool to read a SharePoint file by site name + file name in one call (no driveId round-trip)

Ticket: https://app.clickup.com/t/2280862/PRD-20413
Repo: https://github.com/MSPbotsAI/ms-graph-mcp@master (968369d)
Work branch: dev01.mbagent/PRD-20413
Status: in progress

## Requirement understanding

One line: the reporter wants a single Microsoft Graph MCP tool that reads a SharePoint file by site name + file name server-side, so the calling model never has to copy a long `driveId`/item id between chained tool calls, because that copying is what causes node J's intermittent "malformed drive id" failures.

Today node J of the Onboarding agent reads `Permission Matrix.csv` via three chained calls — `graph_search_sites` → `graph_list_drive_items` → `graph_read_file_text` — and the model has to re-type the long, random `driveId` between the first two. A prompt-only mitigation ("copy the id character for character") was already tried on the SOP side (PRD-20211, `felix.zhou`, 2026-10-09) and did not hold: QA re-verification on 2026-10-10 (PRD-20211, `Pantene Hui`) reproduced the same drive-id corruption on a different run even with the stricter instruction in place, and PRD-20211 is back in `6a - in dev`. The reporter's own conclusion (quoted in this ticket) is that an instruction cannot guarantee verbatim copying and the fix has to remove the model from the data path — i.e. land in the connector, not the prompt. Success is a new read-only tool, `graph_read_site_file_text(site_query, file_name, folder_path?, site_id?)`, that resolves site → drive → file → content in one call, with structured error codes (`site_not_found` / `site_ambiguous` / `file_not_found` / `file_empty` / plus the two added below) so the calling agent can branch on failure instead of getting a generic error.

The ticket already comes with a fairly complete technical proposal (tool name, parameters, server-side logic, response/error shapes) — this design validates that proposal against the real code in `ms-graph-mcp`, adjusts the parts that don't fit the codebase as-is, and flags the parts that need a human call.

## Product design

### Goals / Non-goals

**Goal**: an agent that knows a SharePoint site's name and a file's name can read that file's text content in exactly one tool call, with no `driveId` or item id ever appearing in the model's own output. On failure, the agent receives one of a fixed set of structured error codes it can branch on, instead of a generic error string.

**Non-goals** (not this ticket):
- Replacing or removing `graph_search_sites` / `graph_list_drive_items` / `graph_read_file_text` — they stay for callers who already have a `drive_id` (e.g. browsing a library interactively) or need to list a folder's contents rather than read one named file.
- Reading binary Office documents (`.docx`/`.xlsx`/`.pdf`) — same scope boundary `sites.py`'s module docstring already states (`sites.py:1-19`) for the existing read tool; this ticket's tool inherits the same UTF-8-text-only limit.
- Writing or modifying SharePoint content — the new tool is read-only, same as `graph_search_sites`/`graph_list_drive_items`/`graph_read_file_text`/`graph_get_file`.
- Fixing the pre-existing `dump_json_capped` truncation gap noted above (Open Questions) for every other tool that returns non-list text content — this ticket only has to not make that gap worse for its own payload shape.
- Changing the onboarding agent's SKILL.md / Source card (PRD-20211's territory, a different repo) — this ticket only ships the connector tool; wiring node J to use it is explicitly called out in the ticket as "QA will make these" changes, after release.

### Scope (user-visible behavior)

#### Main flow

The calling agent invokes `graph_read_site_file_text(site_query="permission matrix", file_name="Permission Matrix.csv")`. Server-side: the site is resolved from `site_query` (preferring an exact, case-insensitive name match; see Tech design), its default document library is opened, the named file is located (optionally inside `folder_path`), and its text content is returned — all in the one call's response. The agent never sees or handles a `driveId` or item id for this flow.

#### Interaction / branching on failure

Each failure mode returns a distinct `error.code` plus enough structured context for the agent to act without re-asking a human immediately:

| Code | When | What's returned alongside it |
|---|---|---|
| `site_not_found` | No site matches `site_query` (or `site_id` doesn't resolve) | the search term / id that was tried |
| `site_ambiguous` | More than one site is a plausible match and none is an exact name match | candidate sites (id, displayName, webUrl) |
| `file_not_found` | The resolved site/library has no such file at that name/path (including: the path resolves to a folder, not a file; or the site has no document library at all) | file names actually present in that folder |
| `file_empty` | The file exists but is 0 bytes | file name, last-modified time |
| `file_too_large` | File is over the 200,000-byte read limit | actual size, the limit |
| `not_text` | File content isn't valid UTF-8 (i.e. it's a binary Office document or similar) | the file's reported type |

#### Edge cases and exceptions

- Both `site_id` and `site_query` given → `site_id` wins, `site_query` is accepted (per the ticket's own parameter table marking it required) but not used for resolution. See Open Questions — this is a minor inconsistency in the ticket's own spec, resolved here with a default; flag for groom to confirm.
- `folder_path` omitted → look in the document library root, same convention `graph_list_drive_items` already uses (`folder_id` omitted → root).
- Exactly one exact (case-insensitive) displayName match among several keyword hits → use it, no ambiguity error, even though more than one site was technically returned by the underlying search.
- File exists but is actually a folder at that exact path → treated as `file_not_found` (the file you asked for isn't there; a folder is not a readable text file), not a separate code — the ticket's four-code table doesn't define a fifth code for this and a `not_text`/generic error here would be confusing since there's no file content to even attempt to decode.

#### Permissions & multi-tenant

No new permission scope: this reuses exactly the Graph application permissions `graph_search_sites`/`graph_read_file_text` already require (`Sites.Read.All` or equivalent — per the ticket's own "Permissions" section, confirmed consistent with how every other tool in `sites.py` acquires its client via the same per-request `client_factory()`). Each call's `GraphClient` carries only that call's token (`api_client.py:69-77`); nothing about site/drive/file resolution may be cached across calls — a resolution cached from tenant A's token must never be reused to serve tenant B's call with a matching `site_query`/`file_name`. This is a plain consequence of the existing stateless design, not a new mechanism, but it is called out explicitly because it is the one place a well-meaning "let's cache the site search to save a round trip" optimization would quietly break tenant isolation.

### Acceptance criteria AC1..AC10

- **AC1**: Given a SharePoint site whose displayName exactly (case-insensitively) matches `site_query`, containing a small (`<=200,000` byte) UTF-8 text file named `file_name` in its document library root, When the agent calls `graph_read_site_file_text(site_query=..., file_name=...)` once, Then the response contains that file's exact content and the site/drive/file metadata described in the Tech design's contract, and the agent never had to supply a `driveId` or item id.
- **AC2**: Given a `site_query` with no exact displayName match but exactly one keyword-search hit, When the tool is called, Then that single hit is used (no `site_ambiguous` error) and the file is resolved and read as in AC1.
- **AC3**: Given a `site_query` matching no site at all, When the tool is called, Then it returns `error.code = "site_not_found"` with the search term echoed back, and makes no attempt to query a drive or file.
- **AC4**: Given a `site_query` with more than one keyword-search hit and none of them an exact displayName match, When the tool is called, Then it returns `error.code = "site_ambiguous"` with a candidate list (id, displayName, webUrl) for each match.
- **AC5**: Given a valid `site_id` is passed (with or without `site_query`), When the tool is called, Then site resolution uses `site_id` directly and skips the search call entirely.
- **AC6**: Given a site/drive that resolves successfully but has no file at `file_name` (optionally under `folder_path`) — including the case where that site has no document library at all, or the path resolves to a folder — When the tool is called, Then it returns `error.code = "file_not_found"` with the list of file names actually present in that folder (empty list if the library/folder itself doesn't exist).
- **AC7**: Given the resolved file exists but is 0 bytes, When the tool is called, Then it returns `error.code = "file_empty"` with the file's name and last-modified time, and does not attempt to read/decode content.
- **AC8**: Given the resolved file is larger than 200,000 bytes, When the tool is called, Then it returns `error.code = "file_too_large"` with the actual size and the limit, and does not fetch the file's content bytes.
- **AC9**: Given the resolved file's content is not valid UTF-8 (e.g. a `.xlsx`/`.docx`/`.pdf`), When the tool is called, Then it returns `error.code = "not_text"` with the file's reported type.
- **AC10 (read-only / multi-tenant)**: Given any sequence of calls to this tool, including calls made with different access tokens (different tenants), When those calls run, Then (a) no HTTP request issued by this tool is anything other than `GET`, and (b) no site/drive/file resolution from one call is reused to answer a different call — each call independently re-resolves from its own parameters and its own token.

### Open questions

- [已假设 / assumed] `site_query` vs `site_id`: the ticket's own parameter table marks `site_query` "Required: yes" while separately describing `site_id` as a way to "skip the site search" — those two statements are in tension (if site_id alone were enough, site_query couldn't be unconditionally required). Resolved here as: `site_query` stays required in the tool's schema exactly as the ticket specifies, but when `site_id` is also given, the server-side logic uses `site_id` and ignores `site_query` for resolution (AC5). If this isn't what the reporter meant (e.g. `site_query` should become optional once `site_id` exists), §Data & API contract needs a one-line schema change — low blast radius either way.
- [已假设 / assumed] A site with no default document library, and a file path that resolves to a folder rather than a file, both fold into `file_not_found` rather than getting their own codes, since the ticket's table only defines four codes and neither of these two cases is "a site I can't find" (`site_not_found`) or "several sites, can't tell which" (`site_ambiguous`). If groom wants these split out as distinct codes (e.g. `no_document_library`, `not_a_file`), that's a small addition to the error-handling branch, not a redesign.
- [不阻塞 / non-blocking] The ticket's AC1 ("10 consecutive runs, no malformed-id errors") is a statistical/operational acceptance criterion that depends on a live tenant and the calling agent's own behavior, not something a unit test can assert. It's represented here as a manual/integration test case (see Test cases) rather than a unit-testable AC; the structural guarantee (one call, no id ever leaves the connector) is what AC1 above actually asserts and unit-tests can verify.
- [不阻塞 / non-blocking] `dump_json_capped`'s 20,000-char cap is well under the 200,000-byte read limit this tool reuses from `graph_read_file_text` — meaning a file in the ~19KB–200KB range would, today, get silently replaced by a generic "too large, narrow your query" notice instead of its actual (successfully fetched) content. This is a pre-existing gap shared with `graph_read_file_text` (see Current state), not introduced by this ticket, and the ticket explicitly asks for "same size/encoding limits as graph_read_file_text" — so this design keeps the 200,000-byte ceiling for parity rather than quietly lowering it. Flagged for groom/dev judgement: fixing `dump_json_capped` touches every tool that returns non-list text and is out of proportion to this ticket; a narrower fix scoped to just this tool (e.g. a tighter effective read limit that actually fits the JSON envelope budget) is possible but changes the ticket's own stated requirement. Recommend: accept as a known, pre-existing limitation for now.

## Tech design

### Conclusion

Add one new read-only tool, `graph_read_site_file_text`, to `src/graph_mcp/tools/sites.py`, registered alongside the other seven site/drive tools in the same `register()` function. It composes three already-proven Graph access patterns from this same file — keyword site search + drive enrichment (`graph_search_sites`), path-based item addressing (`graph_create_file_text`'s `root:/{path}:` call), and size-checked UTF-8 content read (`graph_read_file_text`) — into one call, replacing the three round trips with server-side resolution. The one genuinely new piece of shared infrastructure is a small, backward-compatible extension to `error_envelope()` so error responses can carry structured "extra data" (candidate lists, sibling file names) alongside the existing `code`/`message`/`retryable` fields — every other tool's error calls are unaffected since the new parameter is optional and defaults to omitting the extra data entirely.

### Where the current implementation lives

- `src/graph_mcp/tools/sites.py:49-89` — `graph_search_sites`: the keyword-search + drive-enrichment pattern this design's site-resolution step reuses (same `/sites?search=` call, same `/sites/{id}/drive` enrichment call).
- `src/graph_mcp/tools/sites.py:92-129` — `graph_list_drive_items`: the folder-listing pattern reused to produce the "file names in that folder" extra data on `file_not_found`.
- `src/graph_mcp/tools/sites.py:157-203` — `graph_read_file_text`: the size-check-then-read pattern (`_MAX_READ_BYTES`, UTF-8 decode) this design's content-read step reuses, splitting its single generic `invalid_argument` branch into the ticket's `file_too_large` / `not_text` codes.
- `src/graph_mcp/tools/sites.py:270-337` — `graph_create_file_text`: the `root:/{path}:` path-addressing call this design reuses to resolve `file_name` (+ optional `folder_path`) to an item without a separate listing round trip.
- `src/graph_mcp/_json.py:76-77` — `error_envelope(code, message, retryable)`: needs a new optional 4th parameter for structured extra data (see Data & API contract).
- `src/graph_mcp/api_client.py:61-116` — `GraphClient`: no changes; `get`/`get_content` are sufficient, both already used elsewhere in `sites.py`.
- `tests/test_tools.py:16-55` (`EXPECTED_TOOLS`), `:93` (tool-count cap `<=37`) — need a new entry and the cap raised to `<=38` with a justification line, following the file's own established pattern (see Change list).

### Data & API contract

**MCP tool contract** — `graph_read_site_file_text`:

Request:
```json
{
  "site_query": "permission matrix",
  "file_name": "Permission Matrix.csv",
  "folder_path": "HR/Matrix",
  "site_id": null
}
```
- `site_query`: required string (see Open Questions re: required-even-with-`site_id`).
- `file_name`: required string, matched case-insensitively via Graph's own path-addressing semantics (SharePoint/OneDrive paths are case-insensitive).
- `folder_path`: optional string; omitted/`null` → library root.
- `site_id`: optional string; when given, resolution skips the search call (AC5).

Success response (shape matches the ticket's own proposal exactly):
```json
{"site":{"id":"...","displayName":"Permission Matrix","webUrl":"..."},
 "drive":{"id":"...","name":"Documents"},
 "file":{"id":"...","name":"Permission Matrix.csv","size":232,"lastModifiedDateTime":"..."},
 "content":"Job Title,Collaboration,Department,Common,Confidential\n..."}
```

Error responses — all via the extended `error_envelope(code, message, retryable=False, extra=...)`:
- `site_not_found`: `extra = {"searched_for": site_query}` or `{"site_id": site_id}`.
- `site_ambiguous`: `extra = {"candidates": [{"id", "displayName", "webUrl"}, ...]}`.
- `file_not_found`: `extra = {"files_in_folder": [...]}` (or a `"reason"` string for the no-library / path-is-a-folder sub-cases).
- `file_empty`: `extra = {"file": {"name", "lastModifiedDateTime"}}`.
- `file_too_large`: `extra = {"size": N, "limit": 200000}`.
- `not_text`: `extra = {"file_type": "<mimeType>"}`.

All six are `retryable: false` — every one of them is a resolution/content problem that a Graph-level retry cannot fix, consistent with how `_STATUS_TO_CODE` in `api_client.py:31-39` marks `invalid_argument`/`not_found` as non-retryable.

**Graph API calls made** (read-only, in order, short-circuiting on first failure):
1. `GET /sites/{site_id}` (if `site_id` given) or `GET /sites?search={site_query}&$select=id,name,displayName,webUrl` (Graph Search API, same as `graph_search_sites`).
2. `GET /sites/{id}/drive` (default document library).
3. `GET /drives/{drive_id}/root:/{path}:?$select=id,name,size,file,folder,lastModifiedDateTime` (Graph path-addressing — same mechanism `graph_create_file_text:317` already uses).
4. On 404 from step 3: `GET /drives/{drive_id}/root:/{folder_path}:/children?$select=name` or `/drives/{drive_id}/root/children?$select=name` (for the `files_in_folder` extra data).
5. `GET /drives/{drive_id}/items/{item_id}/content` (raw bytes, same as `graph_read_file_text:190`).

**DB**: none — this service holds no state (gateway mode, per-request token only).

**Backward compatibility**: purely additive — a new tool, plus an optional 4th parameter on a shared helper that defaults to today's exact output when omitted. No existing tool's request or response shape changes.

### Key flow / sequence

```
agent → graph_read_site_file_text(site_query, file_name, folder_path?, site_id?)
  → _resolve_site(): site_id given? GET /sites/{id} : GET /sites?search=...
      ├─ not found / 404           → site_not_found
      ├─ >1 candidate, no exact match → site_ambiguous
      └─ resolved to exactly one site
  → _resolve_drive(): GET /sites/{id}/drive
      └─ 404 / no default library  → file_not_found (reason: no document library)
  → _resolve_file(): GET /drives/{drive_id}/root:/{path}:
      ├─ 404                       → list folder children → file_not_found (files_in_folder)
      ├─ resolves to a folder      → file_not_found (reason: path is a folder)
      └─ resolves to a file
  → size == 0                      → file_empty
  → size > 200,000 bytes           → file_too_large
  → GET .../content, decode utf-8
      ├─ UnicodeDecodeError        → not_text
      └─ success                   → {"site","drive","file","content"} via dump_json_capped
```

### Non-functional

- **Idempotency / concurrency**: every step is a `GET`; the tool is naturally idempotent and safe under concurrency — no shared mutable state is introduced (consistent with `GraphClient`'s existing per-instance-only state, `api_client.py:69-77`). Explicitly **do not** cache `site_query → site_id` or `(drive_id, path) → item_id` resolutions across calls, even as a performance optimization — the next caller's token may belong to a different tenant, and nothing in this tool's inputs proves otherwise (AC10).
- **Performance**: up to 5 sequential Graph round trips in the worst case (site search, drive lookup, file-path lookup, folder listing on miss, content fetch) versus the current 3 round trips the agent itself orchestrates today — more total HTTP calls, but zero model round trips for id-copying in between, which is the actual latency/reliability problem this ticket is about (an agent retry after a malformed-id failure costs far more than one extra server-side Graph call). No new caching, no new background work.
- **Security**: no new permission scope (reuses `Sites.Read.All`-equivalent already required by `graph_search_sites`/`graph_read_file_text`); read-only (AC10a) — this tool must never be capable of reaching a write/delete Graph endpoint, which the Change list's helper functions enforce structurally (they only ever call `client.get`/`client.get_content`, never `post`/`put`/`delete`). Error messages echo back caller-supplied `site_query`/`file_name`/`folder_path`, same existing pattern as other tools' validation errors (e.g. `graph_list_messages`'s `received_after` echo) — not a new risk.
- **Multi-tenant isolation**: covered under Permissions & multi-tenant above and asserted by AC10; no code path introduced by this change holds any token or resolved id beyond the single call's own stack frame.
- **Observability**: no new logging — `sites.py` has none today (consistent existing convention, not changed here); failures are fully diagnosable from the returned structured error alone (code + message + extra), which is in fact strictly more debuggable than today's single generic `invalid_argument` from the two existing branches this design replaces.

### Rollout & rollback

- No feature flag / no staged rollout infrastructure exists in this repo (`grep -rn "feature_flag" src/` — no hits, same as noted in the PRD-19661 precedent in this same file's history) — the new tool is purely additive (a new tool name any caller has to opt into by name), so it ships enabled with no gating needed.
- Release order: single repo (`ms-graph-mcp`), no cross-repo dependency for this ticket's own scope — wiring the onboarding agent's SKILL.md / Source card to actually call the new tool (listed in the ticket as "QA will make these" changes) is explicitly a separate, later change in a different repo (PRD-20211's territory), not part of this rollout.
- Rollback: `git revert` the change — it adds one new tool and one optional, backward-compatible parameter on a shared helper; no existing caller or tool is touched, so rollback carries no data-migration or in-flight-caller risk.

### Test strategy

- Unit tests (`tests/test_tools.py`, following the existing `_CapturingClient` fixture pattern used for other tools, e.g. the `graph_send_mail` tests from PRD-19661):
  - AC1: exact-match site + small text file in library root → correct `{"site","drive","file","content"}` shape, content matches exactly, and the capturing client's recorded calls are all `GET`.
  - AC2: no exact match, exactly one keyword hit → that hit used, no `site_ambiguous`.
  - AC3: zero site search results → `site_not_found`, `searched_for` echoed, no drive/file calls attempted (captured call list stops after the site search).
  - AC4: multiple keyword hits, none exact → `site_ambiguous`, candidates list matches the search results' `id`/`displayName`/`webUrl`.
  - AC5: `site_id` given → the capturing client never receives a `/sites?search=` call, only `GET /sites/{site_id}` directly.
  - AC6a: file path 404s → `file_not_found` with `files_in_folder` populated from the folder-listing call.
  - AC6b: path resolves to an item with a `folder` facet (not `file`) → `file_not_found`, reason states it's a folder.
  - AC6c (dev-sourced edge case, `source: dev`): site resolves but its `/drive` call 404s (no default document library) → `file_not_found`, reason states no document library — not independently required by the ticket's own AC list but follows directly from the Change list's `_resolve_drive` branch.
  - AC7: resolved file size `0` → `file_empty` before any content-fetch call is made (captured call list has no `/content` call).
  - AC8: resolved file size `200,001` → `file_too_large`, no `/content` call made; boundary case at exactly `200,000` → proceeds to content fetch (mirrors the `>` vs `>=` boundary test style already used for `graph_send_mail`'s attachment-size tests).
  - AC9: content fetch returns bytes that fail UTF-8 decode → `not_text`, `file_type` populated from the file's `mimeType`.
  - AC10b: two calls in sequence using different `_CapturingClient` instances (standing in for different tenants/tokens) with different site/file names → assert no state (module-level dict, cache, etc.) is shared — this is a structural assertion best enforced by code review (no module-level mutable cache exists in the Change list's design) plus a test that two back-to-back calls with different inputs both independently issue their own full resolution chain (i.e. the second call's site-search call is actually made, not skipped) — a cache bug would make the second call's `_CapturingClient` NOT receive the expected search call.
  - `test_tools_list_snapshot` (existing test): update `EXPECTED_TOOLS` and the `<=38` cap; must keep passing for the other 37 tools unchanged.
- Integration / manual (cannot be unit-tested, needs a live tenant — executed and evidenced in the dev+test leg):
  - The ticket's own AC1 ("10 consecutive runs, no malformed-id-style errors") — run the real onboarding agent (or a scripted equivalent) against a live tenant's `Permission Matrix.csv` 10 times back to back via the new tool, confirm zero id-related failures. This is explicitly an operational/statistical check, not a unit-testable AC (see Open Questions).
  - A real `.xlsx`/`.docx` file in a test tenant → confirm `not_text` fires with a sensible `file_type`, since unit tests can only simulate the UTF-8 decode failure, not Graph's actual `mimeType` reporting for a real binary file.
- Regression: none of the three existing chained tools (`graph_search_sites`/`graph_list_drive_items`/`graph_read_file_text`) are modified — their existing (zero) test coverage is unchanged, and this ticket does not expand it (out of scope; flagged only as an existing gap, not something this ticket is responsible for closing).

### Effort & breakdown

**0.5–1.5 person-days.** Lower bound: the three Graph-call patterns being composed are all already proven elsewhere in this file, and the `error_envelope` extension is a small, additive change — most of the work is writing the ~10 unit tests. Upper bound's uncertainty comes from the two live-tenant manual checks (10-consecutive-run check, real binary-file `not_text` check), which depend on test-tenant/account availability the same way the PRD-19661 precedent's integration step did. No sub-task split needed — this is one file's one new tool plus one shared-helper extension; it doesn't naturally decompose into independently-shippable pieces.

### Risks & dependencies

- **Dependency**: a live, already-consented test tenant with a SharePoint site containing both a small text file and a real binary file, for the two manual/integration checks above. `ms-graph-mcp` is gateway-mode and holds no credentials itself (same as the PRD-19661 precedent's note) — the test account is provided by whoever runs the dev+test leg, not configured as part of this design.
- **Risk**: the `dump_json_capped` truncation gap for non-list payloads (Open Questions) — for a file near the upper end of the 200,000-byte limit, the tool would report success at the Graph-call level but return a useless truncation notice instead of content. This risk already exists for `graph_read_file_text` today and is not introduced by this ticket; flagged so it isn't silently inherited without the groom/dev being aware.
- **Risk**: the `site_query`-required-even-with-`site_id` spec inconsistency (Open Questions) — low impact either way, but worth a one-line confirmation from the reporter before implementation locks in the schema, since `tests/test_tools.py`'s `EXPECTED_TOOLS` snapshot makes the required-parameter set a hard-asserted contract that's mildly annoying to change later (though not expensive — one line in one dict).
- **Risk (minor, not blocking)**: Graph's `root:/{item-path}:` addressing embeds the path directly in the URL; a `file_name` or `folder_path` containing characters like `#` (URL fragment delimiter) could behave unexpectedly depending on how `httpx` builds the request URL from the interpolated string. This is a pre-existing risk shared with `graph_create_file_text:317`'s identical pattern, not newly introduced here, and out of scope to fix generally — noted since this ticket's own example filenames ("Permission Matrix.csv") are unaffected (plain space, which is handled correctly), but a future filename with `#`/`%`/`?` would hit the same latent issue both tools already have.
- **Dependency**: none on PRD-20211 completing first — that ticket's own fix is in a different repo (the onboarding agent's SKILL.md), and its reopened state is actually part of this ticket's own justification (Current state), not a blocker.
