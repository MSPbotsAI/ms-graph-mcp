## Requirement understanding

One line: Update the Microsoft Graph MCP skill so it can list a group's members with pagination, fetch a group's details by ID (including mail-enabled and sync source), list the tenant's domains, and check whether a user exists via proxyAddresses — closing four gaps that block Ginko's Rewst-to-MSPbots migration from reaching parity by the reporter's Nov 7 target.

Developers migrating Ginko off Rewst need to reproduce, using only this Graph MCP's tools, four specific directory lookups that Rewst's existing automations already do. Today's tool set covers adjacent but different questions (search groups by name, list a user's own group memberships, check a user's existence by exact UPN/mail) and has no domain-listing tool at all. The reporter explicitly confirmed all four must ship together as one minimal slice, not partially — see the ticket's "Minimal Viable Slice" and "Priority" sections (reporter set High: "blocks parity ... for the Nov 7 migration goal").

## Current state (every claim carries path:line)

- `graph_list_groups` (`src/graph_mcp/tools/groups.py:118-169`) searches/lists groups by display name; it does not accept a group ID and does not return a given group's member list.
- `graph_list_user_groups` (`groups.py:69-115`) and `graph_list_owned_groups` (`groups.py:171-250`) both walk group membership from the *user* side (groups a user belongs to / owns); no tool walks it from the *group* side (who is in this group).
- No tool fetches one group's full details by ID. The closest is the `$select` used inside `graph_list_groups`/`graph_list_user_groups` (`id,displayName,groupTypes,securityEnabled,mailEnabled`), which already proves `mailEnabled` is readable — it is just not exposed via a get-by-id tool, and `onPremisesSyncEnabled` / `onPremisesLastSyncDateTime` (the "sync source" the ticket asks for) are not selected anywhere in this file.
- There is no `domains.py` in `src/graph_mcp/tools/` at all — the full module list is `calendar.py, devices.py, groups.py, licenses.py, mail.py, sites.py, users.py` (confirmed by directory listing). Tenant domain listing has no existing surface in this repo.
- `graph_check_user_exists` (`src/graph_mcp/tools/users.py:32-72`) takes exactly one of `user_principal_name` or `mail` and does an exact `$filter` match; there is no `proxy_address` parameter and no `proxyAddresses/any(...)` style filter anywhere in the repo (`grep -rn "proxyAddress" src/` → no hits).
- Scope evidence (read-only reference, different repo, no code change requested there by this ticket): `https://github.com/MSPbotsAI/mcp-service-gateway@release (5719ab2)`, `mspbots-mcp-manager/mcp_manager/auth/oauth/vendors/msgraph.py:120-129` — the platform's fixed OAuth consent for this connector already requests `Group.Read.All`, `GroupMember.Read.All`, `GroupMember.ReadWrite.All`, and `Directory.Read.All`. ## Product design

### Goals / Non-goals

Goals:
- G1: An agent can list a given Entra ID group's members, paged, following the repo's existing pagination convention (default 50 / hard cap 200 / `has_more`).
- G2: An agent can fetch one group's details by its object ID, including whether it is mail-enabled and its on-premises sync status ("sync source").
- G3: An agent can list the tenant's registered domains.
- G4: An agent can check whether a user exists by a proxy address, not only by primary UPN/mail — matching what Rewst's current automations already do.
- G5 (reporter-mandated): ship all four in one release; no partial slice.

Non-goals:
- NG1: Any write/mutation on groups, domains, or proxyAddresses — the ticket's "Desired Behavior" section only asks for lookups; all four capabilities are read-only.
- NG2: Any change on the platform side (`mcp-service-gateway`) — not needed per the Current state evidence above, and that repo is not this ticket's Code Project.
- NG3: Any change on Rewst's side — this ticket is scoped to MSPbots' own Graph skill only.

### Acceptance criteria AC1..AC5

- AC1: Given a group with more members than the requested page size, When an agent calls the group-members tool with `max_results=N`, Then it returns at most N members and `has_more=true`; When `max_results` is greater than or equal to the group's total member count, Then `has_more=false` and every member is returned exactly once.
- AC2: Given a valid group object ID, When an agent calls the group-details tool, Then the response includes the group's display name, whether it is mail-enabled, and its on-premises synchronization status (synced from on-prem AD vs. cloud-only, plus the last sync timestamp when synced); When the ID does not resolve to an existing group, Then the tool returns a not-found error, not an empty success.
- AC3: Given no filter, When an agent calls the domain-listing tool, Then it returns every domain registered to the tenant together with each domain's verified/default/authentication-type flags; When the tenant's domain list is empty, Then it returns an empty list, not an error.
- AC4: Given a proxy-address string (e.g. a secondary SMTP alias that is not the user's primary mail or UPN), When an agent calls the existence-check tool with that value, Then it returns `exists=true` plus the matching user's basic profile if any user's `proxyAddresses` collection contains it, and `exists=false` otherwise.
- AC5: Given the four tools above are implemented and deployed, When a tenant admin opens Capabilities > Connectors > Microsoft Graph > Tools and clicks **Refresh Tools**, Then the four new tools appear in the inventory with no other platform change required (wiki: `ProductDocs/15-Capabilities.md § Connector detail view`).

### 4.1 Main flow

An agent resolves a group or user through an existing tool (e.g. `graph_list_groups`, `graph_check_user_exists`), then calls one of the four new/extended tools with that ID to answer the specific question (who is in this group / what are this group's details / what domains exist / does this alias belong to someone) — mirroring the existing `graph_list_user_groups` → `graph_assign_groups` resolve-then-act pattern already documented in this repo's README "Typical Workflows."

### 4.2 Interface & interaction changes

Not applicable in the usual UI sense — this repo has no end-user screen. The only user-facing surface is the Capabilities > Connectors > Microsoft Graph tool list (see AC5), which updates automatically; no dialog, field, or control is added or changed there.

### 4.3 Boundaries & exceptions

- Empty group (zero members) → empty list, `has_more=false`, not an error.
- Non-existent group ID (both for members-listing and get-by-id) → a `not_found` error envelope (existing `GraphError`/404 → `not_found` mapping), never an empty success — a caller must be able to tell "no members" apart from "no such group."
- Tenant with zero or one domain → list still returns correctly; no special-casing required by Graph's `/domains` endpoint.
- proxy-address value containing an apostrophe or other OData-sensitive character (e.g. `O'Brien's alias`) → must be escaped the same way every existing `$filter` literal in this repo already is (`odata_quote`), or the query 400s.
- proxy-address value with no match → `exists=false`, not an error (parity with today's `graph_check_user_exists` behavior for a non-existent UPN/mail).

### 4.4 Permissions & multi-tenancy

No change to this repo's tenant-isolation model: every one of the four tools, like all 32 existing tools, receives the caller's Graph access token per request via the `X-Ms-Graph-Token` header, isolated per request through a `contextvars.ContextVar` (`src/graph_mcp/server.py`, `GatewayTokenMiddleware`), and every Graph call made through `GraphClient` carries only that token (`src/graph_mcp/api_client.py:69-77`). There is no server-side cache or shared client keyed by tenant, so one tenant's token can never leak another tenant's group/user/domain data through these new tools. No new scope is requested (see Current state) and no scope broader than what is already granted is needed — `Directory.Read.All` is already the widest permission in the consent set and is unused today.

## 5. Scope split

MVP = all four tools, per the reporter's explicit non-negotiable ("ship all four together"); there is no smaller slice this ticket should produce. A future iteration (not this ticket) could add write support (e.g. updating a domain's federation settings) if a need for it appears — no such need is stated here.

If the requester needs prefix-insensitive matching, this needs a re-groom of AC4.

Assumed: return the first four; omit `supportedServices` (a multi-value list rarely needed by a migration-parity use case, and keeps the response small) unless groom says otherwise.
- [assumed] "Ship all four together" is read as "delivered in the same release/PR," not "answerable from a single tool call." If this reading is wrong, §10 (effort & breakdown) in the tech design needs to be redone as one combined tool instead of four.

### Conclusion

Add two new tools to `tools/groups.py` (list a group's members, get a group by ID), one new module `tools/domains.py` (list tenant domains), and one new optional parameter on the existing `graph_check_user_exists` in `tools/users.py` (proxy-address lookup). All four reuse the existing `GraphClient`/pagination/error-envelope conventions already in the codebase — this is a code-only change in this repo; no platform-side (`mcp-service-gateway`) change and no new Entra scope are required, because `Group.Read.All`, `GroupMember.Read.All`, `Directory.Read.All`, and `User.Read.All` are already granted (see Current state).

### Option analysis

| Tool | Option | Decision |
|---|---|---|
| Group members | New tool `graph_list_group_members(group_id, max_results)` vs. overloading `graph_list_groups` with an optional `group_id` that switches its return shape | **New tool.** Overloading would make one tool's return shape depend on which argument was passed — exactly the "mode flag" shape this repo's own test comments already reject (see `tests/test_tools.py`'s calendar/mail split rationale, e.g. the comment above `EXPECTED_TOOLS` explaining why listing and reading mail stayed separate tools). |
| Group details | New tool `graph_get_group(group_id)` vs. same overload idea | **New tool**, mirroring the existing `graph_get_user` vs. `graph_list_users` split — a dedicated get-by-id tool already has a precedent in this exact codebase. |
| Domains | New module `tools/domains.py` vs. folding into `tools/licenses.py` (both touch organization-level data) | **New module.** `licenses.py` is scoped to `subscribedSkus`/license assignment, a disjoint Graph resource; `/domains` is its own resource family, same granularity as `devices.py` or `calendar.py` each being one small module per resource family. |
| proxyAddresses | Extend `graph_check_user_exists` with a third optional, mutually-exclusive parameter vs. a new `graph_check_user_exists_by_proxy` tool | **Extend the existing tool.** The question being asked ("does this user exist") is unchanged; only the identifier type changes, matching the tool's current shape (exactly one of `user_principal_name`/`mail` required today). A separate tool would split one question across two tools, which this repo's "disjoint arguments only" rule (same test-comment rationale) argues against — here the three parameters are different ways to ask the same question, not different questions. |

### Data & API contract

**`graph_list_group_members`**
- Request: `group_id: str` (required), `max_results: int = 50` (hard cap 200, same as every other list tool).
- Graph call: `GET /groups/{group_id}/members?$select=id,displayName,userPrincipalName,mail&$top=<page_size>`, follow `@odata.nextLink` until `max_results` or no more pages.
- Response: `{"group_id": "...", "count": 3, "members": [{"id": "...", "displayName": "...", "userPrincipalName": "...", "mail": "...", "member_type": "user"}], "has_more": false}`.
- Errors: unknown `group_id` → Graph 404 → `{"error": {"code": "not_found", "message": "...", "retryable": false}}` (existing mapping, unchanged).

**`graph_get_group`**
- Request: `group_id: str` (required).
- Graph call: `GET /groups/{group_id}?$select=id,displayName,description,mail,mailEnabled,mailNickname,securityEnabled,groupTypes,visibility,onPremisesSyncEnabled,onPremisesLastSyncDateTime,onPremisesSamAccountName`.
- Response: `{"id": "...", "displayName": "...", "mailEnabled": true, "mail": "...", "securityEnabled": false, "groupTypes": ["Unified"], "sync_source": "cloud-only", "onPremisesSyncEnabled": null, "onPremisesLastSyncDateTime": null}`.
- Errors: unknown `group_id` → `not_found` (same mapping).

**`graph_list_domains`**
- Request: no parameters.
- Graph call: `GET /domains?$select=id,isDefault,isVerified,isAdminManaged,authenticationType`.
- Response: `{"count": 2, "domains": [{"id": "contoso.com", "isDefault": true, "isVerified": true, "isAdminManaged": true, "authenticationType": "Managed"}, ...]}`.
- Errors: none specific beyond the existing generic `GraphError` mapping (e.g. `403` if the token's tenant somehow lacks the already-granted scope — should not happen given Current state, but the existing `unauthorized` mapping already covers it defensively).

**`graph_check_user_exists` (extended)**
- Request: exactly one of `user_principal_name`, `mail`, `proxy_address`.
- Graph call (new branch): `GET /users?$filter=proxyAddresses/any(x:x eq '<odata_quote(proxy_address)>')&$count=true&$select=id,displayName,userPrincipalName,mail,accountEnabled`, header `ConsistencyLevel: eventual`.
- Response: unchanged shape — `{"exists": true, "user": {...}}` or `{"exists": false, "user": null}`.
- Errors: zero or 2+ of the three identifiers supplied → `{"error": {"code": "invalid_argument", "message": "Provide exactly one of user_principal_name, mail, or proxy_address.", "retryable": false}}`.
- Backward compatibility: existing callers passing only `user_principal_name` or `mail` are unaffected — the new branch only activates when `proxy_address` is supplied.

No DB, no migration, no event/message changes — this repo has no persistence layer (stateless gateway over Graph).

### Key flow / sequence

1. Agent resolves a group's ID (e.g. via `graph_list_groups`) or already has one from a prior step.
2. Agent calls `graph_list_group_members(group_id, max_results=50)`.
3. `GraphClient.get("/groups/{id}/members", params={...})` → Graph API.
4. If `@odata.nextLink` present and under `max_results`, the tool follows it (same loop shape as `graph_list_groups`).
5. Tool returns `{members, has_more}` to the agent.

(Get-group, list-domains, and the proxy-address check are single-request variants of the same shape — steps 3-5 collapse to one call each, no loop.)

### Non-functional

- **Idempotency & concurrency**: all four are read-only GETs; no state mutation; safe under arbitrary concurrent calls; nothing to coordinate.
- **Performance**: `/groups/{id}/members` can be large for big groups — cap at `max_results` (hard cap 200) and stop, exactly like `graph_list_groups`/`graph_list_user_groups`; deliberately **not** the N+1 full-crawl shape used by `graph_list_owned_groups` (that tool has no alternative; this one does, because Graph's native member listing on a *known* group ID doesn't have the "no filter by owner" problem that forced the N+1 design there).
- **Security**: no new privilege is requested (reuses already-granted scopes, see Current state). The proxy-address filter must reuse `odata_quote` (`_common.py:8-16`) exactly as `mail`/`display_name` filters do today — skipping it would let an apostrophe or crafted value break or manipulate the `$filter` clause. Relevant OWASP API Top-10 entry: API3:2023 (Broken Object Property Level Authorization / excessive data exposure) — on a match, return only the same minimal profile fields `graph_check_user_exists` already returns (`id, displayName, userPrincipalName, mail, accountEnabled`), not the full `proxyAddresses` collection, so this lookup cannot be used to enumerate a user's other aliases.
- **Multi-tenant isolation**: unaffected — see Product design §4.4; every call is scoped by the caller's own per-request delegated token, identical to all 32 existing tools.
- **Observability**: reuse the existing `GraphError` → `error_envelope` mapping unchanged; this repo has no tool-level logging beyond what `httpx`/`GraphClient` already does, so no gap is introduced relative to the rest of the codebase.

### Rollout & rollback

- No feature-flag mechanism exists in this repo (`config.py`/`server.py` confirmed clean of any flag infra) — ship as a normal version bump; all four changes are additive (three new tools, one new optional parameter), so no existing agent-facing behavior changes.
- No platform-side (`mcp-service-gateway`) change is required before these tools work (see Current state) — unlike the `Mail.Read`/`Calendars.ReadWrite` precedent, there is no "already-connected tenants must re-authorize" step here.
- Suggested sequence: implement → extend `EXPECTED_TOOLS`/raise the ceiling assert → merge → deploy → a tenant admin clicks **Refresh Tools** on the Microsoft Graph connector (wiki: `ProductDocs/15-Capabilities.md`) to pick up the four new tools immediately.
- Rollback: revert the commit / redeploy the previous image. Tools disappearing from the MCP capability list is safe — agents simply stop seeing them; nothing existing breaks, since the only modification to an existing tool (`graph_check_user_exists`) is a backward-compatible optional parameter.

### Test strategy

- **Unit/snapshot** (no network): extend `tests/test_tools.py`'s `EXPECTED_TOOLS` and the ceiling assert — existing pattern, zero new infrastructure.
- **Mocked-client tests**: using the existing `_CapturingClient` pattern already in `test_tools.py`, assert each new/changed tool builds the correct Graph request — path, `$select`/`$filter` content, and, critically, that the proxy-address call carries `ConsistencyLevel: eventual` and `$count=true` — without touching a real tenant.
- **Manual / real-tenant verification required before trusting results live** (same caveat pattern this repo already uses for every other tool batch in README § Known Gaps): need (a) a real group with more members than one page, (b) one real AD-synced group and one real cloud-only group to confirm the `sync_source` derivation, (c) the tenant's actual domain list to cross-check `graph_list_domains`'s output, and (d) a real user with a secondary proxy address to confirm this tenant/Graph-version actually accepts the advanced-query filter syntax as documented — Microsoft's advanced-query behavior has shown non-obvious tenant-specific edge cases before in this exact repo (see the `graph_list_owned_groups` delta-endpoint pagination bug story in README § Known Gaps), so this is flagged as the single highest-risk verification item.
- **Regression**: none of the four changes alter any existing tool's request shape except the additive, optional parameter on `graph_check_user_exists` — re-run the full existing suite to confirm.

### Effort & breakdown

- 1.5–2.5 person-days: `domains.py` (smallest, ~0.25d) + group-members and get-group (~0.75d, same file, similar shape to existing code) + proxy-address extension (~0.5d, extra care for the advanced-query header) + test updates (~0.5d) + README table/Known-Gaps updates (~0.25d).
- Main source of uncertainty: how much real-tenant verification time the advanced-query (`ConsistencyLevel`) path needs if the documented behavior doesn't hold on the first attempt — this repo has precedent for Graph behaving differently than documented (the delta-endpoint pagination bug in `graph_list_owned_groups`'s history).
- Suggested as a single sub-task — the reporter explicitly wants all four shipped together (G5), and splitting them would not let any of them ship independently anyway.

### Risks & dependencies

- **R1 (verified low)**: no platform-side scope/consent dependency — see Current state's citation of `mcp-service-gateway`'s `msgraph.py`. Flagging this explicitly so reviewers don't default-assume the `Mail.Read`/`Calendars.ReadWrite` re-authorization pattern applies here; it does not.

Primary technical risk; mitigate by real-tenant verification before merging to the release branch, and add a README § Known Gaps bullet if not verified by merge time (repo convention).
- **R3 (low)**: `/groups/{id}/members` can return nested groups and service principals, not only users — `member_type` must not assume every row is a user.
- **Dependencies**: none on other open tickets. `mcp-service-gateway` is cited as read-only evidence only; this ticket requests no code change there.
