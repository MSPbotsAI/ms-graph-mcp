## 需求理解

一句话：提单人希望 Microsoft Graph MCP 新增一个工具，按「站点名 + 文件名」在服务端一次调用就能读到 SharePoint 文件内容，这样调用模型就不需要在多次工具调用之间复制那个很长的 `driveId`/item id —— 正是这个复制动作导致了 node J 间歇性的 "malformed drive id" 失败。

今天 Onboarding agent 的 node J 读取 `Permission Matrix.csv` 需要串联三次调用——`graph_search_sites` → `graph_list_drive_items` → `graph_read_file_text`——模型要在前两步之间把又长又随机的 `driveId` 重新打一遍。SOP 侧已经试过一次纯提示词层面的缓解（PRD-20211，`felix.zhou`，2026-10-09）但没能稳住：QA 在 2026-10-10 的复核（PRD-20211，`Pantene Hui`）在另一次运行中又复现了同样的 driveId 损坏，即便已经加上了更严格的指令，PRD-20211 因此被重新打回 `6a - in dev`。提单人自己的结论（本单原文引用）是：指令没法保证逐字符复制百分百可靠，真正的修法是把模型从这条数据路径上拿掉——也就是改连接器，而不是改提示词。成功的标志是一个新的只读工具 `graph_read_site_file_text(site_query, file_name, folder_path?, site_id?)`，一次调用内完成站点 → 文档库 → 文件 → 内容的解析，并带结构化错误码（`site_not_found` / `site_ambiguous` / `file_not_found` / `file_empty`，以及下面补充的两个），让调用方能据此分支处理，而不是拿到一个通用错误。

工单本身已经带了一份相当完整的技术提案（工具名、参数、服务端逻辑、响应/错误结构）——这份设计的工作是拿这份提案去对照 `ms-graph-mcp` 的真实代码做核验，调整和现有代码不吻合的地方，并把需要人拍板的地方标出来。

## 产品设计

### 目标 / 非目标

**目标**：一个知道 SharePoint 站点名和文件名的 agent，能用**一次**工具调用读到该文件的文本内容，模型自己的输出里**不会**出现任何 `driveId` 或 item id。失败时，agent 拿到的是一组固定结构化错误码中的一个，可以据此分支处理，而不是一句通用错误文字。

**非目标**（本次不做）：
- 替换或移除 `graph_search_sites` / `graph_list_drive_items` / `graph_read_file_text`——它们仍保留给已经拿到 `drive_id` 的调用方（比如交互式浏览文档库），或者需要列出文件夹内容而不是按名字读单个文件的场景。
- 读取二进制 Office 文档（`.docx`/`.xlsx`/`.pdf`）——与 `sites.py` 模块 docstring 里已经声明的范围边界一致（`sites.py:1-19`）；本单的新工具继承同样的"仅 UTF-8 文本"限制。
- 写入或修改 SharePoint 内容——新工具只读，与 `graph_search_sites`/`graph_list_drive_items`/`graph_read_file_text`/`graph_get_file` 一致。
- 修复上面提到的 `dump_json_capped` 既有截断缺口（见 Open Questions）——本单只要求自己的响应形状不让这个既有问题变得更糟，不负责修别的工具。
- 改动 onboarding agent 的 SKILL.md / Source 卡（PRD-20211 的范围，另一个仓库）——本单只交付连接器工具本身；工单原文明确写了接线 node J 使用新工具是"QA will make these"的发布后动作。

### 方案（用户可见行为）

#### 主流程

调用方（agent）调用 `graph_read_site_file_text(site_query="permission matrix", file_name="Permission Matrix.csv")`。服务端：根据 `site_query` 解析站点（优先精确、大小写不敏感的名称匹配，见技术设计），打开其默认文档库，定位指定文件（可选在 `folder_path` 下），返回其文本内容——全部在这一次调用的响应里完成。整个过程中 agent 不会看到也不需要处理任何 `driveId` 或 item id。

#### 交互与失败分支

每种失败情形返回一个独立的 `error.code`，并附带足够的结构化上下文，让 agent 能直接采取行动，而不必立刻把问题转回给人：

| 错误码 | 何时触发 | 附带的结构化信息 |
|---|---|---|
| `site_not_found` | `site_query` 没有命中任何站点（或 `site_id` 解析不出来） | 用过的搜索词/id |
| `site_ambiguous` | 有不止一个站点可能匹配，且没有一个是精确名称匹配 | 候选站点列表（id、displayName、webUrl） |
| `file_not_found` | 已解析的站点/文档库下找不到该名字/路径的文件（含：路径指向的是文件夹而不是文件；站点根本没有文档库） | 该文件夹下实际存在的文件名列表 |
| `file_empty` | 文件存在但大小为 0 字节 | 文件名、最后修改时间 |
| `file_too_large` | 文件超过 200,000 字节的读取上限 | 实际大小、上限值 |
| `not_text` | 文件内容不是合法 UTF-8（即二进制 Office 文档或类似文件） | 文件的类型信息 |

#### 边界与异常

- 同时传了 `site_id` 和 `site_query`：`site_id` 优先生效，`site_query` 按工单原文的参数表要求仍然必填，但解析时不使用它。见 Open Questions——这是工单自己规格里的一处小矛盾，这里给出一个默认处理，待 groom 确认。
- `folder_path` 省略 → 在文档库根目录查找，沿用 `graph_list_drive_items` 的既有约定（省略 `folder_id` → 根目录）。
- 多个关键词命中中恰好有一个精确（大小写不敏感）displayName 匹配 → 直接用它，不报歧义错误，即便底层搜索技术上返回了不止一个站点。
- 文件路径实际指向的是文件夹而不是文件 → 归为 `file_not_found`（你要找的文件不存在；文件夹不是可读的文本文件），不单独开一个错误码——工单给出的四个码里没有第五个码对应这种情况，而这里如果用 `not_text` 会造成误导（根本没有文件内容可供尝试解码）。

#### 权限与多租户

不引入新的权限范围：复用 `graph_search_sites`/`graph_read_file_text` 已经要求的 Graph 应用权限（`Sites.Read.All` 或等价权限——参照工单自己的"Permissions"一节，且与 `sites.py` 里其它工具都通过同一个按请求创建的 `client_factory()` 获取客户端的方式一致）。每次调用的 `GraphClient` 只携带那一次调用自己的 token（`api_client.py:69-77`）；站点/文档库/文件的解析结果**不得**跨调用缓存——租户 A 的 token 解析出来的结果绝不能被复用去服务租户 B 用相同 `site_query`/`file_name` 发起的调用。这只是现有无状态设计的自然推论，不是新机制，但这里特别点出来，是因为"缓存一下站点搜索结果省一次往返"这种善意的性能优化，恰恰是最容易悄悄打破租户隔离的地方。

### 验收标准 AC1..AC10

- **AC1**：Given 一个 displayName 精确（大小写不敏感）匹配 `site_query` 的站点，其文档库根目录下有一个较小（`<=200,000` 字节）的 UTF-8 文本文件名为 `file_name`，When agent 调用一次 `graph_read_site_file_text(site_query=..., file_name=...)`，Then 响应中包含该文件的精确内容，以及技术设计契约中描述的站点/文档库/文件元信息，且 agent 全程不需要提供任何 `driveId` 或 item id。
- **AC2**：Given `site_query` 没有精确 displayName 匹配，但关键词搜索恰好只有一个命中，When 调用该工具，Then 直接使用这唯一命中（不报 `site_ambiguous`），文件按 AC1 同样方式解析并读取。
- **AC3**：Given `site_query` 没有命中任何站点，When 调用该工具，Then 返回 `error.code = "site_not_found"`，带回搜索词，且不会尝试查询任何文档库或文件。
- **AC4**：Given `site_query` 有不止一个关键词命中且没有任何一个是精确 displayName 匹配，When 调用该工具，Then 返回 `error.code = "site_ambiguous"`，附带每个候选站点的 id、displayName、webUrl。
- **AC5**：Given 传入了一个合法的 `site_id`（无论是否同时传了 `site_query`），When 调用该工具，Then 站点解析直接使用 `site_id`，完全跳过搜索调用。
- **AC6**：Given 站点/文档库解析成功，但在 `file_name`（可选 `folder_path` 下）找不到对应文件——包括该站点根本没有文档库、或路径指向的是文件夹而非文件这两种情形，When 调用该工具，Then 返回 `error.code = "file_not_found"`，附带该文件夹下实际存在的文件名列表（若文档库/文件夹本身不存在则为空列表）。
- **AC7**：Given 解析出的文件存在但大小为 0 字节，When 调用该工具，Then 返回 `error.code = "file_empty"`，附带文件名与最后修改时间，且不尝试读取/解码内容。
- **AC8**：Given 解析出的文件大小超过 200,000 字节，When 调用该工具，Then 返回 `error.code = "file_too_large"`，附带实际大小与上限值，且不拉取文件内容字节。
- **AC9**：Given 解析出的文件内容不是合法 UTF-8（例如 `.xlsx`/`.docx`/`.pdf`），When 调用该工具，Then 返回 `error.code = "not_text"`，附带文件的类型信息。
- **AC10（只读 / 多租户）**：Given 对该工具的任意一串调用，包括用不同访问令牌（不同租户）发起的调用，When 这些调用执行，Then (a) 该工具发出的任何 HTTP 请求都只能是 `GET`，不会是别的方法；且 (b) 任何一次调用的站点/文档库/文件解析结果都不会被另一次调用复用——每次调用都独立地根据自己的参数和自己的 token 重新解析一遍。

### Open Questions

- [已假设] `site_query` 与 `site_id` 的关系：工单自己的参数表把 `site_query` 标为"Required: yes"，同时又把 `site_id` 描述为可以用来"跳过站点搜索"——这两句话本身是矛盾的（如果 `site_id` 单独就够用，`site_query` 就不该是无条件必填）。这里的处理是：按工单原文，`site_query` 在工具 schema 里保持必填；但当 `site_id` 也给出时，服务端逻辑使用 `site_id` 并忽略 `site_query`（对应 AC5）。如果提单人实际想要的是"有了 `site_id` 之后 `site_query` 应该变成可选"，那只需要在"数据与接口契约"一节改一行 schema，影响面很小。
- [已假设] 站点没有默认文档库、以及路径解析到的是文件夹而不是文件，这两种情形都归到 `file_not_found`，而不是各自开一个新码——因为工单的表里只定义了四个码，这两种情形既不是"找不到站点"（`site_not_found`），也不是"多个站点分不清选哪个"（`site_ambiguous`）。如果 groom 希望把这两种情形拆成独立码（比如 `no_document_library`、`not_a_file`），只是错误处理分支上的小改动，不需要重新设计。
- [不阻塞] 工单自己的 AC1（"10 次连续运行，零 malformed-id 错误"）是一条依赖真实租户和调用 agent 自身行为的统计性/运营性验收标准，不是单元测试能断言的东西。这里把它落实成一条手工/集成测试用例（见测试用例一节），而不是写成一条单测能判的 AC；上面的 AC1 实际断言的是其结构性保证（一次调用、id 全程不出连接器），这部分是单测可以验证的。
- [不阻塞] `dump_json_capped` 的 20,000 字符上限，远小于本工具从 `graph_read_file_text` 继承的 200,000 字节读取上限——意味着一个处于约 19KB–200KB 区间的文件，今天会被静默替换成一句通用的"太大了，缩小查询范围"提示，而不是它本该成功取到的真实内容。这是与 `graph_read_file_text` 共有的既有缺口（见现状一节），不是本单引入的，而工单原文明确要求"与 graph_read_file_text 相同的大小/编码限制"——所以这份设计为了与之对齐保留了 200,000 字节这个上限，而不是悄悄调低它。留给 groom/开发判断：修 `dump_json_capped` 会影响所有返回非列表文本的工具，相对本单明显是个更大的改动；只针对本工具单独收紧一个真正能塞进 JSON 预算的有效读取上限也是可行的，但会与工单自己写明的要求不一致。建议：暂时接受这个已知的既有限制。

## 技术设计

### 结论

在 `src/graph_mcp/tools/sites.py` 里新增一个只读工具 `graph_read_site_file_text`，和另外七个站点/文档库工具一起注册在同一个 `register()` 函数里。它把这个文件里已经验证过的三种 Graph 访问模式组合成一次调用——关键词站点搜索 + 文档库补全（`graph_search_sites`）、按路径寻址 item（`graph_create_file_text` 的 `root:/{path}:` 调用）、带大小检查的 UTF-8 内容读取（`graph_read_file_text`）——用服务端解析取代原来的三次往返。唯一真正新增的共享基础设施，是对 `error_envelope()` 做一处小的、向后兼容的扩展，让错误响应除了现有的 `code`/`message`/`retryable` 外还能携带结构化的"附加数据"（候选列表、同级文件名等）；由于新参数是可选的，其余所有调用点都不受影响。

### 现有实现定位

### 数据与接口契约

**MCP 工具契约** —— `graph_read_site_file_text`：

请求：
```json
{
  "site_query": "permission matrix",
  "file_name": "Permission Matrix.csv",
  "folder_path": "HR/Matrix",
  "site_id": null
}
```
- `site_query`：必填字符串（关于"即便有 `site_id` 也必填"，见 Open Questions）。
- `file_name`：必填字符串，大小写不敏感匹配（沿用 Graph 自身路径寻址的语义——SharePoint/OneDrive 的路径本就大小写不敏感）。
- `folder_path`：可选字符串；省略/`null` → 文档库根目录。
- `site_id`：可选字符串；给出时解析跳过搜索调用（对应 AC5）。

成功响应（形状与工单自己的提案完全一致）：
```json
{"site":{"id":"...","displayName":"Permission Matrix","webUrl":"..."},
 "drive":{"id":"...","name":"Documents"},
 "file":{"id":"...","name":"Permission Matrix.csv","size":232,"lastModifiedDateTime":"..."},
 "content":"Job Title,Collaboration,Department,Common,Confidential\n..."}
```

错误响应——全部通过扩展后的 `error_envelope(code, message, retryable=False, extra=...)`：
- `site_not_found`：`extra = {"searched_for": site_query}` 或 `{"site_id": site_id}`。
- `site_ambiguous`：`extra = {"candidates": [{"id", "displayName", "webUrl"}, ...]}`。
- `file_not_found`：`extra = {"files_in_folder": [...]}`（无文档库/路径是文件夹这两种子情形则是 `"reason"` 字符串）。
- `file_empty`：`extra = {"file": {"name", "lastModifiedDateTime"}}`。
- `file_too_large`：`extra = {"size": N, "limit": 200000}`。
- `not_text`：`extra = {"file_type": "<mimeType>"}`。

这六个码全部是 `retryable: false`——每一个都是解析/内容层面的问题，Graph 层面的重试解决不了，与 `api_client.py:31-39` 的 `_STATUS_TO_CODE` 把 `invalid_argument`/`not_found` 标记为不可重试的既有做法一致。

**实际发出的 Graph API 调用**（只读，按顺序，遇到第一个失败就短路）：
1. `GET /sites/{site_id}`（若给了 `site_id`）或 `GET /sites?search={site_query}&$select=id,name,displayName,webUrl`（Graph Search API，与 `graph_search_sites` 相同）。
2. `GET /sites/{id}/drive`（默认文档库）。
3. `GET /drives/{drive_id}/root:/{path}:?$select=id,name,size,file,folder,lastModifiedDateTime`（Graph 路径寻址——与 `graph_create_file_text:317` 已经在用的机制相同）。
4. 第 3 步 404 时：`GET /drives/{drive_id}/root:/{folder_path}:/children?$select=name` 或 `/drives/{drive_id}/root/children?$select=name`（用于生成 `files_in_folder` 附加数据）。
5. `GET /drives/{drive_id}/items/{item_id}/content`（原始字节，与 `graph_read_file_text:190` 相同）。

**DB**：无——该服务不持有任何状态（网关模式，仅按请求携带 token）。

**向后兼容**：纯增量——新增一个工具，以及一个共享辅助函数上新增的、省略时行为与今天逐字节相同的可选第 4 参数。没有任何现有工具的请求/响应形状发生变化。

### 关键流程时序

```
agent → graph_read_site_file_text(site_query, file_name, folder_path?, site_id?)
  → _resolve_site(): 给了 site_id? GET /sites/{id} : GET /sites?search=...
      ├─ 未找到 / 404                → site_not_found
      ├─ 候选 >1 个且无精确匹配       → site_ambiguous
      └─ 解析为恰好一个站点
  → _resolve_drive(): GET /sites/{id}/drive
      └─ 404 / 无默认文档库          → file_not_found（原因：无文档库）
  → _resolve_file(): GET /drives/{drive_id}/root:/{path}:
      ├─ 404                        → 列出所在文件夹 → file_not_found（files_in_folder）
      ├─ 解析为文件夹                → file_not_found（原因：路径是文件夹）
      └─ 解析为文件
  → size == 0                       → file_empty
  → size > 200,000 字节              → file_too_large
  → GET .../content，UTF-8 解码
      ├─ UnicodeDecodeError         → not_text
      └─ 成功                       → {"site","drive","file","content"}（dump_json_capped 包装）
```

### 非功能

- **幂等/并发**：每一步都是 `GET`，工具天然幂等、并发安全——不引入任何共享可变状态（与 `GraphClient` 现有的"状态只存在于实例内"一致，`api_client.py:69-77`）。明确**不得**跨调用缓存 `site_query → site_id` 或 `(drive_id, path) → item_id` 的解析结果，哪怕是出于性能优化的目的——下一个调用方的 token 可能属于另一个租户，本工具的输入参数里没有任何东西能证明不是这样（对应 AC10）。
- **性能**：最坏情况下需要最多 5 次顺序 Graph 往返（站点搜索、文档库查询、文件路径查询、未命中时的文件夹列表、内容拉取），比今天 agent 自己编排的 3 次往返更多——但代价是把中间所有需要模型复制 id 的往返都省掉了，而这才是本单真正要解决的延迟/可靠性问题（一次因 malformed-id 失败触发的 agent 重试，代价远高于服务端多一次 Graph 调用）。不引入新的缓存，不引入新的后台任务。
- **安全**：不引入新的权限范围（复用 `graph_search_sites`/`graph_read_file_text` 已经要求的 `Sites.Read.All` 等价权限）；只读（对应 AC10a）——本工具从结构上就不可能触达任何写/删除类 Graph 端点，因为改动清单里的辅助函数只会调用 `client.get`/`client.get_content`，不会调用 `post`/`put`/`delete`。错误信息会回显调用方传入的 `site_query`/`file_name`/`folder_path`，与其它工具已有的校验错误回显方式一致（例如 `graph_list_messages` 的 `received_after` 回显）——不是新增的风险。
- **多租户隔离**：见上方"权限与多租户"一节，并由 AC10 断言；本次改动引入的任何代码路径，都不会在单次调用自己的调用栈之外持有任何 token 或已解析的 id。
- **可观测**：不新增日志——`sites.py` 目前就没有日志（既有约定，本次不改变）；失败情形完全可以从返回的结构化错误（code + message + extra）里定位，实际上比本设计要替换掉的那两个分支现在的单一通用 `invalid_argument` 更容易排查。

**0.5–1.5 人日。** 下限：要组合的三种 Graph 调用模式在这个文件里都已经有现成实现可以照搬，`error_envelope` 的扩展是个很小的增量改动，主要工作量在写那约 10 个单测。上限的不确定性来自两项需要真实租户的手工检查（10 次连续运行检查、真实二进制文件的 `not_text` 检查），这一点和 PRD-19661 先例里的集成验证步骤依赖测试租户/账号可用性是一样的。不需要拆子任务——这是一个文件里新增一个工具加一处共享辅助函数扩展,不能自然拆成可独立验收的若干块。

### 风险与依赖

- **依赖**：需要一个已完成授权同意的真实测试租户，其 SharePoint 站点下同时有一个小文本文件和一个真实二进制文件，供上面两项手工/集成检查使用。`ms-graph-mcp` 是网关模式，自己不持有任何凭据（与 PRD-19661 先例里的记录一致）——测试账号由负责跑开发+测试棒的人提供，不属于本设计范围内要配置的东西。
- **风险**：`dump_json_capped` 对非列表 payload 的截断缺口（见 Open Questions）——对于接近 200,000 字节上限的文件，工具在 Graph 调用层面会显示成功，但返回的是一句没用的截断提示而不是内容。这个风险在 `graph_read_file_text` 身上今天就已经存在，不是本单引入的；这里特意标出来，是为了不让它被悄悄继承而没人注意到。
- **风险**：`site_query` 即便有 `site_id` 也必填的规格矛盾（见 Open Questions）——无论怎么选影响都不大，但值得在实现落地前让提单人确认一句，因为 `tests/test_tools.py` 的 `EXPECTED_TOOLS` 快照把必填参数集合变成了一条硬断言，之后再改虽然不贵（就一个 dict 里的一行）但有点烦。
- **风险（较小，不阻塞）**：Graph 的 `root:/{item-path}:` 寻址是把路径直接拼进 URL 字符串；如果 `file_name` 或 `folder_path` 里出现 `#`（URL 片段分隔符）这类字符，根据 `httpx` 从拼接字符串构造请求 URL 的方式，行为可能不符合预期。这是与 `graph_create_file_text:317` 相同写法共有的既有风险，不是本次新引入的，也不在本次修复范围内——这里标出来是因为本单自己举的例子文件名（"Permission Matrix.csv"）不受影响（只是普通空格，能被正确处理），但以后如果出现带 `#`/`%`/`?` 的文件名，两个工具会遇到同样的潜在问题。
- **依赖**：不依赖 PRD-20211 先完成——那张单的修法在另一个仓库（onboarding agent 的 SKILL.md），它被重新打开这件事本身恰恰是本单的立项依据之一（见现状一节），而不是本单的阻塞项。
