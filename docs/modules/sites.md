# Module: `src/graph_mcp/tools/sites.py` (SharePoint sites/drives/files)

First entry in this module doc (no prior accumulated facts existed in this repo for `sites.py`).

## PRD-20413 · 2026-10-13

- Added `graph_read_site_file_text` (`src/graph_mcp/tools/sites.py:331-430` @ `2514f69`), a single-call alternative to the `graph_search_sites` → `graph_list_drive_items` → `graph_read_file_text` chain: resolves site → default document library → file → UTF-8 content server-side, so no `driveId`/item id is ever returned to or required from the calling model. Built in direct response to PRD-20211's reopened defect: the model intermittently mis-copies the long, random `driveId` when threading it between the first two chained tool calls, and a prompt-only fix (PRD-20211, 2026-10-09) was empirically shown not to hold (same ticket, QA re-verification, 2026-10-10).
- Three new module-level helpers back it (`src/graph_mcp/tools/sites.py:46-169` @ `2514f69`): `_resolve_site` (`:46-96`, site_id-direct lookup, or search + exact-displayName-first match, falling back to a single keyword hit; `>1` candidate with no exact match → `site_ambiguous`), `_resolve_drive` (`:107-122`, any failure, including no default library, folds into `file_not_found` — there is no separate "no library" error code in this tool's contract), `_resolve_file` (`:125-169`, Graph's `root:/{path}:` addressing, same mechanism `graph_create_file_text:317` already used; 404 → lists the folder's contents for the `file_not_found` error's `files_in_folder` extra; a `folder` facet on the resolved item is also `file_not_found`, not a separate code).
- `src/graph_mcp/_json.py`'s `error_envelope` (`:76-88` @ `2514f69`) gained an optional 4th parameter `extra: dict | None = None` for structured error context (candidate site lists, sibling file names, etc.). Additive and backward-compatible: every pre-existing call site across `mail.py`/`users.py`/`groups.py`/`licenses.py`/`calendar.py`/`sites.py` is unaffected since the parameter defaults to omitting `extra` entirely, producing byte-for-byte the same output as before. Any future tool needing structured error context should extend via this same `extra` dict, not invent a second error-envelope shape.
- Six structured error codes introduced on this tool specifically (not retrofitted onto the three existing chained tools, which keep their original single generic `invalid_argument` for size/decode failures): `site_not_found`, `site_ambiguous`, `file_not_found`, `file_empty`, `file_too_large`, `not_text`. All are `retryable: false`.
- No new Graph permission scope — reuses `Sites.Read.All` (same as `graph_search_sites`/`graph_read_file_text`). Read-only: every Graph call this tool's helpers make is a `GET` (asserted by test, see below) — structurally enforced since the helpers only ever call `client.get`/`client.get_content`.
- Multi-tenant note (carried over from this file's existing design, not new): nothing in this tool's resolution chain caches a `site_query → site_id` or `(drive_id, path) → item_id` mapping across calls — each call independently re-resolves from its own parameters and its own per-request token. A future change that adds such a cache "to save a round trip" would silently break tenant isolation; don't.
- Test coverage: `tests/test_tools.py::test_read_site_file_text_*` — 14 tests (TC1–TC14 in `docs/tickets/PRD-20413.ac.json`), covering the happy path, both site-resolution fallback/ambiguity branches, all three `file_not_found` sub-cases, the empty/oversize/boundary size checks, the UTF-8-decode-failure branch, the GET-only and no-cross-call-state-leak structural assertions.
- Not covered by automated tests (needs a live, consented Entra/SharePoint test tenant — see `docs/tickets/PRD-20413.md` § Self-test, TC15/TC16): the ticket's own 10-consecutive-run operational acceptance bar, and whether Graph's real `root:/{path}:` response populates `file.mimeType` with a sensible value for a real binary Office file. The connector-side logic is verified; the live-tenant behavior is not.
