# Module: `src/graph_mcp/tools/groups.py` (group membership / routing)

First entry in this module doc.

## PRD-20393 · 2026-10-13

- `graph_list_user_groups` and `graph_list_groups` (`src/graph_mcp/tools/groups.py` @ `722e955`) switched from "walk every Graph page internally, stop at max_results" to one-Graph-page-per-call, matching `graph_list_group_members`'s existing contract: `page_token` in, `next_page_token` out via the shared `_common.skiptoken` helper (moved here from being private to this file — now also used by `users.py::graph_list_users`). A caller that relied on one call returning everything up to `max_results` must now follow `next_page_token` instead; no caller of these two tools was found inside this repo (they're exposed only to external MCP clients), so this blast radius could not be fully enumerated from this repo alone — flagged in `docs/tickets/PRD-20393.md` Open questions for groom, not silently assumed safe.
- `graph_list_user_groups` additionally derives `sync_source` ("on-premises"/"cloud") per group from `onPremisesSyncEnabled`, the same derivation `graph_get_group` (`:301-332`) already does — now the second place in this file using that pattern; any future tool needing to classify a group's sync origin should reuse the same `"on-premises" if obj.get("onPremisesSyncEnabled") else "cloud"` expression, not invent another phrasing.
- `_skiptoken` moved out to `_common.py` (renamed `skiptoken`, no longer private) since it's now shared by two files, not one.
- Test coverage: `tests/test_tools.py::test_list_user_groups_paginates_with_skiptoken`, `::test_list_user_groups_returns_group_type_mail_enabled_and_sync_source`, `::test_list_groups_paginates_with_skiptoken`, `::test_list_tools_surface_graph_error_instead_of_raising` (parametrized, covers both tools here plus `graph_list_users`) (all added in this ticket, all passing at `722e955`).
- Not covered by automated tests: none identified for this file's changes — the pagination/sync_source logic is fully exercised against the repo's fake Graph client; no live-tenant-only behavior was touched here (contrast with `users.py`'s UPN/manager changes, which do have a documented live-tenant blind spot).

## PRD-20393-r2 · 2026-10-14

- A 2026-10-14 acceptance test against a live tenant (comment `90170262303660`) found `graph_list_user_groups`'s pagination (the "one-Graph-page-per-call" contract the entry above describes) could lose groups and never terminate: the client-side filter that kept only group-shaped objects out of `/users/{id}/memberOf`'s raw (polymorphic) response did not affect `$top`/`$skiptoken`, which were driven by the raw page — so a page whose items were all filtered out still advanced the cursor, and in the worst case the walk never converged.
- Fix (`src/graph_mcp/tools/groups.py:69-122` @ `ccf3931`, not yet on `master` — see this ticket's work branch): the Graph call path changed from `/users/{id}/memberOf` to `/users/{id}/memberOf/microsoft.graph.group` (a standard OData type-cast segment), and the client-side group-type filter was removed entirely — Graph itself now returns only group objects per page, so the filtered set and the paginated set are the same set by construction. This is a correctness fix only; the tool's request/response JSON contract (`user_id`, `max_results`, `page_token` in; `count`, `groups`, `has_more`, `next_page_token` out) is unchanged.
- Precedent for future pagination fixes on polymorphic Graph navigation properties in this file: **prefer an OData type-cast in the request URL over a client-side post-filter** — a post-filter can silently decouple the filtered set from the page cursor, which is exactly what happened here.
- Test coverage: `tests/test_tools.py::test_list_user_groups_paginates_with_skiptoken` (rewritten to assert the cast URL and a 3-page walk with no duplicates, all passing at `ccf3931`).
- Not covered by automated tests: the `/memberOf/microsoft.graph.group` cast itself has not been re-verified against a live tenant by this round (it is a standard, documented Graph pattern, but this repo has no live Graph tenant to confirm against — same class of blind spot as `users.py`'s UPN/manager entries). See `docs/tickets/PRD-20393-r2.md` § Self-test, "Known local blind spot."
## PRD-20480 · 2026-10-14

- New tool `graph_add_group_owner` (`src/graph_mcp/tools/groups.py:71` @ `ad9f0e2`), placed right after `graph_assign_groups`. `POST /groups/{id}/owners/$ref` with an `@odata.id` body built from `_DIRECTORY_OBJECT_URL` (the same constant `graph_assign_groups` already uses for `/members/$ref`) — structurally identical endpoint, owner instead of member. Mirrors `graph_assign_groups`'s exact 400-"already exist" handling (`:57-59` precedent) to report `already_owner` instead of an error, matching this tool's idempotent annotation.
- Does not special-case Teams vs. plain M365 groups — Microsoft Teams is backed by an M365 Group in Graph, so the same endpoint is assumed to apply to both. Flagged as an assumption in the design doc, not independently re-verified against a real Teams-backed group.
- Enforces no approval workflow of its own — the ticket's own framing ("Teams only sets someone as owner after approval") describes an SOP-level step that must happen *before* an agent calls this tool; out of scope by design (see `docs/tickets/PRD-20480.md` § Non-goals).
- Test coverage: `tests/test_tools.py::test_graph_add_group_owner_adds_new_owner`, `::test_graph_add_group_owner_is_idempotent_for_existing_owner` (both added in this ticket, both passing at `ad9f0e2`).
- Not covered by automated tests (needs a real tenant — see `docs/tickets/PRD-20480.md` § Self-test, TC-MSG-005b): whether Graph's actual "already an owner" error text matches the mocked 400-handling assumption (same open-question shape `graph_assign_groups`'s own `already exist` match originally had to be pinned down the same way). Also depends on the same `Group.ReadWrite.All` cross-repo scope-grant sequencing documented in the `users.md` entry above for `graph_create_tap`.
