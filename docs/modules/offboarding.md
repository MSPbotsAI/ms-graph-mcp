# Module: `src/graph_mcp/tools/offboarding.py` (OneDrive transfer + directory sync)

First entry in this module doc — the file itself is new, created by this ticket.

## PRD-20422 · 2026-10-14

- New module (`src/graph_mcp/tools/offboarding.py` @ `eb38295`), registered in `server.py:115,125` alongside the other eight tool modules. Deferred from PRD-20393 items 7-8.
- `graph_transfer_onedrive` (`:165-264` @ `eb38295`) is stateless and idempotent by construction: every call re-lists both the source and destination OneDrive root/folder contents via `_list_all_children` (`:62-75`) and diffs by `name`+`size`, issuing a Graph `/drives/{id}/items/{id}/copy` only for items not already present at the destination. There is deliberately no separate "check status" tool — calling `graph_transfer_onedrive` again *is* the status check (`_rollup_transfer_status`, `:99-112`, maps the per-item action set to `started`/`in_progress`/`completed`).
- `graph_start_cloud_sync` (`:271-368` @ `eb38295`) only supports Azure AD Connect **cloud sync**, the one directory-sync mechanism reachable from Microsoft Graph (`/servicePrincipals/{id}/synchronization/jobs/{id}/start`). A tenant on classic on-premises AD Connect gets `no_sync_job_configured` naming the `Start-ADSyncSyncCycle` alternative — there is no Graph API surface for that path at all, so this is a hard capability boundary, not a missing feature.
- **Discovery filter is evidenced, not guessed**: `_CLOUD_SYNC_AGENT_HOMEPAGE_FRAGMENT` / `_CLOUD_SYNC_JOB_TEMPLATE_ID` (`:41-42` @ `eb38295`, both `"AD2AADProvisioning"`) come from a real Rewst GraphQL snapshot of Ginko's "08 User Offboarding" workflow (99 workflows, cross-checked against EMD W3), quoted in full in `docs/tickets/PRD-20422.md` § Ticket thread. Rewst's own working `[REWST - TASK] M365: Start Entra Cloud Sync` subflow filters service principals by `homepage` containing this exact fragment (and `accountEnabled`), then filters that principal's sync jobs by `templateId` match and `schedule.state == "Active"` — this module's `_discover_cloud_sync_service_principal` (`:115-133`) and `_discover_cloud_sync_job` (`:136-150`) do the same two-step filter. This was an unconfirmed Open Question in the frozen Tech Design before this evidence surfaced; it is still not independently checked against Microsoft's own API reference (see README Known Gaps).
- **A related but separate question from the same evidence was deliberately *not* acted on**: the same comment shows Rewst's OneDrive step has never done a real content transfer (it only archives-and-shares in place) and suggests narrowing the still-open "what should v1 do" question. The frozen Tech Design had already chosen the "copy content into a new destination folder" approach before this evidence existed (a product-design decision, past this ticket's groom gate) — this implementation ships that approved behavior unchanged. See `docs/tickets/PRD-20422.md` § Self-test, "A discrepancy this self-test surfaced" for the full reasoning; this is recorded here so a future ticket touching this module doesn't have to re-discover it.
- Both discovery helpers return `{"candidates": [...]}` rather than resolving to a single id/raising directly, so `graph_start_cloud_sync` can apply AC10 (zero candidates -> `no_sync_job_configured`) and AC11 (more than one -> `sync_job_ambiguous`, with `extra: {"candidates": [...]}`) uniformly at both the service-principal and the job level.
- `graph_transfer_onedrive`'s drive resolution order is fixed (source first, then destination) specifically so AC5 (source has no OneDrive) short-circuits before any destination call is made, and AC7 (destination has no OneDrive) short-circuits before the source's root is ever listed — order matters here, not just which checks exist.
- No change to `api_client.py` — both tools work entirely from parsed JSON response bodies (see Tech design § Option analysis, "api_client change" row, rejected). `graph_transfer_onedrive` is the first tool in this repo to actually exercise the previously-dormant `Files.ReadWrite.All` grant (README § permission notes, updated this ticket).
- Test coverage: `tests/test_tools.py::test_transfer_onedrive_starts_copy_for_new_items`, `::test_transfer_onedrive_is_idempotent_when_all_items_already_present`, `::test_transfer_onedrive_does_not_recopy_items_mid_transfer`, `::test_transfer_onedrive_reports_drive_not_found_for_source`, `::test_transfer_onedrive_reports_no_content_for_empty_source`, `::test_transfer_onedrive_reports_drive_not_found_for_destination`, `::test_start_cloud_sync_starts_job_for_synced_user`, `::test_start_cloud_sync_is_not_applicable_for_cloud_only_user`, `::test_start_cloud_sync_reports_no_sync_job_configured`, `::test_start_cloud_sync_reports_ambiguous_when_multiple_jobs`, `::test_start_cloud_sync_discovery_is_not_cached_across_tenants` (all added this ticket, all passing at `eb38295`); `test_tools_list_snapshot` extended for the tool-count bump (39→41).
- Not covered by automated tests (needs a live tenant with Azure AD Connect cloud sync configured — see `docs/tickets/PRD-20422.md` § Self-test, TC13/AC8): whether the evidenced discovery filter actually matches a real tenant's registered agent/job, and whether Graph's own `/start` endpoint behaves as assumed under a concurrent retry. Also unconfirmed: whether the tenant(s) behind offboarding workflows 08/03 use cloud sync at all, vs. classic on-premises AD Connect (which this tool cannot reach regardless of implementation correctness).
