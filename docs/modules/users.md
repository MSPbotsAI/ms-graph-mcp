# Module: `src/graph_mcp/tools/users.py` (user profile read/write)

First entry in this module doc (no prior accumulated facts existed in this repo before PRD-20321).

## PRD-20321 · 2026-10-12

- `graph_get_user`'s Graph `$select` (`src/graph_mcp/tools/users.py:396-406` @ `0714c88`) now includes `employeeId,givenName,surname` in addition to the previously-requested fields. Before this ticket, none of the three were requested, so the tool could never return them regardless of whether the directory had them set — this was a connector-side gap, not an account-data gap (confirmed by reading the `$select` string directly, not by observing the API response).
- `graph_update_user` (`src/graph_mcp/tools/users.py:414-500` @ `0714c88`) gained two parameters: `employee_id: str | None = None` (PATCHes `employeeId` to the given value) and `clear_employee_id: bool = False` (PATCHes `employeeId` to `null`). Passing both in the same call returns an `invalid_argument` error envelope *before* calling Graph — this mirrors the existing `_add_profile_fields` (`:50-82`) validate-before-call pattern used for `employee_hire_date`.
- There is now a second precedent (besides `employee_hire_date`) for "optional profile field with explicit-clear support" on this tool — any future field that needs a tri-state (unset / set-to-value / explicitly-cleared) shape should follow the `employee_id`/`clear_employee_id` pair shape here, not invent a new one.
- Test coverage: `tests/test_tools.py::test_update_user_writes_employee_id`, `::test_update_user_clears_employee_id`, `::test_update_user_rejects_employee_id_and_clear_together`, `::test_get_user_returns_given_name_and_surname` (all added in this ticket, all passing at `0714c88`).
- Not covered by automated tests (needs a live Entra ID tenant — see `docs/tickets/PRD-20321.md` § Self-test): what value shape, if any, this tenant's directory schema rejects for `employeeId`; and whether `givenName`/`surname` are populated for real accounts in this tenant (the connector-side fix is verified; the account-data side is not).

## PRD-20412 · 2026-10-13

- `graph_create_user` (`src/graph_mcp/tools/users.py:218-324` @ `3570af5`) already set `passwordProfile.forceChangePasswordNextSignIn = True` unconditionally before this ticket (line 284, unchanged by this ticket) — the forced-password-change behavior was never missing, only unobservable. This ticket is purely about confirmation, not behavior.
- On a successful `201`, the tool's return path (`:311-324`) now merges `passwordChangeRequiredAtNextSignIn: true` into the response before returning, instead of passing Graph's raw response straight through. This mirrors the confirmation-object pattern `graph_reset_password` (`:320-372`, unchanged, pre-existing) already uses for the same reason: Graph's own response never echoes back `passwordProfile` (confirmed against Microsoft's own `POST /users` API reference examples), so passthrough gave zero confirmation.
- Precedent for future response-shape decisions on this file: **don't trust Graph's response body to prove a `passwordProfile`-shaped setting took effect — build and return your own deterministic confirmation instead.** This is now the second tool in this file doing this (`graph_reset_password` was first); a `GET ...?$select=passwordProfile` read-back approach was evaluated and rejected (documented as unreliable — Microsoft Q&A/forum reports of null/empty read-back even when explicitly selected), see `docs/tickets/PRD-20412.md` § Tech design, Option analysis.
- The new field is additive-only; no existing `graph_create_user` response field was renamed or removed (AC4), and the merge builds a fresh `dict` per call with no shared/module-level state (AC5).
- Test coverage: `tests/test_tools.py::test_create_user_response_confirms_forced_password_change`, `::test_create_user_description_documents_forced_password_change`, `::test_create_user_error_envelope_has_no_password_confirmation`, `::test_create_user_response_is_additive_only`, `::test_create_user_confirmation_is_per_call_not_shared_state` (all added in this ticket, all passing at `3570af5`).
- Not covered by automated tests (needs a live/sandbox Entra ID tenant — see `docs/tickets/PRD-20412.md` § Self-test, TC6/AC6): whether Entra actually presents a forced password-change screen at first sign-in for an account created this way. This is the same category of local blind spot already recorded above for PRD-20321's `employeeId` directory-schema behavior — the connector-side request is verified; the tenant-side enforcement is a well-documented Graph behavior but not independently re-verified by this ticket.

## PRD-20393 · 2026-10-13

- `graph_update_user` (`src/graph_mcp/tools/users.py` @ `722e955`) gained `user_principal_name`, `display_name`, `given_name`/`clear_given_name`, `surname`/`clear_surname`. `user_principal_name` changes are pre-flight-checked against `_common.verified_domains(client)` (new helper, a `/domains?$select=id,isVerified` query distinct from `graph_list_domains`'s own richer query) before any PATCH is sent.
- Deliberate deviation from this ticket's own design doc: `given_name`/`surname` use the `clear_<field>` boolean-flag shape, not the `_UNSET`-sentinel-plus-literal-null shape the design proposed — reusing the shape PRD-20321 had, the same day, already established for `employee_id` (see the PRD-20321 entry above: "any future field that needs a tri-state shape should follow the employee_id/clear_employee_id pair shape here, not invent a new one"). `graph_update_user` now has exactly one tri-state mechanism for all three nullable string fields it supports, not two.
- `user_principal_name` and `display_name` deliberately have **no** clear_* option — Microsoft Graph documents both as non-nullable properties of the `user` resource; a real tenant would reject a null PATCH for either with a 400. Anyone adding a future nullable-or-not field to this tool should check Graph's own schema nullability before assuming the clear_X pattern applies.
- `graph_get_user`'s default `$select` (`:397-434` @ `722e955`) widened with `proxyAddresses,identities,onPremisesSyncEnabled,onPremisesLastSyncDateTime,onPremisesDistinguishedName` (constant `_USER_PROFILE_SELECT`); a new optional `select: list[str] | None` param replaces the default list entirely (and drops the default `$expand=manager`) when provided.
- New tool `graph_remove_manager` (`DELETE /users/{id}/manager/$ref`), 404→`status=no_manager` mirroring `graph_remove_group_member`'s 404→`not_a_member` handling in `groups.py`. Tool count cap 37→38.
- `graph_list_users` (`:151-219` @ `722e955`) switched from "walk every page internally up to max_results" to one-Graph-page-per-call (`page_token`/`next_page_token`), matching `graph_list_group_members`'s existing contract — see the `groups.py` module doc for the same change on the two group-listing tools.
- Test coverage: `tests/test_tools.py::test_update_user_omitted_new_fields_are_not_sent`, `::test_update_user_explicit_null_clears_field`, `::test_update_user_rejects_given_name_and_clear_together`, `::test_update_user_rejects_unverified_upn_domain`, `::test_update_user_allows_verified_upn_domain`, `::test_update_user_still_rejects_when_nothing_to_update`, `::test_remove_manager_deletes_manager_ref`, `::test_remove_manager_is_idempotent_on_missing_manager`, `::test_get_user_default_select_includes_new_fields`, `::test_get_user_custom_select_narrows_fields`, `::test_list_users_paginates_with_skiptoken` (all added in this ticket, all passing at `722e955`).
- Not covered by automated tests (needs a live two-tenant Entra setup — see `docs/tickets/PRD-20393.md` § Self-test, TC15/AC15): true cross-tenant isolation. This server performs no tenant check of its own by design (delegated entirely to the caller's bearer token) — not a gap introduced by this ticket, but newly called out here as an explicit AC.
