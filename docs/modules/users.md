# Module: `src/graph_mcp/tools/users.py` (user profile read/write)

First entry in this module doc (no prior accumulated facts existed in this repo before PRD-20321).

## PRD-20321 · 2026-10-12

- `graph_get_user`'s Graph `$select` (`src/graph_mcp/tools/users.py:396-406` @ `0714c88`) now includes `employeeId,givenName,surname` in addition to the previously-requested fields. Before this ticket, none of the three were requested, so the tool could never return them regardless of whether the directory had them set — this was a connector-side gap, not an account-data gap (confirmed by reading the `$select` string directly, not by observing the API response).
- `graph_update_user` (`src/graph_mcp/tools/users.py:414-500` @ `0714c88`) gained two parameters: `employee_id: str | None = None` (PATCHes `employeeId` to the given value) and `clear_employee_id: bool = False` (PATCHes `employeeId` to `null`). Passing both in the same call returns an `invalid_argument` error envelope *before* calling Graph — this mirrors the existing `_add_profile_fields` (`:50-82`) validate-before-call pattern used for `employee_hire_date`.
- There is now a second precedent (besides `employee_hire_date`) for "optional profile field with explicit-clear support" on this tool — any future field that needs a tri-state (unset / set-to-value / explicitly-cleared) shape should follow the `employee_id`/`clear_employee_id` pair shape here, not invent a new one.
- Test coverage: `tests/test_tools.py::test_update_user_writes_employee_id`, `::test_update_user_clears_employee_id`, `::test_update_user_rejects_employee_id_and_clear_together`, `::test_get_user_returns_given_name_and_surname` (all added in this ticket, all passing at `0714c88`).
- Not covered by automated tests (needs a live Entra ID tenant — see `docs/tickets/PRD-20321.md` § Self-test): what value shape, if any, this tenant's directory schema rejects for `employeeId`; and whether `givenName`/`surname` are populated for real accounts in this tenant (the connector-side fix is verified; the account-data side is not).

## PRD-20412 · 2026-10-13

- `graph_create_user` (`src/graph_mcp/tools/users.py:218-324` @ `3570af5`) already set `passwordProfile.forceChangePasswordNextSignIn = True` unconditionally before this ticket (line 284, unchanged by this ticket) — the forced-password-change behavior was never missing, only unobservable. This ticket is purely about confirmation, not behavior.
- On a successful `201`, the tool's return path (`:311-324`) now merges `passwordChangeRequiredAtNextSignIn: true` into the response before returning, instead of passing Graph's raw response straight through. This mirrors the confirmation-object pattern `graph_reset_password` (`:320-372`, unchanged, pre-existing) already uses for the same reason: Graph's own response never echoes back `passwordProfile` (confirmed against Microsoft's own `POST /users` API reference examples), so passthrough gave zero confirmation.
- Precedent for future response-shape decisions on this file: **don't trust Graph's response body to prove a `passwordProfile`-shaped setting took effect — build and return your own deterministic confirmation instead.** This is now the second tool in this file doing this (`graph_reset_password` was first); a `GET ...?$select=passwordProfile` read-back approach was evaluated and rejected (documented as unreliable — Microsoft Q&A/forum reports of null/empty read-back even when explicitly selected), see `docs/tickets/PRD-20412.md` § Tech design, Option analysis.
- The new field is additive-only; no existing `graph_create_user` response field was renamed or removed (AC4), and the merge builds a fresh `dict` per call with no shared/module-level state (AC5).
- Test coverage: `tests/test_tools.py::test_create_user_response_confirms_forced_password_change`, `::test_create_user_description_documents_forced_password_change`, `::test_create_user_error_envelope_has_no_password_confirmation`, `::test_create_user_response_is_additive_only`, `::test_create_user_confirmation_is_per_call_not_shared_state` (all added in this ticket, all passing at `3570af5`).
- Not covered by automated tests (needs a live/sandbox Entra ID tenant — see `docs/tickets/PRD-20412.md` § Self-test, TC6/AC6): whether Entra actually presents a forced password-change screen at first sign-in for an account created this way. This is the same category of local blind spot already recorded above for PRD-20321's `employeeId` directory-schema behavior — the connector-side request is verified; the tenant-side enforcement is a well-documented Graph behavior but not independently re-verified by this ticket.

## PRD-20393 · 2026-10-13

- `graph_update_user` (`src/graph_mcp/tools/users.py` @ `722e955`) gained `user_principal_name`, `display_name`, `given_name`/`clear_given_name`, `surname`/`clear_surname`. `user_principal_name` changes are pre-flight-checked against `_common.verified_domains(client)` (new helper, a `/domains?$select=id,isVerified` query distinct from `graph_list_domains`'s own richer query) before any PATCH is sent.
- Deliberate deviation from this ticket's own design doc: `given_name`/`surname` use the `clear_<field>` boolean-flag shape, not the `_UNSET`-sentinel-plus-literal-null shape the design proposed — reusing the shape PRD-20321 had, the same day, already established for `employee_id` (see the PRD-20321 entry above: "any future field that needs a tri-state shape should follow the employee_id/clear_employee_id pair shape here, not invent a new one"). `graph_update_user` now has exactly one tri-state mechanism for all three nullable string fields it supports, not two.
- `user_principal_name` and `display_name` deliberately have **no** clear_* option — Microsoft Graph documents both as non-nullable properties of the `user` resource; a real tenant would reject a null PATCH for either with a 400. Anyone adding a future nullable-or-not field to this tool should check Graph's own schema nullability before assuming the clear_X pattern applies.
- `graph_get_user`'s default `$select` (`:397-434` @ `722e955`) widened with `proxyAddresses,identities,onPremisesSyncEnabled,onPremisesLastSyncDateTime,onPremisesDistinguishedName` (constant `_USER_PROFILE_SELECT`); a new optional `select: list[str] | None` param replaces the default list entirely (and drops the default `$expand=manager`) when provided.
- New tool `graph_remove_manager` (`DELETE /users/{id}/manager/$ref`), 404→`status=no_manager` mirroring `graph_remove_group_member`'s 404→`not_a_member` handling in `groups.py`. Tool count cap 37→38.
- `graph_list_users` (`:151-219` @ `722e955`) switched from "walk every page internally up to max_results" to one-Graph-page-per-call (`page_token`/`next_page_token`), matching `graph_list_group_members`'s existing contract — see the `groups.py` module doc for the same change on the two group-listing tools.
- Test coverage: `tests/test_tools.py::test_update_user_omitted_new_fields_are_not_sent`, `::test_update_user_explicit_null_clears_field`, `::test_update_user_rejects_given_name_and_clear_together`, `::test_update_user_rejects_unverified_upn_domain`, `::test_update_user_allows_verified_upn_domain`, `::test_update_user_still_rejects_when_nothing_to_update`, `::test_remove_manager_deletes_manager_ref`, `::test_remove_manager_is_idempotent_on_missing_manager`, `::test_get_user_default_select_includes_new_fields`, `::test_get_user_custom_select_narrows_fields`, `::test_list_users_paginates_with_skiptoken` (all added in this ticket, all passing at `722e955`).
- Not covered by automated tests (needs a live two-tenant Entra setup — see `docs/tickets/PRD-20393.md` § Self-test, TC15/AC15): true cross-tenant isolation. This server performs no tenant check of its own by design (delegated entirely to the caller's bearer token) — not a gap introduced by this ticket, but newly called out here as an explicit AC.

## PRD-20393-r2 · 2026-10-14

A 2026-10-14 acceptance test against a live tenant (comment `90170262303660`, SOP 225 / Ginko onboarding agent) found 3 of this file's PRD-20393 round-1 tools needed rework. All three fixes below are **breaking response-shape changes**, flagged explicitly because the tools shipped only days earlier (not additive/corrective like round 1's own field widenings).

- **`graph_update_user`** (`src/graph_mcp/tools/users.py:462-712` @ `ccf3931`, not yet on `master` — see this ticket's work branch): a successful call now issues a follow-up `GET /users/{id}?$select=<changed keys>` after the `PATCH`, and `updated` is built from that read (`{field: value}`) instead of `list(body.keys())`. Round 1's version only ever echoed back the request's own key names, never confirming what Graph actually stored. **Breaking**: `updated`'s type changed from `list[str]` to `dict[str, Any]`.
- **`graph_remove_manager`** (`:709-764` @ `ccf3931`): replaced round 1's delete-then-interpret-404 flow (which assumed a repeat `DELETE` on an already-managerless user 404s — acceptance proved it does not, against a real tenant) with read-manager-then-maybe-delete: `GET /users/{id}/manager` first; a 404 there means no manager and **no `DELETE` is issued at all**; otherwise `previous_manager` is captured from that read before the `DELETE` runs, and a 404 on the `DELETE` itself (a concurrent removal between the GET and the DELETE) is now tolerated as success rather than propagated. **Breaking**: the entire response shape replaced, `{"status": "removed"|"no_manager", "user_id"}` → `{"user_id", "removed": bool, "previous_manager": {id, display_name, user_principal_name}|null, "reason": "no_manager"|null}`.
- **`graph_get_user`** (`:35-47`, `:411-460` @ `ccf3931`): `_USER_PROFILE_SELECT` gained `onPremisesImmutableId`, `onPremisesSamAccountName`, `createdDateTime`, `lastPasswordChangeDateTime` (round 1's default `$select` was simply missing these four acceptance asked for). Separately, a `select` param naming `"manager"` now routes it to `$expand=manager($select=id,displayName,userPrincipalName)` instead of being silently dropped by Graph from `$select` (a navigation property, not a flat property) — round 1's docstring promised `select=["manager"]` worked; it did not. Not breaking: additive to the default response, and `select` without `"manager"` behaves exactly as round 1 shipped it (confirmed unchanged by `test_get_user_custom_select_narrows_fields`, unmodified this round).
- Precedent this round adds for this file: **a tool whose "did Graph actually do X" signal is inferred from one call's own response/error code (not re-read from a dedicated follow-up call) is a correctness risk, not just a style choice** — both `graph_update_user`'s old echo-back and `graph_remove_manager`'s old DELETE-404-means-no-manager inference were exactly this shape, and both were wrong against a real tenant despite passing every unit test round 1 had. Future tools on this file that need to confirm a write's actual effect should re-read, not infer from the write call's own response.
- Why round 1's own test suite didn't catch any of this: every fake-client test only ever modeled the happy path each tool's author expected (a `memberOf` page of pure groups, a `DELETE` that 404s exactly once). None of round 1's tests modeled a mixed-type Graph collection or a double-`DELETE` sequence — see the test coverage entry below and `docs/tickets/PRD-20393-r2.md` § Self-test for the rewritten fakes (`_ManagerRemovalClient`) this round added to close that gap.
- Test coverage: `tests/test_tools.py::test_update_user_returns_rereads_changed_values`, `::test_remove_manager_returns_previous_manager_when_present`, `::test_remove_manager_returns_no_manager_without_calling_delete`, `::test_remove_manager_handles_concurrent_delete_404_as_removed`, `::test_remove_manager_surfaces_non_404_get_error`, `::test_get_user_default_select_includes_onprem_and_audit_fields` (extended), `::test_get_user_select_with_manager_adds_expand` (all added/rewritten in this ticket, all passing at `ccf3931`); 6 pre-existing `graph_update_user` tests had their `client.methods` assertion extended for the new re-read call (behavior/body assertions unchanged).
- Not covered by automated tests: none of the four fixes above have been re-verified against a live Graph tenant by this round (same class of blind spot as PRD-20393's own AC15 above) — acceptance's own evidence run ids (`155f15f9-…`, `a409123d-…`, `f397bf60-…`) are the closest available ground truth, and the design recommends the reporter re-run the exact repro from comment `90170262303660` once this reaches a reachable environment. See `docs/tickets/PRD-20393-r2.md` § Self-test, "Known local blind spot."

## PRD-20393-r3 · 2026-10-16

Minnie Zhou tested round 2's release on INT against the MSPbots production tenant (comment `90170263295399`, agent sopId=345) and found round 2's four fixes mostly held (1.1/1.6 passed fully; 1.4/1.5's write paths are BLOCKED by the test connector's own permissions, not failing), but surfaced one new defect plus one high-risk code-review finding on the same two functions round 2 touched.

- **`graph_remove_manager`** (`src/graph_mcp/tools/users.py:733-769` @ `bd3fe8d`): round 2's fix correctly stopped trusting `DELETE`'s 404 behavior, but still trusted `GET /users/{id}/manager`'s 404 to mean only "no manager" — Graph 404s that same call for a nonexistent `user_id` too. On that 404, the tool now issues `GET /users/{id}?$select=id` first; a 404 there returns a `not_found` error envelope, and only a successful existence check still yields `{"removed": false, "reason": "no_manager"}`. Not breaking: response shape unchanged, only the classification of one previously-mishandled input.
- **`graph_update_user`** (`:462-677` @ `bd3fe8d`): round 2's read-back always targeted `user_id`, which 404s once a `userPrincipalName` PATCH renames it (when `user_id` was itself the old UPN, not a GUID) — a code-review finding, not exercisable on INT this round since the test connector has no user-write permission against the production tenant. Fixed by reading back `body.get("userPrincipalName", user_id)` instead of always `user_id`. Separately, the PATCH and the read-back are now in separate `try` blocks, so a read-back failure after a successful PATCH returns `{"status": "success", "updated": dict(body), "readback_error": {...}}` instead of an error envelope for a write that had already succeeded. Not breaking: `updated`'s shape is unchanged on the success path; `readback_error` is a new, optional key present only when the read-back specifically failed.
- Minor, documentation-only: `graph_update_user`'s docstring now notes the read-back can rarely be stale due to Graph replication lag. A retry was considered and rejected for this round (see `docs/tickets/PRD-20393-r3.md` § Tech design, Option analysis — several fields this tool accepts, e.g. `employeeHireDate`, are normalized by Graph on write, so a naive sent-vs-read-back comparison would false-positive on every call involving them).
- Precedent this round reinforces for this file (continuing round 2's own precedent above): **a single error code from one Graph call can carry more than one real-world cause** — round 2 learned this for `DELETE`'s 404 (removed vs. already-removed), and this round learned the identical lesson one level up, for `GET /users/{id}/manager`'s 404 (no manager vs. doesn't exist). Any future tool on this file that branches on a Graph error code should ask "what else could cause this same code?" before treating it as a single signal.
- `_ManagerRemovalClient` (`tests/test_tools.py:1724-1762` @ `bd3fe8d`) now distinguishes its two possible GET call sites (the manager read vs. the new existence check) by request path suffix, rather than needing a second fake class — a reusable pattern for any future test needing to control two same-shaped calls to the same fake independently.
- Test coverage: `tests/test_tools.py::test_remove_manager_nonexistent_user_returns_not_found`, `::test_update_user_rereads_with_new_upn_after_rename`, `::test_update_user_readback_failure_after_patch_still_reports_success`, `::test_update_user_description_mentions_replication_lag` (all new in this round, all passing at `bd3fe8d`); `::test_remove_manager_returns_no_manager_without_calling_delete` updated for the new existence-check call (behavior for a real managerless user is unchanged, only the call count grew).
- Not covered by automated tests: same class of blind spot as round 2's own entry above — neither fix has been re-verified against a live Graph tenant (the comment this round is based on reports both relevant write paths as BLOCKED by the test connector's permissions, not as failing). See `docs/tickets/PRD-20393-r3.md` § Self-test, "Known local blind spot."
